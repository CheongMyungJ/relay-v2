# 어려운 평가 시나리오 설계 (09~14)

시나리오 01~08은 에이전트에게 쉬웠다. src가 파일 2~4개, 4~29줄이어서 에이전트가 레포 전체를 몇 초 만에 읽었고, 맨 CLI는 80회 모두 세션 한 번, 1분 안팎에 끝났다. 그래서 지금 결과는 "쉬운 버그에서 relay 절차가 얼마나 부담인가"를 잰 것에 가깝다. relay가 내세우는 것(긴 조사를 단계로 나누기, 사람이 중간에 방향 잡기, 검증 근거, 도구가 꺼진 뒤 복구, 범위 통제)은 거의 시험되지 않았다.

이 문서는 그런 강점과 약점이 실제로 드러나는 시나리오 여섯 개를 설계한다. 형식은 `docs/eval.md` 5절을 따르고, 평가 도구에 더 필요한 것은 끝에 따로 적는다.

## 1. 01~08에서 배운 것

| 관찰 | 어디서 | 설계에 주는 뜻 |
|---|---|---|
| 레포가 작으면 "위치를 모르는 버그"도 탐색이 필요 없다 | 02, 03 | 레포를 키우고, 증상이 나는 모듈과 원인이 있는 모듈을 떨어뜨린다 |
| 흔한 해법 하나로 맞게 고쳐지면 묻지 않는다 | 08 (`getUTCDay()`) | 사람만 아는 규칙에 따라 정답이 갈리게 하고, 흔한 해법은 숨긴 시험에서 틀리게 한다 |
| 에이전트가 나중 요구를 미리 채운다 | 05 (`""` 이스케이프) | 새 요구는 미리 짐작할 수 없고, 이미 한 방향을 뒤집는 것이어야 한다 |
| 작업이 1분이면 도중 사건이 작업 뒤에 일어난다 | 05, 06 | 작업 자체가 길어야 한다(여러 파일, 재현 스크립트, 여러 번의 시험 실행). 사건은 한창 고치는 중에 일어나게 잡는다 |
| 증상만 막는 수정을 가려내지 못한다 | (시험이 증상만 봄) | 숨긴 시험은 원인을 보고, 증상만 막는 수정은 실패하게 만든다. 그럴듯한 틀린 수정을 미리 만들어 시험이 가려내는지 확인한다 |
| 결과보다 과정의 차이가 컸다 | 전체 | 판정표와 사람 역할의 말이 과정 차이를 드러내도록, 과정이 길고 결정할 것이 있는 시나리오를 만든다 |

## 2. 공통 원칙

- **레포 크기:** src 15~40개 파일, 800~2,500줄. 버그와 관계없는 모듈(설정, 로깅, 다른 도메인 기능)이 절반쯤 되게 한다. README에 도메인을 짧게 설명한다. 외부 의존성은 두지 않는다(`node --test`만 쓴다).
- **기존 시험:** 기준 상태에서 통과하고, 수십 개이며 몇 초 안에 끝난다. 버그를 잡는 시험은 없다.
- **숨긴 시험:** 원인을 본다. 그럴듯한 틀린 수정 하나 이상이 실패해야 한다. 멀쩡한 동작을 지키는 `guard` 시험을 둔다(과하게 고치거나 증상만 막는 수정을 잡는다).
- **정답과 함정 패치:** 시나리오 폴더에 `reference.patch`(정답 수정)와 `traps/*.patch`(그럴듯한 틀린 수정)를 둔다. 평가 도구는 `repo/`만 복사하므로 에이전트에게 보이지 않는다. 시나리오를 더할 때 아래 네 가지를 확인한다.
  1. 기준 상태: `npm test` 통과, `guard`가 아닌 숨긴 시험 실패
  2. `reference.patch` 적용: 숨긴 시험 모두 통과, `npm test` 통과
  3. `traps/*.patch` 적용: 숨긴 시험 하나 이상 실패
  4. 시범 실행: 맨 CLI 한 번에 3분 넘게 걸리고, 사람이 끼어들지 않으면 쉽게 다 통과하지 않는지
- **제한:** `limits`를 `{ minutes: 90, turns: 100 }`으로 늘린다.
- **사람 역할:** 사람이 판단에 필요한 사실(도메인 규칙, 최근 배포)은 `knowledge`로 준다. 사람이 먼저 말하면 시나리오가 쉬워지는 사실은 `on_ask`로 둔다.

| id | 상황 | 보는 것 |

| 11-amount-sweep | 여러 파일을 고치는 긴 작업 도중 도구가 꺼짐 | 반쯤 고친 상태에서 파악과 복구, 빠진 곳 없이 끝내는지 |

### 09-stock-negative: 증상과 원인이 다른 모듈에 있는 버그

- **레포:** 주문과 재고 서비스(`stock`), 약 25개 파일, 1,500줄
  - `orders/`: 주문, 취소
  - `inventory/`: 예약, 해제
  - `cache/`: LRU 캐시
  - `reports/`: 재고 리포트
  - `warehouses/`: 창고 여러 개
  - 그 밖에 관계없는 `pricing/`, `notify/`, `config/`
- **버그:**
  - `inventory/reserve.js`는 캐시 키를 `${sku}:${warehouse}`로 만들고, `orders/cancel.js`가 부르는 `inventory/release.js`는 `sku`만으로 만든다.
  - 그래서 창고가 둘 이상인 SKU를 취소하면 캐시가 무효화되지 않는다. 다음 예약이 오래된 수량을 읽어 두 번 차감된다.
  - 증상은 `reports/stock.js`의 리포트에 음수로만 나타난다.
- **리포트(사람이 받은 것):** "주간 재고 리포트에 가끔 음수 재고가 찍힌다. 예: SKU A-100이 -3. 매번은 아니고 어떤 주문 뒤인지 모르겠다. 리포트 코드(`reports/stock.js`)가 계산을 잘못하는 것 같다."
- **knowledge:**
  - `on_ask`: 음수가 난 SKU는 모두 두 창고(서울, 부산)에 나눠 보관하는 상품이다.
  - `on_ask`: 그 주에 취소가 평소보다 많았다(프로모션 뒤).
  - `upfront`: 재고는 절대 음수가 되면 안 되지만, 리포트에서 0으로 가리는 것은 해결이 아니다.
- **함정(그럴듯한 틀린 수정):**
  - 리포트에서 `Math.max(0, qty)`로 자르기
  - 예약에서 음수를 막는 검사만 더하기. 주문이 실패하게 되지만 원인은 남는다.
  - 캐시를 끄기. 동작은 맞지만 guard의 캐시 적중 시험이 실패한다.
- **숨긴 시험:**
  - `취소 뒤 재고`: 두 창고 SKU로 주문, 취소, 다시 주문을 한 뒤, 창고별 실제 재고가 맞는지 본다(리포트가 아니라 inventory를 직접 본다).
  - `캐시 유지`(guard): 같은 SKU를 연달아 읽을 때 캐시가 적중하는지 본다(캐시 적중 수를 셈).
  - `리포트 그대로`(guard): 정상 재고의 리포트 출력이 바뀌지 않는지 본다.
- **expectedFiles:** `src/inventory/**`, `src/orders/**`, `src/cache/**`, `test/**`
- **relay에서 보이길 기대하는 것:**
  - 의도 정리에서 재현 조건을 묻는다.
  - 조사 단계의 산출물(재현 스크립트, 원인 추적)이 사람에게 보인다.
  - 사람이 "리포트를 고치는 게 아니다"를 확인할 수 있다.
- **CLI에서 예상되는 위험:** 리포트 파일 경로를 믿고 리포트만 고치고 끝낸다.

### 10-invoice-rounding: 사람만 아는 규칙으로 정답이 갈리는 버그

- **레포:** 청구서 모듈(`billing`), 약 20개 파일, 1,200줄
  - 품목 줄, 할인, 부가세, 합계, PDF용 서식
  - 관계없는 `customers/`, `export/`
- **버그:**
  - 부가세를 합계에서 한 번 반올림한다(`Math.round(subtotal * 0.1)`).
  - 회사 규정은 품목 줄마다 부가세를 원 단위 버림으로 계산하고, 그 합을 그대로 쓰는 것이다.
  - 그래서 회계팀 대조와 1~몇 원 어긋난다.
- **리포트:** "회계팀 대조에서 청구서 합계가 1~3원씩 안 맞는다는 연락이 왔다. 예: 청구서 INV-2031 합계 33,003원, 회계팀 계산 33,001원. 반올림 문제 같다. (`src/invoice/total.js`)"
- **knowledge:**
  - `on_ask`: 회계 규정: 부가세는 품목 줄마다 원 단위 버림으로 계산하고 그 합을 쓴다. 합계에서 다시 반올림하지 않는다.
  - `on_ask`: 할인은 부가세 전에 줄마다 적용한다.
  - `upfront`: 이미 발행된 청구서는 다시 계산하지 않는다(서식 모듈의 출력 형식도 바뀌면 안 된다).
- **숨긴 시험의 예시값은 흔한 해법들이 서로 다른 답을 내도록 고른다:**
  - 합계 반올림(지금 코드)
  - 줄마다 반올림
  - 줄마다 버림(정답)
  - 은행가 반올림
  - 합계 버림
- **함정:** 줄마다 반올림, 은행가 반올림(`toFixed` 기반), 합계에서 버림
- **숨긴 시험:**
  - `줄별 버림`: 세 가지 예시 청구서의 합계가 규정대로 나오는지 본다.
  - `할인 순서`: 할인 품목이 있는 청구서의 합계를 본다.
  - `서식 그대로`(guard): 부가세 없는 청구서와 서식 출력이 바뀌지 않는지 본다.
- **expectedFiles:** `src/invoice/**`, `test/**`
- **보는 것:** 08과 달리 흔한 해법으로는 틀린다. 에이전트가 규칙을 묻는지, 묻지 않고 하나를 골라 틀리는지를 본다. 해법이 여럿이라는 것을 사람에게 보여 주고 고르게 하는지도 본다.

### 11-amount-sweep: 여러 파일을 고치는 긴 작업 도중 꺼짐

- **레포:** 재무 리포트(`ledger`), 약 35개 파일, 2,200줄
  - 리포트 모듈 8개(`reports/*.js`)가 각자 금액 문자열 파싱 코드를 복사해 쓴다. 조금씩 다른 변형이다.
  - 공통 유틸 `lib/money.js`가 있지만 두 모듈만 쓴다.
- **버그:**
  - 회계식 음수 표기 `(1,200)`을 8개 모듈 모두 양수 1200으로 읽는다.
  - 모듈마다 파싱 코드가 조금씩 달라서, 한 곳만 고쳐서는 안 된다.
- **리포트:** "손익 리포트에서 환불(괄호로 표시된 금액)이 매출로 더해진다. 다른 리포트들도 같은지 모르겠다. 예: `(1,200)`이 +1,200으로 합산됨."
- **knowledge:**
  - `upfront`: 괄호 표기는 음수다. `-1,200`과 `(1,200)`은 같다. `₩`나 공백이 붙을 수 있다.
  - `on_ask`: 리포트는 8개 모두 같은 원장 데이터를 읽는다.
- **preferences:**
  - 공통 함수로 모으는 것은 좋다.
  - 각 리포트 모듈의 공개 함수 이름과 인자는 바꾸지 않는다.
- **events:** `{ when: "first_change", afterSeconds: 60, do: "crash" }`. 첫 파일을 고치고 1분 뒤, 여러 파일이 반쯤 고쳐지고 커밋 전일 때를 노린다.
- **함정:** 크래시 뒤 이어 가지 못해 일부 모듈만 고쳐진 채 커밋하는 것, `lib/money.js`만 고치고 복사된 코드는 두는 것
- **숨긴 시험:**
  - `모든 리포트의 음수`: 8개 리포트 각각 괄호 음수가 든 원장을 넣어 합계를 본다. 모듈별 결과를 출력한다.
  - `다른 형식 그대로`(guard): 양수, `₩`, 소수점, 빈 칸을 본다.
  - `공개 API`(guard): 각 모듈이 내보내는 함수 이름과 인자 개수를 본다.
- **expectedFiles:** `src/reports/**`, `src/lib/**`, `test/**`
- **보는 것:**
  - 꺼진 뒤 무엇이 끝났고 무엇이 남았는지 파악하는 부담을 본다. relay는 단계 산출물과 체크포인트, CLI는 `git status`와 `--continue`로 파악한다.
  - 빠진 곳 없이 끝내는지 본다.
  - 모듈별 시험 결과로 부분 완성을 구분해 볼 수 있다.

### 12-flaky-job: 가끔만 실패하는 버그

- **레포:** 작업 실행기(`jobs`), 약 20개 파일, 1,100줄
  - 작업 큐, 병렬 실행(`Promise.all`), 결과 모으기, 재시도 정책, 로그
- **버그:**
  - 병렬 작업의 결과를 공유 배열에 `push`한다.
  - 뒤이어 인덱스로 결과를 짝짓는 코드가 완료 순서가 입력 순서와 같다고 가정한다.
  - 작업 지연은 `Math.random` 기반 흔들림이 있어, 기존 시험 `test/batch.test.js`가 5번에 1번쯤 실패한다.
- **리포트:** "CI에서 `batch.test.js`가 가끔 실패한다. 로컬에서는 잘 된다. 실패 로그: `expected report-3 to belong to job-3, got job-1`. 재실행하면 통과해서 다들 그냥 넘어가고 있다."
- **knowledge:**
  - `upfront`: 시험에 재시도를 붙이거나 skip하는 것은 해결이 아니다. 시간 제한을 늘리는 것도 아니다.
  - `on_ask`: 지난달 성능 때문에 작업을 순차에서 병렬로 바꿨다.
- **숨긴 시험:**
  - `완료 순서와 무관`: `Math.random`과 지연 함수를 바꿔 끼워 역순 완료를 강제하고, 결과 짝이 맞는지 본다.
  - `병렬 유지`(guard): 작업 4개가 동시에 실행되는지 본다(동시 실행 수를 셈). 순차로 되돌리는 수정을 잡는다.
- **함정:** 순차 실행으로 되돌리기, 결과를 정렬해서 우연히 맞추기(입력 id가 정렬 순서가 아닌 예시로 잡음), 시험에 재시도 붙이기
- **expectedFiles:** `src/runner/**`, `src/collect/**`, `test/**`
- **보는 것:**
  - 에이전트가 반복 실행으로 재현하고 근거를 보이는지 본다.
  - 사람이 "진짜 고쳐졌다"고 확신하기 쉬운지 본다. relay는 판정표와 검증 단계를 쓴다.
  - 증상 덮기를 사람이 막기 쉬운지 본다.

### 13-soldout-pivot: 고친 방향을 뒤집는 요구

- **레포:** 상품 검색(`search`), 약 25개 파일, 1,500줄
  - 색인, 점수 계산, 필터, 정렬, 페이지 나누기
  - 관계없는 추천, 로그
- **버그:** 품절 상품이 점수가 높으면 검색 결과 맨 위에 뜬다.
- **리포트:** "검색 결과 맨 위에 품절 상품이 뜬다. 고객이 누르고 실망한다. 품절은 검색 결과에서 빼 주세요. (`src/search/`)"
- **reveals:**
  - `{ when: "first_change", afterSeconds: 20 }`
  - 내용: "영업팀과 이야기해 보니 품절 상품을 빼면 안 된다. 재입고 알림 신청 때문에 검색에는 나와야 한다. 결과 맨 뒤로 보내고, 품절끼리는 점수 순서를 지켜야 한다. 페이지를 넘겨도 품절이 앞 쪽에 섞이면 안 된다. 에이전트에게 알려라."
- **함정:**
  - 필터 수정을 그대로 두고 끝내기
  - 한 쪽 안에서만 정렬하기(페이지 경계에서 품절이 앞 쪽에 섞임)
  - 품절끼리 순서가 흐트러지는 불안정 정렬
- **숨긴 시험:**
  - `품절은 맨 뒤`: 품절이 결과에 남아 있고, 모든 쪽에 걸쳐 재고 있는 상품 뒤에 오는지 본다.
  - `품절끼리 점수 순`
  - `재고 상품 순서 그대로`(guard)
- **expectedFiles:** `src/search/**`, `test/**`
- **보는 것:**
  - 05와 달리 에이전트가 미리 짐작할 수 없고, 이미 한 수정을 되돌려야 한다.
  - relay는 되감기와 되감기 전 미리보기, CLI는 대화로 한다.
  - 되돌린 뒤 남은 흔적이 없는지도 본다. 필터 코드가 남아 있어도 시험은 통과할 수 있으므로 판정의 scope와 quality로 본다.

### 14-double-notify: 원인이 둘인 버그

- **레포:** 알림 발송(`notify`), 약 30개 파일, 1,800줄
  - 이벤트 수신, 중복 제거, 발송 어댑터(메일, 푸시), 재시도 큐, 설정
- **원인(둘이 겹친다):**
  1. 중복 제거 키에 이벤트 수신 시각이 들어가 있어, 같은 이벤트가 다시 들어오면 새 알림으로 본다(`dedupe/key.js`).
  2. 지난주 설정 변경으로 발송 제한 시간이 2초가 됐다. 느린 메일 어댑터가 발송에 성공했는데도 시간 초과로 보고 재시도 큐에 넣는다(`retry/policy.js`, `config/defaults.js`).
  - 1만 고치면 푸시 중복은 사라지지만, 메일 중복은 재시도 경로에서 계속 난다(재시도는 dedupe를 거치지 않는다).
- **리포트:** "일부 고객이 같은 알림을 두 번, 가끔 세 번 받는다. 메일이 더 자주 그렇다."
- **knowledge:**
  - `on_ask`: 지난주 배포에서 발송 제한 시간 설정을 바꿨다(정확한 값은 모른다).
  - `on_ask`: 두 번 받은 메일의 발송 로그를 보면 두 번째가 첫 번째보다 2~3초 늦다.
  - `upfront`: 재시도 자체를 끄면 안 된다(실제로 실패한 발송은 다시 보내야 한다).
- **함정:**
  - 중복 제거 키만 고치기(메일 중복이 남음)
  - 재시도 끄기(guard에서 실패)
  - 제한 시간만 늘리기(느린 어댑터 예시가 여전히 초과)
- **숨긴 시험:**
  - `같은 이벤트 재수신`: 한 번만 발송하는지 본다.
  - `성공 뒤 재시도 없음`: 느린 어댑터로 발송에 성공하면 재시도 큐에 넣지 않는지 본다.
  - `실패는 재시도`(guard): 실제로 실패한 발송은 재시도하는지 본다.
- **expectedFiles:** `src/dedupe/**`, `src/retry/**`, `src/config/**`, `src/adapters/**`, `test/**`
- **보는 것:**
  - 첫 원인을 고치고 끝내지 않는지 본다.
  - 사람이 "메일은 아직 두 번 온다"처럼 조사를 이어 가라고 지시하기 쉬운지 본다. relay는 추가 지시와 되감기, CLI는 대화로 한다.
  - 조사 산출물에 두 경로가 드러나는지 본다.

## 4. 평가 도구에 더할 것

- **`on_ask` 공유 기록:** 사람 역할이 `on_ask` 사실을 말한 차례와, 그것이 에이전트의 질문에 대한 답이었는지를 `turns.jsonl`에 남긴다. 보고서에 "물어서 얻은 사실 수"를 더한다(08, 09, 10, 14). 지금은 사람 역할의 생각을 읽어야만 알 수 있다.
- **모듈별 부분 점수:** 숨긴 시험 파일 하나가 여러 하위 시험을 가질 때 통과한 하위 시험의 비율을 따로 센다(11처럼 부분 완성을 구분하려고).
- **시나리오 검증 명령:** `node eval/check-scenario.mjs <id>`. 2절의 네 가지 가운데 1~3(기준, 정답 패치, 함정 패치)을 자동으로 확인한다.
- **비용과 시간:** 레포가 커지면 relay 한 번이 10~25분, CLI가 3~10분쯤으로 늘 것이다. 여섯 시나리오를 5회씩 돌리면 60회에 4~6시간 걸린다. 먼저 1~2회씩 시범으로 돌려 난이도를 맞춘다.
