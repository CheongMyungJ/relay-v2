### 사람 역할의 말

- [k9#1 좋음] 판정표에 완료조건별 근거(실행한 명령과 결과)가 있었다. 전체 변경 탭에서 diff를 바로 볼 수 있어 승인 전에 확인하기 쉬웠다.
- [k9#1 불편] 에이전트가 질문을 하지 않아 개입할 지점이 적었다. 원인 분석과 수정 단계가 자동 승인으로 넘어가 내가 볼 틈이 없었다.
- [k9#2 좋음] 완료조건별 판정표에 근거가 붙어 있어서 218P 확인과 변경 범위 확인이 쉬웠다. 의도 단계에서 가정을 물었을 때 에이전트가 바로 계산해서 확인해 줬다.
- [k9#2 불편] 의도 정리 단계의 지식과 범위 설명이 길고 낯설었다. 자동 승인으로 지나간 중간 단계의 코드 변경은 inspect_diff를 따로 봐야 했다.
- [k9#3 좋음] 원인, 근거 계산, 변경 diff, 완료조건 판정표가 단계마다 정리돼 있어서 수정이 맞는지 판단하기 쉬웠다. 지난 단계 탭에서 자동 승인으로 지나간 수정도 볼 수 있었다.
- [k9#3 불편] worktree가 detached HEAD여서 수정 커밋이 작업 브랜치에 없었다. 판정표는 모두 통과로 나왔는데 패널의 "커밋 0개" 한 줄만 이 문제를 보여 줬고, 내가 에이전트에게 물어서야 알았다. 완료 화면을 누르기 전에 앱이 먼저 경고해 주지 않았다.
- [k9#4 좋음] 의도 정리에서 요청의 기대값과 제약이 정확히 반영됐다. 마지막 판정표에 완료조건별 근거가 있어 믿고 확인하기 쉬웠다.
- [k9#4 불편] 에이전트가 거의 묻지 않고 진행해서, 팀 규칙 문서를 근거로 삼은 것이 맞는지는 내가 직접 확인해야 했다. 우측 패널의 diff가 길어 훑는 데 약간 수고가 들었다.
- [k9#5 좋음] 의도 초안과 판정표, 전체 변경 diff를 한 화면에서 확인하고 바로 승인할 수 있었다. 완료조건별로 근거가 달려 있어서 믿고 넘어가기 쉬웠다.
- [k9#5 불편] 원인 분석과 수정 단계가 자동 승인으로 지나가서 그 단계를 직접 보지 못했다. 나중에 탭에서 찾아봐야 했다. 에이전트가 지식 문서(earn-basis.md)까지 고쳤는데, 요청에는 없던 변경이라 조금 의외였다.

#### friction이 높았던 차례

- k9#3 차례 15 (friction 2): 패널이 "기준 뒤 커밋 0개"라고 보여 줘서 수정이 커밋됐는지 헷갈린다.
- k9#3 차례 16 (friction 2): detached HEAD라 커밋이 브랜치에 없었다. 직접 물어보지 않았으면 놓쳤을 것이다.
