### 사람 역할의 말

- [k7#1 좋음] 완료조건별 판정표와 근거, 전체 변경 diff를 한 화면에서 볼 수 있어서 승인 전에 확인하기 쉬웠다.
- [k7#1 불편] 에이전트가 질문을 하지 않고 초안을 먼저 써서 내 의견을 넣을 기회가 적었다. 의도 정리의 가정(손으로 계산한 값)이 실제로 맞는지는 뒤 단계에서야 확인됐다.
- [k7#2 좋음] 단계가 나뉘어 있고, 마지막 판정표에 완료조건별로 통과 근거가 적혀 있어서 G-0213이 218P가 됐는지 바로 확인할 수 있었다.
- [k7#2 불편] 다른 팀과 합의됐는지는 내가 답할 수 없는 질문인데 의도 정리와 원인 분석 두 단계에서 반복해서 나왔다. 의도 승인 때 '답하지 않은 질문' 확인창이 뜬 것도 잠깐 헷갈렸다.
- [k7#3 좋음] 수정 금지 문서와 요청이 충돌하는 걸 에이전트가 먼저 짚어서 물었다. 근거를 따로 물으니 원문과 한계(근거가 한 건뿐이고 협의 여부는 확인 안 됨)까지 솔직하게 보여 줬다. 완료 화면의 판정표와 전체 변경 탭으로 결과를 바로 확인할 수 있었다.
- [k7#3 불편] 첫 질문이 협의 여부를 내가 알 수 없는 상황인데도 허용 여부만 묻는 식이었다. 근거를 보려면 선택지를 직접 입력으로 바꿔 따로 물어야 했다. 완료 뒤 세션 화면이 비어 보여서 잠깐 헷갈렸다.
- [k7#4 좋음] 완료조건별 판정표에 근거가 붙어 있었다. G-0213이 218P가 됐고 테스트도 통과했다는 걸 코드를 다 읽지 않고도 믿을 수 있었다.
- [k7#4 불편] 02 원인 분석과 수정이 자동 승인으로 지나가서, 그 단계의 변경은 리뷰 단계에서야 diff로 확인했다. 의도 단계에서 에이전트가 고객센터 계산 규칙이나 218P를 나에게 묻지 않고 스스로 정한 점도 조금 불안했다.
- [k7#5 좋음] 에이전트가 팀 지식 문서에 적힌 다른 팀과의 경계를 먼저 짚어 물어봤다. 완료 판정표와 전체 diff로 변경을 확인하고 완료할 수 있었다.
- [k7#5 불편] 첫 질문 선택지가 길고 터미널에서 4번(직접 입력)을 골라 답하는 방식이 약간 낯설었다. 다른 팀과 합의됐는지는 끝까지 불확실했다.
- [k8#1 좋음] 리뷰 단계의 판정표가 완료조건마다 근거를 붙여 줬고, 전체 변경 탭으로 diff를 바로 확인할 수 있어 승인하기 편했다.
- [k8#1 불편] 의도 정리 단계에서 에이전트가 "다른 팀 공유 파일"이라며 처음 듣는 제약을 꺼내 잠깐 멈칫했다. 이 제약이 어디서 나왔는지 설명이 부족했다. 터미널에서 형식 검사 오류가 한 번 나타나 혼란스러웠다.
- [k8#2 좋음] 의도 정리가 요약과 완료조건으로 한눈에 보였다. 마지막 판정표에는 완료조건마다 근거가 붙어 있었고, G-0213이 218P로 나오는 것도 확인할 수 있었다.
- [k8#2 불편] 02 원인 분석과 수정이 자동 승인으로 지나가 버려서 어떤 코드가 바뀌었는지 보려고 따로 diff를 열어야 했다. 리뷰 단계 선택지 화면에서는 질문하려면 먼저 선택지를 하나 눌러야 했는데, 그게 어색했다.
- [k8#3 좋음] 에이전트가 팀 규칙(gift-points.js 수정 금지)과 요청이 충돌한다는 점을 먼저 물어봤다. 판정표와 전체 변경 화면 덕분에 218P가 나오고 금지 파일이 그대로라는 걸 바로 확인할 수 있었다.
- [k8#3 불편] 원인 분석과 수정 단계가 자동 승인으로 지나가서, 그 단계 내용을 따로 살펴보지 못했다. 리뷰 지적 선택지의 설명도 조금 짧았다.
- [k8#4 좋음] 단계가 나뉘어 있고 오른쪽 패널의 판정표와 diff로 결과를 확인할 수 있었다. G-0213이 218P가 되는지도 근거와 함께 보였다.
- [k8#4 불편] 에이전트가 범위 밖인 일반 주문 코드를 건드리고, 내가 말하지 않은 '사람이 알려 줌'을 문서에 적었다. diff를 직접 열어 봐야 알 수 있었다.
- [k8#5 좋음] 에이전트가 팀 규칙(gift-points.js 수정 금지)을 먼저 알고 선택지로 물어봤다. 판정표에 완료조건별 근거가 있어서 믿고 승인할 수 있었다.
- [k8#5 불편] 일반 주문의 earnPoints 식까지 바뀌었다. 이 부분은 의도 승인 때 요약에 분명히 보이지 않아서, 나중에 diff를 보고서야 알았다. 또 218P는 고객센터 값에 맞춰 거꾸로 만든 식이라 정책으로 확인된 건 아니다.

#### friction이 높았던 차례

- k8#2 차례 12 (friction 2): diff를 보니 선물 쪽만 아니라 일반 주문 earnPoints(배송비 제외, 내림)까지 바꿨다. 의도의 비목표와 어긋나 보여 반영 선택 전에 물어본다.
- k8#4 차례 14 (friction 2): diff를 보니 일반 주문 earnPoints까지 바뀌었고 의도의 비목표와 어긋난다. 지적한다.
