# 지식 관리 후속: 낡은 지식과 규칙·상태 섞임

- 상태: 1·2단계 구현과 평가 (2026-10-04, E10, 9절)
- 바탕: `report.md` 4.4·4.5·7절. 실험 빌드 `d47836a`는 그대로 두고, 이 문서의 변경은 그 뒤의 개발이다(`log.md`의 "실험 뒤 개발").

## 1. 두 문제

| | 문제 1: 바뀐 규칙이 옛 지식과 함께 남는다 | 문제 2: 규칙과 코드의 지금 상태가 섞인다 |
|---|---|---|
| 사례 | hold-out h1에서 무료배송 기준이 30,000원에서 40,000원으로 바뀜. 5번 중 2번, Work 3이 옛 파일을 고치지 않고 새 파일을 만들어 머지 뒤 두 값이 함께 남음 | hold-out h2에서 "부분 취소는 1원 반올림을 쓴다"(고칠 곳이라는 뜻)를 팀원의 에이전트가 규칙으로 읽고 고치지 않아 숨긴 시험 실패 |
| 원인 | ① 같은 대상을 다른 이름으로 부름 ② 다른 주제의 파일에 곁들여 적힌 옛 값 ③ 머지 전 앞 Work의 파일이 지금 폴더에 없음 ④ "어긋나면 고쳐라"는 규칙도 확인도 없음 | 형식이 자유 서술이라 "이래야 한다"와 "지금 이렇다"를 가를 자리가 없고, 안내 문구만 있고 확인이 없음 |

## 2. 원칙

- "같은 내용이면 같은 곳"은 기계적으로 보장할 수 없다. 이름이 달라도 같은 대상일 수 있고, 옛 값이 다른 주제의 파일에 섞여 있을 수 있다.
- 그래서 세 겹으로 막는다: 형식은 앱이 기계적으로 확인하고(K7의 "남긴 지식:" 확인과 같은 방식), 뜻은 작은 검토 호출이 확인하고, 나머지는 사람이 PR 리뷰에서 본다.
- Work 하나의 비용은 지식 전체 크기와 무관해야 한다. 지식이 수백 개여도 Work마다 보는 것은 관련 후보 몇 개로 묶고, 그 대가로 생기는 빈틈은 Work 밖의 정기 정리로 메운다.
- 보장이 아니니 얼마나 줄었는지를 평가 지표로 잰다.

## 3. 해결 방안

### 가. 지식 파일의 형식 (문제 2의 바탕, 문제 1에도 씀)

```markdown
---
kind: rule            # rule | fact | history | pitfall
source: human         # human | investigation
anchor: FREE_SHIPPING_THRESHOLD   # 규칙이 붙은 코드 이름. 있을 때만
---
# 무료배송 기준은 쿠폰 뺀 금액 40,000원

## 규칙
- 쿠폰·할인을 뺀 결제 상품 금액이 40,000원 이상이면 무료다.

## 아직 규칙을 따르지 않는 곳
- `src/returns/return-fee.js`: 할인 전 금액으로 판단한다. 고쳐야 한다.

## 바뀐 이력
- 2026-10-03 30,000원 → 40,000원 (Work w-…-003, 사람이 알려 줌)
```

- 규칙과 상태를 가른다. "부분 취소는 1원 반올림"은 `## 아직 규칙을 따르지 않는 곳`에 들어가 규칙으로 오해되지 않는다. `kind`가 rule이 아니면 본문 절은 `## 내용`이다.
- 한 사실은 한 곳에만 쓴다. 값이나 규칙은 그것을 다루는 항목 한 곳에만 쓰고 다른 항목에서는 가리키기만 한다(원인 ②).
- 영역은 폴더로 나눈다: `docs/knowledge/<영역>/<이름>.md`(영역 없이 바로 두어도 된다). 좁히기와 정기 정리의 단위다.
- 앱이 확인한다(기계적): 머리글 필드와 허용 값, 본문 절, 같은 `anchor`를 가진 항목이 둘인지(코드 이름이 있는 규칙에 한해 문제 1을 확실히 잡음).
- 읽는 쪽의 규칙: `## 규칙`만 따르고, `## 아직 규칙을 따르지 않는 곳`은 고칠 대상이다.

### 나. 관련 지식 좁히기 (규모 대응, 모든 단계에 씀)

앱이 모델을 부르지 않고 싼 신호로 후보를 고른다.

| 신호 | 어떻게 |
|---|---|
| 코드 위치 | 이번 Work가 바꾼 파일과 항목에 적힌 경로가 겹치는가 |
| 코드 이름 | diff에 나온 상수·함수 이름이 항목의 `anchor`와 같은가 |
| 낱말 | 요청, intent, 이번에 새로 쓴 지식과 기존 항목의 제목·규칙이 겹치는가(한국어는 글자 2~3개 단위) |
| 영역 | 바뀐 코드의 영역에 속한 항목 |

- 후보는 많아야 10~20개, 본문째 준다. "관련 있어 보이는 일부"라고 함께 적는다.
- intake와 fix는 요청과 intent로, verify와 검토 호출은 새로 쓰거나 고친 지식 자체로도 찾는다. 그래서 이름이 달라도 옛 항목이 걸린다.
- 지식이 적을 때(예: 전부 합쳐 8,000자 이하)는 지금처럼 전부 넣는다.

### 다. verify가 지식을 남기는 법 (문제 1)

1. 고르게 한다: 남길 항목마다 "기존 항목을 고침" 또는 "새로 만듦"을 고르고, 새로 만들면 맞는 기존 항목이 없는 까닭을 적는다(원인 ①).
2. 어긋나면 반드시 고친다: 사람의 지금 말이 기존 지식과 어긋나면 그 항목을 같은 경로에 고쳐 쓴다. 머지 전 파일이면 앞 내용을 살려 쓴다(원인 ③). `## 바뀐 이력`에 한 줄을 더한다.
3. handoff `## 요약`에 바꾼 지식 파일마다 한 줄: `새 지식: <경로> — <맞는 기존 항목이 없는 까닭>` 또는 `고친 지식: <경로> — <무엇이 바뀌었나>`. 바꾼 것이 없으면 `남긴 지식: 없음 (까닭)`.
4. 앱이 확인한다(기계적): 바꾼 파일마다 줄이 있는지, 이미 있던 경로(기준 커밋이나 머지 전 지식)를 `새 지식`으로 적지 않았는지, 새 경로를 `고친 지식`으로 적지 않았는지, 까닭이 비어 있지 않은지(원인 ④).

### 라. 검토 호출 (문제 1·2의 뜻 확인, Work마다)

- verify가 턴을 끝낼 때(Stop) 앱이 짧은 모델 호출을 한 번 한다.
- 넣는 것: 이번에 쓰거나 고친 지식, 나.에서 고른 후보, 이번 Work에서 사람이 한 말과 사람 결정.
- 찾는 것: 같은 대상을 말하는데 값이나 규칙이 다른 항목 쌍, 사람의 지금 말과 어긋나는데 고치지 않은 항목, `## 규칙`의 상태 서술("~가 남아 있다")과 "모른다" 메모, 근거 없이 넓게 일반화한 규칙.
- 나오면 기존 되돌림(최대 2번)으로 무엇을 고칠지 verify에 돌려보낸다. 사람의 수고는 늘지 않는다. 비용은 후보 수에 묶인다.

### 마. 정기 정리 (Work 밖, 좁히기가 놓친 것)

- 지식 PR을 만들 때나 정한 주기마다, 영역마다 그 안의 항목끼리 비교해 서로 어긋나는 쌍과 오래된 항목을 찾는다.
- 사람에게 정리 목록으로 보이고, 사람이 고치거나 합치거나 걷어 낸다.

### 바. 사람의 리뷰

[PR 생성] 때 PR 본문에 "이번에 고친 지식 / 새로 만든 지식"을 따로 보여 리뷰어가 코드와 갈라 보게 한다.

## 4. 무엇이 보장되고 무엇이 아닌가

| 장치 | 누가 | 잡는 것 | 한계 |
|---|---|---|---|
| 가. 형식 확인 | 앱(기계적) | 형식, 규칙 절의 유무 | 절 안의 뜻은 못 봄 |
| 가. 같은 `anchor` | 앱(기계적) | 코드 이름이 같은 중복 | 코드 이름 없는 규칙은 못 봄 |
| 다. 고르기, 한 곳에만 | 에이전트(안내) | 이름 갈라짐, 곁들인 옛 값을 줄임 | 보장 아님 |
| 다. 새·고친 지식 줄 | 앱(기계적) | 줄과 까닭, 새·고침의 구분이 맞는지 | 내용이 맞는지는 못 봄 |
| 라. 검토 호출 | 모델(Work마다) | 후보 안의 어긋남, 규칙 절의 상태 서술 | 확률적, 후보 밖은 못 봄 |
| 마. 정기 정리 | 모델 + 사람(가끔) | 같은 영역 안의 어긋남 전반 | 영역을 넘는 것, 다음 정리까지의 공백 |
| 바. PR 리뷰 | 사람 | 위가 놓친 것 일부 | 사람이 못 본 것 |

## 5. 확인 방법

- 새 지표: "머지 뒤 레포에 남은 지식 가운데 서로 어긋나거나 낡은 항목 수". 시나리오마다 정답 규칙을 적어 두고 판정 모델이 센다. 지표 도구(`primary.mjs` 등)는 실험 규약의 고정 파일이라, 더하려면 사람의 허락을 받고 새 도구로 둔다.
- 새 개발용 시나리오: h1처럼 규칙이 Work 사이에 바뀌는 것, h2처럼 옛 계산이 남은 별도 모듈이 있는 것. 이번 hold-out은 이미 열었으니 공정한 재비교에는 새 hold-out이 필요하다.
- 좁히기의 놓침률: 서로 어긋나는 쌍을 일부러 심은 수백 개짜리 지식 모음에서 나.의 후보에 그 쌍이 함께 걸리는 비율. 실제 Work 없이 검색만 돌린다.
- 나눠 재기: 기계적 확인(가·다)만 넣은 판과 검토 호출(라)까지 넣은 판을 따로 잰다.

## 7. 1단계 구현 (D293, D294)

- `app/src/core/knowledge.ts`: `checkEntryFormat`(형식), `knowledgeLines`(새·고친 지식 줄 읽기), `knowledgeIssues`(줄과 새·고침 구분, 형식, 같은 `anchor`), verify 안내(고르기, 어긋나면 같은 경로에서 고침, 한 사실은 한 곳에만, 파일 형식, handoff 줄), 읽는 쪽 안내(`## 규칙`만 규칙), 후보 안내(어긋나면 "고칠 지식:" 후보).
- `app/src/adapters/knowledge.ts`: 영역 폴더 한 단계 읽기, `changedKnowledge`(이 Work가 더하거나 고친 지식, 커밋 안 한 것 포함), `knowledgePathsAt`(기준 커밋의 지식 경로).
- `app/src/main/work.ts`: verify의 형식 검사마다 worktree와 머지 전 앞 Work 브랜치를 읽어 지식 확인 결과를 넘긴다(`checkOf`, `knowledgeCheck`). 끈 앱(`RELAY_KNOWLEDGE=off`)과 verify가 아닌 단계에서는 하지 않는다.
- `app/src/core/validate.ts`: 앱이 넘긴 지식 확인 결과를 verify가 승인 대기일 때 형식 오류로 더한다(D291의 "남긴 지식:" 확인을 이것으로 바꿈).
- 옛 형식(형식 도입 전)의 지식은 그대로 읽는다. 확인은 이번 Work가 더하거나 고친 파일에만 하므로, 옛 항목을 고치면 그때 새 형식으로 바뀐다.
- 시험: 단위(`test/unit/knowledge.test.ts`: 경로, 형식, 줄, 확인), 어댑터(영역 폴더, 바뀐 파일, 커밋의 경로), 흐름(verify가 옛 형식과 줄 없이 끝내면 한 번 되돌리고 고친 뒤 Work가 끝남). 앱 시험 899개 통과.
- 아직 하지 않은 것: 평가. 새 지표("머지 뒤 서로 어긋나거나 낡은 항목 수")와 h1·h2 모양의 새 개발용 시나리오가 있어야 이 단계의 효과를 잴 수 있다(5절).

## 8. 2단계 구현 (D295)

- `app/src/core/knowledge.ts`: `termsOf`(낱말, 한글은 붙은 두 글자), `pathsIn`, `identifiersIn`, `rankEntries`(anchor 5, 같은 파일 4·같은 폴더 2, 영역 2, 낱말 3, 머지 전 0.5), `selectEntries(entries, query)`(상한 안이면 전부, 넘으면 15개 본문, 20개 제목, 나머지 뺌), 지식 절에 "관련 있어 보이는 항목만 넣었다(전체 N개 가운데 …)"와 찾아보라는 안내.
- `app/src/main/work.ts`: 지식이 상한을 넘을 때만 단서를 만든다(`knowledgeQuery`): 요청, intent, 지식 후보, diff(바꾼 파일, 바뀐 줄의 코드 이름, 20만 자까지), verify는 바꾼 지식. `knowledge-injected.md`도 고른 것으로 남긴다.
- verify의 지식 확인(같은 anchor)은 좁히지 않고 늘 전부를 본다(모델 호출이 아니라 싸다).
- 시험: 단위(`test/unit/knowledge-rank.test.ts`: 낱말·경로·이름, 신호마다 순위, 좁히기와 안내, 합성 놓침률: 어긋나는 쌍 20개를 심은 200개에서 옛 짝이 후보에 드는 비율 0.9 이상), 흐름(지식 61개에서 요청과 관련된 항목이 맨 앞 본문). 앱 시험 904개 통과.
- 합성 놓침률 시험은 낱말이 겹치는 자료라 쉬운 편이다. 실제 놓침률은 실제 지식(평가에서 쌓인 것)으로 따로 잰다.

## 9. 1·2단계 평가 (E10)

- 새 지표 `app/eval/knowledge-quality.mjs`(고정 파일이 아닌 새 도구): 실행마다 모든 Work가 끝난 뒤 레포에 남는 지식을 Work의 diff로 다시 만든다(팀원 Work는 그 diff가 레포 전체, 같은 사람의 Work는 앞 지식 위에 덮고 같은 경로는 뒤가 이김). 시나리오의 기준(`app/eval/knowledge-truth/<시나리오>.json`: 지금 맞는 규칙, 낡은 서술, 규칙이 아닌 것)과 견줘 판정 모델이 낡은 항목, 상태를 규칙으로 적은 항목, 어긋난 짝, 기준 규칙을 맞게 적었는지를 센다. verify의 지식 되돌림 수도 센다. 머리글 `kind`의 분포(rule·fact·history·pitfall, 머리글이 없는 옛 형식은 "없음")를 쪽마다 세고(기준이 없는 시나리오도), 판정 모델이 `kind`가 내용과 맞지 않는 항목도 센다.
