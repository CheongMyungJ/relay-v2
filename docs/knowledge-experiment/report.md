## 1. 만든 지식 관리 (한 장 요약)

```
일하는 동안 (intake / fix / design / implement)        Work를 닫을 때 (verify)                        다음 일 (task를 시작할 때 앱이)
handoff의 knowledge_candidates에 후보를 한 줄씩        앞 단계들의 후보 + 요청 원문 + intent의          context.md의 "팀 지식" 절에 넣음
 (사람이 말한 것은 "(사람)")                            비목표·제약 + 사람 결정 → docs/knowledge/       ├ worktree의 docs/knowledge/ (머지된 팀 지식)
                                                       <영어-이름>.md, 한 항목 한 파일, 코드와 함께 커밋  └ 같은 앱에서 완료한 앞 Work 브랜치의 지식 중
                                                       앱이 handoff의 "남긴 지식:" 줄을 확인                 지금 HEAD에 없는 것 (머지 전)
                                                       → PR로 팀에 (머지되면 팀원의 clone에)              넣은 것은 task 폴더 knowledge-injected.md
```

- **무엇을:** 다음 일에도 다시 필요하고 코드만 보고는 다시 알기 비싼 사실. 사람이 알려 준 규칙·관례·업무 사실과 이력, 다시 겪을 만한 실패 유형. 이번 일에만 해당하는 것, 코드에 드러난 것, "통하는지 모른다"는 메모, 비밀과 개인정보는 남기지 않는다. 규칙과 까닭을 쓰고 코드의 지금 모양은 "관련 위치"로만 적는다.
- **어디에, 어떤 형식으로:** 레포의 `docs/knowledge/<영어-이름>.md`, 한 항목 한 파일(제목, 종류, 적용, 출처, 본문 5줄 안팎). 사람이 GitHub에서 그대로 읽고, 동시 PR끼리 같은 파일에 덧붙이는 충돌이 적다. `CLAUDE.md`·`AGENTS.md`는 건드리지 않는다.
- **언제 뽑나:** 사람의 말을 직접 들은 단계가 후보를 적고, verify가 Work를 닫기 전에 파일로 정리해 커밋한다. 사람의 따로 하는 수고(지식을 고르는 화면, 승인 차례)는 없다. 팀 지식은 PR 리뷰에서, 같은 사람의 머지 전 지식은 Work 완료 화면의 [변경]에서 보인다.
- **어떻게 쓰나(context.md의 규칙):** 해당하는 규칙은 팀이 이미 아는 사실이라 다시 묻지 않는다. intake는 사람이 정한 규칙만 intent의 `제약`에 "(팀 지식 `<경로>`)"로 옮겨 사람이 의도 승인에서 보게 한다. 실패 유형은 확인해 볼 가설로만 쓴다. 규칙의 말이 이번 경우를 덮으면 따르고, 확인하려고 되묻지 않는다. 머지 전 앞 Work가 고친 곳은 이 브랜치에 아직 없으니 범위를 넓히지 않는다.
- **끄기:** `RELAY_KNOWLEDGE=off`면 지식 절, 후보 안내, 확인, `knowledge-injected.md`가 모두 없다. 지식의 지시를 스킬이 아니라 `context.md`에 두어 스킬은 고치지 않았고, 끈 앱의 스킬과 `context.md`는 `0247049`와 같다.
- **코드:** `app/src/core/knowledge.ts`(지식 절, 고르기, 비밀 거르기), `app/src/adapters/knowledge.ts`(레포와 머지 전 브랜치에서 읽기), `app/src/main/work.ts`·`relay.ts`(넣기, 앞 Work 목록), `app/src/core/validate.ts`(verify의 "남긴 지식:" 확인). 설계는 `docs/design.md` 3.6과 D283~D292.

### 4.4 hold-out에서 본 것

- **relay가 PM2를 잃은 하나(h2 #2, 팀원 Work 3):** 지식은 팀원의 새 clone에 모두 건너갔다(취소 날짜 기준, 10원 버림, 변경 수수료 등 넷). 그런데 앞 Work가 남긴 `partial-cancel-old-rules.md`가 "부분 취소는 전체 취소와 달리 24시간 내림·1원 반올림을 *쓴다*"고, 고칠 곳이 아니라 코드의 지금 모양을 사실처럼 적었다. 팀원의 에이전트는 날짜 계산만 고치고 1원 반올림은 "의도일 수 있어 담당 확인 필요"로 남겨 "부분 취소 10원 버림" 시험을 깼다. K3의 "코드 모양을 사실처럼 쓰지 않는다"를 verify가 어긴 경우이고, 문구만으로는 이 규칙이 늘 지켜지지 않는다는 뜻이다. 결과를 보고 앱을 고치지 않았다(규약 6절 5).
- base와 m17도 같은 사람의 Work에서 규칙을 다시 말했다(h1 Work 2 둘 다 1.6). relay는 남은 PM1이 대부분 사람 역할이 묻지 않은 것을 덧붙인 경우였다(개발용과 같은 모양).

- 판정은 지식의 내용도 짚었다: "반품의 도서산간 회수비도 주문당 한 번", "무료배송 기준 30,000원". 다만 이것은 Work 1 브랜치의 지식이고, 그때는 맞는 규칙이었다. 같은 사람의 Work는 머지되지 않은 채 브랜치마다 따로 있고, 판정은 세 브랜치의 diff를 함께 보았다. 그래서 이 지적은 일부 과장이다. 기록을 다시 보면 Work 3이 바뀐 규칙을 다룬 모양은 다음과 같다.

  | h1 회차 | 무료배송 기준 30,000 → 40,000원 | 반품 회수비 "주문당 한 번" → "상자마다" |
  |---|---|---|
  | 1 | Work 3이 같은 파일을 고침 | 같은 파일을 고침 |
  | 2 | 같은 파일을 고침 | (Work 1이 반품까지 일반화하지 않음) |
  | 3 | **옛 파일(30,000원)은 두고 40,000원 파일을 새로 만듦** | (일반화하지 않음) |
  | 4 | 같은 파일을 고침 | (일반화하지 않음) |
  | 5 | **옛 파일(30,000원)은 두고 40,000원 파일을 새로 만듦** | 같은 파일을 고침 |

- Work 3은 다섯 번 모두 바뀐 규칙을 지식으로 남겼다. 문제는 5번 중 2번, 옛 지식을 고치지 않고 이름이 다른 새 파일을 만든 것이다. 브랜치가 차례로 머지되면 "30,000원" 파일과 "40,000원" 파일이 레포에 함께 남아 서로 어긋난다.
- 까닭: 같은 사람의 Work 2·3은 앞 Work가 머지되기 전에 시작해서, 앞 Work의 지식 파일이 지금 worktree에 없다(앱이 내용만 보여 줌). K3-4의 안내는 "고쳐야 할 때만 앞 내용을 살려 같은 경로에 쓰고, 고칠 것이 없으면 만들지 않는다"였다. 사람의 새 말이 기존 지식과 어긋나면 그 지식을 반드시 고치라는 규칙도, 앱의 확인도 없다. 머지 뒤(옛 파일이 worktree에 있음)에도 같은 일이 생길 수 있는데 이 경우는 재지 않았다.

## 7. 한계와 다음에 볼 것

- **PM2의 여유가 없다.** hold-out의 PM2는 한도에 딱 걸쳐 통과했다. 회차 5, 시나리오 둘이라 실패 하나가 결론을 바꾼다. 개발용 시나리오의 PM2도 대부분 천장(1.0)이라, 지식이 숨긴 시험을 올리는지는 이 실험에서 보이지 않았다. 보인 것은 사람이 다시 말하는 부담(PM1)과 그에 따른 글자, 차례, 토큰의 감소다.
- **지식의 질을 문구에만 맡긴다.** verify가 지식을 *남기는지*는 앱이 확인하지만(K7), *무엇을 어떻게* 쓰는지(규칙 대 코드 모양, 확인 못 한 메모)는 에이전트가 문구를 따르는 데 달렸다. hold-out의 실패 하나가 그 틈에서 나왔다. 다음 후보: verify가 남긴 지식 파일을 앱이 읽어 "~를 쓴다/되어 있다" 같은 코드 상태 서술과 "모른다"는 메모를 찾아 형식 되돌림으로 돌려보내는 것, 또는 별도의 짧은 검토 차례.
- **바뀐 규칙이 옛 지식과 함께 남는다.** hold-out h1에서 Work 3은 바뀐 규칙을 늘 지식으로 남겼지만, 5번 중 2번은 옛 파일을 고치지 않고 새 파일을 따로 만들어 머지 뒤 서로 어긋나는 지식이 남는다(4.5). 머지 전이 이 일을 키우는 조건이었고, 머지 뒤는 재지 않았다. 짝 판정의 결과 선호가 base와 m17 쪽으로 기운 데에는 지식 파일이 diff에 섞이는 범위 문제가 가장 크다. 다음 후보: 지식 항목이 사람의 지금 말과 어긋나면 verify가 그 항목의 경로에 고친 판을 쓰게 하고, 앱이 "고친 지식:" 줄과 같은 주제의 파일이 둘 생기지 않았는지 확인한다. 지식을 코드와 따로 커밋해 리뷰에서 갈라 보게 한다.
- **사람의 검토가 없다.** 사람의 수고를 늘리지 않으려고 지식을 고르는 차례를 두지 않았다. 실제 팀에서는 틀린 지식이 PR 리뷰를 그대로 지나갈 수 있고, 낡은 지식을 고치거나 지우는 길은 "같은 내용이면 그 파일을 고친다"는 안내뿐이다. 몇 달에 걸친 낡음, 지식 파일이 수십 개로 늘 때의 고르기(지금은 8,000자까지 본문, 넘으면 제목만)는 재지 못했다.
- **머지 전 지식은 같은 앱 안에서만.** 같은 사람이 다른 컴퓨터나 맨 CLI로 다음 일을 하면 머지 전 지식은 닿지 않는다.
- **AI 사람 역할.** PM1에 남은 값 대부분은 사람 역할이 묻지 않은 규칙을 스스로 덧붙인 경우다. 실제 사람이 같은지, 지식이 실제 사람의 리뷰 부담을 줄이는지는 모른다.
