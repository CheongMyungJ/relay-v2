### 준비 확인

결과 폴더는 준비한 세션의 컨테이너에만 있었다(커밋하지 않음). 숨긴 시험 결과는 haiku와 낮은 차례 제한 탓이라 지식 관리와 관계없다.

| 확인 | 명령 요지 | 본 것 |
|---|---|---|
| 팀원 교대, relay와 맨 CLI | `--scenarios 24 --arms relay,cli --pairs relay:cli` (haiku) | 두 쪽 모두 Work 1 → 머지(relay는 Work 브랜치 1개, 맨 CLI는 main에 바로 커밋해 머지할 브랜치 0개) → 새 clone → Work 2. relay는 새 앱 저장소로 다시 띄워 프로젝트를 등록했다. 보고서, 짝 판정, `primary.mjs`까지 나왔다 |
| 고친 것 1 | 같은 시나리오 relay 재실행 | 첫 실행에서 팀원 교대 뒤 새 앱 저장소의 Work id가 앞 사람 것과 같아(`w-20261002-001`) Work 2의 결과 폴더를 가르지 못했다. 두 번째 저장소부터 `p2-`를 붙이게 고친 뒤 Work 2가 `p2-w-20261002-001`만으로 판정되는 것을 봤다 |
| 고친 것 2 | 첫 실행의 차례 기록 | haiku 사람 역할이 "물으면 답함" 항목(회계팀 금액)을 첫 요청에 넣고도 `told`에 적지 않았다. 판정 모델의 감사(`lib/told.mjs`)를 더하고 PM1을 감사로 바꿨다. 같은 기록에서 감사는 두 Work 모두 그 항목을 잡았다 |
| 다른 빌드 | `--scenarios 21 --arms base,m17 --app ...` (haiku, 차례 6) | `ref-app.sh`로 만든 `0247049`와 `aa39d16` 빌드가 같은 도구로 떠서 프로젝트 등록, Work 1 → Work 2를 지났다 |
| Work 셋과 팀원 교대, 감사 | hold-out 하나를 relay로 (haiku, 차례 8) | Work 1 → Work 2(같은 사람) → 머지 → Work 3(팀원). Work마다 결과 폴더가 갈리고 감사(`toldAudit`)가 남았다. 자기 보고는 carry 항목을 0으로 적었고 감사는 1로 잡았다 |
| hold-out 시나리오 | `check-scenario.mjs` (봉인 전) | 둘 모두 "이상 없음". 팀원 교대가 있는 쪽은 정답을 차례로 모두 적용해도 모든 시험이 통과 |
| 봉인 | `unseal.sh`를 복사본에서 | 틀린 열쇠는 거절, 맞는 열쇠로 푼 내용이 원본과 같음 |
