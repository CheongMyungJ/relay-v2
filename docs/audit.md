# relay-v2 점검 기록

MVP(M0~M7)를 마친 뒤 하는 전체 점검의 결과를 적는다. 점검은 다섯 단계로 하고, 발견 사항은 이 문서에 모아 4단계에서 나눠 고친다.

| 단계 | 하는 일 | 상태 |
|---|---|---|
| 1 | 자동 점검: 기존 검사, 번호 참조, 완료 기준, 설계와 코드 대조, 문서 목록 대조 | 끝남(2026-09-28) |
| 2 | 전체 코드 리뷰: 마일스톤 사이의 상호작용, 실패 경로 | |
| 3 | 실환경 점검: Windows 러너의 [실제], Windows PC의 [실기] | 당분간 하지 않는다(사용자 결정). 남은 항목은 1.3 |
| 4 | 분류와 수정: 발견 사항을 나눠 고친다 | 하는 중(2026-09-28~). A1부터 차례로 본다 |
| 5 | 문서 정리 | |

- 번호(D·I·G·S, 절, 시나리오)는 바꾸지 않는다. 코드와 시험만으로 D 번호 참조가 1,166개다(1.2).
- 발견 사항의 번호는 A1부터다. 뒤 단계에서 찾은 것도 이어서 붙인다.
- "4단계 제안"은 점검이 붙인 제안이고, 분류는 4단계에서 사람이 정한다. 제안의 뜻은 다음과 같다.

  | 제안 | 뜻 |
  |---|---|
  | 버그 | 코드를 고치고 시험을 더한다 |
  | 설계 빈 곳 | 사람이 정하고 설계 결정 표에 새 D 번호로 적는다 |
  | 시험 | 코드는 맞고 지키는 시험만 더한다 |
  | 문서 | 문서만 고친다. 5단계와 함께 해도 된다 |
  | 나중에 | 설계 9절 추가 후보로 둔다 |
  | 실기 확인 | 3단계에서 확인한 뒤 정한다 |
  | 사람이 정함 | 문서와 코드 가운데 어느 쪽을 고칠지 정한다 |

## 1단계. 자동 점검

- 날짜: 2026-09-28
- 기준 커밋: 2205f25(main, M7 머지). main의 app-ci #55가 통과했다
- 환경: Linux 클라우드 컨테이너(Claude Code 웹 세션), Node 22.22.2, npm 10.9.7, git 2.43.0. node-pty는 소스에서 빌드했다. Electron 바이너리는 받지 않아 [스모크]는 돌리지 않았다
- 방법: 기존 검사와 커버리지를 돌리고, 스크립트로 번호 참조를 모았다. 설계와 코드 대조는 여덟 영역으로 나눠 코드, 시험, 스킬을 읽고 결정마다 판정했다. 판정과 발견 사항에는 file:line 근거와 확신(확인함/추정)을 적었다. 레포 파일과 git은 바꾸지 않았고, git 동작은 임시 레포에서 확인했다

### 1.5 발견 사항

76건이다: 높음 1, 중간 20, 낮음 55. 종류로는 버그 의심 23, 구조 1, 시험 빠짐 7, 문서 빈 곳 26, 문서와 코드가 다름 14, 문서 오류 5이다. 높음과 중간은 먼저 볼 차례로, 낮음은 영역 차례로 적었다. 여러 영역에서 따로 찾은 것은 하나로 합쳤다. A77부터는 4단계에서 찾아 이어 적었다.

| ID | 심각도 | 영역 | 제목 | 4단계 제안 |
|---|---|---|---|---|
| A1 | 높음 | 복구 | 앱을 두 번 실행하면 두 번째 인스턴스가 첫 인스턴스의 살아 있는 claude를 끝낸다 | 버그, 설계 빈 곳(두 번째 실행 때 할 일) |
| A2 | 중간 | 기반 | 할 일 하나가 실패해도 다음 할 일을 그대로 한다 | 설계 빈 곳(할 일이 실패할 때의 규칙). 2단계에서 먼저 본다 |
| A3 | 중간 | 계약 | intake에서 handoff의 status를 읽지 못하면 intent 초안이 없어도 [오류 무시하고 승인]이 된다 | 버그 |
| A4 | 중간 | 되감기 | 되감기에서 reset 뒤 clean이 실패하면 코드는 되돌린 채 기록만 지운다 | 버그 |
| A5 | 중간 | 전달·정리 | 정리 세션이 열린 동안 [단계 선택], [세션 재개], [완료만]을 막지 않는다 | 버그 |

| A7 | 중간 | 복구 | 끊긴 정리의 [다시 시도]가 재시작 뒤 생긴 변경과 커밋을 확인 없이 지운다 | 버그 |

#### A1. 앱을 두 번 실행하면 두 번째 인스턴스가 첫 인스턴스의 살아 있는 claude를 끝낸다

- 심각도: 높음 (버그 의심). 영역: 복구
- 위치: `app/src/main/index.ts`(인스턴스 잠금 없음), `app/src/main/relay.ts:123-126`, `app/src/core/recovery.ts:298-311`, `app/src/adapters/pty.ts:288-313`. 시나리오 9-1, D76
- 내용:
  - 앱은 인스턴스를 하나로 막지 않는다(`requestSingleInstanceLock`이 없다. Electron은 기본으로 여러 인스턴스를 허용한다).
  - 앱이 떠 있을 때 한 번 더 실행하면, 새 인스턴스는 켤 때의 고아 확인(9-1)에서 첫 인스턴스의 살아 있는 task 세션과 정리 세션을 트리째 끝낸다. ID와 시작 시각이 `work.json`의 기록과 같기 때문이다.
  - 이어 재시작 조정이 그 task를 중단됨으로 바꾸고, 도는 중인 되감기·전달·정리 기록에 `interrupted_at`을 적는다. 그 뒤 두 인스턴스가 같은 `work.json`과 `events.jsonl`을 번갈아 쓴다.

#### A4. 되감기에서 reset 뒤 clean이 실패하면 코드는 되돌린 채 기록만 지운다

- 심각도: 중간 (버그 의심). 영역: 되감기
- 위치: `app/src/adapters/git.ts:249-250`, `app/src/main/work.ts:1158-1163`, `1214-1218`, `app/src/core/machine.ts:1586-1588`. `implementation.md` M4(339줄), D77, D122
- 내용:

#### A10. npm으로 설치한 `claude.cmd`를 `cmd.exe`로 감싸면 경로의 공백이나 `&`에서 인자가 깨진다

- 내용:

- 4단계 제안: 버그, 실기 확인

### 1.6 2단계로 넘기는 것

2단계(전체 코드 리뷰)는 다음부터 본다.

- **할 일의 실패 규칙(A2):** 전이 뒤의 할 일이 하나씩 실패해도 이어서 도는 구조가 A3, A51, A52의 뿌리다. 규칙을 먼저 정하면 이 셋을 한 번에 고칠 수 있다.
- **인스턴스 하나(A1):** 고치는 방법은 작지만(인스턴스 잠금), 두 번째 실행 때 할 일(앞 창을 띄움)은 설계로 정한다.
- **기능 사이의 상호작용:** 정리 세션과 다른 조작(A5), 되감기와 전달 상태(A44), 되감기와 git 실패(A4), 재시작과 카운트다운(A23), 재개와 늦은 훅(A22). 마일스톤마다 따로 리뷰해서 겹치는 곳이 비었다.
- **HEAD와 Work 브랜치의 전제(A6):** 전달과 되감기가 함께 기대는 전제라, 확인을 한곳에 두는 방법을 본다.
- **안 지난 경로:** `main/work.ts`(안 지난 문장 122줄, 가지 132개)와 `main/relay.ts`(가지 61%)의 실패 경로(1.1).
- Windows에서만 도는 경로(`taskkill`, PowerShell, `.cmd` 감싸기, 잠긴 파일)는 여기서 돌려 볼 수 없어 3단계 목록(1.3)에 두었다.
