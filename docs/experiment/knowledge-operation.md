# 프로젝트 지식 운영

Relay는 새 task 시작 때 해당 Work worktree의 HEAD에 있는 `.relay/knowledge.md`를 읽어 context.md에 제공한다. Git blob ID가 출처다. 개인 RELAY_HOME에서 검색하거나 이전 대화를 복사하지 않는다. 문서가 없으면 기존 흐름 그대로 진행한다. 일반 파일만 허용한다. 12,000바이트 이하는 전체를 첨부하고, 초과하면 출처 blob ID와 검색·절 목록·범위 읽기 명령을 제공한다. 각 명령의 출력은 최대 12,000바이트이며 원문은 Git에 그대로 보존한다. 질문하거나 정책을 정하기 전에 관련 절의 범위·근거·출처·미확정 사항을 확인한다. 출력이 잘리면 검색 범위를 좁히거나 이어 읽는다. 이미 실행 중인 task의 컨텍스트는 바뀌지 않는다.

fix·implement·refactor는 커밋 전 현재 요청, 승인된 intent, 사람 답변, 실제 관측과 앞 task가 전달한 사실을 기존 공유 기록과 양방향으로 대조한다. 제안한 변경의 정당성과 새로 확인한 재사용 사실의 누락을 함께 확인하며, 지식 diff가 없어도 수행한다. 코드 diff나 완료조건만으로 학습 범위를 정하지 않는다. 기존 task 산출물에 중요한 차이와 근거 또는 변경이 필요 없는 이유를 간결히 남긴다. 모든 요청 문장이나 이미 알려진 사실의 별도 목록을 만들지 않는다.

공유할 수 있는 근거는 두 종류다.

- 사람이 명시적으로 확인한 재사용 업무 규칙: 현재 요청도 확인 근거가 될 수 있다. 필요한 답변 발췌·업무 범위·확인 날짜·출처를 남긴다. 미래 작업에 적용될 확정 규칙도 이번 코드 구현 범위와 구분해 기록한다. 적용 시점이나 조건을 보존하고 구현 완료로 추정하거나 코드 범위를 확대하지 않는다. 일회성 계획·제안·AI 추정은 확정 규칙이 아니다.
- 실제 장애에서 새로 배운 비자명한 검증 절차 또는 기존 절차의 범위·유효성·정확성을 바꾸는 관측: 실패 증상, 도구·런타임·환경, 진단의 지원 근거, 실제 성공 명령·결과·날짜·출처가 필요하다. 성공하지 않은 제안 설정은 검증된 절차가 아니다. 기존 절차가 무효이고 대체가 성공하지 않았으면 확인된 무효 범위와 대체 미확정을 남긴다. 테스트 성공을 사람의 업무 정책 확인으로 바꾸지 않는다.

새 사실, 적용 범위·유효성 변화, 정정, 명시적 정책 대체가 없으면 공유 문서는 바이트 단위로 불변이다. 동일 절차와 범위의 새 Work 출처·날짜·기준 커밋·테스트 수·반복 실패·통과는 실행 이력이다. 사용한 절 제목·blob·원출처와 현재 적용 확인·명령·결과는 task에 두고 handoff에서 참조한다. 재검증 절 추가, 원날짜·출처 갱신, 같은 재사용의 knowledge_candidates 생성은 하지 않는다. 코드/README의 뻔한 사실·일반 테스트 명령·로그 복사도 제외한다. README가 진단만 안내했더라도 진단에서 새로 알아내 실제 검증한 지원 설정은 해당할 수 있다. 명령이 같아도 범위 확장·축소나 무효화 근거가 새로 생기면 영향받는 기록만 갱신한다. 중복 통합은 고유한 사실·범위·원발견·변경 근거와 출처를 보존할 때만 하며 재사용 자체를 이유로 정리하지 않는다.

재사용할 때 범위·근거를 읽고 현재 도구·런타임·로컬 설정 조건을 실제 확인한 뒤 알려진 지원 절차로 필요한 테스트를 실행한다. 같은 도구도 가변 로컬 상태까지 보장하지 않는다. 적용 확인에 충분한 검사만 선택하며 필요한 현재 상태 확인, 근거 부족·충돌, 적용 가능한 절차 실패에는 진단을 실행한다. 재사용을 증명하려고 알려진 설정 없는 실패나 설정 검색을 반복하지 않는다. 필요한 재현·기준 비교·독립 검증은 유지하고 진단이나 설정 없는 실행의 이유를 task에 쓴다. 설정이 정상인 코드 테스트 실패만으로 환경 절차를 무효화하지 않으며 과거 결과로 현재 성공을 대신하지 않는다.

handoff·knowledge_candidates·RELAY_HOME은 이번 Work 내 근거 전달 수단이며 새 clone/Work의 공유 지식이 아니다. intake·design에서 확인한 사실은 근거와 함께 기존 산출물/handoff에 전달하고, 코드 변경 단계에서 요건을 충족하는 사실을 `.relay/knowledge.md`에 커밋한다. 후속 구현 규칙도 handoff에만 남기지 않는다. 일회성 작업 계획은 task에 둔다. 각 공유 사실에 context.md의 `knowledge_source`와 Work/task 출처 및 검색 가능한 제목을 쓴다. `knowledge_source`는 Work 로컬 `knowledge-source-id`의 임의 UUID로 task·앱 재시작 사이 유지된다. 새 clone의 Work는 같은 Work/task 번호라도 다른 출처 ID를 갖는다. 이전 task의 확인은 해당 task ID, 이전 Work의 답변은 원래 ID를 유지하고 없는 과거 ID를 지어내지 않는다. 머신 절대 경로·원격 URL·비밀·개인정보를 복사하지 않는다.

verify는 기준 커밋부터 공유 diff의 정당성을 검토하고, 작성자의 변경 요약과 별개로 요청·intent·사람 답변·실제 관측을 최종 공유 기록과 대조해 누락도 확인한다. 지식 diff가 없어도, 모든 코드 완료조건이 통과해도 생략하지 않는다. 중요한 변경 비교와 사실 전달 여부를 `리뷰 지적`에 기록한다. 동일 재검증 이력은 불필요한 변경으로, 누락된 확정 재사용 사실은 전달 결함으로 지적한다. 정정은 기존 복귀 절차로 코드 변경 단계에서 수행하고, 사람이 지적을 골라도 verify가 공유 지식을 추출·작성하는 우회는 하지 않는다. intake·design도 공유 문서를 수정하지 않는다. 기존 산출물·diff·수동 승인 흐름을 사용하며 별도 화면·후보 승인 단계·자동 의미 판별기는 추가하지 않는다.

공유하려면 기존 프로젝트 Git 절차로 Work 브랜치를 검토하고 기준 브랜치에 merge한다. 다른 팀원은 clone/pull하고 새 Work를 시작한다. 앱 저장소를 복사할 필요가 없다. 실험의 로컬 bare 원격은 Git 전달만 검증하며 실제 GitHub PR 게시는 하지 않는다.

현재 요청과 intent가 공유 문서보다 우선한다. 규칙 변경이 확인되면 기존 활성 규칙을 교체하고 무엇을 대체했는지 적는다. 이번 task와 무관한 항목은 사용하지 않되 다른 팀원에게 유효할 수 있으므로 삭제하지 않는다. 삭제는 사람이 명시적으로 폐기했거나 새 규칙으로 대체됐다는 근거가 있을 때만 하고 근거를 남긴다. 12,000바이트 제한 때문에 확인된 활성 사실을 버리지 않는다. 중복은 의미 손실 없이 줄이고 검색 가능한 제목을 쓴다. 유효한 내용이 커져도 기존·새 사실을 문서에 보존한다. 12,000바이트는 자동 첨부 한도이며 저장 한도가 아니다. 사용한 사실의 출처와 충돌을 task 산출물에 기록한다. 문서 삭제를 커밋하면 이후 task에 제공되지 않는다. 문서만 지워도 이미 시작한 task의 스냅샷은 남으므로 해당 task는 재시작하거나 명시적으로 정정해야 한다.

제약: 적용 범위·노후화·정확성은 모델과 사람이 판단한다. 앱은 내용의 진위를 자동 인증하지 않는다. 작은 문서 전체를 매 단계에 제공하고 큰 문서는 필요한 구간을 검색하므로 토큰 비용이 생긴다. 첨부/개별 출력 한도는 총 검색 횟수나 전체 모델 토큰의 상한을 보장하지 않는다. 큰 문서의 검색 완전성은 모델이 판단하며 명령 예시는 rg/sed/head를 사용할 수 있는 셸을 전제한다. 다수 팀원과 큰 문서에서 효율적이라는 증거는 없다. 추출이 누락되거나 요약이 잘못될 수 있으며, 승인 자체가 미래 모든 작업의 적합성을 보장하지 않는다. 실제 사람의 화면 사용성은 이번 headless 서비스 실험으로 검증되지 않는다.
