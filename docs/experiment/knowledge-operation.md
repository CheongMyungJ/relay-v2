# 프로젝트 지식 운영

Relay는 새 task 시작 때 해당 Work worktree의 HEAD에 있는 `.relay/knowledge.md`를 읽어 context.md에 제공한다. Git blob ID가 출처다. 개인 RELAY_HOME에서 검색하거나 이전 대화를 복사하지 않는다. 문서가 없으면 기존 흐름 그대로 진행한다. 일반 파일만 허용한다. 12,000바이트 이하는 전체를 첨부하고, 초과하면 출처 blob ID와 검색·절 목록·범위 읽기 명령을 제공한다. 각 명령의 출력은 최대 12,000바이트이며 원문은 Git에 그대로 보존한다. 질문하거나 정책을 정하기 전에 관련 절의 범위·근거·출처·미확정 사항을 확인한다. 출력이 잘리면 검색 범위를 좁히거나 이어 읽는다. 이미 실행 중인 task의 컨텍스트는 바뀌지 않는다.

코드를 고치는 스킬은 사람이 확인한 재사용 업무 사실과, 실제 장애를 해결한 검증 절차를 구분해 정리한다. 새로 배운 검증 절차는 실패 증상, 적용 도구·환경, 진단의 지원 설정 근거, 실제 성공한 명령·결과·날짜가 있어야 한다. 코드/README의 뻔한 사실, 일반 테스트 명령, 로그 전체는 수집하지 않는다. 재사용할 때 기록의 범위·근거를 먼저 읽고, 현재 적용에 필요한 도구·런타임·로컬 설정 조건을 실제 확인한 뒤 알려진 지원 절차로 필요한 검증을 실행한다. 도구가 같아도 가변 로컬 상태가 중요하면 현재 진단이 필요하다. 적용 확인에 충분한 검사만 선택하며, 근거가 없거나 충돌하거나 적용 가능한 절차가 실패하면 다시 진단한다. 설정이 정상인 코드 테스트 실패만으로 환경 절차를 무효화하지 않는다. 재사용을 증명하기 위해 알려진 설정 없는 실패나 설정 검색을 반복하지 않는다. 필요한 재현·기준 비교·독립 검증은 그대로 실행하고, 진단이나 설정 없는 실행이 필요한 이유를 이번 task에 남긴다. 테스트 성공을 사람의 업무 정책 확인으로 바꾸지 않는다. 각 사실에 적용 범위, 규칙, 사람 답변 발췌, 확인 날짜, context.md의 `knowledge_source`와 Work/task 출처를 쓴다. `knowledge_source`는 Work 로컬 디렉터리의 `knowledge-source-id`에 보존되는 임의 UUID이며 task와 앱 재시작 사이에도 유지된다. 새 clone에서 새로 만든 Work는 같은 Work/task 번호라도 다른 출처 ID를 갖는다. 공유 문서에는 이 ID만 쓰고 머신 절대 경로나 원격 URL은 쓰지 않는다. 이전 Work 답변의 출처는 그 Work의 ID를 유지하며, 과거 사실에 없는 ID를 소급해서 지어내지 않는다. 모르는 사실은 질문하고 AI 추정은 공유 사실로 만들지 않는다. 변경한 지식 문서는 코드와 같은 diff에서 검토한다. 사람이 산출물과 diff를 읽고 잘못된 요약을 터미널에서 수정 지시한 뒤 다시 검토·승인한다. 별도 자동 승인이나 게시 절차는 없다.

공유 문서 변경 전에는 관련 커밋 기록과 비교하여 다음 팀원이 새로 배우거나 다르게 판단·실행할 사실을 이번 task 산출물에 근거와 함께 쓴다. 새 사실, 적용 범위·유효성 변화, 실제 정정, 명시적 정책 변경이 없으면 문서를 바이트 단위로 그대로 둔다. 동일 절차를 사용한 새 Work 출처·날짜·기준 커밋·테스트 수·반복 실패·통과는 실행 이력이다. 이번 task에는 사용한 절 제목·blob·원출처와 현재 적용 확인·실행 명령·결과를 남기고 handoff에서 참조한다. 재검증 절을 추가하거나 원래 날짜·출처를 갱신하거나 동일 재사용을 knowledge_candidates로 만들지 않는다. 명령이 같아도 실제로 새 환경까지 적용 범위가 확장되거나 기존 범위가 무효화되면 지식 변경이다. 해당 항목만 간결히 고치고 원발견과 변경 근거·출처를 보존한다. 기존 중복 실행 이력은 고유한 사실·범위·원출처·변경 출처를 잃지 않는 경우에만 통합할 수 있으며, 재사용 자체를 이유로 정리하지 않는다.

verify는 기준 커밋부터 공유 문서 diff를 task 근거와 대조한다. 새 지식이 무엇인지 `리뷰 지적`에 쓰고, 지식 diff가 없으면 없다고 쓴다. 변경 없는 절차의 실행 이력만 덧붙였다면 불필요한 변경으로 지적한다. 코드 검사 통과로 승인 근거를 대신하지 않는다. 정정이 필요하면 기존 복귀 절차로 코드 변경 단계에 돌려보내며 verify는 공유 문서를 추출·수정하지 않는다. 별도 검토 화면·후보 승인 단계·자동 의미 판별기는 추가하지 않는다.

일회성 구현 범위는 intent/task 산출물에 두고 지속 업무 규칙과 섞지 않는다. 예를 들어 평균만 고치는 Work여도 확인된 센서 보고서의 평균·중앙값·최댓값 적용 범위는 유지한다. `undefined`/`NaN`처럼 미확인인 사실은 미확인으로 보존한다.

공유하려면 기존 프로젝트 Git 절차로 Work 브랜치를 검토하고 기준 브랜치에 merge한다. 다른 팀원은 clone/pull하고 새 Work를 시작한다. 앱 저장소를 복사할 필요가 없다. 실험의 로컬 bare 원격은 Git 전달만 검증하며 실제 GitHub PR 게시는 하지 않는다.

현재 요청과 intent가 공유 문서보다 우선한다. 규칙 변경이 확인되면 기존 활성 규칙을 교체하고 무엇을 대체했는지 적는다. 이번 task와 무관한 항목은 사용하지 않되 다른 팀원에게 유효할 수 있으므로 삭제하지 않는다. 삭제는 사람이 명시적으로 폐기했거나 새 규칙으로 대체됐다는 근거가 있을 때만 하고 근거를 남긴다. 12,000바이트 제한 때문에 확인된 활성 사실을 버리지 않는다. 중복은 의미 손실 없이 줄이고 검색 가능한 제목을 쓴다. 유효한 내용이 커져도 기존·새 사실을 문서에 보존한다. 12,000바이트는 자동 첨부 한도이며 저장 한도가 아니다. 사용한 사실의 출처와 충돌을 task 산출물에 기록한다. 문서 삭제를 커밋하면 이후 task에 제공되지 않는다. 문서만 지워도 이미 시작한 task의 스냅샷은 남으므로 해당 task는 재시작하거나 명시적으로 정정해야 한다.

제약: 적용 범위·노후화·정확성은 모델과 사람이 판단한다. 앱은 내용의 진위를 자동 인증하지 않는다. 작은 문서 전체를 매 단계에 제공하고 큰 문서는 필요한 구간을 검색하므로 토큰 비용이 생긴다. 첨부/개별 출력 한도는 총 검색 횟수나 전체 모델 토큰의 상한을 보장하지 않는다. 큰 문서의 검색 완전성은 모델이 판단하며 명령 예시는 rg/sed/head를 사용할 수 있는 셸을 전제한다. 다수 팀원과 큰 문서에서 효율적이라는 증거는 없다. 추출이 누락되거나 요약이 잘못될 수 있으며, 승인 자체가 미래 모든 작업의 적합성을 보장하지 않는다. 실제 사람의 화면 사용성은 이번 headless 서비스 실험으로 검증되지 않는다.
