# 자율 Work 설계 제안

- 상태: A1·A2·A4·A5 구현함 (D533~D549, M42~M44). A3·A6(평가)과 열린 문제는 남음
- 작성일: 2026-11-02
- 범위: 고정된 업무 유형과 단계 파이프라인 대신, 의도만 정리한 뒤 메인 세션이 일하는 방식을 고르고 필요하면 자식 Work로 나눠 맡기는 Work. 앱이 과정 대신 결과를 검사하는 하네스.

이 문서는 relay의 다음 모습에 대한 제안이다. 정한 것은 [design.md](design.md) 2절의 D533~D549로 옮겼고, 이 문서는 근거와 들이지 않은 대안을 남기는 곳으로 둔다.

**구현하며 제안과 달라진 것**

- 관문 G2(설계 메모)는 `spawn_child`가 아니라 방식 줄로 본다: `- 방식:`에 설계 먼저가 있으면 `plan.md`의 `## 설계`가 있어야 한다(D535). 설계 메모는 따로 파일을 두지 않고 `plan.md`의 절이다.
- 자식의 `ask_parent`·`report` 도구는 두지 않았다. 자식의 질문은 지금 질문 도구가 부모에게 가고(driver: caller), 자식이 마친 것은 Work 완료 화면이 된 것을 `wait_children`이 알려 준다(D543, D546).
- 사람이 자식 터미널에 말한 것을 부모에게 알리는 것(6.4의 사람 입력 알림)과 관문 표(9절)는 넣지 않았다.
- 계획 승인 설정은 넣지 않았다. 자율 진행은 늘 계획을 사람 승인 없이 진행한다.

## 1. 배경

### 1.1 지금 구조

- Work는 업무 유형(버그 수정, 기능 추가·변경, 리팩터링, 설계, 일반, 커스텀)을 하나 고르고, 그 유형의 단계 파이프라인을 앞으로만 간다(design.md 3.1, D418, D493).
- 단계마다 새 세션을 띄우고 앞 단계의 결과는 산출물과 handoff로 넘긴다(D3).
- 통제 지점은 단계 경계의 사람 승인이다(design.md 1.2).

### 1.2 평가가 보여 준 것

[eval-findings.md](eval-findings.md)의 숫자다.

- **부담은 40짝 모두 맨 CLI가 앞섰다.** 승인 횟수, 세션 수(4~8 대 1), 토큰(3~5배)은 구조에서 나온 숫자다(R1, R9).
- **결과 확신(relay 33 : CLI 0)과 결과 선호(27 : 2)는 relay가 앞섰다.** 그 차이는 단계의 수가 아니라 재현·회귀 시험, 완료조건별 판정표, diff, 의도 승인, 열린 질문에서 나왔다(7절, design.md 3.4).
- **같은 요청에서도 크기 분류가 흔들렸다.** 08은 L 3회, M 1회, S 1회였고 결과는 같았다(R1). 처음에 경로를 한 번 고르는 방식이 약하다.

정리하면 품질은 산출물이 만들었고, 비용은 고정된 경로가 만들었다.

### 1.3 맨 CLI에 큰일을 맡길 때의 문제

한 세션에 큰일을 맡기면 메인 세션이 거의 모든 일을 혼자 하고, 정형화된 설계 문서도 없이 자체 판단으로 진행한다. 무엇을 왜 그렇게 했는지 남지 않고, 시험을 더할지는 그때그때 다르다(eval-findings 7절: 04와 06의 CLI는 5회 모두 시험을 더하지 않았다).

### 1.4 바라는 모습

사람이든 다른 에이전트든 relay에 일을 맡기면, relay는 의도 정리만 먼저 하고 그 뒤로는 알아서 알맞은 방식으로 일한다.

- 레거시 코드의 작은 수정이면 한 세션에서 끝낸다.
- 규모가 있으면 메인 세션이 서브에이전트나 자식 Work를 써서 나눠 맡긴다.
- 설계를 먼저 하고 계획대로 갈 수도 있고, 실험이 중요하면 TDD로 갈 수도 있다.
- 필요하면 PR을 나눈다.
- 사람은 크게 관여하지 않고 과정을 지켜볼 수 있으면 된다. 원하면 어느 세션에든 들어가 보고 대화할 수 있다.

## 2. 목표와 비목표

### 2.1 목표

1. 사람이 승인하는 관문은 의도 하나로 줄인다. 머지는 그대로 사람이 한다.
2. 일하는 방식(전략)과 나누는 방식(실행 형태)은 메인 세션이 고르고, 그 선택을 산출물로 남긴다.
3. 어떤 방식을 골랐든 결과의 품질은 앱이 같은 관문으로 검사한다.
4. 자식 작업도 Work다. 사람이 들어가 보고 대화할 수 있다.
5. 지금 relay가 앞선 것(eval-findings 7절)을 잃지 않는다.

### 2.2 비목표

- 기존 업무 유형의 스킬을 플레이북으로 다시 쓰지 않는다(9.1).
- 자식 Work를 바깥 호출자용 relay MCP로 만들지 않는다(9.2).
- task 안의 작업을 한 걸음씩 통제하지 않는다. 앱은 Stop 같은 경계에서만 검사한다(design.md 1.2의 정신은 남긴다).
- 실행 중인 세션에 글을 넣지 않는다(design.md 1.2). 부모와 자식 사이의 글은 도구 호출의 결과나 턴이 끝난 뒤 다시 여는 길로 전한다(6.4).
- 헤드리스 스트림을 파싱해 CLI 화면을 다시 만들지 않는다.

## 3. 핵심 생각

### 3.1 과정 하네스에서 결과 하네스로

| | 지금 | 제안 |
|---|---|---|
| 앱이 정하는 것 | 단계의 순서 | 내야 할 산출물과 증거 |
| 에이전트가 정하는 것 | 단계 안의 진행 | 전략, 나누기, 순서 |
| 통제 지점 | 단계 경계의 사람 승인 | 앱의 관문 검사와 부모의 승인 |
| 잘못 골랐을 때 | 경로가 고정이라 고칠 수 없음 | 계획을 고치고 다시 나눔. 관문이 같으므로 품질은 지켜지고 효율만 잃음 |

### 3.2 Work는 재귀한다

> **Work = 의도 + 그 의도를 맡은 세션 + 하네스(계획, 관문)**

최상위 Work와 자식 Work는 같은 것이고, 의도가 어디서 오는지만 다르다(4.2).

## 4. 개념 모델

### 4.1 일의 단위

| 단위 | 무엇인가 | 언제 쓰나 |
|---|---|---|
| **Work** | 의도 하나, 세션 하나, 자기 worktree와 브랜치 | 모든 일의 바깥 단위 |
| **자식 Work** | 부모가 의도를 써서 만든 Work | 자기 브랜치와 따로 검토할 만한 코드 변경, 오래 걸리는 일, PR을 나눌 단위 |
| **서브에이전트** | 세션 안에서 Claude Code의 Agent 도구로 부르는 작업 | 코드를 바꾸지 않거나 짧은 일(조사, 검증, 작은 확인) |
| **직접** | 메인 세션이 스스로 함 | 작은 수정, 지금 맥락이 꼭 필요한 일 |

코드를 바꾸는 병렬 작업은 서브에이전트가 아니라 자식 Work로 한다. 서브에이전트의 worktree를 합치는 길을 relay가 따로 만들지 않기 위해서다.

### 4.2 최상위 Work와 자식 Work

| | 최상위 Work | 자식 Work |
|---|---|---|
| 의도를 쓰는 쪽 | 사람이나 호출자와 대화해 정리(지금의 의도 정리) | 부모가 직접 씀 |
| 의도를 승인하는 쪽 | 사람이나 호출자 | 부모(사람 승인 없음) |
| 질문하는 상대 | 사람이나 호출자 | 부모. 부모도 모르는 "사람만 아는 정보"면 부모가 사람에게 올림 |
| 브랜치 | 머지 대상에서 뻗음(D425~D428) | 만들 때의 부모 브랜치 HEAD에서 뻗음 |
| 끝나면 | 관문을 지나 앱이 전달 | 부모에게 보고. 부모가 합칠지, 따로 PR로 낼지, 버릴지 정함 |
| 자식을 다시 만들 수 있나 | 예 | 깊이 상한까지만(기본 1단, **(기본값)**) |
| 독립 리뷰 | PR 단위로 받음 | 따로 PR이 될 때만 받음(5.4) |

### 4.3 Work의 상태

지금의 상태(design.md 3.3)를 그대로 쓰고 두 가지만 더한다.

| 상태 | 뜻 |
|---|---|
| 자식 기다림 | 메인 세션이 자식의 결과를 기다림(6.3) |
| 부모 확인 대기 | 자식이 보고를 마치고 부모의 결정(합침, PR, 버림, 고칠 점)을 기다림 |

## 5. Work의 생애

```
[1] 의도 정리 ──── 사람이나 호출자가 승인 (유일한 필수 사람 관문)
      │ intent.md: 목표, 비목표, 원하는 결과, 완료조건과 각각의 확인 방법, 제약
      ▼
[2] 계획 ──── 메인 세션이 쓴다. 사람 승인은 설정으로 켤 수 있음(기본 끔, (기본값))
      │ plan.md: 전략과 고른 까닭, 조각과 실행 형태, PR 나누기
      ▼
[3] 실행 ──── 조각마다 직접 / 서브에이전트 / 자식 Work
      │ 하다가 계획이 틀렸으면 plan.md를 고치고 까닭을 남긴다
      ▼
[4] 관문 ──── 앱이 검사한다. 못 지나면 같은 세션으로 되돌린다
      ▼
[5] 독립 리뷰 ──── PR 단위마다 앱이 띄운다 (D495, D496)
      ▼
[6] 전달 ──── 앱이 push나 PR 생성. PR이 여럿일 수 있음. 머지는 사람
```

### 5.1 의도 정리

- 지금의 의도 정리(work-start, intent.md 형식, design.md 5.3)를 그대로 쓴다. 업무 유형을 고르는 일만 뺀다.
- 완료조건마다 확인 방법을 적는다. 일반 유형이 이미 이렇게 한다(D302, D305).
- 사람만 아는 규칙은 여기서 묻는다. 평가에서 relay가 가장 크게 이긴 곳이다(eval-findings 7절, 08에서 5/5 대 0/5).

### 5.2 계획

메인 세션은 시스템 프롬프트(5.5)의 기준으로 전략과 실행 형태를 골라 `plan.md`에 쓴다(7.2). 작은 일이면 계획도 짧다. 조각 하나, 직접, PR 하나면 몇 줄로 끝난다.

### 5.3 실행

- 조각을 차례로 또는 나란히 실행한다. 자식 Work는 6절의 도구로 만든다.
- 계획을 고치는 것은 허용한다. `plan.md`의 "바뀐 계획"에 무엇을 왜 바꿨는지 남긴다.
- 의도를 바꿔야 하면 혼자 바꾸지 않는다. 최상위 Work는 사람이나 호출자에게, 자식 Work는 부모에게 묻는다.

### 5.4 관문과 독립 리뷰

8절에 적는다. 독립 리뷰는 PR 단위로 한 번 받는다. 자식 Work가 부모 브랜치에 합쳐지면 부모의 PR 리뷰에 들어가므로 따로 받지 않는다.

### 5.5 메인 세션의 시스템 프롬프트

기존 유형 스킬을 다시 쓰지 않고 자율 진행을 위해 새로 쓴다. 넣는 방식은 D440(시스템 프롬프트에 덧붙임)을 그대로 쓴다. 담을 것은 판단 기준이고, 숫자 상한은 담지 않는다(앱이 강제한다, 10절).

**전략 고르기**

| 신호 | 전략 |
|---|---|
| 고칠 곳이 좁고, 확인 방법이 이미 있음 | 바로 고침. 동작을 바꾸면 회귀 시험을 더함 |
| 버그인데 원인이 확실하지 않음 | 재현 시험 먼저(고치기 전에 실패를 보임) |
| 동작을 바꾸지 않는 구조 변경 | 지금 동작을 잡는 안전망 시험을 먼저 커밋 |
| 새 동작이고 입출력이 분명함 | TDD(시험 커밋이 구현 커밋보다 먼저) |
| 바꿀 곳이 여러 모듈에 걸치거나, 공개 인터페이스·데이터 모양이 바뀜 | 설계 메모 먼저(7.3), 그다음 계획 |
| 될지 모르는 접근(성능, 외부 도구, 라이브러리 동작) | 스파이크 먼저. 결과를 보고 계획을 고침 |

**나누기**

- 지금 맥락이 꼭 필요하면 직접 한다.
- 답이나 조사 결과만 필요하면 서브에이전트에 맡긴다.
- 서로 다른 파일을 건드리고, 따로 검토할 만하거나 오래 걸리는 코드 변경이면 자식 Work로 맡긴다.
- 같은 파일을 건드리는 조각은 나란히 돌리지 않는다.
- 판단이 애매하면 나누지 않는다. 나누는 비용(세션 시작, 맥락 다시 읽기, 합치기)이 확실히 작을 때만 나눈다.

**PR 나누기**

- 리뷰어가 따로 판단할 수 있는 단위(서로 독립인 변경, 준비 리팩터링과 기능)이면 나눈다.
- 서로 기대는 변경은 한 PR로 둔다. 쌓인 PR(stacked)은 처음에는 만들지 않는다(11절 열린 문제 4).

## 6. 부모와 자식

### 6.1 도구

relay 안에서만 쓰는 좁은 도구다. 바깥 호출자용 relay MCP(D516~D526)와 별개이고, 지금 질문에 쓰는 task용 MCP 연결(`relay_task`, I193)에 더한다. approve·deliver 같은 바깥용 절차는 넣지 않는다.

| 쪽 | 도구 | 하는 일 |
|---|---|---|
| 부모 | `spawn_child` | 의도(intent.md 형식), 맡는 파일, 실행 설정을 주고 자식 Work를 만든다. 앱이 상한(10절)을 넘으면 거절하거나 대기열에 세운다 |
| 부모 | `list_children` | 자식들의 상태와 보고 요약 |
| 부모 | `wait_children` | 자식 하나라도 상태가 바뀔 때까지 기다린다(`seen`으로 이미 본 상태를 넘김, I195의 `wait`와 같은 모양) |
| 부모 | `answer_child` | 자식의 질문에 답한다 |
| 부모 | `decide_child` | 보고를 받은 자식에 대해 정한다: `merge`(부모 브랜치에 합침), `pr`(따로 PR), `revise`(고칠 점과 함께 다시 엶), `discard`(버림) |
| 자식 | `ask_parent` | 부모에게 묻고 답을 기다린다 |
| 자식 | `report` | 끝났다고 보고한다. 요약, 완료조건별 판정, 결과 위치 |
| 둘 다 | `ask_human` | 지금처럼 사람에게 묻는다. 자식은 직접 쓰지 않고 부모를 거친다(6.2) |

### 6.2 질문이 올라가는 길

```
자식 ── ask_parent ──▶ 부모가 답할 수 있으면 answer_child
                        └─ 사람만 아는 정보면 부모가 ask_human (최상위면 호출자에게)
```

자식이 사람에게 바로 묻지 않는 까닭: 같은 질문이 여러 자식에서 겹칠 수 있고, 부모가 한 번 묻고 모두에게 나눠 주는 편이 사람의 수고가 적다.

### 6.3 기다리기

- 부모는 자식이 도는 동안 `wait_children`으로 기다린다. 도구 호출의 제한 시간은 질문과 같은 길(`MCP_TOOL_TIMEOUT`, I193)을 쓴다.
- 앱이 다시 켜지면 부모는 재개 첫 입력으로 자식들의 지금 상태를 받는다(지금의 재개 안내와 같은 길).

### 6.4 사람이 자식에게 직접 말할 때

- 사람은 어느 Work든 터미널에 들어가 말할 수 있다. 사람의 말이 부모의 지시보다 우선한다.
- 자식은 사람이 범위나 방향을 바꾸면 `report`로 부모에게 알린다(시스템 프롬프트의 규칙). 앱도 그 터미널에 사람의 입력이 있었다는 사실을 부모의 다음 `wait_children` 결과에 붙인다(`UserPromptSubmit` 훅, 8.3의 계약 확인 필요).
- 부모의 `answer_child`·`decide_child(revise)`는 실행 중인 자식에 글을 넣지 않는다. 자식이 `ask_parent`로 기다리는 중이면 그 결과로, 턴이 끝났으면 같은 대화를 다시 여는 길(I194의 `revise`)로 전한다.

### 6.5 브랜치와 합치기

- 자식 브랜치는 만들 때의 부모 브랜치 HEAD에서 뻗고, 자기 worktree를 갖는다.
- `merge`는 부모가 자기 worktree에서 자식 브랜치를 합친다. 같은 레포의 worktree라 브랜치가 보인다. 충돌은 부모가 푼다.
- 충돌을 줄이려고 `spawn_child`에 맡는 파일을 적게 하고, 앱이 나란히 도는 자식끼리 맡는 파일이 겹치면 경고한다.
- push는 지금처럼 막혀 있다(D17). 전달은 앱이 한다.

### 6.6 PR 나누기

- `decide_child(pr)`로 정한 자식은 전달 때 따로 PR이 된다. 처음에는 머지 대상에서 바로 뻗은 독립 PR만 만든다.
- 부모 브랜치의 변경에 기대는 자식은 `pr`로 정할 수 없다(앱이 자식 브랜치의 뿌리를 보고 막음). 그런 자식은 `merge`한다.
- Work 완료 화면은 PR 단위로 판정표, diff, 독립 리뷰 결과를 보인다.

## 7. 산출물 계약

### 7.1 intent.md

지금 형식(design.md 5.3) 그대로. 자식 Work의 intent.md는 부모가 쓰고, `## 부모`에 부모 Work와 그 계획의 조각 id를 적는다.

### 7.2 plan.md

```markdown
## 전략
<고른 전략>. <고른 까닭: 5.5의 어떤 신호를 봤는지>

## 조각
| id | 목표 | 실행 형태 | 맡는 파일 | 끝난 조건 | 앞 조각 |
|---|---|---|---|---|---|
| p1 | ... | 직접 / 서브에이전트 / 자식 Work | ... | ... | - |

## PR
- PR 1: p1, p2 (까닭)

## 위험과 확인할 것

## 바뀐 계획
- <언제> <무엇을 왜 바꿨는지>
```

### 7.3 설계 메모 (design-note.md)

전략이 "설계 메모 먼저"이거나 자식 Work를 만들면 쓴다. 바뀌는 인터페이스와 데이터 모양, 모듈 사이 책임, 고르지 않은 대안을 짧게 적는다. 레포의 설계 문서를 고치는 일이 의도에 들어 있으면 그것을 고치고 여기에는 가리키기만 한다.

### 7.4 자식의 보고

`report` 도구의 입력을 앱이 자식 Work 디렉터리에 `report.md`로 쓴다. 요약, 완료조건별 판정과 증거, 바뀐 파일, 남은 위험.

### 7.5 verification.md, pr.md

지금 마무리 단계의 형식(D493~D500)을 그대로 쓴다. PR이 여럿이면 PR마다 `pr-<n>.md`를 쓰고, `verification.md`의 완료조건 판정에는 어느 PR이 그 조건을 채우는지 적는다.

## 9. 화면

사람이 지켜보는 데 필요한 것만 둔다.

- **사이드바:** Work 아래에 자식 Work를 들여 써서 보인다. 상태 표시는 지금과 같고, "자식 기다림"과 "부모 확인 대기"를 더한다.
- **계획 탭:** `plan.md`의 조각 표를 진행 상태와 함께 보인다(조각마다 실행 형태, 맡은 자식 Work로 가는 링크, 끝남 여부). 바뀐 계획은 눈에 띄게 둔다.
- **터미널:** 지금처럼 Work마다 터미널. 자식 Work의 터미널에 들어가 말할 수 있다.
- **서브에이전트 활동:** 메인 세션 터미널 위에 지금 돌고 있는 서브에이전트를 한 줄씩 보인다(이름, 시작 시각, 끝남).
- **관문 표:** G1~G7이 지났는지, 못 지났으면 왜인지.
- **Work 완료 화면:** PR 단위로 판정표, diff, 독립 리뷰 결과.

## 11. 열린 문제

1. **전략 선택의 정확도.** 크기 분류처럼 흔들릴 것이다. 잘못 골라도 품질이 떨어지지 않게 관문을 전략과 무관하게 두었지만, 효율이 얼마나 흔들리는지는 재 봐야 안다.
2. **실패하는 시험의 증거.** G5는 커밋 순서만 본다. 앱이 시험 커밋 시점의 코드에서 시험을 직접 돌려 실패를 확인할지(정확하지만 레포마다 시험 명령을 알아야 함).
3. **부모가 기다리는 방식.** `wait_children`으로 세션을 붙잡아 둘지, 부모가 턴을 끝내고 앱이 자식의 변화 때 다시 열지. 앞쪽이 단순하고, 뒤쪽은 세션을 덜 붙잡는다. 처음에는 앞쪽으로 하고 재 본다.
4. **쌓인 PR.** 부모 변경에 기대는 자식을 따로 PR로 내려면 쌓인 PR이 필요하다. 처음에는 막는다(6.6).
5. **토큰 예산.** 넘으면 멈출지, 사람에게 물을지, 알리기만 할지.
6. **기존 유형의 거취.** 옮겨 가는 동안 같이 둔다. 자율 Work가 평가에서 앞서면 기본을 자율로 바꾸고, 고정 유형을 없앨지 "직접 정한 절차"로 남길지 정한다. 커스텀 유형을 쓰는 팀의 요구가 있으면 그때 본다.
7. **Codex 엔진.** 메인 세션과 자식 Work를 Codex로 돌릴 때 서브에이전트와 훅 차이(engines.md). 처음에는 Claude Code만 한다.
8. **바깥 호출자.** relay MCP의 `start_work`에 자율 Work를 고를 수 있게 하는 것은 바깥에서 들어오는 길이라 이 제안과 맞는다. 자식 Work는 바깥 호출자에게 조회로만 보인다.

- **의도 승인 뒤로 끼어들 자리가 없는 것이 약점으로 드러났다.** 07에서 자율의 의도 정리가 짝수 개 중앙값의 틀린 동작을 알아채고도 묻지 않고 비목표에 넣어 숨긴 시험에 실패했다. 전용 유형은 사람이 뒤에 짚어 고쳤고 맨 CLI는 스스로 고쳤다. 의도 정리가 요청 옆의 틀린 동작을 묻게 고쳤다(D550).
- **자식 Work는 쓰이지 않았다.** 07에서 사람 역할이 버그마다 Work를 따로 만들어 나눌 일이 남지 않았다. 자식 Work의 효과는 한 요청 안에 나란히 할 조각이 있는 시나리오(여러 모듈의 같은 수정, 독립된 두 기능을 한 Work로)에서 따로 재야 한다.
- **결과 확신은 유지됐다.** 설문 결과 확신은 세 쪽 모두 6이었고, 사람 역할은 자율의 판정표와 완료조건별 근거를 좋은 점으로 꼽았다.

### 15.2 자식 Work 시나리오 (2026-11-02)

보고서: `app/eval/reports/2026-11-02-auto-07-recheck.md`, `2026-11-02-auto-39.md`, `2026-11-02-auto-40.md`, `2026-11-02-auto-40-recheck.md`. 자식 Work가 나올 만한 시나리오 둘을 더했다: 39(서로 다른 모듈의 작은 기능 셋을 한 요청으로), 40(규칙이 여럿인 독립 기능 셋, 모듈마다 브랜치를 따로).

- **D550 뒤 07은 2/2 통과했다.** 의도 정리가 짝수 개 중앙값을 물었다. 대신 사람 차례가 늘었다(13, 16).
- **조각이 작으면 자율은 자식 Work를 쓰지 않는다.** 39와 40의 첫 평가에서 자율 진행은 매번 자식 Work를 검토하고 "조각이 10~40줄이라 새 맥락과 병합 비용이 더 크다"며 직접 했다. 판단 기준(나누는 비용이 분명히 작을 때만)대로다. 39에서 자율은 전용 유형보다 빠르고(3.4분 대 5.4분) 차례(6.5 대 9.5)와 토큰이 적었다.
- **의도 정리가 Work를 쪼개는 길이 있었다.** 40에서 의도 정리가 "Work 하나는 브랜치 하나"라며 Work 셋으로 나누자고 해 사람의 수고가 크게 늘었다(24차례). 의도 정리는 쪼개지 않고, 부분마다 브랜치·PR을 원하면 자율 진행이 자식 Work로 나누게 고쳤다(D551).
- **D551 뒤 40에서 자식 Work가 돌았다.** 두 번 모두 모듈마다 자식 Work 셋을 나란히 돌려 merge로 합쳤고 2/2 통과했다. 사람 차례는 19에서 10.5로 줄었지만 에이전트 입력 토큰은 1638천에서 4679천으로 늘었다(세션 5개, 자식마다 독립 리뷰). 맨 CLI(1.6분, 차례 3, 283천)와의 차이는 여전히 크다.

### 15.3 지시만 받는 자식 세션 (2026-11-02, D552~D554)

보고서: `app/eval/reports/2026-11-02-auto-40-brief.md`. 40을 relay@auto로 두 번 돌렸고 둘 다 통과했다.

- **자식을 쓸지는 부모가 갈랐다.** #1은 자식 세션 셋을 지시 글과 함께 만들어 merge했고, #2는 "조각이 작아 비용만 는다"며 직접 브랜치 셋을 만들었다.
- **세션 간 메시지는 쓰이지 않았다.** 부모도 자식도 SendMessage를 부르지 않았다. 지시가 분명하고 조각이 독립이라 대화할 일이 없었다.
- **자식은 가벼워졌지만 부모의 기다림이 비쌌다.** 자식 셋은 286~498천 토큰(마무리 절차가 빠짐)이었지만 부모가 3130천을 썼다. 기본 기다림을 120초로 줄인 탓에 `wait_children`를 24번 부르며 깰 때마다 맥락을 다시 읽었다.

다음에 볼 것: `wait_children`의 기다림(길게 기다리거나, 자식이 끝날 때 깨우는 길), 대화가 필요한 시나리오(조각 사이에 맞출 인터페이스가 있는 일).

### 15.4 끝 신호도 직접 (2026-11-02, D555)

보고서: `app/eval/reports/2026-11-02-auto-40-direct.md`. 40을 relay@auto로 두 번 돌렸고 둘 다 통과했다(5.6·5.8분, 차례 13). 두 번 모두 부모가 조각이 작다며 자식 세션을 쓰지 않고 브랜치 셋을 직접 만들었다. 토큰은 1176천·1076천으로 자식 셋을 쓴 평가의 4분의 1 안팎이다. 자식의 끝 신호와 세션 간 메시지는 쓰이지 않아 실제로 되는지 아직 보지 못했다: 자식을 써야 할 만큼 큰 조각이나 조각 사이에 맞출 것이 있는 시나리오가 필요하다.

### 15.5 조각이 큰 시나리오 41 (2026-11-02)

보고서: `app/eval/reports/2026-11-02-auto-41.md`. 모듈마다 100줄 안팎(정답 패치 약 250줄)의 독립 기능 셋을 한 요청으로 맡겼다. 자율 쪽은 두 번 모두 자식 세션을 쓰지 않았다("모듈이 각각 100줄 안팎이라 새 맥락을 읽고 합치는 비용이 더 크다"). 결과는 relay·자율 모두 2/2, 맨 CLI 1/2였다. 자율은 전용 유형보다 조금 빠르고 토큰이 적었다(6.2분, 1208천 대 6.8분, 1699천). 숨긴 Markdown 시험이 요청에서 정하지 않은 모양까지 봐 처음에는 모두 실패로 잡혔고, 시험을 고쳐 다시 판정했다.

지금까지(39, 40, 41) 자율 진행은 부분마다 브랜치를 요구하지 않는 한 자식 세션을 고르지 않았다. 판단 기준("나누는 비용이 분명히 작을 때만")과 모델의 비용 감각으로는 수백 줄 규모까지도 한 세션이 낫다고 본다. 자식 세션이 값을 하는 일은 더 크거나(여러 시간), 오래 기다리는 일(긴 시험, 빌드)이 섞인 일일 것으로 보이며 아직 재지 않았다. 자식의 끝 신호와 세션 간 메시지도 실제 claude에서 아직 쓰인 적이 없다.

### 15.6 시험이 오래 걸리는 시나리오 42 (2026-11-02)

보고서: `app/eval/reports/2026-11-02-auto-42.md`. 41에 시험 파일마다 약 50초 걸리는 픽스처를 더했다. 자율 진행은 두 번 모두 자식 세션을 쓰지 않았다: 시험 파일이 이미 나란히 돌아 기다림이 겹친다고 봤다(시나리오를 만들 때 놓친 점). 자율 9.4분, 전용 유형 18.4분, 맨 CLI 7.0분. 자율 한 번은 사람만 아는 반올림 규칙을 묻지 않아 실패했다.

정리하면 지금의 판단 기준("나누는 비용이 분명히 작을 때만")은 토큰을 아끼는 쪽으로 읽히고, 모델은 관계없음이나 기다림보다 다시 읽는 비용을 크게 본다. 자식 세션을 더 쓰게 하려면 기준이 무엇을 아낄지(벽시계 시간 대 토큰)를 정해야 한다.

남은 것: 자식의 독립 리뷰를 부모의 PR 단위 리뷰로 모으기(토큰), 큰 일에서 자율 진행이 스스로 나누는지(부분마다 브랜치 요구 없이), 회차를 늘린 비교.

### 15.7 나누기를 요청한 시나리오 43 (2026-11-02)

보고서: `app/eval/reports/2026-11-02-auto-43.md`. 42에 "모듈마다 따로 나눠서 동시에 진행, 결과는 브랜치 하나로"를 더했다. 기준은 15.6의 결론대로 토큰을 아끼는 쪽(지금 그대로)으로 두고, 사람이 나누기를 요청하면 자식 세션을 쓰는지와 대화 경로를 실제 claude로 봤다.

- #1: 자식 셋을 만들고 턴을 끝냈다. 자식은 끝나자 부모에게 SendMessage를 한 번씩 보냈고, 부모는 그 메시지로 깨어나 merge로 정하고 합쳤다. D553·D555의 경로가 실제 claude에서 처음 동작했다. 자식 셋이 약 3.5분에 끝났다. 일하는 중의 대화는 없었다.
- #1의 경합: 자식은 메시지를 보낸 뒤에 턴을 끝내므로, 바로 부른 `decide_child`가 "아직 일하는 중"으로 두 번 거절당했다. 부모는 다른 자식을 처리하다 다시 불러 넘어갔지만, 마지막 자식에서 거절되면 부모를 깨울 메시지가 더 오지 않는다.
- #2: 나누기 요청이 의도의 `제약`에 들어갔는데도 자율 진행은 "모듈이 작고 시험은 이미 나란히 돈다"며 직접 했고, 사람 제안 판정에는 "받아들임"이라고 적었다. 나누는 비용 기준이 사람의 요청보다 앞섰다.
- 결과: 둘 다 숨긴 시험 통과. 토큰은 #1 약 333만(세션 5), #2 약 126만(세션 2). 시간은 #1 13.1분(사람이 리뷰에서 round 규칙을 짚어 고친 시간 포함), #2 7.4분.

고칠 것: `decide_child`가 자식의 턴이 끝나기를 잠시 기다리기, 의도가 나누기를 요구하면 비용 기준보다 그것을 따르기(받지 않으려면 사람에게 묻기).

다음에 볼 것: D550 뒤 07의 재평가, 자식 Work가 나올 만한 시나리오(예: 11-amount-sweep을 한 Work로, 07을 한 Work로 맡기기), 회차를 늘린 01·15·17.

## 16. 들이지 않은 대안

| 대안 | 들이지 않은 까닭 |
|---|---|
| 기존 유형 스킬을 플레이북으로 골라 씀 | 유형마다 파이프라인 시절의 전제("fix는 한 세션에서 재현부터", "design은 코드를 바꾸지 않음")가 들어 있어, 고정 단계가 이름만 바꿔 남는다(사용자와 정함) |
| 자식을 바깥용 relay MCP의 Work로 만듦 | 의도 승인, 질문 중계, 전달 같은 바깥 호출자용 절차가 붙어 있어 내부 조각에 무겁다. 앱 안 세션은 조회만 받는다(D520)(사용자와 정함) |
| 서브에이전트만 씀 | 사람이 들어가 대화할 수 없고, 자기 브랜치·PR 단위가 되지 못한다 |
| Claude Code agent teams | 실험 기능이고 기본으로 꺼져 있다. 팀원별 worktree 격리가 없고, relay가 관문을 붙이거나 화면에 보이기 어렵다 |
| 메인 세션이 Bash로 `claude --bg`를 띄움 | relay 밖의 세션이 되어 관문과 화면을 붙일 수 없다. 세션 안에서 `claude`를 띄울 때의 중첩 실행 검사에 걸리는지도 확인하지 않았다 |
| 판단 기준을 프롬프트에만 두고 상한도 프롬프트로 | 프롬프트의 상한은 지켜지지 않는다(10절) |
