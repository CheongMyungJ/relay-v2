# 대규모 프로젝트 기능 실험 규약

- 상태: 끝남(결과는 `report.md`). 결과를 보기 전에 고정했다(2026-10-13). 바꿀 때는 `log.md`에 언제, 무엇을, 왜를 적고, 결과를 본 뒤에는 결정 규칙(4절)을 바꾸지 않는다.
- 위임: 사용자가 기능의 선택, 설계(✅ 결정을 바꾸는 것 포함), 개발, 평가, 남길지 버릴지를 맡겼다. 바꾼 ✅ 결정은 `docs/design.md`에 "(실험 위임)"으로 표시해 사용자가 나중에 한꺼번에 검토한다.
- 예산: 사용자 계정의 주간 사용량 80%까지(시작 42%). 여기서는 사용량 %를 볼 수 없어, 평가 호출의 비용(`total_cost_usd`)을 누적해 `log.md`에 적고, 시범 실행 뒤 사용자에게 %를 물어 비율을 맞춘다. 75%에 닿으면 평가를 멈추고 그때까지의 결과로 정한다.

## 1. 무엇을 보나

relay가 대규모 신규 프로젝트에 도움이 되려면 무엇이 빠졌는지 평가한 대화에서 제안한 기능 가운데 아래 둘을 만들고 잰다.

| # | 기능 | 기대 |
|---|---|---|
| F1 | **구현 나눔으로 Work 만들기.** 설계 문서의 `## 구현 나눔` 표를 앱이 읽어 새 Work 대화상자에서 조각을 고르면 유형과 요청을 채운다. 먼저 끝나야 할 조각이 머지되지 않았으면 고를 수 없게 하고, 조각 Work의 `context.md`에 묶음 안의 위치(조각 상태, 앞 조각의 요약과 완료조건)를 넣는다 | 여러 Work로 나눠 구현할 때 사람이 맥락을 다시 적는 수고가 줄고, 뒤 조각이 앞 조각의 동작과 설계 결정을 덜 깬다 |
| F3 | **지식 정리.** 앱이 모델 없이 지식 항목의 정리 후보(같은 `anchor`의 항목 여럿, 레포에서 사라진 `anchor`)를 찾아 보이고, 누르면 후보 목록을 요청으로 채운 일반 Work를 만든다 | 쌓인 지식의 중복과 낡은 항목이 사람이 일일이 찾지 않아도 정리된다 |

만들지 않는 것과 까닭(평가 전에 정함):

- **판정 근거의 기계 확인(2a).** verify 판정표에는 이미 근거 칸이 있고(`docs/design.md` 5.6.6), 평가에서 본 틀린 확신(14-double-notify relay#1)은 근거를 적고도 원인 하나를 놓친 것이다. 근거가 비었는지 보는 확인으로는 막지 못한다.
- **앞 조각 확인 방법 쌓기(2b)의 명령 실행.** 대부분 레포의 테스트 명령이 앞 조각이 더한 테스트를 이미 돈다. F1의 `context.md`에 앞 조각의 완료조건을 넣는 것까지만 한다.
- **설계 대조 조각(2c), 프로젝트 관문(2d), 다시 나누기(F1 3단계), PR 본문의 지식 절(3a).** AI 사람 역할로는 효과를 잴 수 없거나(팀 리뷰어, 성능 관문), 앞 기능이 남을 때만 뜻이 있다. 이번에는 만들지 않고 남은 안으로 적는다.

## 2. 견주는 쪽

- `relay`: 이 실험의 빌드.
- `base`: 실험 전 커밋(`2bbdb6d`)의 빌드(`eval/ref-app.sh`). 같은 시나리오, 같은 사람 역할 규칙. 다른 것은 도구 설명서(`guides/`)뿐이다.
- 에이전트, 사람 역할, 판정은 평가 도구의 기본(sonnet, effort medium)이다.

## 3. 시나리오

| 기능 | 개발용 (내가 만들고 본다) | hold-out (다른 에이전트가 만들고 봉인) |
|---|---|---|
| F1 | 설계 문서가 머지된 레포에서 조각 3개(의존 있음)를 Work 3개로 차례로 구현. Work 사이에 앞 Work의 브랜치를 main에 머지한다(PR 머지와 같음, 같은 사람). 숨긴 시험은 조각마다 인수 조건과, 뒤 조각이 앞 조각의 동작·설계 결정을 깨지 않는지(guard) | 같은 모양, 다른 도메인 |
| F3 | `docs/knowledge/`에 항목 10개 안팎: 같은 anchor의 중복 쌍, 사라진 코드를 가리키는 항목, 서로 어긋나는 쌍(어느 쪽이 맞는지는 사람만 앎), 손대면 안 되는 멀쩡한 항목. 사람의 요청은 "지식이 많아져 정리하고 싶다" 정도. 숨긴 시험은 파일을 읽어 판정 | 같은 모양, 다른 도메인 |

hold-out은 개발이 끝나고 결과를 고정하기 전까지 열지 않는다. 열쇠는 레포 밖(`/tmp/claude-0/holdout-key`)에 두고 마지막 비교 때만 쓴다.

## 4. 지표와 결정 규칙

회차는 시나리오 × 쪽마다 3번(개발용), 3번(hold-out)이다. 결론은 개발용과 hold-out을 합쳐 내고, 둘의 방향이 다르면 hold-out을 따른다.

**F1**
- 주지표 A: 숨긴 시험 통과(모든 Work의 인수 조건과 guard, Work 단위로 셈).
- 주지표 B: 사람 부담. 사람 입력 글자 수와 사람 행동 수(Work 단위 평균).
- 남김: A가 base보다 낮지 않고, (A가 base보다 높거나 B의 입력 글자가 20% 넘게 줄고), 걸린 시간이 20% 넘게 늘지 않을 때. 아니면 버림.

**F3**
- 주지표 A: 심어 둔 문제의 해결률(중복이 하나로 합쳐짐, 낡은 항목이 고쳐지거나 지워짐, 어긋난 쌍이 사람의 답대로 정리됨).
- 주지표 B: 멀쩡한 항목 보존률(내용이 바뀌거나 지워지지 않음).
- 남김: A가 base보다 15%포인트 넘게 높고 B가 base보다 낮지 않을 때. 아니면 버림.

버림은 기능 코드를 이 브랜치에서 되돌리고, 설계 결정을 "실험 후 버림"으로 남기고, 숫자를 `report.md`에 남기는 것이다.

## 5. 알려진 한계

- 사람 역할과 판정이 AI다. 회차가 적어 작은 차이는 흔들린다.
- 대규모의 축소판이다. 조각 3개, 지식 10개로 수십 개의 Work와 몇 달의 지식을 대신한다.
- 만든 사람과 평가하는 사람이 같다. 결정 규칙을 먼저 고정하고 hold-out을 봉인해 줄이지만 없애지는 못한다.
