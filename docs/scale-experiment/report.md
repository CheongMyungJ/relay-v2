# 대규모 프로젝트 기능 실험 보고서

> main에는 F3만 옮겼다(실험의 D397, D398을 main의 D393, D394로 다시 매김. 후속 실험은 `docs/tidy-experiment/`). F1(실험의 D393~D396)은 옮기지 않았다. 아래의 D 번호는 실험 브랜치의 것이다.

- 규약: `protocol.md`(2026-10-13 결과를 보기 전에 고정). 진행 기록: `log.md`.
- 평가 보고서: `app/eval/reports/2026-10-13-scale-dev-35-36.md`(개발용), `app/eval/reports/2026-10-13-scale-holdout.md`(hold-out).
- 견준 쪽: `relay`(이 실험의 빌드) 대 `pre`(실험 전 커밋 `2bbdb6d`). 에이전트, 사람 역할, 판정은 모두 sonnet(effort medium).

## 결론

| 기능 | 결정 | 근거 (규약 4절의 규칙) |
|---|---|---|
| F3 지식 정리 후보 (D397, D398) | **남김** | 심은 문제 해결률이 개발용 +33%포인트, hold-out +13%포인트로 방향이 같고, 합치면 87.5% 대 66.7%(+20.8%포인트, 기준 15). 멀쩡한 항목 보존은 두 쪽 모두 100% |
| F1 구현 나눔으로 Work 만들기 (D393~D396) | **남김 (근거 약함)** | 숨긴 시험은 relay 6/6회, pre 5/6회로 낮지 않고 높다. 걸린 시간은 합쳐 +14.6%(기준 20% 안). 입력 글자는 개발용 −42%, hold-out +8%로 방향이 달라 hold-out을 따라 줄지 않음. **pre의 한 회 실패는 F1과 관계없는 사람 역할의 포기라, 그 회를 빼면 규칙상 버림이다(민감도, 아래)** |

"방향이 다르면 hold-out을 따른다"(규약 4절)는 지표마다 차이의 부호로 읽었다. 남김·버림이 다를 때로 읽으면 "합쳐 낸다"가 쓰일 때가 없기 때문이다. 이 해석은 결과를 본 뒤에 정했으므로 여기 밝힌다.

## F3 지식 정리

| | 개발용 36 (문제 3개 × 3회) | hold-out (문제 5개 × 3회) | 합침 |
|---|---|---|---|
| 심은 문제 해결 relay | 9/9 | 12/15 | 21/24 (87.5%) |
| 심은 문제 해결 pre | 6/9 | 10/15 | 16/24 (66.7%) |
| 멀쩡한 항목 보존 | 3/3 대 3/3 | 3/3 대 3/3 | 같음 |
| 사람 입력 글자 | 0 대 198 | 112 대 162 | |
| 걸린 시간(분) | 4.4 대 4.4 | 5.0 대 4.6 | |

- pre가 놓친 것은 거의 모두 F3가 기계적으로 찾는 종류였다: 같은 anchor의 두 항목을 합치지 않음, 코드에서 이름이 바뀌거나 사라진 anchor를 그대로 둠. 에이전트가 지식 파일을 모두 읽어도 코드와 대조하는 일을 가끔 빠뜨리고, F3가 그 대조를 대신한다.
- hold-out relay의 놓친 셋 가운데: relay-3은 사람 역할이 후보 버튼을 쓰지 않고 요청을 직접 써서 F3가 쓰이지 않았다(3/5). relay-2의 "낡은 항목(rebalanceCouriers)"은 에이전트가 anchor를 지금 코드의 이름으로 고쳤으나 "15분 주기는 없앴다"는 문장을 남겨 숨긴 시험이 실패로 셌다. 규약대로 결과를 본 뒤 시험을 고치지 않았다.
- 어긋난 규칙(anchor가 달라 F3가 찾지 못하는 것)은 두 쪽 모두 6/6회 사람에게 묻고 정리했다. F3의 이점은 기계적으로 찾을 수 있는 것에 한정된다.

## F1 구현 나눔

| | 개발용 35 (Work 셋 × 3회) | hold-out (Work 셋 × 3회) |
|---|---|---|
| 숨긴 시험 모두 통과(회) | 3/3 대 3/3 | 3/3 대 2/3 |
| Work 단위 통과 | 9/9 대 9/9 | 9/9 대 6/9 |
| 사람 입력 글자 | 216 대 370 (−42%) | 711 대 659 (+8%) |
| 걸린 시간(분) | 14.7 대 14.2 (+3.5%) | 19.9 대 16.0 (+24%) |
| 사람 차례 | 31.0 대 27.3 | 38.7 대 31.3 |
| 사람 역할 비용($) | 4.5 대 3.7 | 7.3 대 5.2 |

- pre의 hold-out 1회 실패: Work 1에서 사람 역할이 사람만 아는 휴관일 규칙을 알려 주면서 "설계 문서를 먼저 고친다"를 골랐고, 에이전트가 이 Work에서 문서를 고치지 않고 멈추자 포기했다(`give_up`). 그 규칙은 조각 표의 목표에 없어 F1이 채운 요청과 관계없다. 같은 일은 relay에서도 생길 수 있다.
- **민감도:** 그 회를 빼면 숨긴 시험은 같고(5/5 대 5/5), 입력 글자는 합쳐 −10%, 걸린 시간은 +14.6%라 규칙상 버림이다. F1의 남김은 이 한 회에 걸려 있다.
- 뒤 조각이 앞 조각을 깨지 않는지(regression·guard)는 두 쪽 모두 사람이 끝까지 간 회차에서 전부 지켰다. 레포의 테스트 명령이 앞 조각의 테스트를 돌리고, 설계 문서 경로가 요청에 있으면(두 쪽 모두 그랬다) 에이전트가 문서를 읽는다. `context.md`의 묶음 절이 더한 차이는 이 규모에서 보이지 않았다.
- relay가 더 오래 걸린 까닭은 다 가리지 못했다. 사람 차례가 Work마다 1~3번 더 많았다.

## 비용

- 실행 28회(시범 4, 개발용 12, hold-out 12). 사람 역할 비용 약 $93(시범 약 $13.5, 개발용 약 $33, hold-out 약 $47). 에이전트는 sonnet으로 Work 하나에 입력 약 100만 토큰(캐시 포함).
- 사용자 계정 주간 사용량: 시작 42%, 개발과 시범 뒤 43%. 끝난 뒤의 값은 사용자가 확인한다.

## 한계

- 사람 역할과 판정이 AI이고, 시나리오마다 쪽마다 3회다. F3의 hold-out 차이(+13%포인트)와 F1의 남김은 한두 회에 흔들린다.
- 대규모의 축소판이다. 조각 셋, 지식 10여 개로 수십 개의 Work와 몇 달의 지식을 대신했다. 지식이 수백 개면 F3의 이점은 커질 것으로 보이지만 재지 않았다.
- 만든 쪽과 평가한 쪽이 같다. 규약을 먼저 고정하고 hold-out을 다른 에이전트가 만들어 봉인했지만, 결정 규칙의 "방향" 해석은 결과를 본 뒤에 정했다.
- F1 시나리오의 `pre` 쪽 사람도 요청에 설계 문서 경로를 적었다(시나리오의 보고 글). 경로를 모르는 사람과의 차이는 재지 않았다.

## 남은 안

- F1: 조각 Work가 더 오래 걸린 까닭(사람 차례가 늘어난 곳) 가리기. 정확도 이점이 보이지 않았으므로, 구현 나눔 표를 읽어 요청을 채우는 1단계만 두고 `context.md`의 묶음 절은 빼는 쪽을 다음에 견줘 볼 만하다.
- F3: 사이드바 알림(대화상자를 열어야만 보이는 지금은 relay-3처럼 쓰이지 않을 수 있다), 지식 파일이 많은 레포에서의 재평가.
- 이번에 만들지 않은 것: 판정 근거 확인(2a), 설계 대조 조각(2c), 프로젝트 관문(2d), 다시 나누기(F1 3단계), PR 본문의 지식 절(3a).
