# 서브모듈이 있는 레포에서 일하기

relay는 서브모듈을 지원하지 않습니다. 대신 서브모듈이 있는 레포에서도 일이 막히지 않고, 작업을 잃지 않게 합니다. 이 문서는 그런 레포에서 relay로 일하는 방법을 설명합니다.

## relay가 하는 일과 하지 않는 일

| | relay |
|---|---|
| 프로젝트 등록 | `.gitmodules`가 있으면 점검 표에 경고를 보입니다. 등록은 막지 않습니다 |
| Work의 worktree | 서브모듈을 받지 않습니다. 서브모듈 폴더는 비어 있습니다 |
| 에이전트에게 주는 안내 | 단계마다 서브모듈을 받는 법(`git submodule update --init --recursive`)과 지킬 것을 알려 줍니다. 빌드나 테스트에 필요하면 에이전트가 받습니다 |
| 서브모듈 안의 변경 | 커밋하지도, 전달하지도, 되감지도 않습니다. 에이전트에게도 서브모듈 안의 파일은 고치지 말라고 알립니다 |
| 서브모듈이 가리키는 커밋을 바꾼 것 | 이 레포의 보통 변경으로 다룹니다. 에이전트가 커밋했거나 [커밋하고 진행]을 고르면 전달됩니다 |
| 화면의 변경(diff) | 서브모듈은 `Subproject commit …` 한 줄로만 보입니다 |
| 서브모듈 push와 PR | 하지 않습니다 |
| [Work 정리] | 서브모듈을 받아 둔 worktree면 "서브모듈 안의 작업도 함께 지웁니다"를 확인받고 지웁니다 |

## 서브모듈을 고치지 않는 일 (대부분)

평소처럼 Work를 만들면 됩니다. 빌드나 테스트에 서브모듈이 필요하면 에이전트가 받습니다.

- **받지 못하면:** 비공개 서브모듈의 자격 증명 문제 등으로 받지 못하면, 에이전트는 우회하지 말고 알리라는 안내를 받습니다. 알려 오면 터미널에서 직접 받은 뒤 이어서 하라고 말합니다.
- **승인 화면에 `Subproject commit` 줄이 보이면:** 서브모듈을 고치지 않는 일인데 이 줄이 있으면 의도한 변경인지 확인합니다. 기준 브랜치를 병합한 뒤 서브모듈을 맞추지 않고 커밋하면, 남이 올린 서브모듈 버전을 되돌리는 변경이 이렇게 보입니다. 에이전트도 병합 뒤 서브모듈을 맞추라는 안내를 받습니다.

## 서브모듈도 고쳐야 할 때: 서브모듈을 따로 먼저

서브모듈 레포를 **별도 프로젝트로 등록해 먼저 고치고**, 메인 레포의 Work는 서브모듈이 가리키는 커밋만 바꿉니다. 이렇게 하면 서브모듈 변경도 relay의 리뷰, 승인, 전달, PR 대응을 그대로 받습니다.

1. **서브모듈 레포를 프로젝트로 등록합니다.**
   - 서브모듈 레포를 메인 레포와 다른 폴더에 따로 clone합니다.
   - relay에서 [프로젝트 추가]로 그 폴더를 등록합니다.
2. **서브모듈 Work를 끝까지 합니다.**
   - 서브모듈 프로젝트에서 Work를 만들어 고치고 [PR 생성]까지 합니다.
   - 이때 서브모듈의 커밋이 원격의 `relay/<work-id>` 브랜치에 올라갑니다.
3. **메인 Work를 만듭니다.** 요청에 서브모듈을 어디로 맞출지 적습니다. 예:

   ```text
   lib 서브모듈을 서브모듈 레포의 relay/w-20261007-001 브랜치 커밋 <커밋 id>로 맞추고 커밋한다.
   그 위에서 <메인 레포에서 할 일>.
   ```

   에이전트가 서브모듈을 받아 그 커밋을 체크아웃하고, 메인 레포에 "가리키는 커밋 변경"을 커밋합니다. [PR 생성]에 함께 들어갑니다. 서브모듈 커밋이 이미 원격에 있으니 메인 PR의 CI도 서브모듈을 받을 수 있습니다.
4. **서브모듈 PR을 먼저 머지합니다.** 서브모듈 Work의 PR 진행 화면에서 [머지]합니다.
   - **merge commit으로 머지했으면:** 메인 PR이 가리키는 커밋이 서브모듈의 기준 브랜치에 그대로 들어가니 할 일이 없습니다.
   - **squash나 rebase로 머지했으면:** 커밋 id가 바뀝니다. 메인 PR이 머지되지 않은 브랜치의 커밋을 가리키게 되니 다시 맞춥니다. 메인 Work의 PR 진행 화면에서 지시를 적고 [대응 시작]을 누릅니다. 예: "lib 서브모듈을 서브모듈 기준 브랜치의 `<머지된 커밋 id>`로 맞춘다". 대응을 승인하면 앱이 push합니다.
5. **메인 PR을 머지합니다.** CI가 통과하면 메인 Work에서 [머지]합니다.
6. **두 Work를 정리합니다.**
   - 서브모듈 Work의 정리에서 origin의 브랜치를 지우는 것은 메인 PR이 머지된 커밋을 가리키게 된 뒤에 합니다. 그 전에 지우면 메인 PR이 가리키는 커밋을 받을 수 없게 될 수 있습니다.
   - 메인 Work의 정리에서 "서브모듈 안의 작업도 함께 지웁니다"가 나오면, 그 안에 남길 작업이 없는지 확인하고 체크합니다.

## 한 Work에서 둘 다 고치면

권하지 않습니다. relay는 서브모듈 안을 다루지 않아 사람이 할 일이 많고, 놓치기 쉽습니다.

- 서브모듈 안의 변경은 승인 화면에 보이지 않습니다. 터미널에서 `git -C <worktree>/<서브모듈> log`나 `diff`로 직접 봅니다.
- 서브모듈의 커밋은 사람이 직접 push하고 서브모듈 레포에 PR을 만듭니다. 에이전트는 push할 수 없습니다. 메인의 [PR 생성]보다 먼저 해야 합니다.
- 서브모듈 안에서 커밋하지 않은 변경은 전달되지 않고, [Work 정리] 때 지워집니다.

꼭 그래야 한다면, 위 절의 머지 순서(서브모듈 먼저, squash나 rebase였으면 다시 맞추기)를 똑같이 따릅니다.
