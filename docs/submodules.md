# 서브모듈이 있는 레포에서 일하기

서브모듈이 있는 레포는 **메인 레포를 프로젝트로 등록**하고, Work마다 **고칠 레포**를 고릅니다. 메인 레포만 고칠 수도, 서브모듈 하나나 여럿만 고칠 수도, 메인과 서브모듈을 함께 고칠 수도 있습니다. 고른 레포마다 기준 브랜치를 따로 정하고, 끝나면 레포마다 push나 PR로 보냅니다. 메인 레포가 가리키는 서브모듈 커밋은 앱이 맞춥니다.

## 새 Work에서 고칠 레포 고르기

새 Work 대화상자의 **고칠 레포** 표에는 메인 레포와, 메인 기준 브랜치의 커밋에 있는 서브모듈이 줄마다 보입니다.

| 칸 | 뜻 |
|---|---|
| [고침] | 이 Work에서 고칠 레포. 하나 이상 고릅니다 |
| 기준 브랜치 | 그 레포의 브랜치. 서브모듈의 기본값은 서브모듈 원격의 기본 브랜치입니다(메인이 가리키는 커밋이 아님) |
| 고급: 기준 위치, 머지 대상 | 레포마다 로컬/원격과 PR을 보낼 브랜치를 고릅니다 |

- 서브모듈을 고르면 메인 체크아웃에 받아 두지 않았을 때 앱이 받습니다(`git submodule update --init -- <경로>`).
- 메인 기준 브랜치를 바꾸면 표를 다시 읽습니다. 그 커밋에 없는 서브모듈은 고를 수 없습니다.
- 서브모듈 안의 서브모듈은 표에 없습니다(한 단계만).
- 메인 레포의 [고침]을 끄면 메인은 기준 커밋에 고정되고 전달하지 않습니다. 서브모듈만 고치되 메인 레포와 함께 빌드하고 테스트할 때 씁니다.

## 작업 공간

```
<Work의 worktree 폴더>/     ← 메인 레포 worktree (메인을 고르면 작업 브랜치, 아니면 기준 커밋에 고정)
  <고른 서브모듈 경로>/       ← 그 서브모듈 레포의 worktree (같은 이름의 작업 브랜치)
  <고르지 않은 서브모듈>/     ← 필요하면 에이전트가 받음. 고치지 않음
```

- 작업 브랜치 이름은 고른 레포 모두 같습니다.
- 에이전트는 메인 worktree 폴더에서 시작하고, 고른 레포마다 따로 커밋합니다. 고친 서브모듈이 곧바로 메인 빌드에 들어갑니다.
- 에이전트는 고르지 않은 레포를 고치지 않습니다. 고쳐야 한다고 보면 알려 옵니다. 그때 액션 바의 **[레포 추가]**로 그 서브모듈을 더하고, 터미널에서 이어서 하라고 말합니다(다음 단계부터는 안내에 들어갑니다). 레포를 빼는 조작은 없습니다. 커밋하지 않은 레포는 전달할 것이 없습니다.
- 에이전트는 메인에 고른 서브모듈의 "가리키는 커밋 변경"을 커밋하지 않습니다. 전달할 때 앱이 맞춥니다.

## 승인 화면

- **[변경] 탭:** 레포 탭으로 레포마다 기준 커밋부터의 diff와 커밋을 봅니다.
- **커밋 안 된 변경:** 레포마다 셉니다. 메인에서 고른 서브모듈의 자리는 세지 않습니다.
- **강조 영역:** 고르지 않은 레포의 변경(고정된 메인, 받아 둔 서브모듈 안)은 "전달 안 됨"으로, 고른 서브모듈이 작업 브랜치에서 벗어났으면 그것을 알립니다.

## 전달 (Work 완료)

마지막 단계가 Work를 마무리할 때 커밋이 있는 레포마다 PR 초안을 씁니다. 메인은 `pr.md`, 서브모듈은 `pr/<서브모듈 경로>.md`입니다. Work 완료 화면에서 레포마다 고릅니다.

| 선택 | 뜻 |
|---|---|
| [PR 생성] | 그 레포에 push하고 PR을 만듭니다 |
| [push] | push만 합니다 |
| [보내지 않음] | 보내지 않습니다 |

- 커밋이 있는 레포만 고를 것이 있습니다. origin, gh 로그인 같은 점검도 레포마다 해서 안 되는 선택은 이유와 함께 꺼집니다.
- **메인이 새 커밋을 가리키게 함(기본 켬):** 메인과 서브모듈을 함께 보내면 서브모듈마다 묻습니다. 켜면 앱이 메인 작업 브랜치에 `relay(<work-id>): <경로> 서브모듈을 <짧은 id>로` 커밋을 더합니다.
- **순서:** 서브모듈마다 push(와 PR) → 메인의 서브모듈 커밋 맞추기 → 메인 push → 메인 PR. 하나가 실패하면 그 뒤는 하지 않고, [다시 시도]는 끝난 레포를 건너뜁니다.
- 메인 PR 본문 끝에는 앱이 "함께 머지할 PR"(서브모듈 PR 링크와 먼저 머지할 것)을 붙입니다.

## PR 진행

[PR 생성]한 레포마다 PR 카드가 하나입니다. 패널 맨 위의 카드 탭으로 고릅니다.

- 읽기, 항목, CI, [대응 시작], 자동 대응, [머지], [머지 없이 끝내기]가 카드마다 따로입니다.
- 서브모듈 카드의 대응 task는 그 서브모듈 폴더만 고치고 그 레포의 PR에 push합니다. 한 Work에서 대응 task는 한 번에 하나라 다른 카드의 대응은 앞 라운드가 끝날 때까지 기다립니다.
- **머지 순서:** 메인 카드의 [머지]는 메인이 새 커밋을 가리키는 서브모듈의 PR이 머지되기 전에는 꺼져 있습니다. 서브모듈 PR을 먼저 머지합니다.
- **[서브모듈 커밋 맞추기]:** 서브모듈 PR을 squash나 rebase로 머지하면 커밋 id가 바뀌어, 메인이 가리키는 커밋이 서브모듈의 머지 대상 브랜치에 없습니다. 메인 카드에 이 버튼이 보이고 [머지]가 꺼집니다. 누르면 앱이 메인 작업 브랜치에 머지된 커밋을 가리키는 커밋을 더하고 push합니다.
- 모든 카드가 머지되거나 끝나야 Work가 완료되고, 그때 [Work 정리] 창이 뜹니다.
- 서브모듈 PR의 받을 봇과 기본 머지 방식은 메인 프로젝트 설정의 **서브모듈별 설정**에서 정합니다. 비우면 메인의 값을 씁니다.

## 정리

[Work 정리]는 고른 서브모듈의 worktree를 레포마다 확인(커밋 안 된 변경, push 안 한 커밋)한 뒤 지우고, 메인 worktree를 마지막에 지웁니다. 작업 브랜치와 원격 브랜치 지우기는 레포마다 고릅니다. 메인 PR이 아직 서브모듈 브랜치에만 있는 커밋을 가리키면 그 원격 브랜치 지우기를 경고합니다. 메인 체크아웃과 그 서브모듈 폴더는 건드리지 않습니다.

## 고르지 않은 서브모듈

| | relay |
|---|---|
| 프로젝트 등록 | `.gitmodules`가 있으면 점검 표의 "서브모듈" 줄에 서브모듈 경로와 다루는 법을 알립니다. 등록은 막지 않습니다 |
| worktree | 받지 않습니다. 서브모듈 폴더는 비어 있습니다. 빌드나 테스트에 필요하면 에이전트가 받습니다(`git submodule update --init --recursive`) |
| 서브모듈 안의 변경 | 커밋하지도, 전달하지도 않습니다. 커밋 안 된 변경이 있으면 승인 화면에 "서브모듈 안의 변경"으로 알립니다 |
| 서브모듈이 가리키는 커밋을 바꾼 것 | 메인 레포의 보통 변경으로 다룹니다. 에이전트가 커밋했거나 [커밋하고 진행]을 고르면 전달됩니다 |
| [Work 정리] | 서브모듈을 받아 둔 worktree면 "체크아웃된 서브모듈 안의 커밋 안 된 변경과 push 안 한 커밋도 함께 지웁니다"를 확인받고 지웁니다 |

- **받지 못하면:** 비공개 서브모듈의 자격 증명 문제 등으로 받지 못하면 에이전트는 우회하지 말고 알리라는 안내를 받습니다. 알려 오면 터미널에서 직접 받은 뒤 이어서 하라고 말합니다.
- **승인 화면에 `Subproject commit` 줄이 보이면:** 서브모듈을 고치지 않는 일인데 이 줄이 있으면 의도한 변경인지 확인합니다. 기준 브랜치를 병합한 뒤 서브모듈을 맞추지 않고 커밋하면 남이 올린 서브모듈 버전을 되돌리는 변경이 이렇게 보입니다.

## 메인 체크아웃을 지키는 장치

고른 서브모듈이 있는 worktree에서 `git submodule update`를 하면 git이 서브모듈 저장소의 설정을 바꿔 **메인 체크아웃의 서브모듈 폴더에서 git이 동작하지 않게 되고**(`fatal: cannot chdir`), 서브모듈 worktree를 작업 브랜치에서 떼어 냅니다. relay는 이렇게 막습니다.

- 에이전트 세션(task, 곁 세션, 정리 세션)에서는 git이 고른 서브모듈을 건너뜁니다(환경 변수로 `submodule.<이름>.update=none`). 레포 설정은 바꾸지 않습니다. 고르지 않은 서브모듈은 그대로 받습니다.
- `--checkout`처럼 직접 고른 옵션은 막지 못합니다. 그래서 앱이 턴이 끝날 때마다(그리고 정리, 앱을 켤 때) 서브모듈 저장소의 설정을 확인해 바뀌었으면 되돌리고 알립니다.

사람이나 IDE가 앱 밖에서 `git submodule update`를 하면 이 보호를 받지 않습니다. 직접 할 때는 고른 서브모듈을 빼고 합니다(`git submodule update --init -- <다른 서브모듈>`).

## 예전 서브모듈 프로젝트

이전 버전에서 서브모듈을 대상으로 고르면 서브모듈 프로젝트가 따로 생겼습니다. 이미 있는 서브모듈 프로젝트와 그 Work는 끝까지(전달, PR 진행, 정리) 쓸 수 있지만, 새 Work는 만들지 않습니다. 서브모듈을 고치려면 메인 프로젝트의 [새 Work]에서 고릅니다. 서브모듈 프로젝트의 받을 봇과 머지 방식은 메인 프로젝트 설정의 서브모듈별 설정으로 옮겨 적습니다. Work가 모두 보관되면 사이드바에서 서브모듈 프로젝트를 우클릭해 [등록 해제]합니다. 메인 프로젝트는 서브모듈 프로젝트를 모두 해제한 뒤에 해제할 수 있습니다.
