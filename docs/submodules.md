# 서브모듈이 있는 레포에서 일하기

서브모듈이 있는 레포에서는 Work마다 **대상**을 고릅니다. 메인 레포를 고치는 Work와 서브모듈 하나를 고치는 Work(서브모듈 Work)가 따로 있고, 어느 Work든 레포 하나만 고치고 전달합니다. 이 문서는 두 Work로 일하는 방법과 둘을 맞추는 순서를 설명합니다.

## 메인 레포의 Work

| | relay |
|---|---|
| 프로젝트 등록 | `.gitmodules`가 있으면 점검 표에 경고를 보입니다. 등록은 막지 않습니다 |
| Work의 worktree | 서브모듈을 받지 않습니다. 서브모듈 폴더는 비어 있습니다 |
| 에이전트에게 주는 안내 | 단계마다 서브모듈을 받는 법(`git submodule update --init --recursive`)과 지킬 것을 알려 줍니다. 빌드나 테스트에 필요하면 에이전트가 받습니다 |
| 서브모듈 안의 변경 | 커밋하지도, 전달하지도, 되감지도 않습니다. 에이전트에게도 서브모듈 안의 파일은 고치지 말라고 알립니다. 서브모듈 안에 커밋 안 된 변경이 있으면 승인 화면(Work 완료 화면 포함)에 "서브모듈 안의 변경"으로 알립니다 |
| 서브모듈이 가리키는 커밋을 바꾼 것 | 이 레포의 보통 변경으로 다룹니다. 에이전트가 커밋했거나 [커밋하고 진행]을 고르면 전달됩니다. [변경 버리고 진행]을 고르면 원래 커밋으로 되돌립니다 |
| 화면의 변경(diff) | 서브모듈은 `Subproject commit …` 한 줄로만 보입니다 |
| 서브모듈 push와 PR | 하지 않습니다. 서브모듈은 서브모듈 Work가 고칩니다 |
| [Work 정리] | 서브모듈을 받아 둔 worktree면 "서브모듈 안의 작업도 함께 지웁니다"를 확인받고 지웁니다 |

- **받지 못하면:** 비공개 서브모듈의 자격 증명 문제 등으로 받지 못하면, 에이전트는 우회하지 말고 알리라는 안내를 받습니다. 알려 오면 터미널에서 직접 받은 뒤 이어서 하라고 말합니다.
- **승인 화면에 `Subproject commit` 줄이 보이면:** 서브모듈을 고치지 않는 일인데 이 줄이 있으면 의도한 변경인지 확인합니다. 기준 브랜치를 병합한 뒤 서브모듈을 맞추지 않고 커밋하면, 남이 올린 서브모듈 버전을 되돌리는 변경이 이렇게 보입니다. 에이전트도 병합 뒤 서브모듈을 맞추라는 안내를 받습니다.

## 서브모듈 Work

메인 프로젝트의 [새 Work]에서 **대상**으로 서브모듈을 고릅니다.

- **처음 고를 때:** 앱이 서브모듈 프로젝트를 만듭니다. 메인 체크아웃에 그 서브모듈을 받지 않았으면 이때 받습니다(`git submodule update --init -- <경로>`). 서브모듈 프로젝트는 사이드바에서 메인 프로젝트 안에 보이고, 그 줄의 [새 Work]로 바로 만들 수도 있습니다. 프로젝트 설정(받을 봇, 머지 방식)도 따로 가집니다.
- **기준 브랜치:** 서브모듈 레포의 브랜치입니다. 기본값은 서브모듈 원격의 기본 브랜치입니다(메인 레포가 가리키는 커밋이 아님). PR이 그 브랜치로 갑니다.
- **고치고 전달하는 레포:** 서브모듈 레포뿐입니다. 작업 브랜치 `relay/<work-id>`, push, [PR 생성], PR 대응, 머지, [Work 정리]가 모두 서브모듈 레포 기준입니다. 메인 레포는 커밋하지도 전달하지도 않습니다.

### 메인 레포에서 통합 검증 (기본 켬)

서브모듈만으로는 빌드나 통합 테스트를 할 수 없는 레포가 많아, 서브모듈 Work는 메인 레포의 worktree를 함께 만듭니다. 새 Work 대화상자에서 끌 수 있습니다.

```
<Work의 worktree 폴더>/   ← 메인 레포 worktree (메인 기준 브랜치의 커밋에 고정, 전달 안 함)
  다른 서브모듈/            ← 필요하면 에이전트가 받음
  <서브모듈 경로>/          ← 서브모듈 Work의 worktree (relay/<work-id>, 전달 대상)
```

- 에이전트는 서브모듈 폴더에서 고치고, 메인 레포 폴더에서 빌드하고 테스트합니다. 고친 것이 동기화 없이 곧바로 메인 빌드에 들어갑니다. 메인 PR에서 서브모듈을 맞춘 뒤의 조합을 미리 검증하는 셈입니다.
- 메인 기준 브랜치와 기준 위치(로컬/원격)는 새 Work 대화상자에서 따로 고릅니다(기본은 메인 프로젝트의 기본 브랜치, 로컬). Work를 만들 때의 커밋에 고정합니다. 그 커밋에 이 서브모듈이 없으면(서브모듈을 더하기 전의 브랜치 등) Work를 만들지 않습니다.
- **메인 쪽 변경:** 에이전트는 메인 레포를 고치지 않으라는 안내를 받습니다. 검증하다 메인 쪽이 바뀌면 승인 화면에 "메인 레포 변경 (전달 안 됨)"으로 알립니다. 이 변경은 [Work 정리] 때 지웁니다. 메인 레포도 고쳐야 하는 일이면 아래 "메인 레포도 맞춰야 할 때"를 따릅니다.
- **끄면:** 서브모듈 레포만의 worktree에서 일합니다. 에이전트는 메인 레포와 함께여야만 확인할 수 있는 것을 통과로 보지 않고 알립니다.

### 메인 체크아웃을 지키는 장치

통합 검증 worktree에서 `git submodule update`를 하면, git이 서브모듈 저장소의 설정을 바꿔 **메인 체크아웃의 서브모듈 폴더에서 git이 동작하지 않게 되고**(`fatal: cannot chdir`), 서브모듈 Work의 worktree를 작업 브랜치에서 떼어 냅니다. relay는 이렇게 막습니다.

- 에이전트 세션(task, 곁 세션, 정리 세션)에서는 git이 이 서브모듈을 건너뜁니다(환경 변수로 `submodule.<이름>.update=none`). 레포 설정은 바꾸지 않습니다. 다른 서브모듈은 그대로 받습니다.
- `--checkout`처럼 직접 고른 옵션은 막지 못합니다. 그래서 앱이 턴이 끝날 때마다(그리고 정리, 앱을 켤 때) 서브모듈 저장소의 설정을 확인해 바뀌었으면 되돌리고 알립니다.
- 서브모듈 Work의 worktree가 작업 브랜치에서 벗어나면 승인 화면에 "서브모듈 worktree"로 알립니다. 전달은 작업 브랜치만 보내므로, 터미널에서 `git switch relay/<work-id>`로 돌아가거나 에이전트에게 맡깁니다.

사람이나 IDE가 앱 밖에서 통합 검증 worktree의 `git submodule update`를 하면 이 보호를 받지 않습니다. 직접 할 때는 이 서브모듈을 빼고 합니다(`git submodule update --init -- <다른 서브모듈>`). 깨졌으면 다음 턴이 끝날 때나 앱을 다시 켤 때 되돌립니다.

### 정리

[Work 정리]는 서브모듈 Work의 worktree를 지금과 같은 확인(커밋 안 된 변경 등)을 거쳐 먼저 지우고, 그다음 메인 레포 worktree를 지웁니다. 메인 쪽 변경이 있으면 정리 요약에 보이고 확인받습니다. 메인 체크아웃과 그 서브모듈 폴더는 건드리지 않습니다.

### 등록 해제

서브모듈 프로젝트는 사이드바의 그 줄을 우클릭해 [등록 해제]합니다(Work가 모두 보관됐을 때). 메인 프로젝트는 서브모듈 프로젝트를 모두 해제한 뒤에 해제할 수 있습니다.

## 메인 레포도 맞춰야 할 때

서브모듈을 고친 뒤 메인 레포가 새 서브모듈 커밋을 가리키게 하려면, 서브모듈 Work와 메인 Work를 차례로 합니다.

1. **서브모듈 Work를 끝까지 합니다.** [PR 생성]까지 하면 서브모듈 커밋이 서브모듈 원격의 `relay/<work-id>` 브랜치에 올라갑니다.
2. **서브모듈 PR을 먼저 머지합니다.** 서브모듈 Work의 PR 진행 화면에서 [머지]합니다.
3. **메인 Work를 만듭니다.** 메인 프로젝트에서 대상을 메인 레포로 두고, 요청에 서브모듈을 어디로 맞출지 적습니다. 예:

   ```text
   lib 서브모듈을 서브모듈 기준 브랜치의 <머지된 커밋 id>로 맞추고 커밋한다.
   그 위에서 <메인 레포에서 할 일>.
   ```

   에이전트가 서브모듈을 받아 그 커밋을 체크아웃하고, 메인 레포에 "가리키는 커밋 변경"을 커밋합니다. [PR 생성]에 함께 들어갑니다.
   - 머지하기 전에 메인 PR을 함께 올려야 하면 `relay/<work-id>` 브랜치의 커밋을 가리키게 할 수도 있습니다. 그때 서브모듈 PR을 squash나 rebase로 머지하면 커밋 id가 바뀌므로, 메인 Work의 PR 진행 화면에서 "lib 서브모듈을 `<머지된 커밋 id>`로 맞춘다"는 지시로 [대응 시작]을 눌러 다시 맞춥니다.
4. **메인 PR을 머지합니다.** CI가 통과하면 메인 Work에서 [머지]합니다.
5. **두 Work를 정리합니다.** 서브모듈 Work의 정리에서 origin의 브랜치를 지우는 것은 메인 PR이 머지된 커밋을 가리키게 된 뒤에 합니다. 그 전에 지우면 메인 PR이 가리키는 커밋을 받을 수 없게 될 수 있습니다.

## 한 Work에서 둘 다 고치면

권하지 않습니다. 메인 레포의 Work는 서브모듈 안을 다루지 않아 사람이 할 일이 많고, 놓치기 쉽습니다.

- 서브모듈 안의 변경 내용은 승인 화면에 보이지 않습니다. 커밋 안 된 변경이 있다는 알림만 뜹니다. 터미널에서 `git -C <worktree>/<서브모듈> log`나 `diff`로 직접 봅니다.
- 서브모듈의 커밋은 사람이 직접 push하고 서브모듈 레포에 PR을 만듭니다. 에이전트는 push할 수 없습니다. 메인의 [PR 생성]보다 먼저 해야 합니다.
- 서브모듈 안에서 커밋하지 않은 변경은 전달되지 않고, [Work 정리] 때 지워집니다.

서브모듈 Work와 메인 Work로 나누는 위의 순서를 쓰세요.
