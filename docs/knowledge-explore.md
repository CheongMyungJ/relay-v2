# 지식 관리 탐색: 실제로 돌려 본 시나리오와 개선점

- 날짜: 2026-10-02. 앱 커밋 aa39d16(M17 지식 관리, D283~D326) 위에서 했다.
- 목적: 지식 관리의 여섯 단계(모으기, 거르기, 저장·공유, 넣기, 낡음·피드백, 지식 화면)를 실제로 돌려 보완하거나 바꾸거나 더할 점을 뽑는다.
- 완료조건(사람이 고름): 단계마다 실제 시나리오를 둘 이상 돌린다. 개선점마다 재현 근거, 우선순위, 해결안을 둔다. 상위 3~5개는 작업 브랜치에서 프로토타입으로 고치고 고치기 전과 뒤를 비교한다.
- 이미 고친 것은 출발점으로 삼지 않았다: 같은 결정의 후보 묶기(D324), 다른 task의 비슷한 후보(D326), 사람이 알려 준 규칙은 domain(D325).
- 표기: 우선순위 **상**은 지식이 틀리거나 서로 모순인 채로 쌓이거나 쓰여야 할 때 쓰이지 않는 것, **중**은 사람의 수고나 잡음을 늘리는 것, **하**는 다듬기다. **[실제]**는 실제 claude 실행, **[흐름]**은 앱 조립과 가짜 claude, **[화면]**은 Electron 앱을 띄워 찍은 것, **[탐침]**은 core 함수를 직접 부른 것이다.

## 3. 단계별 발견

### 3.1 모으기

- **잘 된 것:** 요청에 적힌 회계팀 규칙(billing 1)과 사람이 질문에 답한 규칙(notify 1, shop 3)은 모두 도메인 규칙 후보가 됐다. 같은 규칙을 verify가 다시 올린 것은 D326으로 "비슷한 후보"가 되어 채택 안 함이 기본이었다.
- **뻔한 레시피(K2):** 고치기 전 Work 8개 가운데 7개가 "테스트는 `npm test`(node --test)로 돌린다" 같은 레시피를 기본 채택으로 남겼다. `not_in_code`에 "package.json 스크립트로만 알 수 있음"이라고 적어 코드에 있다는 것을 스스로 적기도 했다. 기본 선택으로 끝낸 뒤 공유 대기 21건 가운데 10건이 시험 실행법 레시피였다.
- **사람 결정과 묶이지 않음(K8):** billing 1의 intake는 요청의 규칙을 `by: human` 결정으로 적고, 같은 규칙의 후보에는 `decision`을 적지 않았다. 완료 화면에 같은 규칙이 "AI 후보"와 "다듬지 않은 사람 결정"으로 두 번 보인다.
- **일회성 결정(K8):** verify의 리뷰 반영 질문(D229)의 답("리뷰 지적 2건을 반영하지 않는다")이 8개 Work 가운데 6개에서 다듬지 않은 사람 결정으로 지식 칸에 떴다. 다음 Work에 쓸 지식이 아니다.
- **환경 레시피(K12):** notify의 fix는 "Node 22에서는 `node --test test/`가 MODULE_NOT_FOUND로 실패한다"를 팀 레시피로 올렸다(이 컨테이너의 Node 버전 문제).

### 3.2 거르기

- **보고된 항목이 남음(K1):** notify 1에서 세 단계의 에이전트가 틀린 항목 3건을 정확히 짚었다("5회다", "test:integration이다", "src/lib/backoff.js로 옮겨졌다"). 보고 칸의 기본은 "그대로 둠"이라 [완료만] 뒤에도 셋 다 남았고, notify 2에서 같은 셋을 다시 짚었다(보고 7건).
- **모순 공존(K1):** [화면]에서 새 후보 "빈 배열의 평균은 0이다"가 틀렸다고 보고된 공유 대기 "빈 배열의 평균은 예외를 던진다"와 겹치는데, 기본은 "새로 더함"이었다. 같은 화면의 "공유 대기에서 함께 실림"은 그 틀린 항목을 "함께 싣기"로 두었다. [흐름]에서 기본 선택으로 [PR 생성]을 하면 지식 커밋에 두 규칙이 함께 실렸다.
- **다시 올린 같은 규칙(K7):** notify 2는 시험 실행법 레시피를 다시 올렸고, 겹치는 기존 항목 2건이 옆에 보였지만 기본은 "새로 더함"이었다. [탐침]으로도 겹치는 항목이 있는 후보의 기본 선택은 새 항목을 하나 더 쓴다.
- **분량(K8):** [화면]의 [지식 15] 탭은 높이 1,755px이고, 오른쪽 패널 폭 608px에서 끝까지 스크롤해야 한다. 그 가운데 새로 쓸 지식은 4건이다.

### 3.3 저장·공유

- **머지 안 된 Work의 지식(K6):** notify 1이 [완료만]으로 끝나 4xx 수정은 Work 브랜치에만 있다. notify 2는 main에서 시작했는데 Work 1의 지식("429를 제외한 4xx는 재시도하지 않는다", "재시도 여부는 `isRetryable`이 정한다")이 표시 없이 들어갔고, intake가 "현재 withRetry는 상태 코드와 관계없이 모든 오류를 재시도한다"며 틀렸다고 보고했다. billing 3도 Work 1의 규칙을 "현재 invoiceTotal은 합계에 한 번 곱해 반올림해 규칙과 다름"이라고 보고했다. 사람이 이 보고를 따라 [버림]을 고르면 맞는 지식을 잃는다.
- **동시에 도는 Work(K7):** [흐름]에서 두 Work가 같은 규칙을 올리고 차례로 [완료만]하면 공유 대기에 같은 규칙이 둘이 되고, 세 번째 Work intake에 두 줄이 들어갔다. D326은 한 Work 안의 task끼리만 묶는다.

### 3.4 넣기

- **다른 말(K3):** billing 2의 요청은 "Refund API의 tax", "프로모션 가격"이라고 썼고, Work 1의 규칙 용어는 `부가세`, `품목 줄`, `할인`, `버림`이었다. intake `참고 지식`은 "없음"이었고 intake가 "기대하는 tax 계산 규칙은 무엇인가요?"를 물었다. 선택지 3번이 팀 규칙(줄 단위 버림)이었지만 추천은 1번 "할인 후 공급가액 기준 합계 반올림"이었다. 추천을 고른 결과가 도메인 규칙 후보로 채택되어 공유 대기에 서로 반대인 두 규칙이 남았고, billing 3의 설계 단계에 둘 다 들어갔다.
- **잘못 걸림(K4):** [탐침] 11개 예 가운데 6개가 잘못 걸리고 4개는 놓쳤다. "로그"→"로그인", "시간"→"시간대", "id"→"valid", "api"→"rapid", "세금"→"세금계산서 PDF 글꼴". 놓친 것은 "부가세"↔"tax", "반품"↔"환불", "빈 배열"↔"0건", "반올림"↔"올림·버림"이다.
- **글에서 경로 뽑기:** "Node.js", "e.g"를 경로로 뽑는다. 해는 작지만(같은 경로의 항목이 없으면 걸리지 않음) 요청에 함수 이름만 있으면("invoiceTotal 함수가") 경로를 못 얻는다.
- **분량(K11):** 한 줄 예 171자 가운데 약 100자가 Windows 앱 저장소의 절대 경로다.

### 3.5 낡음·피드백

- **잘 된 것:** notify의 에이전트는 "(재확인 필요)" 항목과 표시 없는 공유 대기 항목 모두에서 지금 코드와 다른 점을 찾아 보고했다.
- **지워진 경로(K5):** 경로가 없어진 항목은 [그대로 맞음]으로 해시를 다시 적어도 그 경로의 해시가 없어 계속 재확인 필요다. 완료 화면의 보고 칸과 재확인 칸에서는 경로를 고칠 수 없다([대체]는 규칙만 받는다). [흐름]에서 지식 화면의 [그대로 맞음] → 공유 대기 사본 머지 뒤에도 재확인 필요였다.
- **파일 단위 해시(K10):** notify의 외부 호환 제약(`src/webhook.js`)은 main이 import 한 줄만 바꿔 재확인 필요가 됐다. notify 2는 그 파일을 바꾸지 않아 완료 화면에 재확인 칸이 없었고, 두 Work의 모든 단계에 "(재확인 필요)"로 들어갔다.

### 3.6 지식 화면

- **기준이 다름(K9):** 팀 지식을 커밋만 하고 push하지 않은 레포에서 지식 화면은 "팀 (0) · origin/main"이었다. 같은 때 로컬 기준으로 시작한 Work의 `참고 지식`에는 팀 지식이 들어갔다. push한 뒤에는 "팀 (12)"였다.
- **없는 조작(K9):** 버튼은 [고침], [버림], [나만으로]/[팀으로], [그대로 맞음]뿐이고 입력 칸이 0개다. 사람이 아는 규칙을 직접 더할 수 없고, 검색이나 "재확인 필요만 보기"가 없고, 에이전트가 그 항목을 틀렸다고 보고한 이력이 보이지 않는다.

## 4. 프로토타입과 고치기 전·뒤

이 브랜치에서 넷을 고쳤다. 설계 문서(D 번호)는 고치지 않았다. 채택하면 결정 번호를 매기고 `docs/design.md` 5.7과 시험을 정식으로 옮긴다.

### K1 보고된 항목의 거르기 기본 (`app/src/core/knowledge.ts` reviewKnowledge)

- 이 Work에서 틀렸다는 보고를 받은 항목과 같은 종류·갈래, 같은 파일, 겹치는 용어(D326의 "비슷함")인 후보는 `supersedes`를 적지 않았어도 그 항목의 대체가 기본이다. 보고는 후보 밑에 붙는다.
- 틀렸다는 보고를 받은 공유 대기는 "공유 대기에서 함께 실림"에서 빠진다. 보고 칸에서 [그대로 맞음]을 고르면 실린다.

| 확인 | 고치기 전 | 고친 뒤 |
|---|---|---|
| [흐름] 기본 선택의 [PR 생성] 지식 커밋 | 2건: "…예외를 던진다"(보고됨), "…0이다" | 1건: "…0이다". 보고된 공유 대기는 대체되어 지워짐 |
| [화면] 새 후보의 기본 | 새로 더함 | 대체: 공유 대기 domain-…(틀렸다는 보고가 후보 밑에 보임) |
| [화면] 함께 실림 | 보고된 항목 포함 2건 | 1건 |
| [화면] 탭 | [지식 15] | [지식 13] |
| [단위] 새 시험 2개 | 실패 | 통과 |

### K2 후보 스킬 문구 (`skills/_common.md` Knowledge)

- 보고한 항목의 지금 규칙을 알면 `supersedes` 후보로도 적는다(한 번에 대체되게).
- `terms`에 다른 요청이 쓸 말(동의어, 영어, 코드 이름)을 넣는다. 예는 시나리오와 겹치지 않게 `로그인`, `login`, `인증`으로 했다.
- `package.json` 스크립트, Makefile, README에 있는 것은 레시피가 아니다.
- "task마다 3개쯤"을 "3개까지, 없으면 없음"으로.

### K3 intake의 도메인 규칙 (`app/src/core/knowledge.ts` selectKnowledge)

- intake는 경로·용어가 겹치지 않은 도메인 규칙도 맨 뒤에 넣는다. 분량(1,500자) 안에서 겹친 것이 먼저이고, 넘치면 겹치지 않은 것부터 빠진다. 다른 단계는 그대로다.

### K5 지워진 경로의 낡음 (`app/src/core/knowledge.ts` isStale)

- 해시가 적히지 않은 경로는 "적을 때 없던 경로"로 보아, 지금도 없으면 바뀐 것이 없다. 다시 생기면 재확인 필요다. 지워진 경로를 [그대로 맞음]으로 확인하면 더는 재확인 필요가 아니다.

| 확인 | 고치기 전 | 고친 뒤 |
|---|---|---|
| [흐름] 지식 화면 [그대로 맞음] → 머지 | 재확인 필요 | 재확인 아님 |
| [탐침] 확인 뒤 같은 상태 / 파일이 다시 생김 | 재확인 / 재확인 | 아님 / 재확인 |
| [단위] 새 시험 1개 | 실패 | 통과 |

### [실제] 고치기 전·뒤

같은 시나리오와 사람 역할로 고치기 전과 뒤에 한 번씩 돌렸다(K1, K2, K3, K5가 함께 들어간 상태). 거르기는 모두 기본 선택이다.

| 시나리오 · Work | 무엇 | 고치기 전 | 고친 뒤 |
|---|---|---|---|
| billing 2 (다른 말) | intake `참고 지식` | 없음 | 도메인 규칙 1건 (K3) |
| billing 2 | intake 질문과 사람 결정(추천을 고름) | "기대하는 tax 규칙은?", 결정: 합계 반올림(팀 규칙과 반대) | "참고 지식은 줄마다 버림인데 현재 코드는 다르다"는 확인, 결정: 줄별 버림 후 합산(팀 규칙과 같음) |
| billing 2 → 3 | 공유 대기의 모순 규칙 | 2건이 함께 남고 Work 3 설계에 둘 다 들어감 | 1건 |
| notify 1 | 틀린 공유 대기 "재시도 최대 3회" | 보고만, 남음 | "최대 5회" `supersedes` 후보가 기본 대체 (K2·K1) |
| notify 2 | 같은 틀린 항목을 다시 보고 | 3건 다시 보고(보고 7건) | 공유 대기 건은 고쳐져 다시 안 나옴, 팀 2건은 또 보고(보고 5건) |
| Work 8개 합 | 기본 채택 후보 | 20 | 6 |
| Work 8개 합 | 그 가운데 시험 실행법 레시피 | 10 | 1 |
| Work 8개 합 | 완료 화면 지식 칸의 줄(후보·함께 실림·재확인·보고) | 64 | 33 |
| 마지막 Work 뒤 | 공유 대기 (세 시나리오 합) | 21 | 6 |

- **부작용(K2):** 후보가 너무 줄 수 있다. shop 1·2는 후보가 0건이 됐다(고치기 전에는 뻔한 레시피 1건과 설계 결정 1건, 예: "가격 필터는 `!= null`로 검사해 0원을 값으로 다룬다"). notify 1의 사람 결정 "4xx는 재시도하지 않고 429만 재시도"는 도메인 후보로 오르지 않고 다듬지 않은 사람 결정(채택 안 함이 기본)으로만 남았다. "없으면 없음" 문구를 두되, 사람 결정에서 온 오래 갈 규칙은 꼭 후보로 적으라는 문장을 함께 두는 것을 권한다.
- **남은 것(K2):** 팀 지식의 틀린 레시피와 실패 부류는 두 Work 모두 보고만 되고 고친 후보가 없었다. 스킬 문구만으로는 부분 효과다. 보고에 고친 규칙 칸(`suggested_rule`)을 두거나, 완료 화면의 보고 칸에서 보고 문장을 [대체]의 새 규칙 초안으로 미리 채우는 것을 검토한다.
- **K6가 그대로:** billing 2·3, notify에서 머지 안 된 Work 1의 지식을 "지금 코드와 다르다"고 보고하는 일은 고친 뒤에도 났다(billing 2 보고 2건, billing 3 보고 1건).
- 회차가 한 번씩이라 숫자는 경향이다. 후보 수가 준 것에는 K2의 "없으면 없음"과 회차 변동이 함께 들어 있다.

## 5. 고치지 않은 것의 해결안

| # | 해결안 | 크기 |
|---|---|---|
| K6 | 공유 대기·나만 항목을 넣을 때 묶인 경로의 해시를 지금 HEAD와 견줘, 다르면 "(이 Work의 코드와 다름: 출처 Work w-…가 아직 기준에 없을 수 있음)"을 붙인다. D316(공유 대기는 판정하지 않음)을 바꾼다. 에이전트 스킬에는 이 표시가 붙은 항목은 틀렸다고 보고하지 말고 "출처 Work의 코드 기준"으로 읽으라고 적는다. 출처 Work가 [완료만]이면 완료 화면에 "이 지식은 머지되지 않은 코드에 기댐"을 보이는 것도 함께 검토 | M |
| K7 | D326의 "비슷한 후보"를 기존 항목(공유 대기, 나만, 머지된 팀)까지 넓힌다: 비슷한 기존 항목이 있으면 채택 안 함이 기본이고 "기존 항목과 같음"으로 보인다. 동시에 도는 Work는 쓰기 전(storePlan 잠금 안)에 공유 대기와 다시 견줘 같은 것은 쓰지 않는다 | S~M |
| K8 | verify의 리뷰 반영 결정(D229)은 지식 칸에 올리지 않는다(결정에 출처를 적거나 verify의 반영 질문 결정을 표시). 같은 task의 사람 결정과 비슷한 후보는 `decision`이 없어도 묶는다. 채택 안 함이 기본인 줄은 접어 "채택 안 함 n건"으로 둔다 | S~M |
| K9 | 지식 화면의 팀 지식에 "origin/main 기준 n건, 로컬 main 기준 m건"을 함께 보이거나 Work의 기준 위치 설정을 따른다. 검색 칸과 "재확인 필요만/보고 받은 것만" 거르기, [규칙 더하기](종류·규칙·용어·경로를 받아 공유 대기나 나만에 씀), 항목마다 "최근 보고" 줄을 더한다 | M |
| K4 | 영문·숫자 용어는 낱말 경계로 맞추고, 2자 이하 용어는 경계가 있을 때만 맞춘다. 한글 용어는 뒤에 붙는 조사(은·는·이·가·을·를·의·에·로…)까지만 허용할지 [탐침]의 예로 정한다(부가세율 같은 합성어를 놓칠 수 있음) | S |
| K10 | 지식 화면에 "재확인 필요 n건"을 모아 [모두 그대로 맞음]을 둔다. 완료 화면의 재확인 칸을 "이 Work가 경로를 바꿈"뿐 아니라 "이 Work에 넣었고 재확인 필요"까지 넓힌다 | S |
| K11 | `참고 지식` 줄의 파일 경로를 지식 폴더 상대 경로(레포)나 `<앱 저장소>/pending/…`처럼 줄이고 절 머리에 두 폴더의 절대 경로를 한 번만 적는다 | S |
| K12 | 스킬에 "이 기계에서만 맞는 것(버전, OS)은 나만"을 적고, 거르기에서 OS·버전 말이 든 레시피는 나만이 기본인지 검토 | S |

## 6. 다시 돌리는 법

```bash
cd app
# [실제] 시나리오 (한 번에 Work 2~3개, 시나리오마다 5~8분)
RELAY_EXPLORE=billing npx vitest run --project claude test/claude/explore-knowledge.test.ts
# [흐름], [탐침]
RELAY_EXPLORE_FLOW=1 npx vitest run --project flow test/flow/explore-flow.test.ts
RELAY_EXPLORE_PROBE=1 npx vitest run --project unit test/unit/explore-probe.test.ts
# [화면]: 준비 뒤 빌드한 앱을 띄운다 (DISPLAY 필요)
RELAY_EXPLORE_GUI=1 npx vitest run --project flow test/flow/explore-gui-prep.test.ts
npm run build && npx playwright test test/smoke/explore-knowledge.spec.ts
```

결과는 `app/test-results/explore/`에 남는다(git에 들어가지 않음). [실제]는 `log.json`(task마다 `참고 지식`, 후보, 보고, 완료 화면의 지식 칸과 기본 선택, 앱 저장소)과 Work 폴더 사본이다.
