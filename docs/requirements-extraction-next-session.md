먼저 CLAUDE.md, CONTRIBUTING.md, docs/requirements-extraction-flow.md를 읽고, 문서가 인용한 현재 코드와 비교해 전제가 바뀌었는지 확인해줘. 로컬에 없으면 해당 브랜치를 가져와서 읽어줘. 작업 중인 다른 변경은 보존해줘.

목표는 복잡한 레거시 펌웨어에서 AI가 보드·빌드·기능을 스스로 발견하고, 근거가 연결된 기능·비기능 요구사항 후보와 제약을 추출하는 새 requirements type을 설계하는 것이다. 사람이 첫 보드나 기능을 지정해야 하는 흐름은 원하지 않는다. 긴 대화나 컴팩션 요약에 의존하지 않고, 영속 분석 기록과 작은 작업별 새 세션으로 진행해야 한다.

흐름은 intake → extract → verify이며, extract 안에서 앱이 작은 분석 run을 돌리고 결과를 앱 소유 revision에 반영한다. 2차 논의에서 완료의 의미와 run 실행·재개(15절), extract 스킬 지침의 구성(16절)을 정했고, 3차 논의에서 평가(17.1: run 단위 하네스, survey와 trace 네 렌즈, 최소 지시 기준선, 손으로 쓴 합성 픽스처, 혼합 채점, 개발 2와 hold-out 1, 상대 규칙과 관문, 하네스의 주간 사용량 50% 하한), 예산과 범위(17.2: run 수 검문만 두고 비용·사용량 상한은 두지 않음, 부드러운 마감, 상한 도달 때의 선택지, 벤더는 경계, 5시간 창은 기다렸다 잇기, 잠정 기본값, 앱 설정과 work.json 상태), 기록 계약(17.3: work.json 포인터와 불변 변경분, 엄격 비교, 근거 개체와 blob, 종류별 기본 스키마의 run마다 조립, run 전체 반려, 기록 보호, worktree 변경은 전체 멈춤, 실패·미완료는 완료만 끊음, run 도중 사람 답의 보관, scratch는 requirements/ 밖)을 정했다(15.5절의 결정 1~42). 이미 정한 것은 다시 묻지 말고, 기존 relay 기능·제안·결정을 구분해줘.

extract 스킬 지침이 이 Work의 핵심이다. 지침의 구조는 정했고, 고정 계약 문구와 렌즈별 점검표 항목은 평가를 만든 뒤 쓴다(결정 16). 평가의 뼈대는 정했고, 다음 구현 단계는 구현 전 녹화(16.11, 17.2, 17.3의 녹화 목록)와 평가(픽스처·정답 파일·하네스·채점기)다. 하네스와 채점기는 결과 스키마 v0이 있어야 돈다.

우선 현재 이해와 남은 쟁점을 짧게 정리하고, 15.6절·16.12절·17절의 남은 문제 가운데 extract task의 상태와 화면(run 화면, 알림, 사람 결정 필요를 묻는 화면, 14절 8번), 재개·되감기·기준 소스 변경(14절 6번. 결정 33의 고아 파일 규칙 포함), 서브모듈 안의 근거(17.3, D382), intake와 verify의 requirements 구간 순서로 논의하자. 코드로 확인할 수 있는 것은 먼저 조사하고, 결정이 필요한 질문만 추천안과 이유를 붙여 소수씩 물어봐줘.

이번에는 설계 논의를 이어가고, 구현은 내가 요청하면 시작해줘. 논의에서 결정한 내용·이유와 미확정 사항은 문서 15.5절의 결정 기록과 해당 절에 바로 갱신해줘. D/I 번호는 구현을 시작할 때 구현 PR에서 붙인다(결정 8).
