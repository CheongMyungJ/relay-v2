# verify의 코드 리뷰 방법

- 상태: 구현함 (D484~D489)
- 작성일: 2026-10-24 (Work w-20261024-001)
- 범위: 코드를 바꾸는 유형(버그 수정, 기능 추가·변경, 리팩터링, 일반, 커스텀)의 verify 리뷰. 설계 유형 verify의 문서 리뷰(D362)는 이 방법을 쓰지 않는다.

verify(`skills/verify/SKILL.md`, [design.md](design.md) 5.6.6)의 코드 리뷰 지침을 Claude Code 내장 `code-review` 스킬의 high 수준 본문을 참고해 보완했다. 이 문서는 그 본문이 어떻게 짜여 있는지, 그중 무엇을 들이고 무엇을 들이지 않았는지와 그 까닭, 리뷰를 서브에이전트에게 맡기는 판단을 적는다. 결정은 design.md 2절의 D484~D489에 있다.

## 1. 참고 대상

- Claude Code 2.1.310의 내장 `code-review`(`/code-review`, 별칭 `/review`)를 effort high로 불렀을 때의 본문. 공개 문서가 없어 `claude.exe`(Bun 단일 실행 파일)에 든 문자열을 읽었다. 본문은 `var W="## Phase 0`로 시작하는 곳 부근에 있다(2.1.310에서 바이트 약 263,315,000).
- 본문은 effort마다, 그리고 모델 계열마다 다르다. 모델 표(`de`)에 계열 넷이 있다: 기본(`default`), `claude-sonnet-5`, `claude-opus-4-8`, `claude-opus-5`. 표에 없는 모델은 기본을 받는다. high 칸은 다음과 같다.

| 모델 계열 | high 칸 | 모양 |
|---|---|---|
| 기본, Opus 4.8 | `o48-high-v1` | 여덟 각도를 한 컨텍스트에서 차례로, 확인 없음, 10개 이하 |
| Sonnet 5 | `high` | 각도마다 찾기 서브에이전트, 후보마다 확인 서브에이전트, 10개 이하 |
| Opus 5 | `o5-bmin` | 짧은 본문의 한 번 훑기, 15개 이하 |

- 이 레포의 기본 모델 Opus 5.5(`claude-opus-5-5`)는 표에 이름이 없어 기본 칸을 받는 것으로 보인다. 모델 id를 줄이는 함수를 끝까지 읽지 않은 추정이다. relay는 모델과 관계없이 한 본문을 쓰므로(4절) 판단에는 영향이 적다.
- 실행 위치: `ReportFindings` 도구(화면용, `CLAUDE_CODE_REPORT_FINDINGS`)가 있으면 리뷰를 그 세션에서 돌리고, 없으면 리뷰 전체를 fork한 컨텍스트에서 돌려 부른 세션에는 지적 목록만 돌려준다(`getContext`). 그 목록은 JSON으로 받고 글로 바꿔 보인다.

## 2. 내장 code-review high의 구성과 순서

세 본문 모두 첫 줄에 수준과 모양을 한 줄로 밝히고(`high effort → 8 inline angles → dedup (no verify) → ≤10 findings` 같은 꼴), 모두 diff 하나만 범위로 삼는다.

### 2.1 기본·Opus 4.8 (`o48-high-v1`)

1. **목표 문장:** recall. 조심스러운 리뷰어가 한 번에 잡을 실제 버그를 모두 잡는다. 잘못 짚는 것보다 놓치는 것이 더 나쁘다.
2. **Phase 0 — diff 모으기:** `git diff @{upstream}...HEAD`(없으면 `main...HEAD`나 `HEAD~1`). 커밋하지 않은 변경이 있거나 범위가 비면 `git diff HEAD`도 범위에 넣는다. 인자로 PR·브랜치·경로를 주면 그것을 본다.
3. **Phase 1 — 후보 찾기:** 여덟 각도를 이 컨텍스트에서 차례로 한다(서브에이전트를 띄우지 않음). 각도마다 후보 6개까지, 후보마다 `file`, `line`, 한 줄 `summary`, 구체적인 `failure_scenario`.
   - 정확성 셋: A 줄 단위(모든 hunk를 줄마다 읽고 감싼 함수도 읽음. 손댄 함수의 바뀌지 않은 줄도 범위. "어떤 입력·상태·시점·플랫폼이 이 줄을 틀리게 하나"), B 지운 동작(지우거나 바꾼 줄이 지키던 불변식을 새 코드가 어디서 다시 지키는지), C 파일을 넘는 추적(바꾼 함수의 호출부와 피호출부).
   - 정리 셋: 재사용(이미 있는 도우미를 다시 구현함. 찾아서 부를 것을 이름으로), 단순화(파생 가능한 상태, 복사 뒤 조금 고침, 깊은 중첩, 남은 죽은 코드), 효율(반복 계산·I/O, 독립 작업을 차례로, 시작·핫 경로의 막는 일, 클로저가 붙잡는 큰 범위).
   - 깊이(altitude) 하나: 증상을 덧대지 않고 맞는 깊이에서 근본을 고쳤나. 공용 코드 위에 얹은 특수 경우는 깊이가 모자란 신호.
   - 관례 하나(CLAUDE.md): 바뀐 파일을 다스리는 CLAUDE.md를 읽고, 규칙과 그것을 어긴 줄을 그대로 인용할 수 있을 때만 짚는다. 취향과 "문서의 정신"은 짚지 않는다.
   - 정리·깊이·관례 후보는 `failure_scenario` 자리에 충돌 대신 드는 비용을 적는다. 출력 상한 때문에 자를 때는 정확성 버그가 언제나 앞선다.
   - "실패 시나리오를 댈 수 있는 후보는 모두 넘긴다. 반쯤 믿는 후보를 조용히 버리는 찾기가 놓침의 주된 원인이다."
4. **Phase 2 — 중복 정리만:** 후보를 모아 같은 결함·자리·까닭인 것은 하나만 남긴다. 확인을 돌리지 않고 다시 판정하지 않는다. 심각한 것부터 늘어놓는다.
5. **출력:** 하한 "적어도 5개(상한의 절반). 실제 지적이 그보다 적으면 있는 것만, 채우려고 지어내지 않는다"와 상한 10개(넘으면 심각한 10개). JSON 배열(`file`, `line`, `summary`, `failure_scenario`) 또는 `ReportFindings` 한 번.

### 2.2 Sonnet 5 (`high`)

1. 목표 문장과 Phase 0은 2.1과 같다. diff 줄 수로 찾기 서브에이전트 수를 권한다(150줄마다 하나, 2~8개).
2. **Phase 1:** 같은 여덟 각도를 서로 독립인 찾기 서브에이전트 여덟에게 맡긴다(각 6개까지). 서브에이전트 도구가 없으면 각도와 확인을 이 컨텍스트에서 스스로 차례로 한다. 후보를 거르지 말고 넘기라는 문장은 같다.
3. **Phase 2 — 확인(한 표, recall 쪽):** 같은 결함·자리·까닭은 하나로 합친 뒤, 후보마다 확인 서브에이전트 하나에게 diff, 관련 파일, 후보를 주고 셋 중 하나를 받는다.
   - CONFIRMED: 일으키는 입력·상태와 틀린 결과를 댈 수 있다. 줄을 인용한다.
   - PLAUSIBLE: 메커니즘은 실제고 일어나는 조건이 불확실하다(시점, 환경, 설정). 무엇이 확인해 줄지 적는다.
   - REFUTED: 코드가 그렇게 말하지 않거나 다른 곳에서 막는다. 증명하는 줄을 인용한다.
   - "PLAUSIBLE이 기본"이다. 상태가 현실적이면 "추측"이나 "실행 상태에 기댐"으로 틀렸다고 하지 않는다(경쟁, 드물지만 닿는 길의 빈 값, 0을 없음으로 봄, 경계의 하나 차이, 재시도·부분 실패, 앵커를 잃은 패턴). REFUTED는 코드로 보일 때만: 사실과 다름(줄 인용), 타입·상수·불변식으로 불가능(보임), 이 diff에서 이미 막음(막는 곳), 보이는 효과 없는 순수 스타일.
   - CONFIRMED와 PLAUSIBLE만 남긴다.
4. **출력:** 상한 10개, 2.1과 같은 모양. 하한은 없다.
5. 서브에이전트 도구가 아예 없는 세션이면 2.1처럼 한 컨텍스트에서 여덟 각도를 하고 스스로 다시 확인하며, "서브에이전트 없이 한 번에 한 리뷰"라고 요약에 밝힌다.

### 2.3 Opus 5 (`o5-bmin`)

짧은 본문 하나다: diff를 모으고, 경험 많은 엔지니어처럼 모든 hunk를 읽고 주변 파일을 열어(Read, Grep, git log/blame/show) 정확성 문제를 찾는다(틀리거나 뒤집힌 조건, 하나 차이, 빈 값 참조, 빠진 `await`, 떨어진 오류 처리, 지운 막음·검사, 바뀐 함수의 깨진 호출부, 경쟁). 스타일보다 실제 실패이고, 지적마다 코드가 잘못 동작하는 구체적인 시나리오가 있어야 한다. 15개 이하를 `ReportFindings`로 내고 글로도 다시 적는다. "양보다 질: 실제 문제라고 믿는 것은 모두, 믿지 않는 것은 하나도." 이 칸은 측정(`measuredExternal`)으로 고른 것으로 표시되어 있다.

### 2.4 셋에 공통인 것

`--fix`(리뷰 뒤 고침), `--comment`(PR에 줄 댓글), `--max-findings`(상한 바꾸기), 고친 뒤 `ReportFindings`를 결과와 함께 다시 부르기, 리뷰 뒤 다른 스킬을 부르라는 안내(조건부)가 본문 뒤에 붙는다. xhigh·max는 각도 D(언어별 함정)·E(감싸는 형의 올바름)와 Phase 3(빈틈 쓸기)를 더하고, low는 테스트 파일 hunk를 건너뛴다.

## 5. 서브에이전트에게 맡길지

**판단: 맡긴다.** 찾기 서브에이전트 하나(1~3단계: 범위, 모든 각도를 차례로, 중복 정리)와 그 뒤 새 확인 서브에이전트 하나(4단계: 후보를 모두 받아 확인됨 / 가능성 / 틀림)다. 메인 세션은 둘의 결과를 기다리고 확인을 통과한 목록만 받는다(사람이 고름, D488).

근거:

- 내장 `code-review`도 `ReportFindings`가 없으면 리뷰 전체를 fork 컨텍스트에서 돌리고 지적 목록만 돌려준다(1절의 실행 위치). 사람이 짐작한 대로 부른 세션의 컨텍스트를 아끼는 모양이다.
- verify는 리뷰 뒤에도 같은 세션에서 사람에게 묻고, 고른 지적을 고치고, 시험 명령을 돌리고, 완료조건을 판정하고, `pr.md`를 쓴다. diff 전체 읽기와 각도별 검토, 후보 확인을 메인 밖으로 빼는 이득이 크다.
- 확인을 찾기와 다른 서브에이전트에게 주면 확인이 찾은 쪽의 판단에 묶이지 않는다. 리뷰 전체를 하나에 맡기면 이 이득이 없다. 각도마다·후보마다 띄우면(2.2) 독립성은 더 크지만 수십 개가 뜬다.

메인 세션에 두는 것:

- 리뷰 범위와 입력 정하기: 브리프에 `context.md`와 산출물 경로, 기준 커밋(묶음 Work면 `## 레포`의 레포마다의 기준 커밋도), `## What to review` 전문(커스텀 유형이면 `## This Work type's review points` 절도. 그 뒤에 공통 규칙이 붙으므로 지침의 끝에 있지는 않다)과 1~3단계 전문(범위, 후보 형식, 중복 정리)(찾기), `context.md`와 산출물 경로, 기준 커밋(레포마다도), 후보 목록 전부와 확인 규칙 전문(확인)을 그대로 옮긴다. 서브에이전트는 relay 지침(시스템 프롬프트)을 보지 못하기 때문이다. 확인에도 `context.md`와 산출물 경로를 주는 것은 intent·설계와 맞는지, 팀 지식 규칙을 어기는지 같은 후보를 코드만으로는 확인할 수 없어서다(Work w-20261024-001의 verify 리뷰에서 더함). 1~3단계 전문과 레포마다의 기준 커밋은 PR #67 리뷰에서 더했다: 2단계 글만 주면 범위와 중복 정리 규칙이 전해지지 않고, 메인 worktree의 diff에서 서브모듈은 가리키는 커밋으로만 보인다.
- 5단계 쓰기: 심각도를 붙이고 심각한 것부터 `## 리뷰 지적`에 쓰기, 범위 밖 문제를 `나중에 정리할 곳`에 쓰기.
- 사람에게 반영할 지적 묻기(D229), 고른 지적 고치기(필요한 코드는 그 자리에서 다시 읽음), 시험, 판정, `pr.md`.

서브에이전트 둘은 읽기만 한다: 파일을 바꾸지 않고, 사람에게 묻지 않으며(질문은 메인 세션만 한다, D24), 목록만 돌려준다.

서브에이전트를 띄울 수 없는 엔진(Codex 등)이나 세션에서는 메인이 1~5단계를 차례로 하고 `남은 위험`에 "한 세션에서 리뷰함(확인이 찾은 쪽과 같은 컨텍스트)"을 적는다. 지침은 서브에이전트 도구의 이름(`Agent`, `Task`)을 쓰지 않고 "띄울 수 있으면"으로 쓴다.

알려진 위험:

- 서브에이전트가 백그라운드로 돌면 verify가 결과를 기다리며 턴을 끝낼 수 있다. 그동안 앱은 handoff가 없어 task를 쉬는 중으로 보인다. 결과가 오면 이어진다. verify는 늘 수동 승인이라 자동 승인 문제(D129)는 없다.
- 서브에이전트 둘이 diff를 각각 읽어 verify의 토큰 비용이 는다(메인 컨텍스트는 준다).
- 메인이 브리프를 줄여 옮기면 각도나 규칙이 빠질 수 있다. 지침에 "그대로 옮긴다"를 적었다.
