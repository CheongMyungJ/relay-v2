# relay 사용성 평가에서 뽑은 개선점

- 상태: 제안. 코드는 아직 고치지 않았다.
- 근거: 평가 보고서 3개 `app/eval/reports/2026-09-30-01-02-03.md`, `2026-09-30-04-05-06.md`, `2026-09-30-07-08.md`. 시나리오 1~8을 relay와 맨 Claude Code CLI로 쪽마다 5회씩 돌렸고, 사람 역할과 판정은 AI(sonnet)가 했다. 실행 기록 원본(turns.jsonl, 스크린샷, pty 로그)은 남아 있지 않아 보고서의 숫자와 인용이 근거의 전부다. 이전 세션에서 기록을 직접 열어 확인한 사실은 **(기록 확인)**으로 표시한다.
- 코드 위치: 세 보고서의 앱 커밋(9c02b42, 7a4fa7a, 8b6604a)부터 이 문서를 쓴 때까지 `app/src`와 `skills`는 바뀌지 않았다. 평가 도구는 그 뒤 main에서 고친 것이 있다(5.0절). 줄 번호는 main(5c144a0)을 병합한 뒤 기준이다.
- 표기
  - 크기: S는 한두 곳을 고치고 설계 결정은 그대로, M은 여러 층(core, main, renderer, 스킬)을 고치거나 설계 결정(D 번호)을 바꿔야 함, L은 구조를 바꿈.
  - 우선순위: P1은 다음 작업에서 먼저, P2는 그다음, P3은 여유가 있을 때.
  - **⚠AI**는 숫자 차이가 AI 사람 역할 때문일 수 있는 것, **⚠회차**는 회차가 적어 흔들릴 수 있는 것이다.
  - "n회"는 사람 역할의 말(`[relay#k 불편]`)에서 센 횟수다. 집계는 부록 A.

## 2. 먼저 알아 둘 것

### 2.1 보고서 머리말의 참고

- 01 relay#1은 도구 정리 명령으로 앱이 꺼져(`harness_error`) 같은 조건으로 다시 돌린 실행으로 바꿨다(E9).
- 05의 맨 CLI는 1분 안에 끝나며 뒤에 올 요구까지 먼저 처리했다. 요구가 늘 때 방향을 바꾸는 부분은 CLI 쪽에서 거의 시험되지 않았다(E4).
- 06의 맨 CLI는 첫 코드 변경 약 6초 뒤에 꺼져 수정이 거의 끝난 상태였다. relay는 3회(#1, #4, #5)가 수정 도중, 2회(#2, #3)가 수정이 끝난 뒤 꺼졌다. 두 쪽이 이어 간 일의 양이 다르다(E3).
- 07 맨 CLI #2~#4의 숨긴 시험 실패는 측정 오류다. 작업 폴더에서는 5회 모두 두 버그가 고쳐져 있었다(E1).
- 08에서 relay는 5회 모두 의도 정리의 열린 질문으로 사용자 시간대(LA)를 알아냈고, 맨 CLI는 5회 모두 묻지 않고 리포트만으로 고쳤다.

### 2.2 AI 사람 역할과 회차

- 사람 역할은 매 실행이 relay를 처음 쓰는 사람이다. 익숙해지는 효과가 없어, 처음 볼 때만 드는 부담(새 Work 창의 설정 등)이 실제 사용자보다 크게 잡힐 수 있다. 맨 CLI는 모델에게 익숙한 도구다.
- 설문은 거의 움직이지 않는다. relay의 설문 명확함과 결과 확신은 8개 시나리오 모두 6.0 ± 0.0이다. relay의 friction 평균은 8개 가운데 6개 시나리오에서 0.0인데, 사람 역할의 말에는 거의 매번 불편이 있다. 설문과 friction의 작은 차이는 근거로 쓰지 않았다(E6).
- **걸린 시간**에는 사람 역할이 차례마다 화면을 읽고 답하는 시간이 들어간다. relay는 차례가 3~5배쯤이라 이 몫이 크다. "relay 3.2~6.2분 대 CLI 0.8~1.3분"은 relay에 불리하게 부풀려져 있을 수 있다(E2). ⚠AI
- **차례 수**는 "화면이 바뀌었다가 6초 그대로면 깨운다"는 규칙에 달렸다. 검은 화면처럼 멈춘 화면은 사람을 깨우고, 계속 바뀌는 화면은 깨우지 않는다(E2).
- 경험 판정은 가릴 수 없다(기록에 도구가 드러난다). 판정 모델도 Claude다.
- 쪽마다 5회다. 크기별 비교(08의 L 3회, M 1회, S 1회)처럼 더 쪼갠 숫자는 사례로만 본다. ⚠회차
- 시나리오는 모두 작은 버그다(맨 CLI가 1분 안팎에 끝냄). 숨긴 시험은 측정 오류를 빼면 두 쪽 모두 100%다. 이 평가는 relay의 절차 비용이 가장 크게 보이는 영역만 봤다(E7).

### 2.3 흔들리지 않는 신호

- burden은 40짝 모두 CLI 우세다. overall은 CLI 33, relay 3, 비김 4다.
- confidence는 relay 33, CLI 0, 비김 7이다. 결과(가림) 선호는 relay 27, CLI 2, 비김 11이고, 틀어진 07 #2~#4를 빼도 24 : 2 : 11이다. 차이는 대부분 시험에서 난다.
- 같은 불편이 여러 시나리오에서 되풀이된다(부록 A). 승인 횟수와 세션 수는 구조에서 나온 숫자라 AI 사람 역할과 관계없다.

## 4. relay 개선점

### R1. 작은 버그에도 절차가 무겁다 (P1, M)

**증상.** 한 줄 버그에도 의도 정리 → 수정 → 리뷰 → 최종 검증을 모두 거치고 단계마다 승인한다(S 4번, M 5번, L 6번). 버그가 둘이면(07) Work 둘에서 모두 두 번 한다. 크기가 L로 잡히면 한 줄 수정도 6단계다(08).

**근거.**
- "단계와 승인이 많다"가 7개 시나리오 21회(01은 5/5회).
  - "한 줄짜리 버그인데도 승인을 네 번 눌러야 했다." (01 relay#3)
  - "승인 화면이 단계마다 반복돼 대부분 클릭만 했고, 내가 실제로 방향을 잡을 일은 거의 없었다." (02 relay#2)
  - "이 크기의 한 줄짜리 버그에 비해 단계가 많았다(L로 잡혀 6단계)." (08 relay#1)
- 짝 판정 burden은 40짝 모두 CLI 우세, overall은 CLI 33 · relay 3 · 비김 4. 경험 점수 relay 5.6~6.6 대 CLI 6.6~8.4. 가장 단순한 01(목적: 과한 절차인지)에서 "다시 쓰고 싶음"이 5.2 대 6.8로 가장 크게 벌어졌다.
- 사람 행동 수 relay 8.0~18.4 대 CLI 2.0~4.0, 에이전트 세션 4~8 대 1.
- 07은 Work 둘에서 모든 승인을 두 번씩 해 행동 18.4 대 2.8이다 (기록 확인).
- 같은 요청에서도 크기가 흔들린다. 08은 L 3회 · M 1회 · S 1회, 03은 M 4회 · S 1회다. 08의 L 실행은 5.3~5.5분, S 실행은 3.9분이었고 결과는 같았다. ⚠회차

**원인 추정.**
- 경로는 크기로 정해지고 모든 크기가 리뷰를 지난다: `app/src/core/pipeline.ts:81-101` (D147, D163, D166).
- 의도 승인, 리뷰, 최종 검증은 늘 수동이고(`app/src/core/config.ts:24-36`, D7, D167), 자동 승인을 켤 수 있는 단계도 기본은 모두 꺼져 있다(`app/src/shared/config.ts:110`). S 경로의 승인 4번 가운데 설정으로 줄일 수 있는 것은 fix 하나뿐이다. 평가에서는 설명서가 "다른 설정은 기본값 그대로 두어도 된다"고 했고(`app/eval/guides/relay.md:6`), 자동 승인을 켠 흔적은 보고서에 없다("옵션이 많았는데 다 기본값으로 뒀다", 04 relay#3).
- 크기 기준에서 "환경에 달린 버그"는 수정 위치가 한 곳이어도 L이 된다: `skills/work-start/SKILL.md:52-56` (D150). 08의 시간대 버그가 여기에 걸린다.
- 의도 승인 화면의 size 고르기는 S/M/L만 보이고, 그 크기로 무엇을 몇 번 더 거치는지는 보이지 않는다: `app/src/renderer/src/Panel.tsx:531-547`.
- 단계마다 새 세션을 띄운다: `app/src/main/work.ts:713` (`startSession`). 세션을 띄울 때마다 시작 시간과 컨텍스트 읽기가 붙는다(R2, R9).

**제안.** 설계를 바꾸지 않는 것부터 한다.
1. (S) size 고르기 옆에 경로와 남은 승인 수를 보인다. 예: "S: 수정 → 리뷰 → 최종 검증 (승인 3번 더)", "L: 재현과 관찰 → 원인 분석 → 수정 → 리뷰 → 최종 검증 (승인 5번 더)".
2. (S, D150 수정) work-start의 L 기준을 좁힌다. 수정 위치가 한 곳이고 재현을 명령으로 만들 수 있으면(예: `TZ=America/Los_Angeles`로 실행) 환경에 달린 버그라도 L로 올리지 않는다.
3. (S~M, D167 변경) 리뷰 지적이 "없음"이면 리뷰 승인을 따로 받지 않는다. 자동 승인처럼 카운트다운 뒤 넘어가고 [취소]로 멈춘다. D167의 까닭은 "사람이 지적을 고를 시간"인데 지적이 없으면 고를 것이 없다.
4. (S, D7 기본값 변경) S·M에서 fix 자동 승인을 기본으로 켤지 정한다. fix 결과는 리뷰와 Work 완료 화면(전체 diff, 판정표)에서 다시 본다(D7의 까닭). 열린 질문이나 의도 어긋남이 있으면 지금처럼 멈춘다(4.3).
5. (M, D163 변경) 1~4 뒤에도 무거우면 S에서 리뷰를 fix 세션의 자기 점검으로 합쳐 세션 하나를 줄인다. D163은 "건너뛰고 싶은 일이 잦으면 그때 넣음"이라 했고, 이 평가가 그 근거가 된다.

3~5는 사용자가 정한 결정(✅)을 바꾸므로 사용자와 정한다.

### R2. 에이전트가 일하는 동안 터미널이 검은 빈 화면이고 진행 표시가 없다 (P1, S~M)

**증상.** 단계가 바뀌어 새 세션이 뜰 때와 에이전트가 일하는 동안 가운데 터미널이 검은 빈 화면이다. 패널에는 "handoff 아직 없음", "산출물 아직 없음"만 있어 진행 중인지 멈춘 것인지 모른다.

**근거.**
- 7개 시나리오 25회(06만 없음).
  - "단계 사이에 검은 화면으로 기다리는 시간이 있었고, 그동안 진행 상황이 안 보였다." (01 relay#3)
  - "터미널이 까맣게 비어 있는 로딩 구간에는 무슨 일이 일어나는지 알 수 없었다." (02 relay#2)
  - "단계 전환 직후 터미널이 까만 빈 화면으로 잠깐 있어서 멈춘 건지 헷갈렸다." (08 relay#5)

- 짝 판정 코멘트에도 relay의 흠으로 되풀이된다(01#2, 02#2, 02#4, 03#2, 03#3, 04#3, 07#3, 08#2, 08#3, 08#5).
- relay 사람 차례의 약 1/4이 기다리기만 한 차례였다 (기록 확인). 보고서에서 "차례 수 − 행동 수"는 relay 2.4~4.8, CLI 0.4~1.0(대부분 "끝냄" 차례)이다.

**원인 추정.** 확인한 것:

확인하지 못한 것(기록이 없음). 세션이 뜬 뒤에도 검게 남는 까닭의 후보:
- CLI가 시작하고 전체 화면 렌더러를 준비하는 시간. 단계마다 되풀이된다(스파이크 S1·S6에 전체 화면 렌더러 기록).

**제안.**
1. (S) 새 세션을 띄울 때도 `RESUME_MARK`처럼 표시 줄을 넣는다. 예: "── relay: 04 수정 · 새 세션을 띄우는 중 ──".
2. (M) 패널 진행 화면과 머리 띠에 경과 시간과 마지막 동작을 보인다. PreToolUse·PostToolUse 훅의 matcher를 모든 도구로 넓혀 "마지막 동작: Bash(npm test) · 8초 전"처럼 보인다. 훅으로 받으므로 D2(터미널을 파싱하지 않음)와 맞다. 훅이 늘어 생기는 부담(도구 호출마다 HTTP 요청)은 함께 잰다.
3. (S) 세션마다 띄운 때, 첫 PTY 출력, 첫 훅(UserPromptSubmit)의 시각을 events.jsonl에 남긴다. 검은 구간이 얼마나 되고 어디서 생기는지 확인한 뒤 위 후보 가운데 원인을 고친다.

**기대 효과.** 기다리기만 한 차례, 설문과 판정의 clarity, "검은 화면" 불편 언급이 준다.

**주의.** 평가는 화면이 6초 그대로면 사람을 깨운다. 경과 시간처럼 계속 바뀌는 표시를 넣으면 차례 수가 기계적으로 준다. 효과는 차례 수보다 기다리기만 한 차례와 사람 역할의 말로 본다(E2). ⚠AI

### R3. 앱이 꺼진 뒤 [재개]해도 에이전트가 이어서 일하지 않는다 (P1, S)

**증상.**
- 수정 도중 앱이 꺼진 뒤 [재개]를 누르면 세션은 다시 뜨지만 에이전트가 입력을 기다리며 멈춰 있다. 사람이 "이어서 진행해 주세요"를 쳐야 한다.
- 수정이 끝난 뒤 꺼진 경우에는 터미널에 작업하던 옛 화면이 남고 패널은 "승인 대기"라 어느 쪽이 맞는지 헷갈린다.

**근거.** 06 relay 5회 모두.
- 멈춤: #1, #4, #5 (수정 도중 꺼진 3/3회). "[재개]를 누른 뒤에도 에이전트가 멈춰 있어서 터미널에 직접 이어서 진행하라고 입력해야 했다. 이 부분은 이렇게 하면 된다는 안내가 없었다." (relay#1). #4와 #5의 차례 7은 friction 2였고, relay 40회에서 friction 2 이상인 차례는 이 둘뿐이다.
- 엇갈림: #2, #3 (수정이 끝난 뒤 꺼진 2/2회). "그 뒤 터미널은 작업 중인 옛 화면인데 패널은 승인 대기라서 상태가 맞는지 불안했다." (relay#2)

**원인 추정.**
- `resumeArgs`는 스킬을 처음부터 다시 시작하지 않게 첫 프롬프트를 빼고, 대신 줄 입력도 없다: `app/src/core/settings.ts:180-195`, 호출은 `app/src/main/work.ts:768-800`. `--resume`으로 연 세션은 입력을 기다린다(S6).
- 패널은 "중단됨. [재개]하면 이어서 합니다."라고 알리고(`app/src/renderer/src/Panel.tsx:288`), 평가 설명서도 "[재개]로 이어 간다"고 했다(`app/eval/guides/relay.md:13`). 사람의 기대와 실제 동작이 어긋난다.
- 수정이 끝난 뒤 꺼진 경우: 재시작 조정은 유효한 handoff를 보고 승인 대기로 바꾸지만(`app/src/core/machine.ts:2233-2290`, D75), 탭은 pty.log를 아무 표시 없이 그대로 다시 그린다(`app/src/main/work.ts:3557-3565`). 멈춘 스피너가 "작업 중"처럼 보인다.
- 세션이 왜 끝났는지(사람의 [즉시 중단]인지, 앱 재시작인지)가 task 기록에 없다: `app/src/shared/work.ts:161-172` (`TaskSession`). 그래서 재개 때 둘을 가를 수 없다.

**제안.**
1. (S) 사람이 끊지 않은 세션(앱 재시작 조정, handoff 없는 세션 종료나 크래시)을 [재개]할 때는 `--resume <id>` 뒤에 첫 입력을 준다. 예: "relay: 앱이 꺼져 세션이 끊겼습니다. 끊기기 전의 마지막 상태(끝나지 않은 명령 등)를 확인하고 하던 일을 이어서 하세요. 사람에게 물을 것이 있었다면 다시 물으세요." 시작 인자이므로 1.2 비목표(실행 중인 세션에 글을 넣지 않음)와 맞다. 자동으로 여는 것은 아니므로 D75도 그대로다. 사람이 [즉시 중단]한 세션은 지금처럼 비워 둔다. 이를 위해 `TaskSession`에 끝난 까닭을 남긴다. `--resume`과 입력을 함께 주는 동작은 스파이크 S6에 한 줄 더해 확인한다.
2. (S) 앱이 꺼져 끝난 세션의 pty.log를 다시 그릴 때 끝에 "── relay: 앱이 꺼져 세션이 여기서 끝났습니다(기록) ──"를 붙인다. 재시작 조정으로 승인 대기가 된 task에는 "앱이 꺼지기 전에 산출물을 다 썼습니다. 오른쪽에서 확인하고 승인하세요."를 보인다.
3. (S) 중단됨 문구를 실제 동작에 맞춘다.

**기대 효과.** 06의 friction 2 차례(평균 0.4)가 0으로, 사람 행동 수가 1쯤 준다. 설문 복구와 판정 recovery가 좋아질 것으로 본다.

**주의.** ⚠회차. 두 쪽의 비정상 종료 시점이 달라 recovery 비교는 CLI에 유리했다(E3).

### R4. 형식 되돌림이 "Stop hook error"로 사람에게 보인다 (P1, S)

**증상.** 에이전트가 쓴 handoff의 형식이 틀리면 relay가 Stop 훅으로 되돌린다. 터미널에 "Stop hook error: relay 형식 검사에서 오류가 나왔습니다 …"와 YAML 오류, 에이전트가 고치는 과정이 보인다. 에이전트가 스스로 고치지만 사람은 결과에 영향이 있는지 몰라 불안해했다.

**근거.**
- 5개 시나리오 10회 (01#1, 03#3, 03#4, 05#2, 05#4, 05#5, 07#1, 08#1, 08#2, 08#4).
  - "터미널에는 stop hook 오류 같은 내부 메시지가 그대로 보였다. 그 오류가 결과에 영향을 줬는지 바로 알기 어려웠다." (03 relay#3)
  - "터미널에 stop hook의 YAML 형식 오류가 여러 번 보여 잠깐 불안했다." (05 relay#4)
- 짝 판정에도 relay의 흠으로 적혔다(03#3 "내부 오류 메시지가 불편", 03#4 "터미널 오류 노출", 05#5 "내부 로그가 노출돼", 08#2 "오류 로그 혼란").
- 04~06의 단계 pty 로그 62개 가운데 11개(18%)에 있었다 (기록 확인).

**원인 추정.**
- 되돌림 자체는 설계대로다(D21): Stop 때 형식 오류가 있으면 `{"decision":"block","reason":…}`로 답한다(`app/src/core/machine.ts:1412-1422`, `app/src/main/work.ts:553`). Claude Code 2.1.285는 Stop 훅의 block을 오류로 모아 "Stop hook error: <reason>"으로 그리고 "Stop hook error occurred" 알림도 띄운다(설치된 실행 파일의 `stop_hook_summary` 렌더링에서 확인). 머리말은 relay가 바꿀 수 없다.
- 오류가 잦은 까닭(추정): 머리글을 YAML로 읽고 스키마로 엄격하게 본다(`app/src/core/validate.ts:86-110`). 스킬은 검증기를 돌리지 말라고 하고(`skills/_common.md:79`, D29), 템플릿(`skills/_common.md:56-72`)에는 문자열을 따옴표로 감싸라는 말이 없다. 한국어 문장 속의 `: `나 백틱으로 시작하는 값은 YAML이 다르게 읽는다.
- 어떤 오류였는지는 남지 않는다: 되돌림의 효과는 `blockStop` 하나이고 events.jsonl에 기록하지 않는다(`app/src/core/machine.ts:1418-1421`).

**제안.**
1. (S) 되돌림을 오류 목록과 함께 `task.bounced` 같은 이벤트로 남긴다. 다음 평가에서 오류 종류를 센다.
2. (S) 템플릿에 "문자열 값은 모두 큰따옴표로 감싼다"를 적고 값을 채운 예시를 둔다. 1의 기록에서 흔한 실수(목록 항목이 `키: 값`으로 읽힘 등)가 보이면 검사기가 경고로 받아 준다.
3. (S) 되돌리는 동안 패널에 "형식 확인으로 되돌림(1/2): 에이전트가 handoff 형식만 고칩니다. 결정과 판정은 바뀌지 않습니다."를 보인다. 되돌림 횟수는 이미 화면 모델에 있다(`app/src/main/work.ts:3679`).
4. (S) 되돌림 문구(`app/src/core/validate.ts:749-755`)의 첫 줄은 사람도 읽는다고 보고 쓴다. 예: "[relay 형식 확인] 작업 결과와는 관계없고 handoff 형식만 고칩니다."
5. 1~4로 충분히 줄지 않으면 D29(에이전트용 검증 명령을 두지 않음)를 다시 정한다.

**기대 효과.** 사람 역할의 "Stop hook / YAML" 언급(10/40)과 pty 로그의 되돌림 비율(11/62)이 준다. 설문 신뢰와 판정 confidence를 지킨다. 되돌림마다 드는 에이전트 턴과 토큰도 준다.

### R6. 열린 질문에 어디서 답하는지, 답이 반영됐는지 안 보인다 (P1, S~M)

## 5. 평가 도구 개선점

### 5.0 main에서 이미 고친 것

이 문서를 쓰는 동안 main에 평가 도구 작업이 들어왔다(360ad56~5c144a0).

- **E1:** 360ad56이 고쳤다. 맨 CLI도 기준 뒤에 커밋이 있고 HEAD에 없는 로컬 브랜치를 `git archive`로 꺼내 결과 폴더로 삼는다. 지난 07 CLI 실행 5개를 다시 재면 모두 두 버그 통과다.
- **E7:** 어려운 시나리오 09~14와 설계(`docs/eval-hard-scenarios.md`), 정답·함정 패치를 확인하는 `app/eval/check-scenario.mjs`가 들어왔다. 10은 사람만 아는 회계 규칙으로 정답이 갈린다. 다만 시범 실행에서 맨 CLI는 여섯 시나리오를 모두 1분 반 안에 풀었다(`docs/eval-hard-scenarios.md:214`).
- **E3·E4의 취지:** 11은 여러 파일을 고치는 도중(첫 변경 15초 뒤) 꺼지고, 13은 이미 고친 방향을 뒤집는 요구(첫 변경 20초 뒤)라 에이전트가 미리 채울 수 없다. 05와 06 자체는 그대로다.
- **사람 역할:** `on_ask` 사실은 에이전트가 물었을 때만 답하게 규칙을 좁혔다(5c144a0).

### E1. 맨 CLI 결과를 마지막에 체크아웃된 브랜치 하나로만 잰다 (main에서 고침, 360ad56)

**증상.** 07에서 사람 역할이 버그마다 브랜치를 나눠 달라고 했고 에이전트는 두 브랜치에 각각 제대로 커밋했다. 평가는 마지막에 체크아웃된 브랜치만 판정해 다른 브랜치의 수정을 놓쳤다.

**근거.** 07 맨 CLI 숨긴 시험 40%(2/5), 레포 시험 80%, 커밋 80%, correctness 3.0 ± 1.9. 작업 폴더에서는 5회 모두 두 버그가 고쳐져 있었다(보고서 참고 줄). 짝 판정 #2~#4의 결과 선호(relay)와 CLI 점수가 틀어졌고, 3개 보고서를 합친 결과 선호 relay 27에 이 3짝이 들어 있다.

**원인.** 고치기 전의 `app/eval/lib/cli-arm.mjs`의 `finalTrees()`가 레포 폴더(지금 체크아웃) 하나만 돌려줬다. 바뀐 폴더가 없으면 레포 시험과 커밋도 실패로 센다(`app/eval/lib/episode.mjs:355`, `app/eval/lib/episode.mjs:378`, `app/eval/lib/episode.mjs:382`).

**고침.** main의 360ad56(5.0절). 판정은 꺼낸 브랜치마다 diff를 따로 본다. 커밋과 브랜치를 어떻게 나눴는지는 여전히 보지 않는다(E5).

**남은 일.** 07을 다시 돌려 보고서의 07 CLI 숫자(숨긴 시험, 레포 시험, 커밋, correctness, 짝 판정 결과 선호)를 바꾼다.

### E2. 걸린 시간과 차례 수에 AI 사람 역할의 몫이 섞인다 (P2, S)

**증상.** "걸린 시간"은 시작부터 끝까지의 벽시계 시간이라 사람 역할이 차례마다 스크린샷을 읽고 답하는 시간이 들어간다. 차례 수는 깨우기 규칙에 달렸다.

**근거.** relay는 차례 11~21번, CLI는 3~4번쯤이다. relay 사람 역할은 차례마다 스크린샷을 읽어 비용이 실행당 1.5~5.5달러(CLI 0.1~0.2달러)다. "차례 수 − 행동 수"는 relay 2.4~4.8, CLI 0.4~1.0이다.

**원인.** 평가 고리는 사람 역할의 답을 기다린다(`app/eval/lib/episode.mjs:225`). 에이전트가 승인을 기다리는 동안에는 이 시간이 그대로 걸린 시간이 된다. 차례 기록에는 사람 역할의 응답 시간(`ms`, `app/eval/lib/episode.mjs:250`)이 있지만 보고서는 벽시계 시간만 보인다(`app/eval/report.mjs:88`). 깨우기 규칙은 `app/eval/lib/episode.mjs:13`, `app/eval/lib/episode.mjs:190-197`이다.

**제안.** 보고서에 사람 역할 응답 시간의 합, 그것을 뺀 시간, 기다리기만 한 차례(행동이 `wait`뿐인 차례) 수를 더한다. R2처럼 계속 바뀌는 진행 표시를 넣으면 깨우는 횟수가 기계적으로 줄므로, 개선 전후는 기다리기만 한 차례와 사람 역할의 말로 비교한다.

**기대 효과.** 시간 차이에서 relay의 몫과 평가의 몫을 가를 수 있다.

### E3. 06의 비정상 종료 시점이 두 쪽에서, relay 안에서도 다르다 (P2, S)

**증상.** 맨 CLI는 수정이 거의 끝난 뒤 꺼졌다. relay는 3회가 수정 도중, 2회가 수정이 끝난 뒤 꺼졌다. 이어 간 일의 양이 달라 recovery 비교가 CLI에 유리했고, relay 안에서도 회차마다 다른 상황을 시험했다.

**근거.** 보고서 참고 줄("첫 코드 변경 약 6초 뒤에 꺼져 수정이 거의 끝난 상태", "relay는 수정 도중 꺼진 3회(#1, #4, #5)"). 판정 recovery CLI 3 · relay 1 · 비김 1.

**원인.** 종료는 "첫 코드 변경 + 5초"다(`app/eval/scenarios/06-paginate-crash/scenario.json:10-16`, 판정은 `app/eval/lib/episode.mjs:82-92`, 3초마다 확인 `app/eval/lib/episode.mjs:162-188`). CLI 에이전트는 한 번에 고쳐 첫 변경이 곧 수정이다. relay의 fix는 재현 시험을 먼저 더하는 일이 많아(`skills/fix/SKILL.md`의 Reproduction test, 06 relay#5 "재현 테스트를 먼저 추가하고") 첫 변경이 시험이면 5초 뒤는 수정 도중이다. 첫 변경을 3초마다 확인하므로 시점이 몇 초씩 흔들린다.

**main.** 새 시나리오 11은 여러 파일을 고치는 도중(첫 변경 15초 뒤)에 꺼지게 잡았다(5.0절). 06의 시점은 그대로다.

**제안.** 두 쪽이 비슷한 진행 지점에서 꺼지게 한다. 예: "src/ 파일의 첫 변경 + n초"이면서 에이전트가 아직 일하는 중(화면이 바뀌는 중)일 때. 꺼진 때의 진행(바뀐 파일, 커밋 여부, handoff 유무)을 기록해 비교에 쓴다. R3의 두 경우(수정 도중, 수정 뒤)는 따로 이름 붙인 사건으로 나눠 돌린다.

### E4. 05의 새 요구가 맨 CLI에서는 일이 끝난 뒤 온다 (P2, S)

**증상.** 맨 CLI는 새 요구가 오기 전에 그 요구("" 이스케이프, 빈 칸)까지 먼저 처리했다. 방향을 바꾸는 부분이 CLI에서 시험되지 않았다.

**근거.** 보고서 참고 줄. CLI 사람 역할 4/5회가 "이미 처리돼 있었다"고 했다(cli#2~#5).

**원인.** 새 요구는 "첫 코드 변경 + 0초"다(`app/eval/scenarios/05-csv/scenario.json:9-14`). CLI는 첫 변경 때 이미 파서 전체를 새로 썼다. 요구 자체도 CSV 표준(RFC 4180)이라 에이전트가 먼저 해 버린다.

**main.** 새 시나리오 13은 이미 고친 방향을 뒤집는 요구를 첫 변경 20초 뒤에 준다. 에이전트가 미리 채울 수 없는 요구다(5.0절). 05는 그대로다.

**제안.** 에이전트가 먼저 하지 않을 요구(표준에 없는 규칙, 예: "따옴표 없는 칸의 앞뒤 공백을 지운다")로 바꾸고, 시작 뒤 일정 시간(`elapsed`)이나 첫 도구 동작 때 알린다.

### E5. 결과 판정이 커밋과 브랜치 나눔을 보지 못한다 (P2, S)

**증상.** 07의 목적은 "변경이 섞이지 않게 나누기 쉬운지"인데, 가린 결과 판정은 코드 차이만 본다.

**근거.** 판정 07#4 "기록만으로는 B가 실제로 커밋을 나눴는지 알 수 없다", 07#5 "기록에는 실제 커밋이나 브랜치를 나눴는지가 없어서 그 점은 평가에 반영하지 않았다".

**원인.** `app/eval/lib/judge.mjs:64-86`의 결과 판정 입력은 시험 결과와 diff뿐이다(커밋 메시지는 도구가 드러나므로 뺐다).

**제안.** 도구가 드러나지 않게 이름을 바꾼 구조를 더한다: 브랜치 수(B1, B2), 브랜치마다 커밋 수와 커밋별 파일, 한 커밋에 두 버그의 파일이 섞였는지. 메시지와 브랜치 이름은 넣지 않는다.

### E6. 설문과 friction이 거의 움직이지 않는다 (P3, M)

**증상.** 사람 역할의 말에는 불편이 있는데 설문과 friction에는 드러나지 않는다.

**근거.** relay의 설문 명확함과 결과 확신은 8개 시나리오 모두 6.0 ± 0.0, relay의 friction 평균은 6개 시나리오에서 0.0이다. CLI도 명확함 6.0~6.6, 결과 확신 5.2~6.0으로 폭이 좁다.

**원인.** 척도에 기준점이 없고(`app/eval/lib/human.mjs:195-211`), friction은 사람 역할이 스스로 매긴다(`app/eval/lib/human.mjs:21-27`). AI 사람 역할은 너그럽고 지치지 않는다(`docs/eval.md` 8절).

**제안.** 점수마다 예시를 단 척도, 특정 순간(재개 뒤, 검은 화면)에 대한 질문을 쓴다. 행동에서 friction을 뽑는다(기다리기만 한 차례, 탭 오가기, 같은 말 다시 치기). 설문보다 짝 판정과 행동 지표에 무게를 둔다.

### E7. 시나리오가 결과와 "묻기"를 가르지 못한다 (P2, M)

**증상.** 측정 오류를 빼면 숨긴 시험이 두 쪽 모두 100%다. 모든 시나리오가 작은 버그다.

**근거.** 02(동점자)와 03(진짜 원인)은 CLI도 5/5회 찾았다. 08은 CLI가 한 번도 묻지 않고도(0/5) 시간대 시험을 모두 통과했다. `getUTCDay`로 고치는 데 LA라는 정보가 필요하지 않다. CLI가 1분 안팎에 끝나는 버그뿐이라 relay의 절차 비용만 크게 보인다.

**main.** 09~14가 들어왔다(5.0절). 시범 실행에서 맨 CLI는 여섯 모두 1분 반 안에 풀었으므로, 결과가 갈리는지는 실제 평가에서 본다. 자동 승인을 켠 relay 변형은 아직 없다.

**제안.** 사람만 아는 정보가 없으면 틀리게 고치게 되는 시나리오(업무 규칙이 코드에 없는 버그), 여러 파일에 걸치거나 간헐적인 버그, relay의 자동 승인을 켠 변형을 더한다.

### E8. 사람 행동 수가 클릭과 입력을 같이 센다 (P3, S)

**증상.** relay의 행동은 대부분 [승인]과 탭 클릭이고, CLI의 행동은 대부분 글 입력이다. 입력 글자 수는 비슷하다(relay 94~315자, CLI 136~382자).

**원인.** `app/eval/lib/episode.mjs:392-394`가 `wait`, `done`, `give_up`만 빼고 모두 더한다.

**제안.** 행동을 종류별(click, type, key, scroll, inspect_diff)로, 승인 클릭을 따로 보고한다.

### E9. 문제 해결 안내의 pkill이 돌고 있는 실행까지 끈다 (P3, S)

**증상.** 01 relay#1이 시작 직후 정리 명령에 앱이 꺼져 `harness_error`로 끝났다.

**원인 추정.** 평가 스킬의 안내 `pkill -f 'electron.*relay-eval'`(`.claude/skills/relay-eval/SKILL.md:53`)은 앞 실행의 찌꺼기만이 아니라 돌고 있는 모든 평가 앱에 맞는다. 도구 코드(`app/eval/`)에는 다른 종료 명령이 없다.

**제안.** 결과 폴더 이름까지 넣은 패턴으로 좁히거나, run.mjs가 자기 프로세스 번호를 적어 두고 그것만 정리하게 한다. 안내에 "실행 중에는 돌리지 않는다"를 적는다.

### E10. relay 사람 역할의 비용이 커서 회차를 늘리기 어렵다 (P3, S~M)

**근거.** 사람 역할 비용 relay 1.5~5.5달러 대 CLI 0.1~0.2달러(실행당).

**제안.** 화면 배치가 바뀌었을 때만 스크린샷을 붙이고 해상도를 낮춘다. 줄인 만큼 회차를 늘려 ⚠회차 항목을 확인한다.

## 6. 추가 평가로 확인할 것

근거가 한두 번뿐이거나 이번 자료로는 원인을 가를 수 없는 것이다.

1. **크기(L)의 값.** 08의 L 3회는 5.3~5.5분, S 1회는 3.9분이었고 결과는 같았다. 02는 5회 모두 L이었다. 같은 시나리오를 크기를 고정해(S, M, L) 돌려 L의 따로 된 재현 단계가 결과나 확신을 바꾸는지 본다.
2. **자동 승인을 켠 relay.** 평가에서 켠 흔적이 없다. fix(와 investigate)를 켠 변형으로 R1의 효과를 미리 잰다.
3. **검은 화면의 원인.** R2의 계측(세션 시작부터 첫 출력, 첫 훅까지의 시간)과 스크린샷으로 후보를 가른다.
4. **04에서 relay의 통제감이 낮았던 까닭.** 설문 통제감 5.0 대 6.0, 판정 control CLI 5 : 0. CLI 쪽은 "사람이 범위를 직접 정했다"고 판정됐다. relay는 비목표가 [산출물] 탭의 intent 초안에만 있어 사람이 범위를 정했다는 감각이 약했을 수 있다(가설, R6의 2와 이어짐).
5. **의도 정리에서 가설이 근거처럼 보임.** "에이전트가 코드를 읽고 추정한 가설을 근거처럼 적었고, 실제로 돌려 본 건 아니었다." (03 relay#4, 판정 03#4). 1회.
6. **리뷰 단계에서 에이전트가 수정을 되돌렸다가 다시 적용.** "에이전트가 실수로 git checkout으로 수정을 되돌렸다가 다시 적용했다." (05 relay#3). 1회. 되풀이되면 리뷰 단계의 deny 규칙이나 스킬 문구를 본다.
7. **요구가 늘 때의 길.** 05에서 relay는 4회가 승인 전에 터미널로 요구를 더했고(결정 기록에 [사람]으로 남음, 좋음), 1회가 의도 정리로 되감았다(5.3분, 세션 6). 의도의 비목표와 새 요구가 부딪히는 것(05 relay#2, #4)을 되감기 없이 풀 길이 필요한지 본다.
8. **여러 버그를 한 번에(07).** Work를 둘 만드는 부담, 두 Work가 동시에 돌았는지, "요청을 버그별 Work 여러 개로 나누기"가 필요한지.
9. **익숙한 사용자와 실제 사람.** 매 실행이 처음 쓰는 사람이라 R8 같은 처음 부담이 크게 잡혔을 수 있다. 같은 사람 역할이 Work를 여러 개 이어서 하는 변형, 가능하면 실제 사람 몇 명으로 확인한다.
10. **더 크고 어려운 버그.** relay의 단계와 승인이 값을 하는 영역이 있는지(E7).

## 7. 개선하면서 지킬 것

relay가 확실히 나았던 것이다. R1처럼 절차를 줄이는 변경은 아래를 잃지 않는지 같은 지표로 확인한다.

- **회귀 시험을 기본으로 더한다.** 판정 tests relay 4.2~5.0 대 CLI 1.0~4.2(04~06은 4.9 대 1.2). CLI는 시험을 더할 때와 안 더할 때가 갈렸다. 04와 06은 5회 모두 더하지 않았고(tests 1.0), 07 cli#2와 08 cli#5는 사람이 따로 요청해야 더했다. relay는 fix의 재현 시험(수정 전 실패, 수정 뒤 통과)과 verify의 수정 전 코드 확인이 기본이라 사람이 잊어도 남는다(`skills/fix/SKILL.md`). 결과(가림) 선호 relay 27 · CLI 2의 대부분이 여기서 나온다.
- **단계 요약, diff, 판정표로 얻는 결과 확신.** confidence relay 33 · CLI 0 · 비김 7. relay 사람 역할의 [좋음]은 거의 모든 실행에서 "요약, 변경 diff, 판정표를 보고 승인할 수 있었다"였다. R1에서 승인을 줄여도 Work 완료 화면의 판정표와 전체 diff는 그대로 둔다.
- **되감기 전 미리보기.** "되감기 전에 폐기될 산출물, 되돌릴 커밋, 백업 브랜치를 미리 보여 줘서 안심하고 눌렀다." (05 relay#1). 승인 전에 더한 요구가 결정 기록에 [사람]으로 남는 것도 좋게 봤다(05 relay#3, #5).
- **열린 질문으로 사람만 아는 정보를 끌어낸다.** 08에서 relay 5/5 대 CLI 0/5. R6은 이 흐름을 쓰기 쉽게 하는 것이지 줄이는 것이 아니다. R1의 자동 승인도 열린 질문이 있으면 멈추는 조건(4.3)을 지킨다.
- **의도 승인에서 방향을 바로잡을 수 있다.** 07 relay#2는 에이전트가 짝수 개 중앙값을 범위 밖으로 둔 것을 의도 단계에서 바로잡았다. R1에서도 의도 승인은 남긴다.
- **Work마다 브랜치가 따로 생긴다.** 07에서 relay 5/5회가 Work마다 브랜치가 따로 생겨 두 버그가 섞이지 않은 것을 좋은 점으로 꼽았다("브랜치와 커밋이 자연스럽게 분리됐고", relay#1).
