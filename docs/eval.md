# relay 대 맨 CLI 사용성 평가

- 상태: 사용 중. 평가 보고서는 `app/eval/reports/`에 있다(지난 것은 `reports/archive/`)
- 코드: `app/eval/`
- 새 세션에서 돌리기: `.claude/skills/relay-eval/SKILL.md` (예: "시나리오 3번으로 5번 돌려서 평가해줘")
- relay-v3 평가: relay-v3의 M2 평가 규약(`relay-v3/docs/experiments/m2/protocol.md`)이 이 도구에 relay-v3 쪽과 아래 2·3·4·6·7절의 옵션을 더해 쓴다

## 1. 목적

버그 수정, 기능 추가(relay D232), 리팩터링(relay D258), 일반(relay D302)에서 relay가 Claude Code CLI를 그냥 쓰는 것보다 얼마나 쓰기 좋은지 본다. 지식 관리는 같은 레포에서 Work 여럿을 잇는 시나리오(21~24, 개발용 25~27)로, 지식을 켠 relay와 끈 relay(또는 다른 빌드)를 견준다. 지식 관리 실험의 규약과 주지표는 `docs/knowledge-experiment/protocol.md`에 있다. 여러 상황(시나리오)을 두 쪽으로 똑같이 돌리고, 사람의 판단은 AI가 대신한다. 결과는 경향을 보는 자료다. 사람 역할과 판정이 AI이므로 실제 사용자 시험을 대신하지 않는다.

## 2. 구성

```
시나리오(버그 레포 + 숨긴 시험 + 사람이 아는 것)
  ├─ relay 쪽: 빌드한 Electron 앱(out/)을 가상 화면에 띄우고 Playwright로 누른다
  ├─ relay-off 쪽: relay와 같고 앱에 RELAY_KNOWLEDGE=off를 준다(지식 관리를 끔, Work 여럿을 잇는 시나리오 21~27의 짝)
  ├─ 다른 빌드 쪽(--app 이름=폴더): eval/ref-app.sh로 만든 다른 커밋의 앱. 이름-off는 그 빌드에서 지식을 끔
  ├─ relay-v3 쪽(relay3, relay3-noreview): RELAY3_APP(기본 relay-v2 옆의 relay-v3)의 빌드한 앱. noreview는 RELAY_ABLATE=review
  ├─ relay-v3 M2.1 쪽(relay3-m21, relay3-m2p): relay3-m21은 RELAY3_APP의 빌드, relay3-m2p는 RELAY3_M2P_APP(기본 relay-v2 옆의 relay-v3-m2p)의 빌드
  ├─ relay-v3 장기 평가 쪽(relay3, relay3-m2, run-sequence.mjs): RELAY3_APP의 빌드. relay3는 앱 기본(M3 장치 켬), relay3-m2는 RELAY_M3=off
  └─ 맨 CLI 쪽: 레포 폴더의 bash(PTY)에서 claude를 띄워 둔다
사람 역할(claude -p 세션 하나) ── 화면을 보고 행동을 JSON으로 고른다
판정: 숨긴 시험, 바뀐 파일, 설문, 짝 판정(claude -p)
보고서: report.md, report.json
```

## 3. 공정하게 두는 것

- **같은 에이전트:** 두 쪽 모두 같은 claude 실행 파일(맨 CLI는 경로로 직접 띄우고, 셸의 `claude`도 PATH 맨 앞의 링크로 같은 파일을 가리킨다), 모델(`ANTHROPIC_MODEL`), effort(`CLAUDE_CODE_EFFORT_LEVEL`)다. 맨 CLI는 relay와 같게 `--dangerously-skip-permissions`로 띄운다(D17). `--cli-permission default`로 권한 확인을 켤 수 있다.
- **같은 환경:** 세션의 환경 변수를 넘기지 않고 고른 것만 넘긴다(`env -i`와 같음, 8.4). 에이전트, 사람 역할, 판정은 설정 폴더(`CLAUDE_CONFIG_DIR`)를 따로 써서 사용량을 나눠 센다. 두 쪽 모두 자동 업데이트 알림과 입력창의 흐린 추천 문구(prompt suggestion)를 끈다. 추천 문구는 화면 글자만 보는 사람 역할이 자기가 친 것으로 착각했다.
- **같은 사람:** 두 쪽의 사람 역할은 같은 모델, 같은 규칙, 같은 시나리오 정보를 받는다. 다른 것은 도구 설명서와 행동 목록뿐이다. 둘 다 "끝의 기준"(버그가 고쳐졌다고 납득하고 로컬 브랜치에 커밋됨)이 같다.
- **같은 깨우기:** 사람은 화면이 바뀌었다가 6초 동안 그대로면 깨어난다(화면이 멈춘 것을 알아챔). 스스로 기다리기로 한 시간이 지나도 깨어나고, 화면이 계속 바뀌어도 4분마다 한 번 들여다본다. relay의 OS 알림은 알림으로 보이고 사람을 깨운다(relay만 가진 기능이므로 그대로 둔다). relay 화면에서 시계만 따라 바뀌는 글자(진행 표시의 경과 시간, `data-tick`, relay D216)는 화면이 바뀐 것으로 보지 않는다. 시계가 도는 것으로는 사람이 멈춤을 알아채지 않기 때문이다. 사람 역할이 보는 화면 글자와 스크린샷에는 그대로 있다. 같은 까닭으로 Claude Code 터미널에서 시계만 따라 바뀌는 것(스피너 그림, 경과 시간 "12s"·"1m 5s", 깜빡이는 점)도 세 쪽(relay, relay-v3, 맨 CLI)에서 똑같이 가린다(`eval/lib/util.mjs`의 `withoutClock`). relay-v3 세션이 MCP 도구 안에서 사람의 승인을 기다리는 동안 시계만 돌아 사람 역할이 최대 2분 늦게 깨던 것을 없앤 것이라, 그 전 보고서와 차례 수의 정의가 조금 다르다.
- **같은 레포(`--quality-overlay`):** 켜면 모든 쪽의 평가 레포 첫 커밋에 relay-v3 `relay init`(쓰지 않고 출력만)이 그 레포에서 내는 초안을 `.relay/quality.json`으로 넣는다. relay-v3는 레포의 품질 기준으로 증거를 재므로 이것이 없으면 증거가 비고 관문이 늘 사람 머지다. 초안은 레포 파일로만 정해져 시나리오마다 한 번 만들어 모든 쪽·회차에 같게 넣는다(기준 커밋의 트리가 같다, `run.json`의 `baseTree`). 팀원 교대의 clone은 그 커밋에서 이어진다. relay·맨 CLI에는 쓰이지 않는 파일이다. 숨긴 시험, 시나리오 정의, `check-scenario.mjs`에는 넣지 않는다. `config.json`의 `qualityOverlay`·`qualityOverlayFiles`와 `run.json`의 `options.qualityOverlay`(경로와 sha256, 끄면 false)에 남는다.
- **같은 시작점:** relay는 프로젝트가 등록된 앱에서, 맨 CLI는 레포 폴더에서 claude가 떠 있는 상태에서 시작한다. 등록과 첫 실행 창은 도구가 한다.
- **relay 설정:** 앱 설정은 바꾸지 않고 앱의 기본값으로 돈다. 지금 기본값은 fix, implement, refactor, execute를 자동 승인한다(`app/src/shared/config.ts`의 `DEFAULT_CONFIG`). M12(relay D214) 전의 보고서(`app/eval/reports/archive/`)는 자동 승인이 꺼진 기본값으로 돌았으므로 견줄 때 이것을 감안한다. 프로젝트 설정의 이슈 기록(relay D337)만 등록 직후 도구가 끈다. 평가 환경의 gh는 로그인하지 않아 게시가 늘 실패하고, 그 알림이 사람 역할의 friction으로 잡혔다(2026-10-05 평가 31). 그 전의 relay 결과는 이 알림을 본 채로 돌았다.
- **보는 것:** relay의 사람 역할은 스크린샷(요소 번호를 얹은 것), 보이는 글자, 누를 수 있는 요소 목록을 본다. 맨 CLI의 사람 역할은 터미널 화면 글자를 본다(터미널은 글자가 곧 화면이다). 둘 다 지금 보이는 만큼만 본다. 스크린샷은 창(1500×950)을 1000픽셀 너비로 줄인 것이고, 화면 배치(누를 수 있는 요소와 그 상태, 열린 대화상자)가 앞에 붙인 그림과 같으면 다시 붙이지 않는다. 글자와 요소 목록은 차례마다 준다(eval-findings E10). 사람 역할 비용을 줄여 회차를 늘리려는 것이다.
- **코드 보기:** 두 쪽 모두 `inspect_diff`로 바뀐 코드를 볼 수 있다(에디터로 훑어보는 것). 사람의 부담으로 센다.

## 4. 사람 역할

- `claude -p` 세션 하나가 한 실행 내내 같은 사람이다(`--session-id`로 시작, `--resume`으로 잇는다). 시스템 프롬프트를 바꿔 개발자 역할만 한다. 도구는 쓰지 않는다. relay의 스크린샷은 메시지에 그림으로 붙인다(도구로 읽게 하면 자주 건너뛴다). 배치가 바뀐 차례에만 붙이고, 붙이지 않은 차례에는 그렇다고 알린다(3절).
- 차례마다 `thought`, `friction`(0 매끄러움 ~ 3 막힘)과 까닭, 행동 1~5개를 JSON(`--json-schema`)으로 답한다.
- 행동: relay는 `click`, `fill`, `select`, `scroll`, 맨 CLI는 `new_terminal`, `switch`, 공통으로 `type`(터미널 입력), `key`, `inspect_diff`, `wait`, `done`, `give_up`.
- 시나리오의 사실은 "처음부터 앎"과 "물으면 답함"으로 나뉜다. 물으면 답함은 에이전트가 묻거나 꼭 필요할 때만 말한다.
- 끝나면 같은 세션에서 설문(1~7)에 답한다: 수고, 명확함, 통제감, 결과 확신, 신뢰, 복구, 다시 쓰고 싶음, 좋았던 점, 불편했던 점.
- **손 뗀 사람(`--human-mode hands-off`):** 의도·계약을 승인한 뒤 결과를 확인하지 않는다. `inspect_diff`를 쓰지 않고, 결과가 아는 사실과 어긋나도 지적하지 않으며, 에이전트가 끝났다고 하면 받아들인다. 질문에는 평소처럼 답한다. 설명서의 확인·고치기 안내보다 이 규칙이 앞서고, 끝내는 방법(완료·끝내기·끝 확정)만 설명서대로 따른다(끝내기 전에 보이는 판정표·증거·리뷰 지적도 따지지 않는다). 기계로 세는 어김(`inspect_diff`, 변경 화면 열기, 터미널의 `git diff`·`show`·`log -p`)은 `run.json`의 `human.handsOffViolations`에 둔다. 결과 폴더를 합쳐 읽을 때 이 실행은 `<쪽>-handsoff`다.
- relay-v3 쪽의 설명서는 `guides/relay3.md`(두 쪽 같음)다. 끝내기는 두 단계다: [끝내기]가 내보내기 증거와 리뷰를 돌려 [증거]에 확인 상자를 띄우고(리뷰를 끈 쪽은 '리뷰가 꺼져 있음'), 사람이 고칠 것을 세션에게 말하거나 [끝 확정]을 누른다.
- **장기 평가의 사람(5절 '장기 평가 돌리기'):** 같은 사람이 열을 잇는다. 세션은 Work마다 새로 두고 기억(앞서 한 일, 실제로 말한 규칙)을 프롬프트로 잇는다. 이미 말한 규칙은 먼저 꺼내지 않고 다시 물으면 다시 말한다(PM1). relay-v3 쪽의 끝은 세션에게 push와 PR을 시킨 뒤 [머지]이고, 빚 확인에는 늘 '빚으로 남기고 …'를 누른다(`guides/relay3-sequence.md`). 맨 CLI의 끝은 커밋이고 도구가 main에 합친다. 봉인 과제에는 사람이 없다.

**Work 둘을 잇는 시나리오(`works`):** 한 실행이 같은 레포(relay는 같은 앱과 프로젝트)에서 Work 1을 끝낸 뒤 Work 2를 한다. 사람 역할은 Work마다 새 세션이고 그 Work의 리포트와 아는 것만 받는다(같은 사람이므로 Work 1에서 알려 준 규칙은 Work 2에서도 "물으면 답함"으로 둔다). relay 쪽 사람은 앞 Work를 끝낸 뒤 같은 프로젝트에서 [새 Work]로 시작하고, 맨 CLI 쪽은 도구가 앞 터미널을 닫고 같은 레포 폴더에서 claude를 새로 띄운다. 두 번째 Work부터는 다음 Work로 넘긴 뒤 에이전트가 일한 기록(대화 기록의 메시지)이 늘지 않았으면 도구가 사람의 `done`을 받지 않고 "아직 시작하지 않았다"고 돌려준다(행동 수와 헛동작으로 세지 않고 `refusedDone`으로 세며, 보고서의 Work 표에 보인다. 맨 CLI는 새로 띄울 때 세션이 생기고 그 세션에서 일할 수 있어 새 세션이 있는지로 보지 않는다). 2026-10-02 평가에서 사람 역할이 화면에 남은 앞 Work의 완료 화면을 이번 일로 읽고 [새 Work] 없이 끝내, Work 2가 돌지 않은 채 앞 Work의 worktree로 판정된 일이 18회 중 6회 있었다. 평가는 맨 CLI의 자동 메모리를 끄지 않으므로, 그 쪽은 CLI 자체 메모리가 Work 1의 정보를 얼마나 잇는지 보는 참고다. 짝 판정은 relay 대 relay-off다(`--pairs`로 바꿀 수 있다). relay의 Work 2는 기준 브랜치(main)에서 시작하고 Work 1의 수정은 들어 있지 않으므로([완료만]은 머지하지 않음), Work 2의 숨긴 시험은 Work 2의 수정만으로 통과해야 한다.

**장기 평가(`sequence`, 48):** 같은 레포에서 요청 열을 잇고, 각 쪽이 만든 마지막 레포의 구조가 뒤 일을 얼마나 쉽게 하는지 잰다(relay-v3 `docs/m3-design.md` 6절). `works`와 같은 꼴에 이것을 더한다.

- `chain: true`: 앞 Work의 결과가 다음 Work의 기준이다. n번째 Work를 끝낸 레포에서는 1..n번째 Work의 숨긴 시험이 모두 돈다(누적 회귀, `workScenario`의 `checks`. 앞 Work의 것은 `regression: true`). 규칙이 바뀌어 옛 시험이 틀려지면 바꾸는 Work의 `retires`로 뺀다.
- `persona: "continuous"`: 같은 사람이 열 전체를 잇는다. `rules`의 규칙은 처음 드는 Work에서 '물으면 답함'이고, 그 뒤 Work에서는 '이미 말함'(`share: "told"`, `carry: true`)이다. 사람 역할은 이미 말함 항목을 먼저 꺼내지 않고, 다시 물으면 다시 말한다. 다시 말한 수가 `carriedTold`(PM1)다. 규칙이 바뀌는 Work(`changes[].work`)에서는 요청이 새 규칙을 말하므로 '처음부터 앎'이고 그 뒤는 새 글로 '이미 말함'이다(`lib/works.mjs`의 `ruleKnowledge`).
- `lines`: 줄 수를 셀 파일(glob)과 범위. `bait`: 처음부터 심은 래칫 거리(파일 줄 상한, 큰 파일, 중복된 곳). 구조 지표의 기준점이다.
- `sealed: { dir, tasks }`: 봉인 과제. `<dir>/tasks.json`의 `tasks[]`가 `{ id, type, report, checks, retires }`이고, 숨긴 시험은 `<dir>/hidden/`, 정답은 `<dir>/reference-<id>.patch`다. 과제는 요청 열이 끝난 뒤 각 쪽의 마지막 레포에서 같은 기준 에이전트가 사람 없이 하므로 `report`가 혼자 다 말한다. 판정은 그 과제의 시험과, 마지막 Work의 누적 시험 가운데 과제의 `retires`를 뺀 것이다(과제 전 마지막 main에서 이미 실패하던 누적 시험은 세지 않는다).
- 정답은 Work마다 `reference-<n>.patch`이고 앞 정답을 쌓은 레포 위의 diff다. `check-scenario.mjs`가 확인한다: 기준에서 모든 숨긴 시험이 실패, n번째 Work의 시험은 `reference-1..n-1`에서 실패하고 `reference-1..n`에서 누적 시험과 `npm test`가 통과, 기준과 마지막 레포의 줄 수가 `lines` 안, 봉인 과제마다 마지막 레포에서 실패하고 정답을 얹으면 통과(누적 시험도). 봉인 과제는 이름과 출력을 찍지 않고 수만 찍는다.
- 봉인: 숨긴 시험(`hidden/`), 정답 패치(`reference-*.patch`), 봉인 과제 폴더(`sealed/`)는 트리에 평문으로 있다. relay-v3 설계자는 결과를 고정할 때까지 이 셋을 열지 않는다(M2.1 규약의 H2와 같음). 요청 글, 규칙, 레포는 열어도 된다.
- `run.mjs`는 장기 평가를 돌리지 않는다(고르면 막는다). 도는 길은 `run-sequence.mjs`다(아래).

**장기 평가 돌리기(`run-sequence.mjs`, relay-v3 `docs/m3-design.md` 6·7절):** 쪽은 `relay3`(relay-v3 앱 기본: M3 장치 켬), `relay3-m2`(같은 빌드에 `RELAY_M3=off`: M3 장치 모두 끔, relay-v3 `engine/m3.ts`·V39), `cli`(맨 claude CLI)이고, 정한 규모는 요청 15개 × 3쪽 × 3회 = Work 135개다. 쪽 × 회차 하나(줄)마다 레포 하나에서 Work를 차례로 한다. 정한 것:

- **Work 하나 = episode 한 번.** Work마다 쪽을 새로 띄운다: relay-v3는 같은 앱 저장소(`RELAY_HOME`: 프로젝트 등록, Work 기록, 실적 장부)로 앱을 다시 켜고(첫 Work만 프로젝트를 등록), 맨 CLI는 같은 레포 폴더(main)에서 claude를 새로 띄운다. 에이전트 설정 폴더는 줄 내내 하나다(Claude Code 프로젝트 메모리가 이어진다). relay-v3 쪽의 뒤 Work는 앞 Work의 worktree·브랜치·스냅숏을 그 Work의 판정 폴더와 사람 역할의 '바뀐 코드'에 넣지 않는다(squash로 넣은 앞 브랜치는 지금 main과 달라 뒤 Work의 변경이 거꾸로 보였다). 사람 역할의 '바뀐 코드'와 판정의 diff 기준은 그 Work를 시작한 main의 트리다.
- **결과를 기준 브랜치에 넣기.** relay-v3 쪽은 앱의 머지 흐름을 쓴다(앱의 실적 장부가 머지를 본다): 사람 역할이 세션에게 작업 브랜치 push와 PR 열기를 시키고 [증거]의 [머지]를 누른다(`guides/relay3-sequence.md`). 앱(`RELAY_GH_BIN`)과 세션(PATH 맨 앞의 `gh`)이 쓰는 gh는 `lib/fake-gh.mjs`다: relay-v3 가짜 gh(v2 녹화본 모양)에 넘기고, `pr merge`만 원격(로컬 bare)의 main에 머지 방식대로(기본 squash) 실제로 넣는다(충돌이면 GitHub처럼 머지할 수 없음). 앱은 fetch하지 않으므로 Work가 끝나면 도구가 레포에서 fetch하고 main을 맞춘다. 앱으로 머지되지 않은 Work 브랜치(시간 제한, [끝내기]로 끝남)는 도구가 머지하고 `landing.via`에 `harness`로 적는다(버린 Work는 넣지 않음). 그 Work의 worktree에 커밋하지 않은 변경은 cli와 같게 먼저 그 브랜치에 커밋한다(`leftovers`. 같은 끊긴 상태가 쪽에 따라 다음 Work의 기준을 다르게 만들지 않게). 맨 CLI는 도구가 커밋하지 않은 변경을 커밋하고(`leftovers`), main 밖 브랜치 가운데 main에 없는 커밋이 있는 것을 오래된 차례로 main에 머지해(충돌하면 뒤 브랜치 쪽 `-X theirs`) push한다.
- **누적 숨긴 시험.** 넣은 뒤 main의 트리에서 그 Work까지의 숨긴 시험(`activeChecks`, `retires`를 뺌)을 돌린다. Work마다 `cumulative { total, pass, own, regression, broken }`. 결과에는 시험 이름과 통과만 남기고 출력은 남기지 않는다(봉인). 판정 폴더(숨긴 시험을 겹친 사본)는 줄의 작업 폴더 밖 임시 폴더에 두고 판정이 끝나면 지운다: 작업 폴더에 남으면 다음 Work의 에이전트가 레포 위에서 지금과 뒤 Work의 숨긴 시험을 읽을 수 있고, 닿는 깊이가 쪽마다 다르며, 체크포인트에서 이어 돈 줄만 그것을 잃는다.
- **한 사람 역할과 기억.** 같은 사람이 열을 잇는다. 사람 역할 세션은 Work마다 새로 두되(화면이 쌓여 맥락이 넘치지 않게, 컨테이너가 다시 떠도 이어 가게), 기억(`state.json`의 `memory`)을 다음 Work의 프롬프트에 넣는다: 앞서 한 일(요청 첫 줄과 끝)과 실제로 말한 규칙. 규칙은 사람이 그 글을 실제로 말했으면(다시 알려 줌의 감사, 없으면 자기 보고) 다음 Work에서 '이미 말함'이고, 규칙이 든 Work에서 에이전트가 묻지 않아 말하지 않았으면 다음에도 '물으면 답함'이다(`lib/sequence.mjs` `personaKnowledge`. 정적인 `ruleKnowledge`와 다른 점). 바뀌는 Work는 요청이 새 규칙을 말하므로 '처음부터 앎'이고 끝나면 새 글로 말한 것이다. 이미 말한 규칙을 다시 말한 수가 PM1(`carriedToldAudit`, 없으면 `carriedTold`)이다.
- **빚 확인 규칙(M3b).** 앱이 [머지]나 [그래도 끝내기]에서 '빚으로 남기고 …' / '그냥 …'을 물으면 사람 역할은 늘 '빚으로 남기고 …'를 누른다(`DEBT_RULE = always-record`, 설명서에 적음). 사람마다 다른 판단이 장치의 효과와 섞이지 않게 고정한다. 장부의 '받아들였지만 기록하지 않음'은 그래도 생길 수 있다(앱 밖 머지, 도구의 머지, 사람 역할이 규칙을 어김).
- **봉인 과제.** 모든 Work가 끝나면 줄의 마지막 main을 새로 clone한 사본에서 과제마다 기준 에이전트를 돌린다: 맨 `claude -p --dangerously-skip-permissions`, 쪽과 상관없이 같은 모델·effort(`--baseline-model`, `--baseline-effort`, 기본 sonnet·medium)·시간 제한(`--baseline-minutes`, 기본 30)·프롬프트(과제의 `report`와 '물을 수 없으니 끝까지 하고 커밋한다' 한 줄), 사람 없음. 판정은 과제의 시험(`sealed/hidden`)이 모두 통과하고, 마지막 Work의 누적 시험 가운데 과제의 `retires`를 뺀 것 중 과제 전 마지막 main에서 통과하던 것이 모두 통과하면(기준 에이전트가 깨뜨리지 않으면) 통과다. 과제 전부터 실패하던 누적 시험은 `kept.preBroken`에 수만 남기고 통과에 세지 않는다(그것은 C2가 센다. 세면 한 번 깨진 시험이 그 줄의 봉인 과제를 모두 실패로 만들어 S1이 C2를 되풀이한다). 기준 에이전트가 깨뜨린 수는 `kept.broke`. 토큰(대화 기록), 걸린 시간, 비용을 남긴다. 과제의 시험은 차례 번호와 통과만 남긴다. 기준 에이전트는 쪽의 작업 폴더 밖, 쪽 이름도 회차도 없는 새 임시 폴더(`task-XXXXXX/repo`)에서 돌고(Claude Code는 cwd를 시스템 프롬프트에 넣는다), 판정은 다른 임시 폴더에서 하며 둘 다 과제가 끝나면 지운다(앞 과제의 판정, 쪽의 앱 저장소·대화 기록에 닿지 않게). 폴더를 떼어 둘 뿐 같은 사용자의 파일 읽기는 막지 못하므로(시나리오 폴더의 숨긴 시험은 디스크에 평문으로 있다) 대화 기록의 도구 호출 가운데 평가의 자리(시나리오 폴더, `relay-eval`·`relay-judge-`·`relay-final-` 임시 폴더, 사람 역할·감사의 설정 폴더 이름, `eval/results`, 결과·체크포인트 폴더, 환경 변수 `RELAY_EVAL_MARKS`(':'로 나눈 경로: 배치 전에 옮겨 둔 시범 결과 등) 등)를 가리킨 수를 `outside { calls, reach, seen, github }`에 남기고(`seen`은 도구 결과의 글에 평가 자리가 보인 수: `ls ..`이 사람 역할 폴더 이름을 보여 준 것 등, `github`는 `github.com`을 가리킨 호출: 에이전트 프록시가 api.github.com을 통과시킨다), `m3-primary.mjs`의 줄 표에 `reach`가 0이 아닌 과제를 보인다(격리 감사). 상대 경로·와일드카드로 닿은 것은 입력에 표시가 없어 `reach`가 놓친다. 기준 에이전트가 돌지 못하면(`ending: error`: API·CLI 오류) 과제의 실패가 아니라 도구 문제로 멈추고 `--retries`로 그 과제부터 다시 한다. 시간 초과는 과제의 실패다(`pass: false`, 레포에 남은 것이 시험을 통과해도). 판정은 기준 에이전트가 커밋하지 않은 변경도 든 작업 트리로 한다(`uncommitted`에 수). 기준 에이전트는 프로세스 묶음으로 띄우고 끝나거나 시간이 넘으면 묶음째 죽인다(남은 자식 프로세스가 판정 중에 레포를 바꾸지 못하게).
- **Work 에이전트의 격리 감사.** 사람 역할의 설정 폴더(`cfg-human-N`: 그 Work의 '물으면 답함' 규칙이 든 사람 역할 프롬프트), 감사 폴더(`told/`), 사람 역할의 화면(`human/`)이 줄의 작업 폴더에 있어 레포의 위(cli는 한 층, relay-v3 worktree는 세 층)에서 닿는다. Work마다 에이전트 설정 폴더(`cfg-agent`)의 대화 기록을 같은 방식으로 세어(자기 레포, 원격, 앱 저장소, 가짜 gh, claude 심은 지운 뒤. 다른 줄의 작업 폴더와 시나리오·결과·체크포인트 폴더는 평가의 자리) 그 Work의 몫을 `sequence.json`의 `outside`에 남기고 줄 표에 합을 보인다. Work마다 넣은 main의 규칙 승격(`rules`: `docs/knowledge`의 `kind: rule` 항목, `check:`, `.relay/quality.json`의 `rules`, 승격된 검사)도 남긴다(V42 '쓸모없음'). 구조 지표에는 에이전트의 프로젝트 메모리(`agentMemory`: 작업 폴더 키 수, 메모리가 있는 키, 파일 수)를 더한다.
- **구조 지표(보조).** 마지막 main과 기준 레포에서: `lines.include`의 줄 수와 가장 긴 파일, 상한(`bait.maxLines`)을 넘는 파일 수, `src/**/*.js`의 6줄 창 글 중복 비율, 두 파일 이상에 정의된 같은 이름의 함수 수(48의 금액 표시처럼 글은 달라도 이름이 같은 도우미). relay-v3 쪽은 장부의 받아들임·기록, 마지막 레포의 `.relay/debt`·`docs/knowledge`도.
- **Work마다 지표.** episode의 Work 결과(사람의 부담, 다시 알려 줌과 감사, 설문, 그 Work에서 생긴 에이전트 세션의 토큰 + 그 Work의 앱 Work가 부른 독립 리뷰)에 더해, relay-v3 쪽은 그 Work에서 생긴 앱 Work마다 관문 요약, 끝(`end`), 장치 지표(M2.1 지표와 끝의 까닭 `endReasons`: `ended.how` once·armed·box·handed, 넘긴 끝, 푼 까닭 human·contract·human_input·hand_failed, `ended.memos`)와 M3 지표(`m3`: 스위치, 기록 안 된 나빠짐, request.md의 관련 지식·기록 안 된 나빠짐·이 레포의 빚 항목 수, 지식 확인, 근거 knowledge, 빚 기록·덮음, 곁들일 정리, 끝낼 때 메모)와 장부.
- **이어 돌기.** 걸음은 Work 하나, 봉인 과제 하나, 구조 지표다. 걸음이 끝날 때마다 줄의 작업 폴더와 결과 폴더를 체크포인트 하나(`<checkpoints>/<시나리오>/<쪽>-<회차>.tar.gz`, 같은 절대 경로로 풂)로 쓴다(판정 폴더, 스크린샷, 사람 역할 설정, 에이전트 대화 기록, node_modules는 뺀다). 같은 `--out`으로 다시 돌리면 끝낸 걸음은 건너뛰고, 걸음 중간에 끊겼거나(state의 `inProgress`) 결과 폴더가 없으면(컨테이너가 다시 뜸) 마지막 체크포인트를 풀어 그 걸음부터 다시 한다. 작업 폴더는 `/tmp/relay-eval/<결과 폴더 이름>/`이라 같은 `--out` 이름이면 경로가 같다. 컨테이너가 다시 떠도 남게 하려면 `--checkpoints`를 git 체크아웃 안에 두고 `--archive-push`를 붙인다(걸음마다 커밋·push, relay-v3 `docs/experiments/m2.1/run-batch.sh`와 같은 방식, 끝에 붙일 줄은 `RELAY_BATCH_TRAILER`). 결과 폴더도 체크포인트에 들어 있다. 도구 문제(harness_error, human_error)로 멈춘 줄은 이번 실행 안에서 체크포인트부터 `--retries`(기본 1)번 다시 한다. 걸음 하나의 시도는 이어 돌기를 넘어 `state.json`의 `attempts`로 세고 `--max-attempts`(기본 3)를 다 쓰면 그 줄은 멈추고 다시 하지 않는다(명령을 다시 돌려도 같다). 시도마다 까닭을 `failures`에 남긴다: `tool_error`(도구 문제로 멈춤, 오류 글 앞 300자)와 `restart`(끊겨서 다시: kill, 컨테이너가 다시 뜸). 집계가 다시 한 걸음과 까닭을 줄마다, 쪽마다 보인다. 끝내지 못한 줄을 처음부터 새 회차로 다시 돌릴 때는 `--first-run`(예: `--arms relay3 --first-run 4 --runs 1`이면 `relay3-4`)을 준다. 이어 돌 때 모델·시간 제한(`--max-minutes`)·차례 제한(`--max-turns`)·기준 에이전트·덧씌우기 같은 고정 값이 앞 `config.json`과 다르거나, relay-v3 쪽이 있는데 앱 빌드(`RELAY3_APP`의 commit)가 바뀌었으면 멈춘다. 고정 값과 빌드의 확인은 결과 폴더의 `config.json`으로 하고, 결과 폴더가 없어졌으면(컨테이너가 다시 뜸) 체크포인트 폴더의 사본(`<checkpoints>/<시나리오>/config.json`, 돌 때마다 쓰고 `--archive-push`면 커밋·push)으로 한다. 평가 도구의 commit, 앱 commit, claude 버전은 시작과 이어 돌 때마다 `config.json`의 `builds`에 쌓는다(덮어쓰지 않는다).
- **품질 기준 덧씌우기.** 기본으로 모든 쪽의 첫 커밋에 relay-v3 `relay init` 초안의 `.relay/quality.json`을 넣는다(M2·M2.1 규약과 같음. 빚 기록은 래칫이 있어야 묻는다). `--no-quality-overlay`로 끈다.
- **건식(`--dry`).** 사람 역할과 에이전트 대신 그 Work의 정답 패치를 얹는다(relay-v3 쪽은 작업 브랜치 push, 가짜 gh로 PR 열기와 squash 머지까지), 봉인 과제는 과제의 정답을 얹는다. 모델을 부르지 않고 앱을 띄우지 않는다. 도구의 길(차례, 넣기, 누적 시험, 기억, 체크포인트, 봉인 과제, 구조, 집계)을 확인할 뿐 결과가 아니다. 평가 도구에는 사람 역할까지 대신하는 가짜 claude가 없다.
- 결과: `<out>/<시나리오>/<쪽>-<회차>/`에 `state.json`, `work-NN/`(episode의 `run.json`, `turns.jsonl`, 앱 Work 기록, `sequence.json`), `sealed-<id>.json`, `structure.json`, `run.json`(모음). 집계는 `m3-primary.mjs`(6절).

**팀원 교대(`teammate: true`):** 그 Work 전에 도구가 앞 사람 레포의 브랜치 가운데 main에 없는 커밋이 있는 것을 오래된 차례로 main에 머지하고(PR 머지 흉내, 충돌하면 뒤 브랜치 쪽으로 머지하고 `handoffs`에 적음), 팀 원격(bare)에 올린 뒤 새로 clone한다. relay는 새 앱 저장소(`RELAY_HOME`)와 새 Electron 사용자 폴더로 그 clone을 프로젝트로 등록해 두고, 맨 CLI는 그 폴더에서 claude를 새로 띄운다. 커밋하지 않은 변경과 앱 저장소에만 있는 것은 건너가지 않는다. 레포 경로가 바뀌어 Claude Code의 프로젝트 메모리도 이어지지 않는다. 사람 역할은 Work를 [완료만]으로 끝내므로 Work 브랜치에 커밋된 것만 다음 사람에게 간다. 팀원 교대 뒤의 Work는 앞 Work의 정답이 머지된 상태에서 판정하므로, `check-scenario.mjs`가 `reference-1..n`을 차례로 모두 적용해도 모든 시험이 통과하는지 확인한다.

**다시 알려 줌(`told`):** 사람 역할은 차례마다 "네가 아는 것"의 몇 번 항목을 새로 알려 줬는지 `told`에 적는다(에이전트가 먼저 꺼낸 것을 맞다고만 한 것은 빼고). Work마다 `told`, `carriedTold`(다시 알려 준 carry 항목 수), `carriedTotal`을 `workResults[].human`에 둔다.

**처음에 다 말하지 않는 사람(`recall`):** 실제 사람은 주요 요구만 짧게 말하고 세부 사항은 그때 떠올리지 못한다. 에이전트가 그 경우를 짚어 주면 떠올려 답하거나, 결과물에 드러난 것을 보고 알아챈다. 이것을 재려면 `report`는 사람이 실제로 할 만큼만 짧게 쓰고, 세부 사항은 `share: "recall"`로 둔다. 사람 역할은 이 항목을 처음 요청에도, "더 고려할 것 있나요?" 같은 일반적인 물음에도 꺼내지 않고, 에이전트가 그 경우나 차이를 구체적으로 짚었을 때만 답한다. 결과를 볼 때도 일부러 대조하지 않고 화면에 드러난 것만 알아채며, 한 항목이 떠올랐다고 다른 항목까지 말하지 않는다(`lib/human.mjs`). `on_ask`는 사람 역할이 결과를 자기가 아는 사실과 대조해 먼저 지적할 수 있어, 묻지 않은 쪽도 한 번 바로잡고 끝나기 쉽다(10에서 맨 CLI가 그랬다). 31의 첫 평가(2026-10-05)는 이 규칙을 `on_ask` 글로 적어 돌렸고, 사람 역할이 짚지 않은 항목을 먼저 말한 일이 한 번 있어 전용으로 바꿨다. 세부 사항이 코드의 차이로 드러나 있으면 맨 CLI도 결과에서 짚어 내므로(31), 묻기를 가르려면 코드만 봐서는 알 수 없고 흔한 구현이 틀리는 사실을 `recall`로 둔다(32).

시나리오 폴더에 `reference.patch`(정답 수정)와 `traps/*.patch`(그럴듯한 틀린 수정)를 둘 수 있다. Work 둘을 잇는 시나리오는 Work마다 `reference-<n>.patch`를 둔다. `repo/`를 뿌리로 한 git diff이고, 평가 도구는 `repo/`만 복사하므로 에이전트에게 보이지 않는다. `node eval/check-scenario.mjs <id>`가 확인한다: 기준에서 `npm test`와 guard는 통과하고 나머지 숨긴 시험은 실패, 정답 패치에서 모두 통과, 함정 패치마다 숨긴 시험 하나 이상 실패. 숨긴 쟁점은 모델이 가르므로 여기서는 돌리지 않고 모양만 본다(설계 시나리오의 함정은 코드를 바꾸는 패치라 범위 guard가 깨진다). `reference-<n>.patch`는 그것만 적용하면 n번째 Work의 숨긴 시험과 guard, `npm test`가 통과하고 다른 Work의 guard가 아닌 숨긴 시험은 실패해야 한다(Work마다 고칠 것이 갈림). 09~14의 설계는 `docs/archive/eval-hard-scenarios.md`에 있다.

## 6. 판정과 지표

- **Work 둘을 잇는 시나리오:** 위 지표는 실행 전체로 세고, Work마다 따로 숨긴 시험(relay는 그 Work에서 생긴 worktree, 맨 CLI는 레포와 브랜치 모두로 판정), 사람 차례·행동·입력, 에이전트 질문 수(대화 기록의 `AskUserQuestion` 도구 호출), 그 Work에서 생긴 에이전트 세션의 토큰, relay의 `context.md` 글자와 넣은 지식 글자(앱이 task 폴더에 `knowledge-injected.md`를 남기면 그 글자, 없으면 `context.md`의 `## 참고 지식` 절)를 `run.json`의 `workResults`에 둔다. 보고서는 Work마다 표를 두고 재는 Work(`measure`)를 앞에 보인다. 설문은 Work마다 하고, 짝 판정은 마지막 Work의 설문을 본다.
- **relay의 지식 파일(`docs/knowledge/*.md`, relay D283):** 앱이 verify에서 남기는 팀 지식이라 코드 결과로 보지 않는다. 바뀐 파일과 줄 수, 기대 밖 파일, 결과 판정의 코드 차이에서 빼고 "지식 파일 수(판정에서 뺌)"로 따로 센다(`eval/lib/repo.mjs`의 `KNOWLEDGE_FILE`). 맨 CLI에는 없는 파일이라 판정에 두면 결과 판정의 가림도 깨진다. 2026-10-04 M18 평가에서 판정 모델이 이 파일을 범위 밖 변경으로 보고 relay의 scope를 깎아 바꿨다. 저장하는 `final/*.diff`에는 그대로 두어 지식의 질은 `knowledge-quality.mjs`가 따로 본다. 그 전에 돌린 결과도 `report.mjs --rejudge`로 같은 규칙으로 다시 판정할 수 있다.
- **결과(자동):** 숨긴 시험, 레포 시험, 바뀐 파일과 줄 수, 기대 밖 파일, 커밋 여부. relay는 Work마다 worktree가 있으므로 결과 폴더가 여럿일 수 있다. 맨 CLI도 에이전트가 버그마다 브랜치를 나누면 고친 것이 흩어지므로, 평가 레포(체크아웃된 브랜치)에 더해 체크아웃되지 않은 로컬 브랜치 가운데 기준 뒤에 커밋이 있고 HEAD에 아직 들어 있지 않은 것을 `git archive`로 꺼내 결과 폴더로 삼는다. 고친 것을 보는 시험은 한 곳에서라도 통과하면 통과이고, `guard` 시험은 바뀐 결과 폴더 모두에서 통과해야 통과다(바뀐 폴더가 없으면 모든 폴더). worktree가 [Work 정리]로 지워져도 판정할 수 있게 사람의 차례마다 복사해 둔다.
- **사람의 부담(자동):** 차례 수, 행동 수, 입력 글자 수, 코드 보기, 헛동작(쪽이 실패로 돌려준 행동: 없는 요소, 열린 터미널 없음 등), friction, 걸린 시간.
  - 걸린 시간에는 평가 고리가 사람 역할(AI)의 답을 기다린 시간이 들어 있다. 보고서는 사람 역할 응답 시간의 합과 그것을 뺀 시간을 따로 보인다. 기다리기만 한 차례(행동이 `wait`뿐이거나 없음)도 센다. 진행 표시(relay D216)처럼 화면이 계속 바뀌면 깨우는 횟수가 기계적으로 달라지므로, 개선 전후는 이 줄과 사람 역할의 말로 견준다(eval-findings E2).
  - 스크린샷을 붙인 차례 수(relay만)를 센다(E10).
- **에이전트(자동):** 설정 폴더의 대화 기록에서 토큰(같은 메시지 id는 마지막 줄 하나. Claude Code는 메시지 하나를 여러 줄에 쓰고 앞 줄의 출력 토큰은 다 세지 않은 값이다), 세션 수.
  - 앱이 따로 부른 `claude -p`(relay-v3 독립 리뷰, relay 독립 리뷰·지식 검토)는 대화 기록을 남기지 않으므로(`--no-session-persistence`) 앱의 기록으로 세어 에이전트 토큰(입력, 출력, 캐시 읽기·쓰기)에 더하고 그 몫을 `agent.review`에 따로 둔다. relay-v3는 Work의 `events.jsonl`의 `review` 기록의 `usage`, relay는 task 폴더의 `independent-review.json`·`knowledge-review.json`이다. 세션 수와 메시지 수에는 넣지 않는다. 사용량을 알리지 못한 리뷰(시간 초과 등)는 `usageUnknown`으로 센다.
  - relay는 task마다 세션 id로 대화 기록을 맞춰 단계별 토큰(입력(캐시 포함), 캐시 쓰기, 출력)과 `context.md` 글자 수를 `run.json`의 `agentSteps`에 두고, 보고서의 "relay 단계별 에이전트" 표에 단계마다 평균으로 보인다(eval-findings R9). 대화 기록을 찾지 못한 세션은 빼고 센다.
- **설문:** 4절.
- **relay-v3 쪽(자동):** Work마다 계약 승인, 관문 결론(마지막 evidence 기록이 내보내기이고 그 head가 내보낸 head이자 끝낸 때의 worktree HEAD면 내보내기 결론. G1·G2는 이것만 센다), 리뷰 호출·토큰, 리뷰 뒤 세션이 더 일했는지, Work의 끝(`end`)을 `run.json`의 `works`에 둔다. 끝은 `confirmed`([끝 확정]), `merged`·`closed`(PR), `prepared`([끝 확정] 없이 끝났지만 끝낸 커밋이 내보내기 증거·리뷰를 받은 그 커밋이고 커밋하지 않은 변경이 없음), `stale`([끝내기] 뒤 커밋이 더 생겼거나 커밋 안 된 변경이 남음), `abandoned`, `null`([끝내기] 없음)이다. 끝의 기준은 커밋된 상태라 앞의 넷을 relay@auto의 [Work 완료]와 같은 수준의 끝으로 센다(`ended`). 사람 역할의 `done`은 쪽과 상관없이 받고([끝 확정]·[Work 완료]를 누르지 않았어도), 숨긴 시험은 다른 쪽처럼 worktree 그대로로 판정한다.
- **장기 평가(`m3-primary.mjs`, relay-v3 `docs/m3-design.md` 6절):** 분석 단위는 줄(쪽 × 회차)이다. 주지표: S1 봉인 과제 통과율, S2·S3 봉인 과제의 기준 에이전트 입력 토큰(천, 캐시 포함)과 걸린 시간(뒤 Work 비용), C1 누적 숨긴 시험 통과(Work마다 비율의 평균), C2 마지막 Work 뒤 통과 비율, PM1 다시 말하기(열 전체 수). 보조: T1 가장 긴 파일, T2 상한을 넘는 파일, T3 중복 줄 비율, T4 같은 이름의 함수, W1·W2 Work당 에이전트 토큰·사람 차례. 쪽마다 평균, 짝(relay3 − relay3-m2, relay3 − cli, relay3-m2 − cli)의 차이와 bootstrap 95% 구간(시나리오마다 층, M2·M2.1과 같은 `compare`), 동등 판정(±δ, `equivalence`)을 좋은 방향에 따라 좋음·나쁨·같음·모름으로 읽는다. 두 쪽의 모든 줄이 같은 값이면 '판정 없음(천장·바닥·모두 같은 값)'이다(같다는 증거가 아니다). n=3에서 percentile bootstrap은 구간이 좁으므로(같은 분포에서 뽑아도 95% 구간이 0을 비키는 일이 약 20%) 줄 셋 대 셋의 정확한 순열 p(20가지 나눔, 가장 작은 양쪽 p 0.1)를 함께 보이고, 판정 규칙에 드는 지표(S1·C1·C2·PM1, `decides`)의 좋음·나쁨은 순열 p가 0.1 이하이고 쪽마다 다 한 줄이 둘 이상일 때만 '규칙에 듦'이다. S2·S3·C3·T·W는 보고만이다. δ는 제안(S1·C1·C2 10%포인트, PM1 1회, T1 50줄, T2 1개, T3 0.01, T4 1개, 나머지는 0을 넘는지)이고 규약에서 결과 전에 고정한다. 덜 한 줄은 그 지표에서 빠진다(봉인 과제가 없으면 S, Work가 모자라면 C·PM1·W). 줄 표에는 다시 말할 기회(`carriedTotal`의 합)와 Work 에이전트의 격리 감사가 든다. Work마다 누적 통과·넣기 방식·깨진 앞 Work 시험의 수, relay-v3 쪽의 M3 장치와 끝의 까닭 표가 따른다. 장치 표는 장치만의 끄는 조건에 쓰는 셈을 분모와 함께 낸다(다 한 줄만): V38 어느 묶음에서든 형식 오류가 난 앱 Work와 그 가운데 형식 오류가 남은 채 머지된 것, V41 목록에 빚이 있던 Work의 수용, 계약 tidy id의 해결(마지막 묶음 `tidy.items`의 `status: paid`), 상한 넘음, 멀쩡한 항목(계약 tidy가 아닌데 `open`이고 detail에 relay-v3 `engine/tidy.ts` payoff의 글 '항목 파일을 지움'이 든 항목)과 그 Work의 숨긴 시험 실패의 겹침, V42 승격률(마지막 레포), '쓸모없음'(한 번이라도 승격된 검사 가운데 뒤에 빠졌거나 허용 목록이 늚을 남긴 채 머지된 것), 허용 목록이 늚과 그 머지, 말로만 남은 규칙의 추세. V35 표는 앱 Work의 끝 방식마다 수와 자기 시험 통과다. 봉인 과제는 id와 통과 수만 보인다.
- **짝 판정:** 같은 시나리오 같은 회차의 relay와 맨 CLI(`works`가 있는 21~27은 relay와 relay-off, `--pairs`를 주면 그 짝들)를 A, B로 무작위로 놓고 판정 모델이 비교한다.
  - 결과 판정(가림): 코드 차이와 시험 결과만 본다. 커밋 메시지는 보이지 않는다. correctness, scope, quality, tests (1~5), 선호. `--no-judge-purpose`(relay-v3 쪽이 돌면 늘)면 판정 모델에 시나리오의 평가 목적(무엇이 relay의 강점인지)을 주지 않는다.

## 8. 한계

- 사람 역할과 판정이 모두 Claude다. 같은 계열 모델의 편향이 있을 수 있고, AI 사람은 실제 사람보다 설명서를 잘 따르고 덜 지친다.
- 화면은 Linux 가상 화면이다. 주 플랫폼인 Windows(D12)의 글꼴과 ConPTY 차이는 보지 못한다.
- PR 진행(M9~M11)은 시나리오에 없다. 이 세션에서는 GitHub GraphQL이 막혀 gh의 PR 명령이 돌지 않는다(`spikes.md` S7). 장기 평가의 relay-v3 쪽만 가짜 gh(`lib/fake-gh.mjs`)로 PR을 열고 머지한다: CI가 없고(statusCheckRollup 빈 것), 서버 보호가 없고, 머지할 수 있는지는 충돌로만 가린다.
- 장기 평가의 사람 역할은 Work마다 새 세션이고, 이어지는 것은 기억 파일(앞서 한 일, 실제로 말한 규칙)뿐이다. 실제 사람의 흐린 기억(말했는지 헷갈림)은 흉내 내지 않는다.
- 회차가 적으면 편차가 크다. 시나리오마다 3회 이상을 권한다.
