- 상태: 진행 중. 실행 UI와 전환 범위는 확정했고 엔진 선택·기록과 Claude 실행 경계를 구현 중이다. Codex 질문 도구와 실행 경로는 아직 확정/연결 전이다.
- 작업 브랜치: `feat/claude-codex-engines`
- 출발점: `main`의 `9c02b42` (평가 도구 추가, #18).
- 작성일: 2026-09-30.

## 1. 목표와 기존 설계와의 관계

Claude 사용자는 기존 기록과 작업 흐름을 계속 쓸 수 있어야 한다. Codex 사용자도 같은 intent, 산출물, handoff, 단계 경계 승인, 되감기, Git/PR 전달을 사용한다. 엔진 선택은 파이프라인과 handoff 형식의 변경을 뜻하지 않는다.

기존 규칙은 [design.md](design.md), 구현 경계는 [implementation.md](implementation.md)를 따른다. 이 문서는 확장안을 먼저 다루며, 아직 정하지 않은 제안으로 기존 사용자 결정을 덮어쓰지 않는다. 확정한 변경은 이 문서의 E 결정 표에 기록하고, 기존 문서의 관련 절과 연결한다.

## 3. 확인한 사실과 검증해야 할 점

Codex 근거는 2026-09-30의 공식 문서와 환경에 설치된 `codex-cli 0.159.0-alpha.3`의 도움말, 기능 목록, 생성한 TypeScript 프로토콜 스키마다. 공개 저장소 main과 설치 버전은 다를 수 있다. alpha 버전을 배포 최소 버전으로 정한 것은 아니다. 실제 모델 작업과 Windows 실기는 아직 하지 않았다.

## 4. 선택 범위와 기록 (Q2 확정안)

### 4.1 설정

`config.json`에 `agent_engine: 'claude' | 'codex'`를 더한다. 필드가 없으면 Claude다. 값이 잘못되면 기존 설정 정규화 방식대로 기본값과 경고를 사용한다. 설정 화면의 저장값은 엄격히 검사한다.

처음에는 앱 기본값 한 곳에서 선택한다. 프로젝트/Work/단계별 모델, effort, 복잡한 우선순위는 이번 목표의 필수 기능이 아니다. Work별 엔진 덮어쓰기를 추가할 필요가 확인되면 별도 결정한다.

### 4.2 task 선택과 재개

task 생성 시 기본 엔진을 task 기록에 고정한다. 대기열에서 실행을 기다리는 동안 앱 설정이 바뀌어도 그 task는 바뀌지 않는다. 시작 실패 후 다시 시작해도 선택한 엔진을 유지한다.

재개는 task의 엔진과 실제 세션 ID를 사용한다. 기본 엔진을 바꿨다는 이유로 Claude의 ID를 Codex에 전달하지 않는다. 다른 엔진으로 같은 단계를 수행하려면 새 task·새 세션으로 다시 시작한다. 앱이 세션을 몰래 바꾸거나 대화 내용을 변환하지 않는다.

새 task는 승인된 intent/decisions/handoff와 현재 코드로 시작한다. 따라서 같은 Work 안에서 단계 사이 엔진을 바꿀 수 있다. 직접 입력하지 않은 대화의 내용까지 전달된다고 설명하지 않는다.

### 4.3 파일 호환

- TaskRecord에 `engine`, `engine_version`을 기록한다. Claude 실행/재개에는 `claude_version`도 함께 기록하여 이전 필드의 호환을 유지한다. Codex 버전을 Claude 필드에 기록하지 않는다.
- session ID는 벤더가 제공하는 문자열이다. PID·시작 시각은 실행 프로세스 복구용이고 ID와 구분한다.
- engine이 없는 기존 task는 Claude다. 명시된 알 수 없는 엔진은 Claude로 조용히 바꾸지 않고, 재개 불가 사유를 표시한다.
- 살아 있는 정리 세션도 엔진을 고정하고 기록한다. 추천안은 그 정리를 요청한 verify task의 엔진을 사용한다. 이 정책도 Q2 답에 맞춰 확정한다.
- 새 필드는 기존 schema_version 1에 추가한다. 기존 기록을 새 앱에서 읽는 호환을 제공한다. Codex 기록을 엔진 선택이 없는 이전 앱에서 재개하는 것은 지원하지 않는다. 이전 앱은 엔진 필드를 모르므로 실제 엔진을 보존할 수 없고, schema_version 숫자만 바꿔도 이를 막는다는 보장은 없다. 오래된 Claude 필드를 즉시 삭제하지 않는다.
- 세션 시작 전에 종료된 Codex task에는 임의 UUID로 재개 가능한 세션이 있는 것처럼 기록하지 않는다. 실제 ID를 받기 전과 후를 구분한다.

## 5. 실행 경계 (Q1 확정안)

`main/work`는 task 디렉터리, context, 검사, 상태 저장, Git 작업을 맡는다. 엔진별 어댑터는 실행 파일 점검, 지시·설정 준비, 새 세션/재개/정리 실행, 벤더 이벤트 변환을 맡는다. 순수한 옵션 생성은 core 쪽에 두어 기존 I9를 지킨다.

예상 경계:

```text
설정 + task 기록
  → 엔진 선택
  → Claude/Codex 어댑터: 설치·인증·버전·설정·실행 인자
  → 공통 PTY/로그/파일 감시/프로세스 관리
  ← Claude HTTP 훅 / Codex command·MCP 훅 브리지
  → 벤더 이벤트 변환
  → 공통 내부 이벤트 → 상태 기계 → 승인·다음 task
```

두 어댑터가 서로 다른 구현을 가져도 PTY와 상태 저장은 공통으로 둔다. 원시 벤더 payload를 core로 넘기고 벤더별 분기를 계속 늘리는 방식은 피한다. 기존 Claude 이벤트 순서와 동작은 회귀 시험으로 유지한다.

내부 이벤트 후보는 `turn.started`, `question.started`, `question.finished`, `input.required`, `turn.completed`, `session.identified`, `session.ended`다. 세션 실행 인스턴스 식별자를 함께 보아 앞 프로세스의 늦은 이벤트를 새 세션에 적용하지 않는다(D144).

### 5.1 Codex 훅 브리지

command 훅은 stdin JSON을 받아 앱의 기존 로컬 서버에 전송하고, 서버의 JSON 응답을 stdout으로 반환한다. task 토큰은 환경 변수로만 넘긴다. 다른 task의 ID나 앞 프로세스에서 온 응답을 적용하지 않는다.

브리지는 별도 Node 설치를 새 필수 조건으로 만들지 않는 배포 방법을 검증한다. 개발 환경의 `node`에서만 동작하는 결과로 Windows 설치본 지원을 선언하지 않는다. 훅 timeout과 SessionEnd의 짧은 제한도 각각 처리한다.

task별 훅 설정을 사용자의 전역 Codex 설정에 영구 설치하지 않는다. 설정 override/profile 등 지원 버전에서 실제 가능한 방법을 확인한다. 이미 설치된 사용자 훅과 합쳐지는 방식 및 서로 다른 Stop 응답의 우선순위도 확인한다.

정상적인 훅 신뢰 확인을 자동 수락하지 않는 것이 현재 D69의 출발점이다. 동적으로 생성한 훅이 매번 검토를 요구한다면 고정 브리지 정의를 사용할 수 있는지 먼저 확인하고, 그래도 다른 정책이 필요하면 사람에게 묻는다.

### 5.2 질문과 지시 전달

Claude의 AskUserQuestion은 그대로 유지한다. Codex는 실제 사용할 모드에서 native 질문 도구를 검증한다. 모드를 plan으로 바꾸어 질문만 된다는 결과는 수정 단계의 호환 근거가 아니다.

native 도구가 적합하지 않으면 relay 전용 MCP 질문 도구를 후보로 둔다. 이 경우 앱 질문 UI, 답변 IPC, pending 질문의 취소·종료·복구가 필요하므로 Q1의 터미널 유지와 별개로 사용자의 의견을 구한다. 원래 도구의 최대 4개 질문 규칙을 무조건 3개로 줄이지 않는다.

스킬 본문과 공통 종료 규칙은 한 벌의 원본을 유지한다. 배포 시 Claude/Codex metadata와 질문 도구 안내만 각 엔진에 맞춘다. 산출물 템플릿과 사람/AI 결정 기록 규칙은 공유한다. 기존 skills/check.mjs의 Claude 전용 metadata 검증도 배포본의 엔진별 검사와 구분한다.

Codex의 `--add-dir`은 쓰기 범위 확장 옵션이다. 이것만으로 레포 밖 스킬이 읽힌다고 가정하지 않는다. 원본 레포와 worktree에 relay 지시 파일을 심지 않는 방법을 먼저 검증한다. 지시 파일의 명시적 읽기 또는 지원되는 세션 지시 입력을 사용할 경우에도 초기 명령줄에 긴 본문을 넣지 않고, 압축·재개 후에도 종료 규칙을 유지하는지 시험한다.

### 5.3 보호와 자동 승인

Codex 보호 정책은 Claude 문자열을 번역하는 것만으로 완료되지 않는다. git push/gh pr, 앱 소유 파일, 이전 task, 배포한 지시 파일에 대한 보호를 쉘·patch·스크립트에서 시험하고, 기존 D91의 실수 방지 보장과 비교한다. 조직 정책이나 사용자 설정 때문에 실제 모드가 달라지면 엔진에 맞는 안내를 표시한다.

Codex turn.completed/Stop을 받아도 pending 상태를 모르면 자동 승인하지 않는다. 내부 모델은 `없음 / 있음 / 알 수 없음`을 구분한다. Claude의 기존 판정은 유지한다. 자동 승인을 허용하려면 새 이벤트·훅, 미완료 프로세스/서브에이전트 추적, 기능 제한 등 실제 완료를 확인하는 방법이 필요하다. 이를 위한 기능 제한 또는 Codex만 수동 승인하는 차이가 발생하면 사람이 선택한다.

후속 수정 턴은 사람이 새 요청을 보낸 턴과 구분하여 bounce_count를 유지한다. 후속 프롬프트의 UserPromptSubmit을 사람 요청으로 잘못 세어 무한 되돌림을 만들지 않는다. 파일 감시는 패널 갱신용이고 완료 판정은 종료 신호와 재검사로 한다(I15).

## 6. 설정·화면·평가 도구

- 설정: 기본 엔진 선택과 설치·인증·지원 기능 점검 결과. 미설치 엔진을 선택했다면 구체적인 안내를 제공한다.
- 등록: 선택된 엔진만 점검한다. Codex만 설치된 사용자에게 Claude 설치를 요구하지 않는다.
- task: 사용 엔진과 버전을 확인할 수 있다. 앱 기본값이 바뀌어도 기존 task 표시와 재개 대상은 그대로다.
- 실패: 선택한 엔진의 설치·인증·버전 문제인지 task 시작 실패인지 구분한다. 다른 엔진으로 자동 대체하지 않는다.
- 정리: 같은 선택 규칙, 훅, 보호, 프로세스 종료를 사용한다. 정리 동안의 기존 조작 제한을 유지한다.

최신 main의 [평가 도구](eval.md)는 agent, AI 사람 역할, 판정자를 모두 Claude로 실행한다. 이번 기능의 검증을 위해 평가 모델까지 모두 Codex로 바꾸지는 않는다. 필요하면 평가 대상 agent만 고를 수 있게 하고, 사람 역할과 판정자 설정은 분리한다. Claude 기존 평가 경로는 유지한다. 기능 시험과 사용자 경험 평가는 서로 대체하지 않는다.

## 7. 실행 계획과 통과 기준

| # | 시험 | 통과 기준 |
|---|---|---|
| C1 | CLI 설치·인증·실행 설정 | 지원 버전에서 실제 옵션·정책 적용. 버전 불일치/로그아웃은 명확히 안내 |

### P1. Claude 보존을 먼저 확인하는 엔진 경계

공통 타입/어댑터 경계를 만들고 Claude 구현을 옮긴다. 기존 단위·어댑터·흐름·스모크 시험을 유지한다. UI 동작 변경 없는 단계로 나누어 회귀를 확인한다.

### P2. 엔진 선택과 기록

config 기본값·검사, 설정 UI, 등록 점검, task 엔진 고정, 기존 기록 읽기, 재개·정리 선택을 구현한다. 실제 Codex 실행과 독립된 가짜 엔진으로 아래 시나리오를 시험한다.

- engine 없는 기존 기록과 중단된 Claude task.
- 앱 기본값 변경 전후 새 task, 이미 대기 중인 task, 시작 실패 후 재시도.
- Claude task 재개 시 앱 기본값이 Codex인 경우와 반대 경우.
- 잘못된/알 수 없는 엔진, 미설치·로그아웃 엔진, 자동 대체 없음.
- Claude/Codex Work 동시 실행에서 풀의 합계 상한 유지.

### P3. Codex 수동 흐름

검증한 설정·브리지·질문·지시 전달을 연결한다. intake → fix → review → verify, 조사 포함 경로, 추가 요청, 되감기, 복구, 정리, PR 대응을 검증한다. 코드·handoff는 두 엔진 사이 다음 task로 전달하고 대화 자체는 전달하지 않는 것을 확인한다.

### P4. 자동 승인과 전체 호환

C9 근거와 사람의 결정을 반영한 뒤 Codex 자동 승인/대응을 연결한다. 취소·새 요청·형식 변경·세션 종료·앱 종료·재시작에서 기존 카운트다운 규칙을 검증한다. pending/unknown 상태의 오래된 handoff로 다음 task나 push가 시작되지 않아야 한다.

마지막으로 타입 검사, lint, 관련 단위/어댑터/흐름 시험, 빌드 및 Windows 설치본 스모크를 수행한다. 실제 Claude와 Codex 시험은 각각의 인증 환경에서 기록한다. 기존 평가 도구 변경이 필요하면 별도 작은 커밋으로 반영한다.

## 8. 진행 기록

현재 구현은 중간 단계다. `agent_engine` 설정 UI/검사, 새 task의 엔진 고정, 엔진/버전 표시, Claude 실행·재개 어댑터, 대기열·재시작의 이전 기록 호환이 들어 있다. 정리 세션은 해당 verify task의 엔진을 메모리에 고정한다. Codex 실제 실행 및 훅 브리지는 아직 연결하지 않았으며, 그 사이에도 Codex task를 Claude로 실행하는 자동 대체는 막는다. 설정에 Codex 선택지가 있다는 것을 실제 Codex 작업 흐름 검증 완료로 해석하지 않는다.

모든 구현 단계에서 Claude 경로는 사용할 수 있어야 한다. 다음 단계는 Q3 답과 실제 훅·권한 스파이크를 반영해 Codex 실행을 연결하는 것이다. 중간 가드와 Codex 미연결 시험은 연결 시 실제 Codex/가짜 Codex 시험으로 교체한다.
