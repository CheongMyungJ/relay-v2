### 사람 역할의 말

- [relay#1 좋음] 완료조건 판정표에 근거가 한 줄씩 붙어 있고, 실패한 항목도 숨기지 않고 실패로 적어 줬다. 의도 단계에서 비목표와 반복 실행 근거가 먼저 정리돼서 믿고 승인할 수 있었다.
- [relay#1 불편] 완료 화면의 판정표에 실패가 두 줄 남아 있는 채로 완료를 눌러야 해서 찜찜했다. 에이전트가 원인 분석 단계에서 팀 규칙이나 동시 실행 같은 배경을 묻지 않았다. 원인 분석과 수정 단계는 자동 승인으로 지나가서 내가 diff를 보려면 따로 찾아봐야 했다.
- [relay#2 좋음] 판정표에 완료조건별로 근거(반복 실행 횟수, 수정 전 실패 횟수)가 붙어 있었다. 전체 변경 탭에서 diff도 바로 볼 수 있어서 승인 전에 확인하기 쉬웠다.
- [relay#2 불편] 새 Work를 시작할 때 이전 완료 Work가 화면에 그대로 떠 있어서 잠깐 헷갈렸다. 리뷰 단계 질문은 터미널에서 방향키로 골라야 했고, 지식 탭이나 '공유 대기' 안내는 무슨 뜻인지 바로 와닿지 않았다.
- [relay#3 좋음] 원인 설명과 diff, 완료조건별 판정표가 근거와 함께 한 화면에 나와서 결과를 믿고 승인할 수 있었다. 이전 Work의 팀 규칙(재시도·skip 금지, 병렬 유지)을 에이전트가 알아서 제약에 넣었다.
- [relay#3 불편] 터미널에 입력한 직후 [의도 승인]을 눌렀더니 클릭이 먹지 않아 다시 눌러야 했다. 02단계는 자동 승인으로 지나가서 내용을 보려면 탭을 직접 눌러야 했다.
- [relay-off#1 좋음] 단계가 나뉘어 있고 판정표에 반복 실행 횟수와 근거가 보여서, 결과를 믿을지 판단하기 쉬웠다. 범위 밖인 batch 실패를 묻는 질문에서 내가 방향을 정할 수 있었다.
- [relay-off#1 불편] 원인 분석과 수정 단계가 자동 승인으로 지나가서 무엇을 고쳤는지는 inspect_diff로 따로 확인해야 했다. 완료조건 하나가 '실패'로 표시된 채 완료 승인을 눌러야 해서 찜찜했다.
- [relay-off#2 좋음] 단계별로 나뉘어 있고, 원인·결정·위험이 요약으로 정리되어 보였다. 리뷰 단계에서 선택지에 직접 입력으로 추가 요청(정산팀 문의 확인)을 할 수 있었고, 판정표에 반복 실행 횟수 같은 근거가 있어 믿을 만했다.
- [relay-off#2 불편] 앞 일의 완료 Work가 사이드바와 화면에 그대로 남아 처음에 어느 Work인지 헷갈렸다. inspect_diff도 앞 Work 변경까지 같이 보여 이번 변경만 가려 읽어야 했다. 02 단계는 자동 승인으로 지나가서, 리뷰 단계 전에는 따로 탭을 눌러 봐야 원인을 확인할 수 있었다.
- [relay-off#3 좋음] 판정표에 완료조건별 판정과 근거(반복 횟수 포함)가 나와서 승인 전에 확인하기 쉬웠다. 범위 밖인 batch 실패도 숨기지 않고 판정 불가로 따로 보여 줬다.
- [relay-off#3 불편] 에이전트가 물은 판정 질문이 터미널의 선택지 화면에만 있어서, 오른쪽 패널에서 뭘 해야 하는지 바로 알기 어려웠다. 승인 화면에서 바뀐 코드를 보려고 별도로 inspect_diff를 써야 했다.

- 판정 #1: 결과 선호 relay-off — A는 숨긴 시험 6개 중 5개를 통과한다. 실패한 것은 "같은 이벤트 재수신" 하나뿐이고, 이는 Work 1 쪽 시험이다. 요약 쪽 원인 둘은 모두 고쳤다. 하나는 발송 기록 키에서 runId를 뺀 것이다. 다른 하나는 느린 성공을 시간 초과로 보지 않게 한 것이다. 요약 재실행, 느린 요약 성공, 요약 실패 재시도가 모두 통과한다. 시험도 폭넓다. 느린 성공, 재실행, 실패 뒤 재시도와 재실행을 다룬다. 어댑터에 `deliveryUnknown` 같은 변경이 더 들어가 범위가 약간 넓다.

B는 키와 시간 초과 원인을 같은 식으로 고쳤다. 그런데 `ledger.js`에 abandonedKeys와 inflight 같은 새 상태를 추가했다. 그 결과 숨긴 시험 중 요약 재실행과 요약 실패 재시도가 실패했다. 요약 재실행 쪽은 B가 직접 쓴 시험이 통과하는데도 숨긴 시험은 실패한다. 이는 ledger 변경이 어떤 경로를 막았다는 뜻이다. B의 시험에는 요약 실패 재시도 시험이 없어서 이 회귀를 잡지 못했다.

두 쪽 모두 같은 이벤트 재수신 시험이 실패한다. 그래서 차이는 요약 쪽 정확성에서 난다. 이 기준으로는 A가 낫다.
  - 경험 전체 relay (relay 6, relay (지식 끔) 5) — 두 기록 모두 Work 1에서 배운 시간 초과 문제를 Work 2에서 스스로 짚지 못했고, 사람이 ETIMEDOUT 재시도를 물어서 고쳤다. B는 수고와 혼란이 더 적었다. A는 검증 근거가 약간 더 풍부했지만, 앞 일 화면 때문에 헛걸음을 했고 입력도 두 배쯤 많았다.
- 판정 #2: 결과 선호 relay-off — 두 결과 모두 요약 쪽 원인 둘을 고쳤다. 하나는 키에서 runId를 뺀 것이고, 다른 하나는 늦은 성공을 시간 초과로 보지 않게 한 것이다. 숨긴 시험 결과도 같다. 둘 다 Work 1의 '같은 이벤트 재수신'은 실패로 남았다. 그 부분은 비교에서 차이를 만들지 않았다.

차이는 두 가지다.

1. 동시 실행 처리: B는 ledger에 claim/release(보내는 중인 키를 선점)를 추가했다. 사람이 알려 준 '서버 두 대가 같이 돈다'는 사실은 확인과 발송 사이에 다른 실행이 끼어드는 경우를 가리킨다. A의 has 확인 후 발송 방식은 이 동시 실행을 막지 못할 수 있다. 다만 B의 변경이 더 크고, claim이 메모리 기반이라 실제 운영 환경에 그대로 맞는지는 불확실하다.
2. 시험: A는 재실행, 느린 성공, 실패 재시도를 한 파일에 모았고 늦게 실패한 경우도 다뤘다. B는 digest와 notifier 양쪽에 시험을 더했지만, 보이는 범위에는 같은 날 재실행 시험이 뚜렷하지 않다.

B가 원인 분석에 조금 더 가깝다고 보고 근소하게 B를 골랐다. 시험 구성은 A가 더 낫다.
  - 경험 전체 relay-off (relay 6, relay (지식 끔) 7) — B가 수고와 혼동이 적고 흐름이 깔끔했다. A는 기준 코드 실패 증거로 확신 면에서 앞서지만 앞 일 화면 혼동과 초안 정정 부담이 있었다. 전체로는 B가 근소하게 낫다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험을 전부 통과했고 두 원인을 모두 찾았다. 원인 하나는 요약 발송 기록 키에 runId가 들어간 것이고, 다른 하나는 느린 성공을 시간 초과로 보고 다시 보낸 것이다. 둘 다 키에서 runId를 빼고, withDeadline이 느린 성공을 오류로 바꾸지 않게 하고, 재시도 정책에서 성공이면 바로 끝내도록 고쳤다. 또 ledger 선점(claim)을 추가해 서버 두 대가 동시에 돌 때를 막았다.

A는 기대 밖 파일인 README.md와 src/notifier.js까지 바꿨고, audit/재발송 기능과 tick 재실행(최대 5번) 같은 부수 기능을 더했다. 보이는 diff에는 없지만 변경 파일 목록과 README 내용으로 보면 그렇다. 요청보다 범위가 넓다. 시험은 요약, 알림, 재시도 정책을 각각 시험 파일에 나눠 더해서 더 촘촘하다. 특히 실패 뒤 재시도와 느린 성공을 둘 다 시험한다.

B는 기대 범위 안에서만 바꿨다. 변경 내용은 키, 선점(claim/release), 느린 성공 처리다. 시험도 새 파일에 정책, 메일, 푸시, 요약 경로를 나눠 담았다. 한 가지 약점은 retry/policy.js에서 `elapsedMs > timeoutMs`면 실패한 시도도 timeout으로 분류하는 기존 동작을 그대로 둔 것이다. 실제 실패는 어차피 재시도되므로 동작에는 문제가 없다.

사람이 원인을 알고 고치고 싶다고 했고 경로별 근거를 보고 싶다고 했으니 두 결과 모두 맞는 편이다. 다만 범위를 지키고 변경이 작은 B를 조금 더 좋게 본다. A의 시험이 더 충실하다는 점은 인정한다.
  - 경험 전체 relay (relay 7, relay (지식 끔) 5) — B가 사람 수고와 막힘이 적고 근거 제시가 더 분명했으며, 사람의 개입 없이도 원인을 다 찾았다. A는 사람이 직접 짚어야 했고 읽기 전용 세션 때문에 한 번 막혔다.

### 사람 역할의 말

- [relay#1 좋음] 리뷰 단계에서 내가 지적한 timeout 중복 위험을 에이전트가 코드로 확인하고, 선택지로 물은 뒤 고쳤다. 완료 화면 판정표에 완료조건별 근거가 있어서 경로마다 한 번만 받는지 확인하기 쉬웠다.
- [relay#1 불편] 원인 분석과 수정 단계가 자동 승인이라, 15초 카운트다운 안에 긴 요약을 읽고 판단해야 했다. 카운트다운은 읽는 중에 끊겼고, 내가 묻기 전까지 timeout 재시도 문제가 드러나지 않았다. 에이전트가 루트에 만든 /p.patch는 지워지지 않고 남아 내가 직접 지워야 했다.
- [relay#2 좋음] 의도 정리 단계에서 에이전트가 쓴 초안이 내 말과 어긋난 부분을 승인 전에 짚어서 고칠 수 있었다. 판정표에 완료조건마다 근거가 붙어 있었고, 기준 코드에서는 새 테스트가 실패했다는 내용이 있어 경로별 근거를 보고 싶다는 내 요구에 맞았다.
- [relay#2 불편] 이전 Work가 화면에 남아 있어 지금 보는 것이 이번 일인지 잠깐 헷갈렸다. 변경 화면이 좁은 패널에 긴 diff로 나와 읽기 불편했다. 에이전트가 의도 초안에서 '실패한 요약은 다시 보낸다'를 '과거 누락분 재발송 도구'로 넓게 해석했는데, 질문 없이 쓴 초안이라 내가 직접 바로잡아야 했다.
- [relay#3 좋음] 완료 화면의 판정표가 완료조건마다 근거를 붙여 줬다. 기준 커밋에서는 테스트가 실패하고 수정 후에는 통과한다는 내용과 경로별 1통 확인이 들어 있어서, 내가 원한 경로별 근거를 바로 볼 수 있었다.
- [relay#3 불편] 처음 Work에서는 에이전트가 서버 두 대나 배포일 재실행 같은 경로를 묻지 않았다. 그래서 요약 중복의 일부만 고쳐진 채 완료됐고, 새 Work를 하나 더 만들어야 했다. 앞 Work에서 놓친 부분을 이어서 고치는 흐름이 없었다.
- [relay-off#1 좋음] 원인 3개가 요약에 근거와 함께 정리돼 있었다. 판정표가 완료조건마다 통과 근거를 보여 줬다. 리뷰 단계에서 메일 타임아웃 재시도가 중복을 남긴다고 물었더니 에이전트가 자기 판단이 틀렸다고 인정하고 그 경로까지 고쳤다.
- [relay-off#1 불편] 리뷰 단계가 앞 단계의 위험 항목(ETIMEDOUT 재시도)을 스스로 짚지 않아 내가 직접 물어야 했다. 묻지 않았다면 알려진 한계로 넘어갈 뻔했다. 작업을 시작할 때 이전 일의 화면이 그대로 남아 있어 헷갈렸다.
- [relay-off#2 좋음] 판정표에 완료조건별로 근거가 있고 [전체 변경]에서 코드와 테스트를 바로 볼 수 있어서, 경로마다 한 번만 받는지 확인하기 쉬웠다. 리뷰 단계에서 지적 반영을 선택지로 물어서, 내가 아는 서버 두 대 동시 실행 사실을 근거로 방향을 정할 수 있었다.
- [relay-off#2 불편] 리뷰 단계의 추천 선택지가 '반영하지 않음'이었다. 내가 아는 맥락이 없었다면 동시 실행 경쟁을 그냥 넘길 뻔했다. 원인 분석 단계는 자동 승인으로 지나가서 따로 확인하지 못했다.
- [relay-off#3 좋음] 리뷰 단계의 선택지 질문에서 직접 입력으로 지적 3번(서버 간 중복)을 반영해 달라고 했고, 에이전트가 이를 고쳐 경로별 테스트와 근거를 판정표로 보여 줬다. 변경 탭에서 diff 전체를 볼 수 있어 확인하기 좋았다.
- [relay-off#3 불편] 첫 Work에서는 이미 읽기 전용으로 끝난 세션에 질문을 입력했는데 답이 없었다. 승인 화면이 아닌 완료 뒤에는 에이전트에게 물을 길이 없어서 새 Work를 열어야 했다. 에이전트는 서버 두 대 경로를 의도 정리 단계에서 묻지 않았고, 리뷰 단계에서 내가 짚은 뒤에야 반영됐다.

#### friction이 높았던 차례

- relay-off#3 차례 11 (friction 2): 세션이 읽기 전용이라 응답이 없다. 요약 탭에서 서버 두 대 경로를 다뤘는지 확인한다.
- relay-off#3 차례 12 (friction 2): 완료된 세션은 읽기 전용이라 질문할 수 없다. 서버 두 대 경로의 근거가 없어서 이 문제로 새 Work를 연다.
