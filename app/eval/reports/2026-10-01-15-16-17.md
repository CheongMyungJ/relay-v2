- 판정 #1: 결과 선호 tie — 두 결과는 구조와 동작이 거의 같다. 둘 다 구분자 옵션을 더했고 기본값은 쉼표이며, 구분자가 든 값만 따옴표로 감싼다. 바뀐 파일도 같다. A는 `needsQuote` 변수를 따로 둬서 읽기 조금 더 쉽다. B는 한 줄 삼항식이라 약간 빽빽하다. 시험은 둘 다 세미콜론, 탭, 다른 구분자 유지, 따옴표·줄바꿈, exportOrders 전달을 확인한다. B는 빈 옵션 `{}`도 시험하고, A는 exportOrders의 기본값 경로를 시험한다. 차이는 미미해서 동점으로 본다.
  - 경험 전체 cli (relay 6, CLI 8) — 작은 기능에서 A가 더 적은 수고로 더 빨리 끝냈다. B는 결과를 믿을 근거는 좋았지만 승인 단계가 부담이었다.
- 판정 #2: 결과 선호 relay — 둘 다 숨긴 시험을 통과하고, 바꾼 파일도 기대한 세 곳뿐이다. 구현도 거의 같다. A는 구분자 검증을 더했다. 빈 문자열이나 여러 글자를 막아 주는 점은 견고하지만, 요청에 없던 동작이라 "작은 일을 빨리" 끝내려는 선호에는 조금 과하다. 반면 B는 최소한으로 구현했고, 그 대신 빈 문자열 구분자를 막지 않는다. 시험은 B가 더 넓다. 기본 쉼표 유지, 탭, 선택한 구분자가 든 값 감싸기, 세미콜론일 때 쉼표만 든 값은 감싸지 않기, 큰따옴표·줄바꿈 감싸기, exportOrders의 기본값과 옵션 전달까지 다룬다. 큰따옴표 시험의 기대 문자열은 읽기 불편하다. A의 시험은 검증 동작까지 다루지만 큰따옴표와 줄바꿈의 회귀는 다루지 않는다. 종합하면 B가 요청 범위에 더 맞고 회귀 방지도 더 낫지만, 차이는 작다.
  - 경험 전체 cli (relay 6, CLI 8) — 작은 기능이고 사람이 빠른 완료를 원했으므로 A의 낮은 부담(0.8분, 3차례)이 유리하다. B는 설계와 리뷰 단계 때문에 8차례·3.5분이 들었고 스스로도 무겁다고 평했다. 다만 B는 통제와 확신 면에서 더 낫다. A의 임의 검증 추가는 흠이지만 전체로는 A가 앞선다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 같은 세 파일을 고쳤고 숨긴 시험도 통과했다. 기본 쉼표와 탭, 구분자가 든 값의 따옴표 처리도 둘 다 맞다.

A는 구분자가 쉼표가 아니어도 쉼표가 든 값을 계속 따옴표로 감싼다. 기존 동작을 보존하는 쪽이고 이 동작을 확인하는 시험도 있다. 옵션 처리는 최소한이다. exportOrders가 options를 그대로 넘기므로 null이 들어오면 오류가 날 수 있지만, 이는 사소하다. 시험은 빈 옵션, undefined, 따옴표 이스케이프까지 다룬다.

B는 구분자를 검증해 잘못된 값이면 예외를 던진다. 요청하지 않은 기능이라 "작은 일이라 빨리 끝내고 싶다"는 선호에는 조금 어긋나지만, 안전장치로는 쓸 만하다. 다만 쉼표가 구분자가 아닐 때 쉼표가 든 값을 감싸지 않는다. 이는 허용 가능한 설계이지만 기존 동작과 달라진다. 이 변화는 시험에도 박혀 있다. 예를 들어 `p,q`를 감싸지 않는 것을 시험이 요구한다. 엑셀에서 열 때 쉼표가 든 값을 감싸지 않으면 오히려 안전하지 않을 수 있다.

종합하면 A가 범위가 좁고 기존 동작 보존 면에서 약간 낫다.
  - 경험 전체 cli (relay 6, CLI 8) — 작은 기능이고 사람이 빨리 끝내고 싶어 했다. B는 3차례, 0.9분에 구현·테스트·커밋까지 끝냈다. A는 8차례, 3.4분이 걸렸고 승인이 많아 사용자 스스로도 과하다고 했다. A는 판정표로 확신 근거를 더 줬지만, 수고 차이가 더 크다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 필터→정렬→쪽 나누기 순서, 양 끝 포함, 동점 id 오름차순, RangeError 처리를 같게 구현했다. 차이는 세 가지다. (1) A는 요청하지 않은 규칙을 만들었다. 음수나 Infinity 가격을 RangeError로 막는데, 이는 사람이 알려 준 사실에 없어서 범위가 조금 넓어졌고 기존 호출자를 놀라게 할 수 있다. B는 숫자가 아니거나 NaN인 값만 막아 요구에 더 가깝다. (2) A는 함수 주석을 새 동작에 맞게 고쳤고 정렬 표를 따로 둬서 읽기 좋다. B는 "total은 전체 개수다"라는 주석을 그대로 둬서 낡았다. (3) 시험은 B가 더 낫다. B는 page만 넘긴 기존 호출을 확인하는 시험과, 같은 가격끼리 오름·내림 모두 id 오름차순임을 따로 보는 시험을 더했다. 사람이 원한 "기존 화면이 깨지지 않았다는 확인"도 B가 더 직접 보여 준다. A도 원본 순서 유지와 여러 입력 오류 시험을 넣었지만, 동점 규칙은 전체 목록 비교에 기대고 있다. 설계를 먼저 사람에게 보였는지는 기록에 없어서 두 결과를 같게 보았다. 종합하면 B를 약간 더 낫게 본다.
  - 경험 전체 relay (relay 7, CLI 6) — A는 빠르고 간결했지만, 사람이 아는 동점 규칙을 묻지 않고 등록 차례로 가정했다. 테스트 기대값을 바꾼 일도 요약에 충분히 드러나지 않았다. B는 시간이 더 들었지만, 경계 규칙을 선택지로 물었고 기존 호출이 같다는 확인 근거도 제시했다. 그래서 사용 경험은 B가 약간 더 낫다.
- 판정 #2: 결과 선호 cli — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 기존 호출(page만 넘김)이 그대로인지 확인하는 시험도 있다. 같은 가격은 id 오름차순이고, 범위가 잘못되면 RangeError를 던진다. 설계를 먼저 묻는 모습은 기록에서 어느 쪽에도 보이지 않는다. 차이는 코드 모양과 시험의 성격이다. A는 정렬 함수를 SORTS 맵에 두어 읽기 쉽고 변경이 작다. 시험은 짧고 핵심(양끝 포함, 같은 가격 차례, 쪽 넘김, 범위 밖 쪽, 필터+정렬+쪽 조합)을 모두 짚는다. B는 시험이 더 많고 null, Infinity, 원본 불변도 확인하지만, 시험 안에서 기대값을 코드와 같은 방식으로 다시 계산해 구현을 되풀이하는 부분이 있고 길다. 전체적으로 A가 더 간결하며 회귀 방지력은 비슷해 근소하게 A를 택한다.
  - 경험 전체 tie (relay 7, CLI 7) — A는 수고가 적고 B는 확신 근거가 강해 서로 상쇄됐다. 두 쪽 모두 경계 규칙을 먼저 묻지 않았고, 사람이 직접 짚어 교정했다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험을 통과했고 동작도 거의 같다. A는 요청에 없던 음수 금지 규칙을 더해 범위를 약간 벗어났지만, SORTS 테이블 덕에 코드는 더 깔끔하다. B는 요청한 범위에 머물렀고 시험이 더 넓다(쪽 이어 붙이기의 중복·누락 검사, 필터와 정렬 조합, 기존 호출 유지). 그래서 B를 근소하게 앞선다고 봤다. 설계를 먼저 보여 줬는지는 기록에 없어 비교하지 않았다.
  - 경험 전체 cli (relay 6, CLI 7) — 두 기록 모두 설계 단계에서 사람이 동점 처리와 min>max 오류를 바로잡았다. A는 수고가 절반이고 통제가 더 뚜렷했다. B는 판정표와 테스트 보고로 확신을 더 줬지만, 절차가 길고 구현이 자동 승인으로 지나갔으며 파일이 잠시 지워진 일이 불안을 줬다.

### 사람 역할의 말

- [relay#1 좋음] 설계 단계에서 내가 정해야 할 모호한 점(범위 역전, 동점 순서)을 에이전트가 선택지로 물었다. 설계서에는 그 결정이 [사람]으로 표시됐다. 마지막 판정표에는 기존 호출이 같다는 확인이 근거와 함께 있었다.
- [relay#1 불편] 완료 화면이 잠깐 로딩 중인 터미널 같아 보였고, 완료 화면의 판정표는 좁아서 읽기 불편했다. 승인 전에 코드를 보려면 별도 행동(inspect_diff)이 필요했다.
- [relay#2 좋음] 설계를 승인하기 전에 요구사항을 출처와 함께 볼 수 있었다. 마지막 판정표는 완료조건마다 통과 여부와 근거 테스트를 보여 줘서 믿고 완료할 수 있었다.
- [relay#2 불편] 의도 초안에서 에이전트가 min>max 동작과 동가격 정렬을 묻지 않고 위험이나 가정으로만 적어 둬서, 내가 직접 짚어서 터미널에 말해야 했다.
- [relay#3 좋음] 의도 단계에서 에이전트의 잘못된 가정(동가격은 등록 차례, min>max는 빈 결과)을 바로 고쳐 달라고 했고, 그 내용이 완료조건과 결정란에 '[사람]'으로 반영됐다. 마지막 판정표가 완료조건마다 근거를 붙여 줘서 확인하기 쉬웠다.
- [relay#3 불편] 구현 단계가 자동 승인으로 지나가서 내가 본 시점이 없었고, 나중에 diff를 직접 열어서야 확인했다. 리뷰 단계에서 주석 수정 중 함수 선언이 지워졌다가 복구된 일이 있었는데, 화면에는 커밋 메시지 한 줄로만 나와서 조금 불안했다.
- [cli#1 좋음] 설계를 먼저 구체적으로 보여 주고 확인 사항을 물어서, 동점 규칙을 바로잡은 뒤 구현과 커밋까지 한 번에 끝났다.
- [cli#1 불편] 에이전트가 동점 규칙을 마음대로 등록 차례로 가정했다. 그리고 테스트 기대값을 중간에 고쳤는데, 요약에는 한 줄만 나와서 diff를 따로 봐야 했다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 기존 함수의 반환값과 오류도 그대로다. 구현도 거의 같다. 둘 다 이메일을 가려서 기록하고, 같은 시각이면 순번으로 순서를 정하며, 조회 결과는 복사해서 돌려준다. 잘못된 since는 ValidationError로 처리한다. A는 변경 범위가 작다. maskEmail을 users.js 안에 두고 기존 시험 파일에만 시험을 더했다. 다만 maskEmail이 users.js의 주석 "사용자 서비스…" 위에 끼어들어 원래 주석과 함수 사이가 어색해졌다. 시험은 기록 보호, 실패 시 기록 없음, 필터, 차례를 모두 다룬다. B는 maskEmail을 audit.js로 분리했고, 마스킹을 단독으로 시험한다. 또 원문 이메일이 기록 어디에도 남지 않는지 JSON 전체로 확인한다. 이 시험은 개인정보 규정에 대한 회귀 방지력이 더 크다. 그 밖에 Date와 ISO 문자열 동치, 빈 인자 조합, 시각 순서가 뒤바뀐 경우도 시험한다. 파일 분리는 약간 더 많이 바꾼 것이지만 합리적이다. 시험 파일에서 import가 중간에 놓인 점은 사소한 흠이다. B의 시험이 더 촘촘하므로 근소하게 B를 선호한다.
  - 경험 전체 relay (relay 7, CLI 6) — A는 수고가 적고 빨랐다. 하지만 B는 단계별 승인과 판정표 덕에 명확성, 통제, 확신에서 앞섰다. 수고는 B가 더 크지만 설문 점수가 같고 평가 목적과 맞아 B가 약간 낫다고 본다.
- 판정 #2: 결과 선호 relay — 숨긴 시험과 레포 시험은 둘 다 통과했다. 차이는 아래와 같다.

A는 record()에서 now()를 따로 한 번 더 호출한다. 그래서 createUser는 now()를 두 번 부르고, 기록의 at이 사용자의 createdAt과 어긋난다. 시계를 호출 횟수로 세는 시험에서는 기존 동작이 달라졌다고 볼 수 있다. A의 테스트 주석("now() 1회는 createdAt")도 이 어긋남을 드러낸다. 사용자 생성 기록의 시각이 생성 시각과 달라지는 것은 감사 로그로서 아쉽다. 한편 A는 잘못된 since를 검사하고, 마스킹에서 첫 글자를 Array.from으로 잘라 서로게이트 쌍도 처리한다. 변경 범위는 users.js 한 파일로 가장 작다.

B는 create에서 now()를 한 번만 부르고 그 값을 createdAt과 기록의 at에 같이 쓴다. 그래서 기존 동작의 호출 횟수를 지키고 시각도 일치한다. maskEmail을 email.js로 옮겨 재사용하기 쉽고, 단위 테스트도 따로 있다. 테스트는 마스킹 단위, 이메일 원문 부재, 기존 반환값 유지, 결합 필터, 기록 보호까지 더 넓게 다룬다. 파일이 하나 더 바뀌지만 합리적인 범위다.

종합하면 B가 정확성과 테스트에서 앞선다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 설계를 먼저 보여 주고 사람이 두 번 지적한 뒤 바로 구현해 5차례, 1.8분에 끝냈다. B는 의도, 설계, 리뷰 단계를 거치며 10차례, 5.2분이 걸렸다. B의 판정표는 확신을 높였지만, 두 쪽 모두 에이전트가 개인정보와 정렬을 먼저 묻지 않았다. 설문 점수도 확신과 통제가 같아 수고가 적은 A를 약간 높게 봤다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 이메일 가리기, 실패 시 기록 안 함, 반환값 사본 보호도 갖췄다. 차이는 정렬과 변경 범위, 시험의 두께다. A는 at을 실제로 파싱해 내림차순으로 정렬하고 같은 시각이면 기록 순번으로 나중 것을 앞에 둔다. 그래서 시계가 거꾸로 가도 "at 내림차순" 규칙을 지킨다. B는 저장된 순서를 단순히 뒤집기만 한다. 시계가 단조 증가하지 않으면 최신순이 깨질 수 있다. 또 B는 로그를 공유 store에 두고 store.js까지 바꾸는데, 로그가 store를 쓰는 다른 코드에 드러날 수 있어 범위가 조금 넓다. A는 로그를 서비스 클로저 안에만 둔다. A는 새 시험 파일에서 maskEmail 단위 시험, 잘못된 since, userId와 since 조합, 원문 이메일이 없는지 확인하는 시험까지 더 촘촘히 다룬다. B의 시험도 쓸 만하고 같은 이메일로 바꾸는 경우를 다루는 점은 좋지만, 시각 순서가 거꾸로인 경우는 시험하지 않는다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 구조화된 설계 검토와 근거가 강점이지만 수고가 컸다. B는 같은 핵심 정정을 거쳐 훨씬 적은 수고로 끝냈고, 설문의 수고 점수도 더 좋았다. 확신 점수는 같았다. 그래서 전체로는 B를 약간 더 낫게 본다.

- [cli#2 좋음] 코드를 고치기 전에 설계와 결정이 필요한 점(잘못된 since, 같은 이메일로 변경, 로그 크기)을 먼저 보여 줘서, 내가 방향을 정하고 규정을 반영시킬 수 있었다.
- [cli#2 불편] 설계 단계에서 이메일 마스킹과 정렬 규칙을 에이전트가 묻지 않아서(최신순 대신 기록순, 이메일 평문을 제안했다), 내가 직접 짚어야 했다. 그리고 now()를 두 번 호출하는 부분은 요약에 있어서 알 수 있었지만, 그 설명이 길어서 읽기 번거로웠다.
- [cli#3 좋음] 코드를 고치기 전에 조회 규칙을 표와 목록으로 먼저 보여 줘서 방향을 정하기 쉬웠다. 에이전트가 최종 요약에 개인정보 관련 주의점도 짚어 줬다.
- [cli#3 불편] 설계안이 정렬 순서를 오래된 것 먼저로 잡았고 이메일 마스킹은 아예 넣지 않아서, 내가 직접 짚어 줘야 했다. 에이전트가 이 규칙들을 먼저 묻지 않았다.
