- [relay#1 좋음] 의도 초안에 완료조건이 체크리스트로 있었고, 최종 검증에서 조건별 판정표와 근거(실행한 명령, 결과)를 보여 줘서 믿기 쉬웠다. 요청한 테스트도 바로 반영됐다.
- [relay#1 불편] 수정과 리뷰 단계가 자동 승인이라, 내가 승인하기 전에 지나갔다. 코드는 inspect_diff로 따로 찾아봐야 했다. 세션이 뜨는 동안 검은 화면만 보여 잠깐 기다려야 했다.
- [relay#2 좋음] 의도 정리가 완료조건과 테스트 요구까지 잡아 주었고, 마지막 판정표에 조건별 근거(실행 결과, diff)가 있어 믿고 완료할 수 있었다.
- [relay#2 불편] 수정과 리뷰 단계가 기본 자동 승인이라 내가 확인하기 전에 지나갔다. 리뷰 지적은 볼 기회가 없었고, 수정은 inspect_diff로 뒤늦게 봤다.
- [relay#3 좋음] 의도 승인 화면과 최종 판정표(완료조건별 근거)와 전체 변경 diff를 한곳에서 볼 수 있어서, 간단한 버그를 빠르게 확인하고 끝낼 수 있었다.

- [relay#2 불편] 수정 단계가 자동 승인되어 내가 확인하기도 전에 리뷰로 넘어갔다. 그래서 diff를 따로 열어 봐야 했다. 세션이 뜨는 동안 까만 화면만 보여 기다리는 시간이 조금 답답했다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 truncate와 median 수정이 같고 숨긴 시험도 모두 통과한다. 차이는 시험이다. A는 시험을 더하지 않아 회귀를 막지 못한다. B는 두 버그 각각에 대해 경계값, 짝수 개, 입력 불변을 확인하는 시험을 추가했다. B는 빈 배열 처리(undefined)를 요구 밖으로 더했지만 영향이 작고 시험으로 고정했다. 두 버그의 파일이 text와 stats로 나뉘어 있어 변경을 따로 커밋하기 쉽다는 점은 B도 A와 같다. 전체적으로 B가 낫다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 훨씬 적은 수고로 두 버그를 별도 브랜치와 커밋으로 나눠 끝냈다. B는 명확성과 확신 근거가 더 좋았지만 절차가 길고 대기가 많았다.
- 판정 #2: 결과 선호 cli — 두 결과 모두 숨긴 시험을 통과하고 두 버그를 끝까지 고쳤다. 정렬 비교 함수와 짝수 개 평균 처리는 같다.

A는 n<1 처리와 빈 배열 처리를 더했다. 이 덕에 n=0일 때 slice(0,-1)이 엉뚱한 결과를 내는 경계 문제를 피하고, 시험도 더 촘촘하다. 하지만 리포트에 없는 동작(빈 배열은 undefined, n=0은 빈 문자열)을 정해 버렸다. 이런 동작은 각 팀이 정할 일이라 리뷰 부담이 늘 수 있다.

B는 리포트가 요구한 만큼만 고쳤고 변경이 작다. 리뷰 팀이 서로 다르고 변경을 깔끔하게 나누고 싶다는 사람의 선호에는 B가 더 맞는다. 다만 n=0 같은 경계는 다루지 않았다.

두 결과 모두 기록상 커밋이나 브랜치 분리 여부는 드러나지 않는다. 그래서 범위 면에서 더 절제한 B를 근소하게 선호한다.

- 판정 #3: 결과 선호 relay — 두 결과 모두 src 코드 수정은 사실상 같고 숨긴 시험도 모두 통과한다. 차이는 시험이다. A는 시험을 전혀 추가하지 않아 두 버그의 회귀를 막지 못한다. B는 truncate와 median 각각에 대해 리포트 사례, 경계값(길이가 n과 같은 경우), 짝수 개 평균, 빈 배열 시험을 추가했다. 시험 파일도 text와 stats로 나뉘어 있어 두 버그를 따로 리뷰하기 쉽다. B의 `s.length > 0` 검사는 빈 배열의 기존 동작(undefined)을 지키려는 것이라 약간 군더더기일 수 있지만 해롭지 않다. 이 기록에는 커밋이나 브랜치를 나눴는지 나와 있지 않아 그 부분은 비교하지 않았다. 종합하면 B가 낫다.
  - 경험 전체 cli (relay 6, CLI 8) — 두 기록 모두 두 버그를 따로 끝냈다. A가 훨씬 적은 수고로 해냈고 범위 밖 수정도 먼저 물었다. B는 검증 근거가 더 풍부했지만 차례와 대기가 많았고 에이전트가 짝수 길이를 임의로 제외해 사람이 바로잡아야 했다.

A는 `isParenNegative`와 `applyParen`을 공통 모듈에 추가하고, 각 리포트의 기존 파싱 코드는 그대로 둔 채 그 위에 덧붙였다. 이 방식은 동작하지만 파싱 로직 복사본 6개가 계속 남는다. 이미 모듈마다 제각각이라 생긴 버그인데, 같은 구조가 이어지는 셈이다. 또 `category.js`의 `applyParen(text, negative ? -n : n)`은 `-(1,200)` 같은 입력에서 의도가 불분명하다. 반면 시험은 A가 더 넓다. 음수 5종과 양수 3종을 16개 안팎의 리포트 함수에 돌린다. 여기에는 balance와 vat 리포트, 예산 계획값, 기초 잔액까지 들어간다.

B는 기존 복사 파싱 코드를 지우고 공통 함수 `parseAmount`를 부르도록 바꿨다. 사람이 좋다고 밝힌 선호와 맞고, 앞으로 생길 불일치도 줄인다. 다만 이 방식은 `toNumber`나 `readWon`이 관대하게 받던 입력에서 예외를 던질 수 있다. 그 위험은 숨긴 시험을 통과했으니 크지 않아 보인다. B의 시험은 `parseAmount` 단위 시험과 리포트 시험이다. 잘린 부분 때문에 전체 범위는 확인하지 못했다. 그래서 tests는 A보다 조금 낮게 줬다.

종합하면 코드 품질 차이가 더 크다고 보고 B를 선호한다.
  - 경험 전체 relay (relay 7, CLI 6) — B는 수고가 훨씬 적다. A는 단계별 산출물, 8개 리포트 전수 확인, 사람의 방향 조정이 있어 명확성, 통제, 확신에서 앞선다. 그래서 전체로는 A가 조금 낫다.
- 판정 #3: 결과 선호 cli — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 8개 모듈의 금액 읽기를 공통 함수 parseAmount로 모았다. 공개 함수 이름과 인자도 그대로다. 차이는 공통 함수의 구현 방식과 시험 범위다.

A는 parseAmount를 정규식 두 개(AMOUNT, PARTIAL)와 lenient 전처리로 다시 짰다. 짝이 안 맞는 괄호도 음수로 읽고, `+`·`-`와 괄호가 섞인 형식까지 받는다. 그래서 복잡하고 범위가 넓다. 원래 엄격 모드에서 던지던 입력 일부를 이제 받아들이는 것도 변경 범위가 커진 부분이다. 시험은 163줄로 넓다. 형식 5가지를 8개 리포트에 모두 적용해 본다.

B는 기존 AMOUNT 정규식을 조금만 고쳤다. 괄호 짝이 맞아야 하고, 안 맞으면 엄격 모드에서는 던진다. lenient 모드는 첫 숫자를 찾아 그 앞의 `-`나 `(`로 부호를 정한다. 더 작고 읽기 쉽다. 시험은 money 단위 시험과 리포트 시험으로 나눠 추가했다. 다만 형식 3가지만 다루고, 현금흐름 전체와 거래처 합계 같은 경로는 덜 본다.

정확성은 같고 scope와 quality는 B가 낫다. A의 시험이 더 넓은 점은 인정한다. 그래도 전체로는 B를 택한다.
  - 경험 전체 relay (relay 7, CLI 5) — A는 시간과 차례가 더 들었지만 크래시에서 재개가 쉬웠고, 단계별 근거와 회귀 검출, 완료 판정표로 신뢰를 줬다. B는 빠르고 수고가 적었지만 터미널이 닫혀 상태가 불분명했고, 중간·최종 보고가 없어 사람이 범위를 직접 확인해야 했다.

### 사람 역할의 말

- [relay#1 좋음] 단계별 산출물과 최종 판정표(완료조건별 근거)가 있어서 결과를 믿기 쉬웠다. 공통 함수로 모으라는 내 선호를 원인 분석 단계에서 말하니 바로 반영됐다.
- [relay#1 불편] 수정 단계가 자동 승인되어 내가 보기 전에 리뷰로 넘어갔다. 앱이 중간에 꺼져 재개해야 했고, 검은 화면으로 세션이 뜨기를 기다리는 시간이 잦았다.
- [relay#2 좋음] 단계마다 산출물과 판정표(완료조건별 근거)가 나와서 무엇이 바뀌었고 왜인지 확인하기 쉬웠다. 터미널에서 질문하면 에이전트가 솔직하게 확인 범위의 한계를 인정하고 보완해 줬다.
- [relay#2 불편] 수정 단계가 자동 승인돼서 코드를 보기 전에 리뷰로 넘어갔다. 앱이 중간에 꺼져 재개를 눌러야 했다. 단계가 많아 기다리는 시간이 길었다.
- [relay#3 좋음] 단계마다 산출물과 근거를 보여 줘서 승인하기 쉬웠다. 리뷰 단계에서 기존 입력이 0이 되는 회귀를 잡아냈고, 내가 번호로 골라 고치게 할 수 있었다. 최종 판정표도 완료조건별로 정리돼 있었다.
- [relay#3 불편] 앱이 갑자기 꺼져 재개를 눌러야 했다. 재개한 뒤에는 수정 결과를 내가 보기도 전에 자동 승인으로 리뷰까지 넘어갔다. 수정 단계 요약을 놓쳐서 코드 변경은 inspect_diff로 따로 확인했다.
- [cli#1 좋음] 한 번의 요청으로 8개 리포트를 모두 훑어 공통 함수로 모았다. 물어보니 잔액과 부가세를 왜 안 건드렸는지, 테스트 실패를 어떻게 고쳤는지 정직하게 설명했다.
- [cli#1 불편] 터미널이 갑자기 닫혀 --continue로 다시 열어야 했다. 작업 중에는 화면이 오래 멈춘 듯 보여 진행 상황을 알기 어려웠고, 끝에 diff와 질문을 통해서야 전모를 알 수 있었다.
- [cli#2 좋음] 원인과 수정 범위, 동작이 달라진 부분을 요약으로 솔직하게 알려 줬다. 리포트 6곳을 공통 함수로 모으고 공개 함수 시그니처는 유지했으며 테스트도 추가했다.
- [cli#2 불편] 중간에 터미널이 닫혀 claude를 --continue로 다시 열어야 했다. 이미 작업이 끝나 있어서 중간 과정은 거의 보지 못했다.
- [cli#3 좋음] 리포트 6개의 각자 파서를 공통 parseAmount로 모으고 공개 함수 시그니처는 그대로 둔 점이 좋았다. 회귀 테스트도 같이 추가됐다.
- [cli#3 불편] 중간 진행 보고가 거의 없었고, 작업 완료 여부를 diff로 직접 확인해야 했다. 처음엔 8개 중 6개만 바뀐 것처럼 보여 내가 물어봐야 했다. 터미널이 갑자기 닫혀 세션을 다시 열어야 했다.</worst>

- 판정 #2: 결과 선호 relay — 두 결과 모두 같은 원인을 고쳤다. results.push를 입력 인덱스에 넣는 방식으로 바꿔 완료 순서에 기대지 않게 했고, 병렬 실행은 유지했다. 숨긴 시험과 레포 시험도 둘 다 통과했다. 재시도, skip, 시간 제한 증가 같은 증상 덮기는 없다. 차이는 작다. A는 done을 start+chunk.length로 계산해 단순하다. B는 finished 카운터를 새로 뒀는데, 동작은 맞지만 변수가 하나 늘었다. B의 주석은 collectResults가 인덱스로 짝짓는다고 하는데, 이 기록만으로는 확인되지 않는 내용이라 부정확할 수 있다. 시험은 A가 지연 값을 입력 값과 분리해 더 명확하고, 늦게 끝나는 작업이 여러 개인 경우(1~3번)를 다룬다. B는 지연 값을 그대로 입력으로 써서 약간 덜 명확하다. 두 결과 모두 반복 실행 근거는 기록에 나오지 않는다. 그래서 tests는 둘 다 4점이다.
  - 경험 전체 relay (relay 7, CLI 6) — B가 훨씬 간결하지만, 사람이 요청한 반복 실행 근거(수정 전 재현과 수정 후 100회)는 A가 더 충실히 보였다. 그래서 A를 근소하게 앞선 쪽으로 봤다.
- 판정 #3: 결과 선호 cli — 두 결과는 사실상 같은 수정이다. 결과 배열을 입력 인덱스 자리에 채우고 병렬 청크는 유지한다. 완료 순서에 기댄 짝짓기라는 원인을 고쳤고, 숨긴 시험도 둘 다 통과했다. 차이는 두 가지다. A는 끝나는 순서가 아니라 입력 순서 자리에 넣는 이유를 주석으로 설명해서 읽기에 조금 낫다. A의 시험은 키 이름 a~e와 동시성 3으로 선행 작업이 늦게 끝나는 상황을 만든다. B는 지연값 자체를 결과로 써서 간결하지만 의도가 덜 드러난다. 둘 다 반복 실행 근거는 기록에 없어서 tests 점수는 같게 줬다. 주석 때문에 A를 근소하게 우위로 본다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 효율적이고 사람이 주도했다. B는 재현 횟수 등 확신 근거가 더 풍부했지만 차례가 많고 경고와 자동 승인으로 헷갈렸다. 전체 경험은 A가 근소하게 낫다.

- 판정 #1: 결과 선호 cli — 둘 다 숨긴 시험과 레포 시험을 통과했고, 품절을 필터로 빼던 흔적도 남기지 않았다. 정렬 뒤 쪽 나누기 전에 전체에서 품절을 뒤로 보내므로 페이지 경계도 맞다.

A는 sort.js에 soldOutLast 함수를 새로 만들고 engine.js에서 호출한다. 동작은 맞지만 두 파일을 고쳤고, 품절 처리가 정렬과 분리됐다. 시험은 더 꼼꼼하다. 텀블러 예제로 전체 순서를 확인하고, 쪽 넘김, 다른 정렬, facet 개수, stock null 경계까지 다룬다. 다만 facet 시험은 `b.count ?? b` 같은 추측성 코드가 있어 조금 불안하다.

B는 sortHits의 비교 함수 안에서 품절 여부를 먼저 비교하고 고른 정렬을 따른다. 변경이 한 곳이고 줄 수가 적어 더 간결하다. 주석도 이유를 설명한다. 시험은 sort 단위 시험과 엔진 쪽 넘김 시험을 더했다. 다만 A보다 경계 사례는 적다.

A의 시험이 더 풍부한 점을 감안해도, 변경 범위가 최소이고 코드가 더 깔끔한 B를 약간 더 좋게 본다.
  - 경험 전체 cli (relay 6, CLI 8) — A는 되감기 미리보기와 검증표로 안심감이 컸지만 차례와 시간이 B의 약 4배였다. B는 짧은 대화로 되돌림과 재구현을 끝냈고 잔재도 없었다.
- 판정 #2: 결과 선호 tie — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 품절 필터 흔적도 남기지 않았다. 페이지를 나누기 전에 품절을 뒤로 보내므로 페이지 경계도 맞다.

A는 sort.js 한 곳만 고쳤다. 비교 함수에 품절 여부를 합쳐서 정렬 한 번으로 끝낸다. 품절끼리는 선택한 정렬 순서를 지키므로 요구와 맞는다. 다만 `isSoldOut(a.product) - isSoldOut(b.product)`는 불리언 뺄셈에 기대서 읽기가 조금 불편하다. 시험은 전체 결과, 페이지 경계, 다른 정렬을 다룬다. 다만 테스트 기대값이 19개 예제 상품 구성에 강하게 묶여 있다.

B는 `soldOutLast`라는 안정적인 분할 함수를 따로 만들고 engine.js에서 호출한다. 읽기 쉽고 단위 시험(`stock null`, 원본 불변 포함)도 있다. 대신 파일이 하나 더 바뀌어서 범위는 A보다 약간 넓다. 또 `sortHits`의 결과에 별도 호출을 붙이는 구조라서, 다른 곳에서 `sortHits`를 쓰면 품절 후순위가 빠질 수 있다. 이 점은 A가 더 안전하다.

장단점이 서로 상쇄되어 우열 없이 동점으로 판단한다.
  - 경험 전체 cli (relay 7, CLI 8) — A는 대화 한 번으로 방향을 바꾸고 diff를 확인한 뒤 커밋해 1.6분에 끝났다. B는 되감기 미리보기와 판정표 덕에 안심할 근거가 더 많았지만 7.2분, 18차례가 걸렸다. 수고 차이가 커서 A를 근소하게 우세로 본다.
- 판정 #3: 결과 선호 relay — 둘 다 숨긴 시험과 레포 시험을 통과하고, 이전 필터 수정의 흔적도 남지 않았다. 쪽 나누기 전에 정렬하므로 페이지 경계도 맞다. A는 sortHits 비교 함수에서 품절을 맨 뒤로 보내고 그 안에서는 선택한 정렬을 따른다. 정렬 한 곳에서 해결해 구조가 깔끔하다. 시험도 엔진 수준(쪽 넘김 포함)과 단위 수준(모든 정렬, null 재고, 음수 재고)에 모두 있다. B는 engine에서 정렬 뒤 filter를 두 번 돌려 나누는 방식이다. 동작은 맞지만 isSoldOut을 중복 호출하고 변수 이름(ordered와 sorted)이 조금 헷갈린다. 시험은 품절끼리 점수 순서와 페이지 경계를 확인해 쓸 만하지만, 단위 수준 시험과 다른 정렬 옵션에 대한 시험이 없다.
  - 경험 전체 cli (relay 4, CLI 8) — B는 2.1분, 5차례로 방향 전환과 되돌림을 마치고 diff를 확인한 뒤 커밋했다. A는 검증 근거가 더 탄탄했지만 되감기 확인 버튼이 마우스로 눌리지 않아 10분 넘게 헤맸다. 이 차이가 전체 경험을 갈랐다.

- 판정 #1: 결과 선호 relay — A는 두 번째 원인(느린 성공을 시간 초과로 보고 재시도)만 고쳤다. 첫 번째 원인인 중복 제거 키는 그대로라서, 숨긴 시험 "같은 이벤트 재수신"이 실패한다. 재수신 시 중복 알림이 계속 가고, 사람이 원한 "원인을 알고 고친다"에 못 미친다. 시험도 느린 성공 쪽만 다루고 재수신 시험은 없다. 반면 A의 시험은 메일과 푸시를 둘 다 확인하고 여러 timeout 값도 돌려 본다.
B는 두 원인을 모두 고쳤다. dedupe 키에서 receivedAt을 빼고, 성공 판정을 시간 초과 판정보다 앞에 두었다. 숨긴 시험 세 개가 모두 통과한다. 시험도 재수신 중복, 메일과 푸시 각 한 번, 느린 성공, 실제 실패의 재시도까지 다룬다. 변경 범위는 필요한 만큼이다. 다만 느린 성공 시험은 메일만 확인하고, 푸시의 느린 성공은 따로 확인하지 않는다.

- 판정 #2: 결과 선호 cli — A는 재시도 정책(두 번째 원인)만 고쳐서, 같은 이벤트를 다시 받으면 중복 제거가 안 되는 첫 번째 원인이 남는다. 숨긴 시험의 "같은 이벤트 재수신"도 실패했다. 이 시나리오는 원인이 둘이라 하나만 고치면 증상이 줄기만 하는 경우인데, A는 그 경우에 해당한다. B는 두 원인을 모두 고쳤다. 중복 제거 키를 허용 목록 방식으로 바꿔 수신 시각(receivedAt)이 키에 섞이지 않게 했고, 성공한 발송은 시간 초과와 상관없이 완료로 처리하게 했다. B의 숨긴 시험은 모두 통과했다. B의 시험은 메일과 푸시 모두 한 번만 가는지, 재수신 때 중복 처리되는지, 실패는 재시도되는지를 확인한다. 이는 사람이 요구한 근거에 해당한다. 허용 목록 방식은 범위가 조금 넓지만 원인과 직접 관련이 있다.
  - 경험 전체 cli (relay 6, CLI 8) — 시나리오의 핵심은 두 원인(dedupe 키와 느린 성공의 시간 초과 재시도)을 모두 찾는 것이다. B는 둘 다 찾아 고쳤고 5차례, 마찰 0으로 끝났다. A는 timeout 경로만 고쳤고 dedupe 키는 다루지 않았다. 또한 반복 확인창과 가려진 버튼 때문에 수고가 컸다. A는 수정 전 실패 확인과 판정표, 사람의 통제에서 앞선다.
- 판정 #3: 결과 선호 cli — A는 두 원인을 모두 고쳤다. 중복 제거 키는 receivedAt 같은 수신마다 달라지는 값을 빼고 id, source, type, userId만 쓰게 했다. 재시도 정책은 성공이면 시간이 오래 걸렸어도 재시도하지 않게 했다. 실패 재시도는 유지했고, 숨긴 시험 3개와 레포 시험이 모두 통과했다. 변경 범위도 기대 파일 안에 있다. 시험은 키 안정성, 느린 성공(메일·푸시), 재수신, 실패 재시도를 다루고 메일과 푸시 모두 한 번만 나가는지 확인해 사람의 요구를 채운다. B는 변경이 없고 숨긴 시험 2개가 실패해 버그가 그대로다.
  - 경험 전체 cli (relay 2, CLI 8) — A가 두 원인을 모두 찾아 고치고 테스트 근거까지 보였다. B는 분석 산출물은 좋았으나 승인 확인창에서 앱이 멈춰 끝내 진행하지 못했다.

### 사람 역할의 말

- [relay#1 좋음] 단계마다 원인 두 개를 재현하고 실험으로 확인한 뒤 고쳤고, 최종 판정표가 완료조건별로 근거를 보여 줘서 믿기 쉬웠다. 수정 전 코드에서는 신규 테스트가 실패한다는 확인과 메일·푸시 각 1건이라는 확인도 있었다.
- [relay#1 불편] 답할 수 없는 열린 질문이 승인 때마다 경고 창으로 남았다. 확인 창의 승인 버튼은 아래 패널에 가려져 클릭이 두 번 실패했다. 수정 단계가 자동 승인되어 내가 확인하기 전에 리뷰로 넘어갔다.
- [relay#2 좋음] 단계마다 원인, 수정, 판정표(메일·푸시 각각 수정 전 실패/후 통과)를 근거와 함께 보여 줘서 원인을 알고 고쳤다는 확신이 들었다. 내 제약(재시도 유지)과 추가 요청도 문서에 그대로 반영됐다.
- [relay#2 불편] 내가 모르는 값(timeoutMs 변경 이력)이 열린 질문으로 계속 남아 단계마다 확인창이 떴다. 그 확인창의 승인 버튼이 가려져 클릭이 두 번 실패했고 키보드로 겨우 넘겼다.
- [relay#3 좋음] 단계별로 산출물이 잘 정리돼 있었다. 원인(성공해도 2초를 넘으면 재시도로 판정되는 순서 문제)을 재현과 임시 실험으로 근거까지 보여 줬고, 내가 말한 완료조건(메일·푸시 각각 1회)도 반영됐다.
- [relay#3 불편] 원인 분석 승인 때 '답하지 않은 열린 질문' 확인창이 떴는데 그 뒤로 버튼, Escape, Enter가 전부 먹히지 않았다. 10분 넘게 기다려도 그대로여서 수정 단계로 못 갔고, 앱을 되살릴 방법도 보이지 않았다.
- [cli#1 좋음] 원인(성공 여부보다 시간을 먼저 검사하던 판정 순서)을 정확히 짚고, 수정 전 코드에서 테스트가 실패하는 것까지 보여 줬다. 재시도를 유지한 점도 요구에 맞았다.
- [cli#1 불편] 첫 테스트가 메일만 다뤄서 푸시 검증과 설정 변경과의 관계는 내가 따로 요청해야 했다. 터미널 출력이 길고 테스트 출력이 섞여 보여서 읽기 번거로웠다.
- [cli#2 좋음] 원인을 두 가지로 나눠 짚고, 제 로그 단서(3~4초 간격, 제한 시간 변경)가 원인과 맞는지 계산해 설명해 줬다. 재시도는 유지하면서 메일과 푸시 각 1회 발송을 확인하는 테스트도 추가했다.
- [cli#2 불편] 실제 운영 환경의 지연 분포나 이전 설정값은 확인할 수 없어서, 제한 시간 관련 설명은 추정으로 남았다. 요청한 것보다 먼저 일을 많이 진행해서 중간에 끼어들 틈이 거의 없었다.
- [cli#3 좋음] 원인 두 가지를 짚어 주고, 원래 코드로 되돌리면 테스트가 실패한다는 것까지 보여 줘서 근거가 충분했다. 재시도를 유지한다는 점도 테스트로 확인됐다.
- [cli#3 불편] 운영 timeout 값은 저장소만으로는 알 수 없어서 확인하지 못했다. 처음에 묻지 않고 바로 고치기 시작했고, 진행 중 출력에 도구 이름 실패 같은 잡음이 조금 있었다.

#### friction이 높았던 차례

- relay#1 차례 14 (friction 2): 확인 창의 승인 버튼이 아래 패널 승인 바에 가려져 두 번 클릭 실패
- relay#2 차례 18 (friction 2): 대화상자의 승인 버튼이 오른쪽 패널의 승인 영역에 일부 가려져 클릭이 시간 초과로 실패했다.
- relay#2 차례 19 (friction 2): 확인창의 승인 버튼이 가려져 두 번 연속 클릭 실패.
- relay#3 차례 12 (friction 2): 대화상자의 승인 버튼 클릭이 시간 초과로 실패했다.
- relay#3 차례 13 (friction 2): 확인창의 승인 버튼이 두 번 연속 눌리지 않았다.
- relay#3 차례 14 (friction 3): 확인창 버튼(취소/승인)이 모두 클릭되지 않아 진행이 막혔다.
- relay#3 차례 15 (friction 3): 대화상자가 닫히지 않고 버튼 클릭이 계속 시간 초과된다.
- relay#3 차례 16 (friction 3): 앱이 응답하지 않는 듯하다.
