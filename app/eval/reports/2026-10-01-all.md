- 판정 #2: 결과 선호 cli — 소스 변경은 두 결과가 완전히 같다. 둘 다 숫자 정렬로 고쳤고, 동점자는 정렬 후 slice로 처리해 이름 중복을 없앴다. 시험에서 차이가 난다. A는 동점 시험이 n=2로 3명 중 2명을 자르므로, 동점일 때 입력 순서로 n명에서 자른다는 요구를 직접 확인한다. 자릿수 시험도 9, 100, 10으로 n=1과 n=2를 모두 본다. B의 동점 시험은 n=3이라 자르는 동작을 확인하지 못한다. 그래서 A가 회귀를 더 잘 막는다.

A는 `topScores`를 고쳤지만 이를 검증하는 시험이 없어, `leaderboard`가 더 이상 `topScores`를 쓰지 않는 만큼 그 수정은 시험에 걸리지 않는다. 기록에는 조사나 질문 과정이 보이지 않아 이 점은 비교에 반영하지 않았다.

- 판정 #2: 결과 선호 relay — 두 결과의 src/inventory/release.js 수정은 완전히 같다. 해제할 때 창고별 키로 캐시를 갱신하고, 키가 맞지 않던 SKU 단위 invalidate는 뺐다. 원인을 고쳤고 리포트 코드는 건드리지 않았으며 캐시도 유지했다. 숨긴 시험과 레포 시험도 둘 다 통과했다. 차이는 회귀 시험뿐이다. A는 주문, 취소, 재주문을 재현하고 예약량과 가용 재고 비음수를 확인한다. B도 같은 흐름을 재현하는데, 할당이 부산으로 가는지, 캐시를 거친 getStock 값이 테이블과 같은지, 모든 창고 기록의 가용 재고가 비음수인지까지 확인한다. 그래서 B의 시험이 더 촘촘해 근소하게 B를 택한다. 또 B는 주문 관련 시험 파일에 시험을 넣었는데, 여러 단계 흐름이므로 적절하다.

- 판정 #1: 결과 선호 relay — 두 결과는 같은 근본 수정이다. 결과를 입력 순서 자리에 넣고 진행 카운터를 따로 둔다. 병렬은 유지했고 숨긴 시험도 모두 통과했다. B는 JSDoc과 주석이 더 낫다. 다만 시험이 묶음 하나(동시성 4, 항목 4개)뿐이라 묶음 경계의 인덱스 오프셋(start+i)을 검증하지 못한다. A는 5개 항목을 동시성 3으로 돌려 여러 묶음을 가로지르는 경우까지 확인하므로 회귀 방지력이 더 크다. 그래서 A를 근소하게 선호한다.
  - 경험 전체 cli (relay 6, CLI 7) — 두 쪽 모두 증상 덮기 없이 원인을 고치고 병렬을 유지했으며 반복 실행 근거를 냈다. B는 수고가 훨씬 적다(3차례, 1분). A는 판정표와 20회 반복으로 확신 근거가 조금 더 낫지만, 자동 승인으로 diff를 따로 열어야 했고 시간도 더 걸렸다. 그래서 B를 근소하게 우세로 본다.
- 판정 #2: 결과 선호 relay — 두 결과의 코드 수정은 사실상 같다. 결과를 `push`로 쌓던 것을 입력 위치 `results[start+i]`에 넣도록 바꿨고, 병렬(청크 동시 실행)은 그대로다. 그래서 완료 순서와 무관하게 결과가 작업과 짝지어진다. 숨긴 시험도 둘 다 통과했다. 변경 파일도 같고 범위도 적절하다. 차이는 회귀 시험에 있다. A는 항목을 `{ms, i}` 객체로 만들고 인덱스 `i`를 반환한다. 지연 값이 같아도 위치 대응이 분명히 검증된다. 동시성 3에 지연 [20,1,10,2,15,1]이라 청크 안의 완료 순서가 뒤바뀌는 경우도 확실히 나온다. B는 지연 값 자체를 반환하고 비교한다. 값이 모두 달라서 동작은 하지만, 값이 겹치면 순서 검증이 약해질 수 있고 의도가 덜 분명하다. 두 결과 모두 반복 실행 근거는 기록에 나타나지 않아서, 이 점으로는 우열을 가릴 수 없다. 따라서 시험이 조금 더 견고한 A를 선호한다.
  - 경험 전체 cli (relay 6, CLI 8) — 두 기록 모두 근본 원인을 고치고 병렬을 유지했으며 반복 실행 근거를 제공했다. B는 수고가 훨씬 적고 흐름이 간결했으며 운영 문의까지 연결했다. A는 자동 승인으로 원인 확인 기회를 놓쳤고 대기가 길었다.
- 판정 #3: 결과 선호 tie — 두 결과는 사실상 같다. 둘 다 runPool에서 결과를 끝난 순서대로 push하던 것을 입력 위치(results[start+i])에 넣도록 바꿨다. 이것이 완료 순서에 기댄 짝짓기라는 원인이다. 병렬(chunk 단위 동시 실행)은 유지했고 숨긴 시험도 통과했다. onChunk의 done 값은 카운터로 유지해 기존 동작이 같다. 변경은 pool.js와 pool.test.js뿐이며 범위도 같다. 회귀 시험도 둘 다 지연을 섞어 입력 순서를 확인한다. A는 지연이 6개이고 B는 5개라 차이가 아주 작다. 반복 실행 근거는 기록에 없어서 둘 다 tests는 4점이다. 변수 이름(finished/done)만 다르다. 우열을 가릴 근거가 없어 tie로 판단한다.
  - 경험 전체 cli (relay 6, CLI 8) — A가 수고가 훨씬 적고 수정 전후 반복 실행 근거(3/30 → 0/30)를 보여 확신 근거가 더 컸다. B는 의도 단계에서 요구를 반영하게 했다는 통제 장점이 있으나 9차례로 길었고 수정 전 재현 근거가 없었다.

- 판정 #1: 결과 선호 cli — A는 두 원인을 모두 고쳤다. 중복 제거 키에서 receivedAt처럼 수신 때마다 달라지는 값을 빼고 id, source, type, userId만 쓰게 했다. 또 느리게 성공한 발송을 재시도하지 않도록 policy를 바꿨다. 숨긴 시험 세 가지가 모두 통과했다. 실제 실패는 여전히 재시도하고, 느린 일시 오류는 timeout 사유로 재시도한다. 시험도 두 경로를 다룬다. 같은 이벤트가 늦게 재수신되는 경우, 느린 성공, 메일과 푸시가 둘 다 한 번만 가는 경우를 확인한다. 사용자가 원한 "둘 다 한 번" 근거에 맞는다. KEY_FIELDS를 허용 목록으로 바꾼 것은 약간 넓은 변경이지만 원인에 직접 닿는다. B는 재시도 쪽 원인만 고쳤다. 첫 원인인 중복 제거 키는 손대지 않아 숨긴 시험 "같은 이벤트 재수신"이 실패했고, 증상이 일부만 줄어든다. 시험은 재시도 경로만 다루고, 중복 재수신 시험이 없다. 재시도 시험 자체는 꼼꼼하고 정책 수정도 깔끔하다.
  - 경험 전체 relay (relay 7, CLI 6) — A는 두 원인(dedupe 키, 느린 성공 재시도)을 찾았고 빠르게 끝났다. 하지만 timeout 설정과 푸시 테스트는 사람이 묻기 전에 다루지 않았다. B는 더 오래 걸렸고 중간 단계를 볼 틈이 없었다. 반면 완료조건별 근거, 실패 재시도 테스트, 복원 시 실패 확인으로 신뢰가 더 높았다. 기록상 B의 요약은 retry 경로만 언급해 dedupe 키 원인은 드러나지 않는다. 이는 감점 요인이다. 그래도 근거 제시 면에서 B가 근소하게 낫다고 판단한다.
- 판정 #2: 결과 선호 cli — 두 결과 모두 중복 제거 키를 신원 필드로 한정하고, 느린 성공을 재시도하지 않게 고쳤다. 숨긴 시험도 모두 통과했다.

차이는 policy.js에 있다. B는 성공 확인만 앞으로 옮겼다. 그래서 느리게 실패한 영구 오류는 여전히 'timeout' 사유가 되어 재시도된다. 영구 오류는 재시도해도 소용없는데도 그렇게 된다. A는 영구 오류 판정을 시간 초과 판정보다 먼저 하므로 그 경우에 give-up이 된다. 다만 이것은 원래 동작을 바꾸는 변경이라 약간 범위를 넓힌 면이 있다. 그래도 논리가 더 정확하고, 이 경우를 시험으로도 확인한다.

시험은 둘 다 충분하다. B는 메일과 푸시를 채널별로 나눠 검증하고 decide 단위 시험도 더했다. A는 느린 영구 오류와 일시 오류까지 다루고, 한 시험 안에서 메일과 푸시를 함께 확인한다. 그래서 시험 범위는 A가 조금 더 넓다.

종합하면 A의 정확성이 약간 더 높다.
  - 경험 전체 cli (relay 6, CLI 7) — 두 기록 모두 두 원인을 찾았고 재시도를 유지했으며 메일과 푸시 근거를 보였다. A는 수고가 적고 사람이 diff를 직접 확인한 뒤 커밋을 지시했다. B는 판정표로 확신 근거는 더 나았지만, 단계가 자동 승인되고 대기가 길어 경험이 약간 떨어진다.
- 판정 #3: 결과 선호 relay — A는 두 번째 원인(느린 성공을 시간 초과로 보고 재시도)만 고쳤다. 첫 원인인 중복 제거 키는 그대로라 숨긴 시험의 "같은 이벤트 재수신"이 실패한다. 증상만 줄어드는 전형적인 부분 수정이다. 추가한 시험도 정책 단위 시험뿐이라 메일과 푸시가 한 번만 가는지는 보여 주지 못한다.

B는 두 원인을 모두 고쳤다. 키를 식별 필드(source, id, type, userId)만으로 만들어 재수신을 걸러내고, 성공이면 시간과 상관없이 done으로 처리한다. 숨긴 시험도 모두 통과했다. 시험은 메일과 푸시가 각각 한 번만 가는지, 느린 성공이 재시도되지 않는지, 실패는 여전히 재시도되는지를 통합 수준에서 확인한다. 사용자가 원한 근거로 충분하다.

B의 키 변경은 화이트리스트 방식이라 범위가 약간 넓지만, 원인을 고치는 변경이므로 타당하다.
  - 경험 전체 relay (relay 7, CLI 5) — B가 두 원인 모두를 찾아 조사 산출물에 드러냈고 검증 근거도 더 풍부했다. A는 사람이 방향을 쥐었지만 첫 원인을 놓쳤고 설정값도 확인하지 못했다.

### 사람 역할의 말

- [relay#1 좋음] 판정표에 완료조건마다 근거가 붙어 있었다. 기존 코드로 되돌리면 테스트가 실패하는 것까지 확인해 줘서 믿을 만했다.
- [relay#1 불편] 원인 분석과 수정 단계가 자동 승인돼서 빨리 지나갔다. 그 단계 산출물을 볼 틈이 없어서 diff를 따로 열어야 했다. 세션이 뜨는 동안 빈 화면으로 기다린 점도 불편했다.
- [relay#2 좋음] 완료조건별 판정표에 근거(명령과 결과 수치)가 붙어 있었다. 메일과 푸시 각각 통과했다는 것을 바로 확인할 수 있었다.
- [relay#2 불편] 원인 분석과 수정 단계가 자동 승인되어, 에이전트의 원인 설명을 보고 승인하는 과정 없이 리뷰 단계로 넘어갔다. 코드를 직접 보려면 inspect_diff를 써야 했다.
- [relay#3 좋음] 리뷰 단계의 판정표가 완료조건마다 근거를 붙여 줬다. 수정 전 코드로 돌리면 테스트가 실패한다는 확인까지 있어서 믿을 만했다.
- [relay#3 불편] 원인 분석과 수정 단계가 자동 승인으로 바로 지나가서, 원인 설명을 보기 전에 3단계로 넘어갔다. 내가 직접 inspect_diff로 확인해야 했다.
- [cli#1 좋음] 근본 원인 두 가지를 짧은 시간에 찾아 설명했다. 회귀 테스트를 추가했고, 수정 전 코드에서 실패하는 것도 확인했다.
- [cli#1 불편] 지난주 timeout 설정 변경은 내가 물어보기 전에는 확인하지 않았다. 확인해 달라고 한 뒤에도 저장소로는 알 수 없다는 결론이었다. 푸시 쪽 테스트도 내가 물어본 뒤에야 보강했다.
- [cli#2 좋음] 원인을 두 가지로 나눠 설명했고, 수정 전에는 실패하던 테스트를 추가해 메일과 푸시가 한 번만 가는 근거를 보여 줬다. 그래서 증상만 막은 수정이 아니라는 확신이 들었다.
- [cli#2 불편] 에이전트가 아무것도 묻지 않았다. 지난주에 바꾼 발송 제한 시간 설정이나 발송 로그 같은 내 단서를 쓸 기회가 없었다. 실제 설정값이 바뀐 건지는 확인하지 못했다.
- [cli#3 좋음] 원인을 근본까지 짚어 설명했고, 메일과 푸시 둘 다 수정 전후 전송 횟수를 실행 결과 표로 보여 줘서 근거가 분명했다.
- [cli#3 불편] 첫 응답에서는 설정 변경과 로그 지연 정황을 확인하지 않았다. 내가 따로 물어야 했고, 운영 설정값은 끝내 확인하지 못했다.
