- [relay#1 불편] 에이전트의 열린 질문(짝수 길이)에 답할 곳이 터미널이라는 걸 바로 알기 어려웠다. 터미널에 Stop hook 오류가 보였는데 그게 문제인지 알 수 없었다.
- [relay#2 좋음] Work를 버그마다 따로 만들어서 브랜치와 커밋이 자연스럽게 나뉘었다. 단계마다 요약, 변경 diff, 판정표를 볼 수 있어서 승인하기 전에 확인하기 쉬웠다.
- [relay#2 불편] 에이전트가 짝수 개수 배열을 범위 밖이라고 가정해서 내가 의도 단계에서 직접 바로잡아야 했다. 단계가 많아 승인 버튼을 여러 번 눌러야 했고, 세션이 뜨는 동안 검은 화면으로 기다리는 시간도 있었다.
- [relay#3 좋음] Work를 둘로 나눠 동시에 진행할 수 있어서 두 버그가 섞이지 않았다. 각 단계의 요약과 diff, 최종 판정표를 보고 승인할 수 있었다.
- [relay#3 불편] 단계가 많아서 승인을 여러 번 눌러야 했고, 세션이 뜨는 동안 까만 화면에서 기다려야 했다. 완료 뒤 커밋이나 브랜치 이름이 화면에 잘 안 보여서, 로컬 브랜치에 커밋됐는지는 앱을 믿고 넘어갔다.
- [relay#4 좋음] Work마다 브랜치가 따로 생겨서 두 버그가 섞이지 않았다. 단계마다 요약, 변경 diff, 판정표가 바로 보여서 승인하기 전에 확인하기 쉬웠다.
- [relay#4 불편] 새 Work 창에 자동 승인과 질문 방식 같은 옵션이 많고 화면에 보이지 않는 선택 항목도 있어 처음엔 산만했다. 단계가 많아서 승인을 여러 번 눌러야 했다.
- [relay#5 좋음] Work마다 브랜치가 따로 생겨서 두 버그를 섞지 않고 진행할 수 있었다. 단계마다 요약과 diff, 판정표를 바로 볼 수 있어서 승인 판단이 쉬웠다.
- [relay#5 불편] 단계가 많아서 작은 버그인데도 승인을 여러 번 눌러야 했다. 세션이 시작될 때 터미널이 까맣게 비어 있는 시간에는 무슨 일이 벌어지는지 알 수 없었다.
- [cli#1 좋음] 한 번 요청으로 두 버그를 따로 커밋해 줬고, 화면에 diff와 실행 결과가 바로 보였다. 짝수 중앙값 문제도 에이전트가 먼저 짚어 줬다.
- [cli#1 불편] 별도 테스트 없이 node 한 줄로만 확인해서 회귀 방지 근거가 약했다. 브랜치는 나누지 않고 main에 바로 커밋했다.
- [cli#2 좋음] 브랜치를 나눠 따로 커밋해 달라는 요청을 그대로 지켰다. 짝수 개수 이슈도 범위 밖이라며 먼저 알려 주고 내 지시를 기다렸다.
- [cli#2 불편] 테스트 추가는 처음에 시키지 않아서 내가 따로 요청해야 했다. 끝난 뒤에는 원래 브랜치로 돌아가지 않았고, 이 점은 요약에서야 알게 됐다.
- [cli#3 좋음] 요청 한 번으로 두 버그를 별도 브랜치와 별도 커밋으로 나눠 고쳤다. 실행으로 검증한 결과와 커밋 해시도 요약에 있었다.
- [cli#3 불편] 작업 과정이 접혀 있어서 diff는 내가 따로 확인해야 했다. 에이전트가 만든 브랜치 구성도 직접 확인해야 했다.
- [cli#4 좋음] 한 번 요청으로 브랜치 두 개를 따로 만들어 각각 커밋해 줬다. 변경이 섞이지 않았고 요약도 짧고 정확했다.
- [cli#4 불편] 버그를 재현하는 테스트를 추가하지 않았다. 확인은 node -e로만 했고, 내가 시키기 전에는 테스트 추가를 제안하지 않았다.
- [cli#5 좋음] 두 버그를 따로 요청하니 각각 별도 커밋으로 깔끔하게 나뉘었다. 원인 설명과 테스트 추가도 함께 나왔다.
- [cli#5 불편] 별로 불편한 점은 없었다. 굳이 꼽자면 에이전트가 브랜치를 나누지 않고 한 브랜치에 커밋 두 개로 처리해서, 팀별로 리뷰하기엔 브랜치 분리가 더 나았을 수 있다.

A는 자식 프로세스에서 TZ를 바꿔 실행하는 회귀 시험을 추가했다. 로스앤젤레스, 서울, UTC에 극단적인 시간대 두 개까지 포함하고, 일주일 전체를 검증한다. 이 시험은 시간대에 따라 결과가 달라지는 버그를 실제로 막는다. B는 시험을 추가하지 않았다. 기존 시험은 실행 환경의 시간대에 좌우되므로, 같은 버그가 다시 생겨도 개발자 PC에서는 통과할 수 있다. A의 시험은 35줄로 다소 길지만 근거가 분명해서 scope 위반으로 보지 않는다.
  - 경험 전체 cli (relay 6, CLI 8) — B는 3차례, 0.9분 만에 원인 설명과 시간대별 검증까지 얻어 수고가 훨씬 적었다. A는 테스트 추가와 검증 판정표로 확신 근거가 더 많고 사람이 방향도 더 세게 쥐었다. 다만 15차례와 4.8분이 들었고 요약 탭 갱신 문제도 있었다. 작은 버그에는 B가 더 나은 경험이다.
- 판정 #5: 결과 선호 relay — 두 결과 모두 코드 수정이 같다. getDay()를 getUTCDay()로 바꿨고, 날짜만 있는 문자열이 UTC 자정으로 파싱된다는 점을 주석으로 설명했다. 숨긴 시험(로스앤젤레스, 서울, UTC)도 둘 다 통과했다. 차이는 시험에서 난다. A는 금·토·일·월 네 날짜를 네 시간대에서 확인해 주말 경계를 양쪽으로 검증한다. B는 토요일과 금요일만 확인하므로 일요일과 월요일 경계는 빠져 있다. 그래서 A를 약간 더 낫다고 판단했다.
  - 경험 전체 cli (relay 6, CLI 7) — 두 기록 모두 getUTCDay로 고치고 여러 시간대 테스트를 추가했다. B는 3차례에 1분으로 끝났고, A는 승인 단계와 대기가 많아 12차례에 3.9분이 걸렸다. 반면 A는 사람이 diff와 판정표를 직접 확인할 수 있어 확신과 통제가 더 나았다. A는 빈 화면과 질문에 답할 곳이 없다는 불편이 있었고, B는 회귀 테스트를 처음부터 넣지 않아 따로 요청해야 했다. 수고 차이가 커서 전체로는 B를 조금 더 높게 봤다.

### 사람 역할의 말

- [relay#1 좋음] 단계마다 요약, 판정표, 변경 내용이 나와서 승인 전에 근거를 확인할 수 있었다. 특히 LA 시간대에서 실패를 재현했고, 수정 전에는 실패하고 수정 후에는 통과하는 테스트를 확인했다.
- [relay#1 불편] 이 크기의 한 줄짜리 버그에 비해 단계가 많았다(L로 잡혀 6단계). 단계 사이에 기다리는 시간이 있었고, 작업 중에는 검은 화면만 보였다. 수정 단계에서 handoff YAML 형식 오류가 났지만 에이전트가 스스로 고쳤다.
- [relay#2 좋음] 단계마다 산출물, 판정표, 변경 diff를 바로 확인할 수 있었다. LA 시간대에서 재현하고 시간대별 회귀 테스트로 검증한 근거가 잘 보였다.
- [relay#2 불편] 단계가 많아서 승인 클릭이 반복됐고, 작업 중에는 검은 빈 화면이 나와 기다리는 동안 상태를 알기 어려웠다. 리뷰 단계에서 handoff 형식 오류 로그가 잠깐 보여 당황스러웠다.
- [relay#3 좋음] 단계마다 요약·가정·위험이 정리되어 나왔고, 재현 결과와 시간대별 테스트, 최종 판정표가 근거로 붙어 있어서 결과를 믿기 쉬웠다.
- [relay#3 불편] 리뷰 요약 탭에는 지적 내용이 없어 산출물 탭을 따로 열어야 했다. 작업 중에는 터미널이 빈 검은 화면이라 진행 상황을 알 수 없었다.
- [relay#4 좋음] 단계마다 승인 패널에 요약, 결정, 가정, 위험이 정리돼 있었다. 최종 검증 판정표에는 완료조건별 근거로 시간대별 테스트 결과가 나와서 결과를 믿기 쉬웠다.
- [relay#4 불편] 의도 정리에서 내가 답한 뒤에도 요약 탭에는 옛 내용이 그대로 남아 있었다. 산출물 탭을 따로 열어 봐야 반영 여부를 알 수 있었다. 터미널의 stop hook 오류 메시지도 뜻을 알기 어려웠다.
- [relay#5 좋음] 단계마다 요약, 변경, 판정표가 승인 패널에 나와서 diff와 검증 결과(여러 시간대 테스트, 수정 전 실패 재현)를 바로 확인하고 승인할 수 있었다.
- [relay#5 불편] 단계 전환 직후 터미널이 까만 빈 화면으로 잠깐 있어서 멈춘 건지 헷갈렸다. 의도 정리의 열린 질문에 답할 곳이 따로 없어 터미널에 직접 쳐야 했던 것도 아쉬웠다.
- [cli#1 좋음] 원인 설명이 정확했고, 여러 시간대(TZ)를 바꿔 직접 돌려 본 검증이 바로 나왔다. 몇 분 만에 끝났다.
- [cli#1 불편] 저장소에 테스트가 있는지 확인하지 않았다고 에이전트가 말했는데, 그 부분이 조금 아쉬웠다. 커밋 전에 diff를 따로 열어 보지 않았다.
- [cli#2 좋음] 원인을 시간대 동작으로 설명해 줬고, 여러 TZ로 테스트를 돌려 검증했다. 수정 전 실패도 확인해 줘서 믿을 수 있었다.
- [cli#2 불편] 처음에는 수정 전 실패를 확인하지 않고 끝냈다. 내가 따로 요청해야 확인해 줬다. 커밋 전에 diff를 직접 열어 보지는 않았고 화면 요약에 의존했다.
- [cli#3 좋음] 원인(UTC 파싱과 로컬 getDay의 불일치)을 바로 설명해 줬다. 여러 시간대로 테스트를 돌려 검증해서, 내 PC에서 재현이 안 되던 문제도 믿을 수 있었다.
- [cli#3 불편] 딱히 불편한 점은 없었다. 에이전트가 너무 빨리 끝내서, 작업 중에 내가 끼어들거나 방향을 조정할 여지가 거의 없었다.
- [cli#4 좋음] 원인 설명이 명확했고, 여러 시간대(LA, 서울, 키리티마티)로 직접 돌려 검증한 결과를 보여 줬다.
- [cli#4 불편] 별도로 눈에 띄는 불편은 없었다. 굳이 꼽자면 커밋 요청 때 새 브랜치를 자동으로 만든 점(사후 안내만 있었음)과 테스트 파일이 추가되지 않은 점.
- [cli#5 좋음] 원인 설명이 명확했고, 시간대별로 테스트를 돌렸다. 수정 전 코드에서 LA 케이스가 실패하는 것까지 확인해 줬다.
- [cli#5 불편] 첫 수정에서는 회귀 테스트를 넣지 않았고 수정 전 코드도 돌려 보지 않아서, 내가 따로 요청해야 했다. 나는 diff를 직접 보지 않고 요약에 의존했다.
