B는 이 키 불일치를 직접 고쳤다. 해제할 때 할당된 창고마다 `invalidate(sku, warehouse)`를 호출하고, 다른 것은 건드리지 않았다. 시험은 서울 주문·취소 뒤 부산 주문, 부산 단독 주문·취소·재주문, 예약 실패 되돌리기까지 세 경로를 다룬다. 리포트 행까지 확인해 리포트가 그대로 맞는지도 본다. 이 시험들은 원인과 재현 단계를 잘 드러낸다.

A는 해제할 때 캐시를 `set`으로 갱신해 불일치를 우회했다. 캐시를 끄지 않았고 이 변경으로 재현 시나리오는 고쳐진다. 그러나 `reserve.js`에 예약 상한 검사를 추가했다. 이는 요구 범위 밖이고, 증상을 막는 방어 코드에 가깝다. 이 검사는 실재고보다 많은 예약을 예외로 던지므로 기존 흐름에서 새 실패를 만들 수 있다. 시험 두 개는 유용하지만 B보다 재현 범위가 좁다.
  - 경험 전체 cli (relay 7, CLI 8) — A는 원인 재현과 계획 설명 뒤 한 번의 승인으로 끝났다. 그래서 수고가 크게 적었다. B는 통제와 확신 근거가 더 풍부했지만, 승인과 대기가 많고 형식 오류가 두 번 노출돼 수고가 컸다. 설문 점수는 같았다.
- 판정 #2: 결과 선호 relay — 코드 수정은 A와 B가 바이트 단위로 같다. 둘 다 release.js에서 `invalidate(sku)` 대신 `stockCache.set(sku, warehouse, next)`로 창고별 키를 갱신한다. 숨긴 시험도 모두 통과했고 바뀐 범위도 같다. 차이는 시험뿐이다. A의 시험은 부산 창고에서 예약→부분 해제→재예약→전체 해제를 거치며, 캐시 경유 값(getStock)과 테이블 값을 둘 다 비교한다. 마지막에는 모든 레코드가 `onHand - reserved >= 0`인지도 확인한다. 부분 해제와 여러 단계를 다루므로 회귀를 더 잘 막는다. - 판정 #2: 결과 선호 cli — A와 B 모두 숨긴 시험과 레포 시험을 통과했고, 페이지 나누기 전에 품절을 맨 뒤로 보내므로 페이지 경계도 맞다. 앞서 뺀 필터 코드가 남았는지는 두 diff에서 모두 보이지 않는다. 차이는 변경 범위와 코드 품질이다. B는 sort.js의 비교 함수에 품절 여부를 우선 조건으로 넣어, 파일 두 개를 21줄만 고쳤다. 이 방식이면 어떤 정렬이든 품절이 뒤로 가고, 그룹 안 순서는 원래 비교 함수가 정한다. A는 engine.js에 단계를 하나 더하고 sort.js에 함수를 추가했다. 동작은 맞지만 변경이 더 크고 흐름이 늘었다. A의 시험은 더 많지만 마지막 시험은 `||` 조건 때문에 검증이 느슨하다. B의 시험은 5가지 정렬과 여러 쪽 경계를 함께 확인해 간결하고 충분하다.
  - 경험 전체 cli (relay 6, CLI 8) — A는 되감기 미리보기, 백업, 검증 단계로 통제와 확신이 강했지만 22차례와 잦은 승인, 대기, 오류 메시지 부담이 컸다. B는 6차례에 방향 전환, 되돌리기, 커밋까지 끝냈고 diff로 흔적 없음을 확인했다. 전체 경험은 B가 낫다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 이전의 품절 필터 흔적도 남기지 않았다. 품절을 페이지 나누기 전에 전체 결과의 맨 뒤로 보내므로 페이지 경계도 맞다.

A는 sort.js의 sortHits 안에서 처리한다. 변경이 작고 정렬 5종에 모두 적용된다. 다만 시험이 약하다. 정렬 종류는 기본 관련도만 확인한다. 재고 상품의 상대 순서는 검증하지 않는다. 품절끼리의 순서 검사는 점수가 같은 항목에서도 통과할 수 있다.

B는 engine.js에서 sortHits 뒤에 soldOutLast를 호출한다. 정렬 5종 전체, 여러 쪽에 걸친 경계, 그룹 안 상대 순서, 재고가 null인 경우까지 시험한다. 회귀 방지 면에서 훨씬 낫다. 시험용으로 만든 soldOutOnly 헬퍼가 조금 복잡하고 변경 분량이 더 크다. 그래도 전체적으로 B가 더 낫다.
  - 경험 전체 cli (relay 6, CLI 8) — 두 기록 모두 방향 전환 뒤 이전 코드를 남기지 않고 새 방향으로 마쳤다. 사용 경험은 A가 훨씬 가벼웠다. B는 되감기와 미리보기가 좋았지만 차례가 많고 오류 메시지와 옛 완료조건 때문에 번거로웠다. 확신 면에서는 B가 앞섰다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 두 원인을 찾았다. 하나는 중복 제거 키에 receivedAt이 섞인 것이고, 다른 하나는 느린 성공을 시간 초과로 보고 재시도하는 것이다. 숨긴 시험도 모두 통과했다. 차이는 수정 범위와 시험에서 난다.

A는 receivedAt 한 필드만 제외하고, 성공이면 바로 done을 반환하도록 순서만 바꿨다. 실패의 재시도 동작은 그대로다. 시험은 키 단위, 정책 단위, 통합 수준을 모두 다룬다. 통합 시험은 메일과 푸시 각각의 느린 성공, 시각이 다른 재수신, 실제 실패의 재시도를 확인한다. 사람이 원한 "메일과 푸시 둘 다 한 번만"이라는 근거도 각각 나눠 보여 준다.

B는 키를 id, source, type, userId만 쓰는 허용 목록 방식으로 바꿨다. 이벤트에 다른 구분 필드가 있으면 서로 다른 알림이 중복으로 처리될 위험이 있다. 이는 필요 이상으로 넓은 변경이다. 정책 쪽에서도 영구 오류가 시간 초과를 넘기면 예전에는 재시도했지만 이제는 give-up으로 바뀐다. 이 동작 변화는 요청 범위 밖이다. 시험은 좋은 편이지만, 푸시와 메일을 한 시험에 묶어 원인 분리가 덜하다.
  - 경험 전체 tie (relay 7, CLI 7) — 두 기록 모두 원인 둘을 찾아 고쳤고 재시도도 유지했다. A는 단계별 산출물과 재현 근거로 신뢰를 더 줬지만 승인과 대기가 많아 6.8분이 걸렸다. B는 2.1분에 끝나 수고가 적었으나, 처음에 근거 없이 단정했고 운영 값은 확인하지 못했다. 그래서 종합은 비슷하다고 본다.
- 판정 #2: 결과 선호 relay — 둘 다 중복 제거 키(첫 원인)를 못 고쳐 숨긴 시험 '같은 이벤트 재수신'이 실패한다. 둘 다 느린 성공을 재시도하던 두 번째 원인만 고쳤다. B는 변경이 더 최소이고, 메일과 푸시가 각각 한 번만 가는지, 연속 느린 성공, 실제 실패의 재시도까지 통합 시험으로 보여 사람이 원한 근거를 준다. A는 단위 시험만 있고 영구 오류 동작까지 바꿨다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 2분에 원인과 근거, 커밋까지 끝냈다. B는 검증 근거와 구조는 더 좋았지만 16차례, 6분이 들었고 남은 열린 질문이 혼란을 줬다. 수고 차이가 커서 A가 근소하게 앞선다.
- 판정 #3: 결과 선호 relay — A는 두 원인을 모두 고쳤다. dedupe 키에서 재수신마다 달라지는 receivedAt을 제외했고, 느린 성공을 timeout으로 보던 retry 정책도 고쳤다. 숨긴 시험 3개가 모두 통과했다. 시험은 메일과 푸시를 각각 검증하고, 실제 실패와 timeout 오류의 재시도, 시간차를 둔 재수신까지 다룬다. B는 retry 정책만 고쳤고, 중복 제거 키 문제는 놓쳐서 숨긴 시험 '같은 이벤트 재수신'이 실패했다. 이 시나리오가 확인하려는 첫 번째 원인을 찾지 못한 것이다. B의 시험은 재시도 경로는 잘 검증하지만 재수신 중복은 검증하지 않는다. 보조 함수 config_baseDelay도 이름이 어색하다.
  - 경험 전체 relay (relay 8, CLI 6) — B가 훨씬 적은 수고로 끝냈다. 그러나 시나리오 목적은 두 원인을 다 찾고 근거를 보여 주는 것이다. A만 두 원인과 메일·푸시 근거를 산출물로 보여 줬고 사람이 승인 전에 확인할 수 있었다.

### 사람 역할의 말

- [relay#1 좋음] 단계마다 산출물과 판정표가 나왔다. 원인을 두 가지로 나눠 각각 임시로 고쳐 확인했고, 메일과 푸시 둘 다 한 번만 가는지 근거로 볼 수 있었다.
- [relay#1 불편] 리뷰 단계 요약 탭에는 지적 내용이 없어서 산출물 탭을 열어야 했다. 에이전트가 물어본 적이 없어서 내가 아는 사실(제한 시간 설정 변경, 두 번째 발송이 3~4초 늦음)은 전달할 기회가 없었다.
- [relay#2 좋음] 단계마다 요약, 결정, 가정, 위험이 정리돼 있었다. 마지막 판정표에서 메일과 푸시가 각각 한 번만 가고 재시도도 유지된다는 근거를 바로 볼 수 있었다.
- [relay#2 불편] 승인 대기 중에도 "열린 질문"이 계속 떠 있었다. 이미 답한 타임아웃 값 질문이 끝까지 남아서, 답이 반영됐는지 헷갈렸다. 새 Work 창에 설정 항목이 많아 처음엔 어수선했다.
- [relay#3 좋음] 단계마다 산출물과 판정표를 보여 줘서 원인, 수정, 메일·푸시 둘 다 한 번만 가는 근거, 실패 재시도가 유지되는 근거를 승인 전에 확인할 수 있었다.
- [relay#3 불편] 단계 전환 때 터미널이 까만 화면으로 한동안 비어 있어서 무슨 일이 일어나는지 알기 어려웠다. 운영의 timeout 실제 값은 끝까지 확인되지 않았고, 근거도 가짜 전송과 가상 시계로 만든 재현이었다.
- [cli#1 좋음] 원인을 두 가지 찾아 고쳤고, 재시도는 유지한 채 메일·푸시 각 1건을 확인하는 테스트까지 추가해 근거를 보여 줬다. 추측과 사실을 구분해 솔직하게 인정한 점도 좋았다.
- [cli#1 불편] 처음 요약에서 원인 2가 주원인일 가능성이 크다고 근거 없이 단정했다. 내가 물어보고서야 추측이었다고 밝혔다. 운영 값(타임아웃 설정)은 저장소에서 확인할 수 없어 원인 1을 완전히 입증하지 못했다.
- [cli#2 좋음] 원인(성공 여부 전에 시간부터 확인)을 짚고, 로그의 3~4초 간격과 '가끔 세 번'까지 가상 시계 재현으로 설명했다. 수정 전후 표로 메일·푸시가 한 번만 가고 재시도는 유지됨을 보여 줬다.
- [cli#2 불편] 처음에는 수정이 끝난 뒤에야 설정 변경과 로그 정보를 물어보게 됐다. 에이전트가 먼저 묻지 않았고, 검증도 가짜 전송·가상 시계로만 해서 실제 환경 검증은 빠졌다.
- [cli#3 좋음] 원인을 코드 근거로 짚어 줬고, 수정 전 코드로 되돌려 새 테스트가 실패하는 것까지 확인해 줬다. 재시도가 꺼지지 않았다는 점도 테스트로 보여 줬다.
- [cli#3 불편] 에이전트가 제한 시간 설정을 먼저 묻지 않았고, 내가 물은 뒤에야 확인했다. 그마저 저장소 이력이 없어 운영 값은 확인하지 못했다. 3~4초 지연 패턴도 계산한 추정일 뿐이다.
