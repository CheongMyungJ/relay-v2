- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 파서 구조도 거의 같다. 차이는 두 가지다. 첫째, A는 테스트를 추가했다. 따옴표 안 쉼표, 이중 따옴표, 빈 칸, 맨 앞·맨 뒤 칸, 따옴표 없는 줄을 다룬다. B는 시험을 전혀 추가하지 않아 회귀를 막지 못한다. 둘째, A는 따옴표가 칸의 맨 앞에 있을 때만 따옴표 칸으로 취급한다(`field === ''`). B는 칸 중간의 따옴표도 따옴표 모드를 켠다. 예를 들어 `ab"c,d"`는 B에서 다르게 해석된다. 이 시나리오의 요구 범위 밖이라 큰 결함은 아니지만 A가 더 엄밀하다. 다만 A에는 한 가지 허점이 있다. 따옴표 칸이 닫힌 직후 칸 내용이 비어 있으면(`""` 뒤에 따옴표가 또 오는 경우 등) 다시 따옴표 모드가 켜질 수 있다. 이 경우는 이중 따옴표 처리 때문에 대체로 드물게 나타난다. 전체적으로 A가 낫다.
  - 경험 전체 cli (relay 6, CLI 8) — 두 기록 모두 두 요구를 채웠다. A는 되감기 안전장치와 검증 근거가 강점이지만, 단계와 승인이 많아 작은 버그에는 과했다. B는 4차례, 0.9분에 끝났다. 테스트 파일이 남지 않은 점은 약점이다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 숨긴 시험을 통과했고 외부 라이브러리 없이 비슷한 상태 기계로 세 요구(따옴표 안 쉼표, "" 이스케이프, 빈 칸)를 채운다. 차이는 시험이다. A는 test/csv.test.js에 따옴표 안 쉼표, 이중 따옴표, 빈 칸, 따옴표로 감싼 빈 칸 시험을 더해 회귀를 막는다. B는 시험을 하나도 더하지 않았다. 코드 품질은 비슷하다. B는 inQuotes 분기가 조금 더 명확하다. A는 quoted 토글이 간결하다. 다만 A는 칸 중간에 나오는 따옴표도 토글하는데, B도 마찬가지다. 그래서 전체로는 시험을 더한 A가 낫다.
  - 경험 전체 cli (relay 6, CLI 7) — A는 도중에 요구를 추가하는 흐름이 잘 작동했고 검증 근거도 충분했다. 다만 시간과 차례가 많이 들었고 UI에 사소한 불편이 있었다. B는 훨씬 가볍게 끝났지만 테스트가 없었고 빈 칸 확인이 부족했다.
- 판정 #3: 결과 선호 tie — A와 B 모두 숨긴 시험과 레포 시험을 통과했고, 외부 라이브러리 없이 요구 세 가지(따옴표 안 쉼표, 이중 따옴표, 빈 칸)를 채웠다.

A: 상태 기계가 단순하고 읽기 쉽다. 칸 중간의 따옴표도 따옴표 모드를 켜지만, 이 경우는 요구에 없다. 시험은 세 요구를 다루지만 기존 동작(따옴표 없는 줄, 칸 중간 따옴표)은 다루지 않는다.

B: atCellStart 플래그로 칸 중간의 따옴표를 글자로 남긴다. 이는 RFC 4180에 더 가깝다. 다만 요구에 없던 처리를 더했고, 분기 구조(`else` 한 줄, `continue`)가 조금 더 어색하다. 시험은 더 폭넓고, 요구 예시인 '"say ""hi""",2'를 그대로 검증한다.

정확성은 같고 A는 더 단순하며 B는 시험이 더 두텁다. 서로 상쇄되어 동률로 본다.
  - 경험 전체 cli (relay 6, CLI 8) — A는 4차례 만에 모든 요구를 채우고 커밋까지 끝냈다. B는 방향 전환과 검증 근거가 더 나았지만 15차례에 마찰이 4번 있었다. 이 시나리오의 평가 목적은 도중에 늘어난 요구를 받아들이기 쉬운지인데, B는 승인 전에 요구를 추가할 수 있어 통제 면에서 강점을 보였다. 그래도 전체 경험은 A가 낫다.
- 판정 #4: 결과 선호 relay — 두 구현 모두 숨긴 시험을 통과하고, 따옴표 안 쉼표, 이중 따옴표, 빈 칸을 올바르게 처리한다. A는 따옴표 상태를 토글하는 방식이라 B의 상태 분기보다 조금 덜 명확하다. 그래도 동작에는 문제가 없다. A는 세 요구(쉼표, "", 빈 칸)를 각각 검증하는 회귀 시험을 test/에 추가했다. B는 시험을 전혀 추가하지 않았고, 이 점이 결정적이다. 테스트 부재가 가장 큰 차이여서 A를 선호한다.
  - 경험 전체 cli (relay 6, CLI 8) — 두 기록 모두 최종 결과가 두 요구를 채웠다. B는 훨씬 적은 수고로 끝났고 friction도 없었다. A는 검증 근거와 통제는 좋았지만 단계가 많았다. 또 이스케이프를 범위 밖으로 둔 채 승인해서 뒤늦게 추가 요청을 해야 했다.
- 판정 #5: 결과 선호 relay — 두 결과 모두 숨긴 시험(따옴표 안 쉼표, 이중 따옴표, 빈 칸)을 통과했고 외부 라이브러리도 쓰지 않았다. A는 파서가 단순하고 표준 CSV 동작에 맞는다. 다만 시험을 하나도 더하지 않아 회귀를 막지 못한다.   - 경험 전체 relay (relay 7, CLI 6) — A는 빠르고 간단하지만 검증이 없었다. B는 크래시 후 혼란이 잠깐 있었으나 진행이 보존됐고 테스트와 리뷰로 신뢰 근거를 얻었다.

  - 경험 전체 cli (relay 6, CLI 7) — 두 쪽 모두 충돌 후 이어 가기에 성공했다. B는 부담이 훨씬 적고 복구가 빨랐다. A는 재개 후 멈춤 때문에 손이 더 갔지만 검증 근거와 가시성은 더 좋았다.
- 판정 #5: 결과 선호 relay — 두 결과의 src/page.js 수정은 같습니다. 시작 인덱스를 (page-1)*size로 바꾸고 쪽 수는 올림으로 바꿨으며, 둘 다 숨긴 시험을 통과했습니다. 차이는 시험입니다. A는 시험을 더하지 않았습니다. B는 25개 항목의 1·2·3쪽 내용, 올림 쪽 수, 나누어떨어지는 경우의 빈 쪽을 확인하는 회귀 시험을 추가했고, 범위도 test/ 안에 머물렀습니다. 따라서 B가 낫습니다.
  - 경험 전체 tie (relay 7, CLI 7) — 충돌 후 이어 가기는 A가 훨씬 간단했고 수고도 적었다. B는 재개 후 멈춰 있어 직접 지시해야 했지만, 테스트와 리뷰로 결과를 믿을 근거를 더 많이 얻었다. 그래서 전체는 비슷하다고 봤다.

### 사람 역할의 말

- [relay#1 좋음] 단계마다 요약, 변경 diff, 판정표가 오른쪽 패널에 정리돼 있어서 터미널을 다 읽지 않고도 무엇이 왜 바뀌었는지 확인하고 승인할 수 있었다. 최종 검증 판정표에 기준 코드에서 재현한 결과와 현재 코드의 결과가 함께 나온 점이 좋았다.
- [relay#1 불편] 수정 단계에서 앱이 갑자기 꺼져 작업이 중단됐고, [재개]를 누른 뒤에도 에이전트가 멈춰 있어서 터미널에 직접 이어서 진행하라고 입력해야 했다. 이 부분은 이렇게 하면 된다는 안내가 없었다.
- [relay#2 좋음] 단계마다 요약, 변경 diff, 판정표가 오른쪽 패널에 보여서 터미널을 읽지 않고도 무엇이 왜 바뀌었는지 확인하고 승인할 수 있었다.
- [relay#2 불편] 수정 단계에서 앱이 갑자기 꺼졌다가 다시 켜졌다. 그 뒤 터미널은 작업 중인 옛 화면인데 패널은 승인 대기라서 상태가 맞는지 불안했다.
- [relay#3 좋음] 단계마다 요약, 가정, 위험, 변경 diff, 판정표가 오른쪽 패널에 정리돼 나와서, 터미널을 읽지 않고도 승인 여부를 판단할 수 있었다.
- [relay#3 불편] 수정 단계에서 앱이 갑자기 꺼졌다 켜졌는데, 터미널은 작업 중인 듯 보이고 패널은 승인 대기라 상태가 맞는지 잠깐 헷갈렸다. 마지막에 커밋이 됐는지를 화면에서 직접 확인하기 어려웠다.
- [relay#4 좋음] 단계마다 요약, 변경 diff, 판정표를 오른쪽 패널에서 바로 볼 수 있어서 무엇이 왜 바뀌었는지 확인하고 승인하기 쉬웠다.
- [relay#4 불편] 수정 단계 도중 앱이 갑자기 꺼졌다. 재개를 눌렀는데도 에이전트가 멈춰 있어서, 내가 터미널에 직접 계속하라고 입력해서 깨워야 했다.
- [relay#5 좋음] 단계마다 요약과 판정표가 나오고 코드 변경을 바로 볼 수 있어서, 승인하기 전에 무엇이 왜 바뀌었는지 확인하기 쉬웠다. 재현 테스트를 먼저 추가하고 수정 전에는 실패하고 수정 후에는 통과하는 것까지 보여 준 점이 믿음직했다.
- [relay#5 불편] 수정 단계 도중 앱이 갑자기 꺼졌다. 재개를 눌렀는데도 에이전트가 자동으로 이어 가지 않고 멈춰 있어서 터미널에 직접 이어서 하라고 말해야 했다. 그 사이에 정말 진행 중인지 알 수 없었다.
- [cli#1 좋음] 한 번 요청하니 원인 두 가지를 찾아 고치고 커밋까지 했다. 변경 내용이 화면에 그대로 보였다.
- [cli#1 불편] 터미널이 갑자기 닫혀 세션이 끊겼다. 테스트나 실행 없이 코드만 고쳤다고 에이전트가 직접 밝혔다.
- [cli#2 좋음] 요청 한 번으로 원인 두 개(시작 위치, 쪽 수 올림)를 찾아 고치고 커밋까지 끝냈다. 변경 요약도 짧고 분명했다.
- [cli#2 불편] 터미널이 갑자기 닫혀서 claude --continue로 다시 열어야 했다. 에이전트가 테스트를 돌리지 않았다고 했는데 내가 직접 돌려 보지는 않았다.
- [cli#3 좋음] 요청 한 번으로 두 버그를 원인 설명과 함께 금방 고쳤고, diff와 커밋까지 빠르게 끝났다.
- [cli#3 불편] 중간에 터미널이 닫혀 claude를 다시 띄워야 했다. 에이전트가 테스트나 실행을 하지 않아서 검증은 내가 코드만 보고 판단해야 했다.
- [cli#4 좋음] 요청하자마자 원인 두 곳을 바로 짚어 고쳤다. 변경 diff가 화면에 그대로 보였고, 요청하니 실제로 실행해 검증한 뒤 커밋까지 했다.
- [cli#4 불편] 중간에 터미널이 갑자기 닫혀서 claude를 --continue로 다시 띄워야 했다. 처음에는 에이전트가 테스트를 돌리지 않았고, 내가 시켜야 검증했다.
- [cli#5 좋음] 요청 한 번으로 원인 두 가지를 찾아 고치고 커밋까지 끝났다. 설명도 짧고 명확했다.
- [cli#5 불편] 중간에 터미널이 닫혀서 작업 상태를 다시 확인해야 했다. 에이전트가 테스트나 실행 없이 코드만 읽고 고쳤다고 스스로 밝혔다.

#### friction이 높았던 차례

- cli#1 차례 2 (friction 2): 터미널이 갑자기 닫혀 claude가 종료됨; 진행 상황 불명
- cli#4 차례 2 (friction 2): 터미널이 갑자기 닫혀 작업 상태를 알 수 없음
- cli#5 차례 2 (friction 2): 터미널이 갑자기 닫혀 작업이 어디까지 됐는지 모름
- relay#4 차례 7 (friction 2): 재개했는데 에이전트가 아무 진행 없이 멈춰 있어 직접 깨워야 했다.
- relay#5 차례 7 (friction 2): 재개했는데 에이전트가 자동으로 이어가지 않고 멈춰 있어 직접 말해야 함
