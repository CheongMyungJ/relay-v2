- 판정 #1: 결과 선호 relay — 두 결과 모두 동기 EventEmitter를 쓴다. 구독자 오류는 placeOrder까지 그대로 전달되고, points를 notifications보다 먼저 등록해 적립이 메일보다 먼저 실행된다. orders.js는 email.js와 points.js를 import하지 않는다. 숨긴 시험도 둘 다 통과했다. 차이는 작다. A는 이벤트 페이로드를 order 그대로 두어 변경 범위가 가장 작다. B는 아직 쓰이지 않는 items를 페이로드에 추가했는데, 해롭지는 않지만 요청 밖의 변경이다. 시험은 둘 다 오류 경로(저장과 적립이 남고 메일은 안 나감)를 확인한다. A는 거기에 빈 items 오류, 적립 누적, 메일 제목 검증까지 더했다. B는 beforeEach로 상태를 초기화해 시험 격리가 더 낫고 반환값에 items가 없음을 확인한다. 다만 A가 오류 경로와 차례를 더 폭넓게 확인하고 변경 범위도 더 작아서 A를 근소하게 선호한다. 주어진 기록만으로는 두 결과 모두 설계 방향을 사람에게 보고했는지 알 수 없다.
  - 경험 전체 cli (relay 6, CLI 8) — B가 설계를 먼저 보여 줘서 사람이 방향을 쥐었고 수고도 적었다. A는 판정표 같은 증거가 더 나았지만, 설계를 미리 보고 싶다는 선호가 자동 승인으로 무시됐다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 동기 EventEmitter를 쓰고, 구독 등록 순서를 적립 다음 메일로 맞췄다. 그래서 숨긴 시험과 레포 시험을 모두 통과하고, 잘못된 메일 주소 오류도 placeOrder까지 전달된다. 적립이 메일보다 먼저라는 순서도 지켜진다. 코드 차이만 보면 사람에게 따로 물어본 흔적은 어느 쪽에도 없다. 다만 둘 다 사람이 알려 준 동작을 그대로 지켰다.

A는 안전망 시험을 추가했다. 시험은 적립 계산, 메일이 placeOrder 반환 전에 나감, 잘못된 주소일 때 저장과 적립은 남고 오류가 던져짐, 상품이 없을 때 아무것도 안 남음을 확인한다. 이 중 오류 경로 시험이 이번 시나리오의 핵심 회귀를 막는다. 다만 A는 app.js에서 순서를 주석으로만 설명하고, points.js는 app.js가 `export { balance } from './points.js'`를 하는 덕에 로드된다. 이 구조는 등록 순서가 간접적이어서 약간 취약하다.

B는 app.js에서 points와 notifications를 명시적으로 import해 순서가 더 분명하다. payload도 복사본으로 넘긴다. 하지만 시험을 전혀 더하지 않아 회귀 방지가 없다. 이 시나리오는 안전망이 오류 경로를 잡는지도 평가하므로 이 점이 크게 감점된다.

전체적으로 시험을 더한 A를 선호한다.
  - 경험 전체 relay (relay 7, CLI 6) — 둘 다 설계를 사전에 보여 주지 않았고 동작도 보존했다(동기 emit, 적립이 메일보다 먼저). 사람이 동작이 그대로라는 근거를 보고 싶어 했으므로 기준 코드 대조와 판정표를 낸 A가 신뢰 근거에서 앞선다. B는 더 빠르고 수고가 적다. 하지만 설계 요청을 무시했고 근거가 상대적으로 약하다.
- 판정 #3: 결과 선호 relay — 두 결과의 설계는 거의 같다. 둘 다 동기 EventEmitter를 쓰고 orders.js는 'placed'만 낸다. 구독자의 예외는 placeOrder까지 전파되고, 적립이 메일보다 먼저 등록된다. 그래서 correctness와 scope는 같은 점수다. A는 app.js에서 points.js와 notifications.js를 명시적으로 import하고, 순서를 지켜야 하는 이유를 자세히 주석으로 적었다. 순서가 import에 달려 있다는 점이 B보다 눈에 잘 띄어 quality는 A가 약간 낫다. B는 `export ... from './points.js'` 줄 뒤에 import를 두어 순서가 암묵적이고, 주석도 짧다. 시험은 B가 더 낫다. A는 잘못된 메일 주소일 때 던지고 주문과 적립이 남는 오류 경로 시험 하나만 더했다. B도 같은 오류 경로 시험을 넣었고, 여기에 적립 금액, 메일 내용, 빈 items, 반환값 시험까지 더해 동작 보존의 근거가 더 두텁다. 적립과 메일의 순서는 두 쪽 모두 오류 경로 시험으로 간접 검증한다. 설계를 사람에게 묻는지는 기록에 나타나지 않아 평가에 반영하지 않았다. 시험 차이가 커서 B를 약간 더 선호한다.
  - 경험 전체 relay (relay 7, CLI 6) — B는 마찰 없이 한 번에 끝났고 판정표와 기준 코드 검증이라는 근거를 줬다. A는 설계 선요청이 무시되고 재요청이 필요했지만, 순서 테스트로 확신 근거는 더 강했다. 둘 다 동기/순서 제약을 먼저 묻지 않았다.

- [cli#1 불편] 적립이 메일보다 먼저 실행되는 것이 import 순서에 달려 있어 다소 깨지기 쉽다. 순서 자체를 테스트로 고정하지는 못했고 주석에만 의존한다. 또 inspect_diff를 따로 열어야 코드를 볼 수 있었다.

- [cli#2 불편] 고치기 전에 이벤트 설계를 먼저 알려 달라고 했는데, 에이전트가 설계를 보여 주지 않고 바로 구현했다. 설계는 끝난 뒤 요약에서야 볼 수 있었다.
- [cli#3 좋음] 변경 요약이 명확했고, 오류 전파와 적립 순서를 실제로 확인했다. 순서를 바꿔 테스트가 실패하는 것까지 보여 줘서 믿을 수 있었다.
- [cli#3 불편] 고치기 전에 설계를 먼저 알려 달라고 했는데 바로 구현해 버렸다. 적립이 메일보다 먼저여야 한다는 제약도 내가 짚기 전에는 몰랐다.
