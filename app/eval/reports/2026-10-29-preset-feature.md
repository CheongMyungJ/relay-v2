- 판정 #1: 결과 선호 relay — 두 결과는 핵심 구현이 같다. 구분자가 든 값은 따옴표로 감싸고, 기본값은 쉼표이며, exportOrders가 옵션을 넘기고, 시험도 통과한다. 차이는 B가 구분자 검증(assertDelimiter)과 RangeError 시험을 더했다는 점이다. 요청은 작은 기능을 빨리 끝내는 것이었고 검증은 요구에 없었다. 그래서 B는 범위를 조금 넘었고 코드도 더 길어졌다. 검증이 방어에 도움은 되지만 필요한 만큼만 바꾸라는 기준에서는 A가 낫다. A의 시험은 탭, 세미콜론, 기본값, 따옴표 처리, 주문 내보내기를 고르게 다룬다. B의 시험도 좋지만 검증 쪽에 시험이 쏠려 있다. 그래서 A를 근소하게 선호한다.
  - 경험 전체 relay (relay 7, relay (설정 confirm-each) 5) — 두 기록의 명확성, 통제, 확신은 비슷했다. 차이는 수고였다. A는 차례와 행동이 절반 정도였고 1.8분 빨랐다. 작고 빨리 끝내고 싶은 일이라 B의 질문과 체크박스 조작이 더 부담이었다.
- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 바뀐 파일도 기대한 범위 안이다. 차이는 B가 요청에 없는 구분자 화이트리스트와 RangeError 검증을 더했다는 점이다. 사람은 "작은 일이라 빨리 끝내고 싶다"고 했고, 요청에도 허용 목록은 없었다. 이 검증은 범위를 넘고, '|' 같은 구분자를 막아서 필요 이상으로 제한한다. 탭은 "쓸 수 있으면 좋겠다"는 정도였는데 B는 이를 허용 목록으로 굳혔다. A는 요청한 것만 구현하면서 따옴표 규칙, 탭, 세미콜론, 기본값, exportOrders 전달을 시험으로 고루 지킨다. 특히 탭 구분자 값에 구분자가 있을 때 따옴표로 감싸는 시험과 exportOrders가 탭을 넘기는 시험이 있다. B의 시험도 괜찮지만 exportOrders 시험이 세미콜론뿐이고, 요청에 없던 검증 시험이 많다. 그래서 A가 더 낫다.
  - 경험 전체 relay+design-auto (relay 6, relay (설정 design-auto) 7) — 두 기록은 결과 품질과 확신이 비슷하다. B가 차례와 시간이 적어 작은 기능의 빠른 완료 선호에 더 맞는다. A는 설계를 직접 승인해 통제력이 높았지만, 그 대가로 단계와 읽을 글이 늘었다.
- 판정 #2: 결과 선호 relay+confirm-each — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 바뀐 파일도 기대한 범위 안이다. 차이는 세 가지다.

1. 쉼표 처리. B는 구분자가 `;`일 때 쉼표가 든 값을 따옴표로 감싸지 않는다. 구분자가 아닌 쉼표는 감쌀 필요가 없으니 CSV 문법으로는 맞다. 그러나 기존 동작이 달라진다. 또 쉼표 기본 설정으로 받는 쪽 도구가 쉼표 값을 다르게 읽을 위험이 있다. 이 점은 B의 시험에 명시돼 있어 의도한 선택이다. A는 쉼표·따옴표·줄바꿈을 항상 감싸서 더 보수적이고 안전하다.
2. 구분자 검증. A는 잘못된 구분자(빈 문자열, 여러 글자, `"`, 줄바꿈 등)를 오류로 막는다. B는 검증이 없다. 그래서 `"`나 빈 문자열을 넘기면 조용히 깨진 CSV가 나오거나, `''.includes` 때문에 모든 값이 감싸진다. 검증은 요청에 없던 것이라 A의 범위가 조금 넓다. 하지만 코드 양이 작고 방어 효과가 있다.
3. 시험. A는 머리글 제목, 잘못된 구분자, 기본값 시험까지 더 넓게 덮는다. B도 충분하지만 오류 경우는 다루지 않는다.

사람이 "작은 일이라 빨리 끝내고 싶다"고 했으므로 B가 더 간결하다는 점은 인정한다. 그래도 A의 추가분이 과하지 않고 안전성과 시험 범위가 더 낫다고 판단해 A를 택한다.
  - 경험 전체 relay (relay 8, relay (설정 confirm-each) 6) — B가 절반의 차례와 짧은 시간으로 같은 수준의 명확성과 확신을 얻었다. A는 통제가 조금 나았지만, 작은 일에 질문이 많아 빨리 끝내려는 선호와 어긋났다.
- 판정 #2: 결과 선호 relay+design-auto — 두 결과의 구현 코드는 거의 같다. 둘 다 구분자 옵션을 추가하고 기본값은 쉼표다. 구분자가 든 값은 따옴표로 감싸고, 쉼표만 든 값은 다른 구분자에서 감싸지 않는다. 숨긴 시험과 레포 시험도 모두 통과했고 바뀐 파일도 같다. 차이는 두 가지다. B는 csv.js 위쪽에 options.delimiter 설명 주석을 한 줄 더했고, A는 하지 않았다. 시험은 둘 다 충실하다. A는 탭 구분자를 따로 시험하고, B는 `delimiter: undefined`와 탭이 든 값을 시험한다. 주석 한 줄 차이로 B를 근소하게 앞세운다.
  - 경험 전체 relay+design-auto (relay 6, relay (설정 design-auto) 7) — 두 기록 모두 약 3분에 끝났고 설문 점수도 같다. B는 승인이 한 번 적어 사람의 수고가 약간 적었다. 대신 설계 단계를 직접 보지 못해 통제는 A가 낫다. 빨리 끝내려는 선호를 고려해 B를 근소하게 앞선 것으로 봤다.

### 사람 역할의 말

- [relay#1 좋음] 완료조건별 판정표와 구현 전 실패, 후 통과라는 근거가 있어서 결과를 믿기 쉬웠다. 탭 요청을 한 번 말했더니 완료조건에 정확히 반영됐다.
- [relay#1 불편] 이렇게 작은 일에도 단계(의도 정리, 설계, 구현)와 승인이 많아서 빨리 끝내고 싶은 마음에는 조금 무거웠다. 승인 화면의 글이 길어 읽는 데 시간이 걸렸다.
- [relay#2 좋음] 단계마다 요약, 결정, 판정표, diff가 오른쪽 패널에 정리돼 있어서 코드를 따로 열지 않아도 결과를 믿고 승인할 수 있었다.
- [relay#2 불편] 작은 일인데도 의도 정리, 설계, 구현 세 번 승인해야 해서 다소 무거웠다.
- [relay+confirm-each#1 좋음] 단계마다 선택지로 결정을 묻고, 승인 화면에서 요구사항과 판정표, 테스트 결과를 한눈에 볼 수 있었다. 탭 지원과 따옴표 처리 같은 내 요구가 완료조건에 그대로 들어갔다.
- [relay+confirm-each#1 불편] 작은 일인데 질문과 승인 단계가 많았다. 선택지에서 체크하고 Submit까지 가는 키 조작이 번거로웠다.
- [relay+confirm-each#2 좋음] 결정마다 선택지로 물어서 내가 방향을 정할 수 있었다. 판정표와 전체 변경 diff에서 테스트와 코드를 바로 확인하고 승인할 수 있었다.
- [relay+confirm-each#2 불편] 작은 기능인데 질문이 많았고 승인 단계도 여럿이라 빨리 끝내고 싶은 마음에는 다소 길게 느껴졌다. 질문 중 일부는 세부 사항이 많았다.
- [relay+design-auto#1 좋음] 요청을 한 번 쓰고 승인 두 번으로 끝났다. 완료조건별 판정표와 테스트 결과가 근거와 함께 나와서 diff와 맞춰 보기 쉬웠다.
- [relay+design-auto#1 불편] 이렇게 작은 일에도 의도 정리, 설계, 구현, 독립 리뷰까지 단계가 많았다. 설계와 계획은 자동 승인으로 지나가서 내가 따로 본 것이 없다.
- [relay+design-auto#2 좋음] 완료조건 목록과 판정표에 테스트 이름과 근거가 나란히 붙어 있어서, 요구대로 됐는지 코드를 보기 전에도 믿을 수 있었다. 쉼표 따옴표 처리 변경 같은 가정도 요약에 적혀 있었다.
- [relay+design-auto#2 불편] 이렇게 작은 일에 비해 단계가 많았다(의도 정리, 설계와 계획, 구현, 독립 리뷰). 설계와 계획 단계는 자동 승인으로 지나가서 내가 직접 보지 못했다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고 필터, 정렬, 같은 가격일 때 id 오름차순, RangeError, 기존 호출 유지 구현도 거의 같다. 차이는 두 가지다. 첫째, A는 요청에 없던 규칙을 하나 만들었다. 음수 가격이면 RangeError를 던진다. 사람에게 묻지 않고 밖에서 보이는 동작을 정한 것이어서 범위가 조금 넓다. B는 요청된 범위만 구현했다. 둘째, 시험에서 B는 모든 쪽을 이어 붙여 같은 가격 상품이 겹치거나 빠지지 않는지 확인한다. 이 점이 사람이 말한 이유와 직접 맞는다. B는 기본 호출 결과도 고정했다. A도 시험은 충실하지만 이 점에서 B가 약간 낫다. 두 결과 모두 설계를 먼저 보여 주거나 확인을 묻는 모습은 기록에 없다.
  - 경험 전체 relay (relay 7, relay (설정 confirm-each) 6) — 두 기록 모두 요구를 충족하고 기존 호출 보존을 확인했다. A는 선택지로 묻는 방식이 명확했지만 수고가 컸고 키 조작이 헷갈렸다. B는 사람이 가정을 직접 고쳐 훨씬 적은 단계로 끝냈다. 다만 B는 내부 로그가 노출되어 잠깐 헷갈렸다.
- 판정 #1: 결과 선호 relay+design-auto — A와 B 모두 숨긴 시험을 전부 통과했고 요구 규칙도 지켰다. 두 구현 모두 필터 후 정렬하고 쪽 나누기를 하며, 양 끝을 포함하고, 같은 가격은 id 오름차순으로 둔다. minPrice가 maxPrice보다 크면 RangeError를 던지고, 모르는 sort도 RangeError다. 기존 호출도 그대로 동작한다. 기록에는 설계를 먼저 보여 달라는 선호에 따라 사람에게 물었는지가 없다. 그래서 그 점은 둘 다 평가하지 못했고, 구현과 시험으로만 비교했다.

차이는 작다. A는 SORTS 맵과 Object.hasOwn을 써서 'toString' 같은 프로토타입 키를 거부하고, 시험도 그 경우를 확인한다. 정렬은 toSorted로 하며 원본을 건드리지 않는다. 시험은 쪽을 모두 모았을 때 중복이나 누락이 없는지, 필터와 정렬을 함께 쓸 때, 결과가 빈 경우, 원본 순서가 유지되는지까지 확인한다. 기존 호출 시험도 더 촘촘하다.

B도 정확하고 간결하다. 다만 byPrice의 dir * (a.price - b.price) 방식은 A의 비교 함수보다 조금 덜 직관적이다. B의 시험도 충분히 좋다. 쪽 넘김 시험은 allIds로 전체 순서를 확인하지만, 중복·누락을 직접 점검하는 시험은 A보다 약하다.
  - 경험 전체 relay (relay 8, relay (설정 design-auto) 7) — 두 기록 모두 사람이 아는 규칙을 승인 전에 바로잡았고 기존 호출 호환도 확인했다. 차이는 수고다. A는 설계 자동 승인을 끄는 설정을 찾는 데 시간이 걸렸고, B는 그런 단계 없이 더 적은 행동으로 끝났다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 필터, 정렬, 동점 시 id 오름차순, RangeError, 기존 호출 유지를 모두 구현했다. 기록에는 설계를 먼저 사람에게 보여 줬는지 드러나지 않아 이 점은 비교하지 않았다.

A는 요청에 없던 "가격은 0 이상" 규칙을 새로 만들어 음수 minPrice와 maxPrice에 RangeError를 던진다. 밖에서 보이는 동작을 임의로 정한 것이고, 그 동작을 시험으로도 굳혔다. compareBy 분리는 깔끔하다. 시험은 경계, 조합, 기존 호출 유지를 다루지만 쪽을 넘길 때 중복이나 누락이 없는지는 직접 확인하지 않는다.

B는 유한한 숫자인지만 검사해 요청 범위를 더 잘 지켰다. total 주석도 새 동작에 맞게 고쳤다. 시험은 기존 호출의 결과 모양, 빈 결과, 쪽을 이어 붙였을 때 중복·누락이 없는지, 원본 순서가 바뀌지 않는지까지 확인한다. 기존 화면이 깨지지 않았다는 사람의 선호에도 더 잘 맞는다. 정렬 분기가 두 줄로 반복되는 점은 A보다 약간 덜 깔끔하다.
  - 경험 전체 relay+confirm-each (relay 6, relay (설정 confirm-each) 8) — A는 설계 단계에서 경계 규칙을 사람에게 물어 처음부터 맞게 갔다. 질문이 길고 선택지가 일부 안 맞은 불편은 있었다. B는 차례는 적었지만 묻지 않고 가정해 틀렸고, 사람이 diff로 잡아 고쳤다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 숨긴 시험을 통과했고 기존 호출 결과도 같다. 같은 가격은 id 오름차순이고, minPrice가 maxPrice보다 크면 RangeError이며, 모르는 sort 값도 RangeError다. 설계를 먼저 묻거나 제시했는지는 기록에 없어서 이 점은 비교하지 않았다.

A는 minPrice와 maxPrice에 숫자가 아닌 값(NaN, 문자열, null 등)이 오면 RangeError를 던진다. B는 이 입력을 검사하지 않는다. 예를 들어 minPrice가 NaN이면 모든 비교가 거짓이 되어 조용히 빈 목록을 반환한다. 이 검사는 요구사항에 없던 것이라 범위가 조금 넓어진 셈이다. 그래도 합리적인 방어이고, 화면이 입력 오류를 보여 준다는 맥락과도 맞는다.

A의 시험이 더 넓다. 기존 호출(page 1~3)의 결과와 total을 확인하고, 잘못된 입력을 여러 종류로 시험하며, PRODUCTS가 바뀌지 않는지와 쪽을 이어 붙였을 때 중복·누락이 없는지도 확인한다. 기존 화면이 깨지지 않았다는 확인이라는 선호에는 A가 더 가깝다. B는 기존 호출 확인이 page 1~2에 그치고, 시험 이름과 달리 maxPrice 경계 포함을 직접 따로 검증하는 시험은 약하다.

B의 코드는 더 간결하고 byPrice 헬퍼도 읽기 좋다.
  - 경험 전체 relay+design-auto (relay 6, relay (설정 design-auto) 8) — 둘 다 설계 단계에서 선택지를 먼저 묻지 않았다. B는 사람이 승인 전에 두 규칙을 한 번에 알려 바로잡았고 수고도 적었다. A는 동률 규칙 어긋남을 구현 뒤 diff에서야 발견해 재수정과 재확인이 필요했다.

### 사람 역할의 말

- [relay#1 좋음] 의도 정리 단계에서 에이전트가 세운 가정이 요약에 그대로 보였다. 내가 아는 것과 다른 부분을 승인 전에 바로 고칠 수 있었다. 판정표와 diff도 완료조건별로 정리돼 있어 확인하기 쉬웠다.
- [relay#1 불편] 터미널 로그에 stop hook 오류나 handoff 형식 수정 같은 내부 동작이 그대로 보여서 처음엔 무슨 일인지 잠깐 헷갈렸다. 단계가 많아서 승인을 여러 번 눌러야 했다.
- [relay#2 좋음] 단계마다 승인 화면이 있어서 설계를 먼저 볼 수 있었다. 판정표와 diff로 결과를 확인하기 쉬웠다.
- [relay#2 불편] 에이전트가 같은 가격 규칙과 min>max 처리를 먼저 묻지 않고 자기 가정으로 정했다. 내가 diff를 보고서야 어긋남을 알아챘고, 그 뒤 구현 단계에서 고쳐야 했다. 형식 검사기가 사람의 말을 못 봐서 오류를 낸 것도 어색했다.
- [relay+confirm-each#1 좋음] 의도 정리와 설계 단계에서 경계, 오류 처리, 동점 정렬 같은 결정을 선택지로 하나씩 물었다. 승인 전에 요약, 판정표, diff로 확인할 수 있었다.
- [relay+confirm-each#1 불편] 다중 선택 질문에서 방향키와 숫자키로 Submit까지 가는 조작이 헷갈렸다. 이미 정한 사항을 같은 방식으로 여러 번 확인하는 느낌도 있었다.
- [relay+confirm-each#2 좋음] 설계를 코드보다 먼저 보여 줬고, 선택지 질문으로 경계 포함, RangeError, 동점 규칙 같은 결정을 내가 직접 정할 수 있었다. 완료조건별 판정표와 회귀 테스트까지 한 화면에서 확인했다.
- [relay+confirm-each#2 불편] 동점 순서 질문은 선택지 두 개가 모두 내 의도와 달라서 직접 입력해야 했다. 질문이 여러 번 이어져 단계가 좀 길게 느껴졌다.
- [relay+design-auto#1 좋음] 설계 단계에서 멈춰 내가 아는 규칙(동점 id 순, 양끝 포함, RangeError)을 바로잡을 수 있었다. 판정표와 테스트 통과 수, diff로 결과를 확인하기 쉬웠다.
- [relay+design-auto#1 불편] 새 Work 창의 고급 설정에서 설계 자동 승인을 끄는 곳을 찾는 데 시간이 걸렸다. 터미널 로그가 길고 기술적이라 오른쪽 패널을 더 많이 봐야 했다.
- [relay+design-auto#2 좋음] 의도 정리에서 어긋난 가정(min>max를 빈 결과로 둠)을 승인 전에 바로잡았고, 설계 승인 화면과 판정표로 기존 호출 불변까지 확인할 수 있었다.
- [relay+design-auto#2 불편] 새 Work 창의 고급 설정에서 설계 자동 승인을 끄는 위치를 찾기가 약간 번거로웠다. 에이전트가 가정을 먼저 묻지 않고 초안에 적어 둔 것도 아쉬웠다.
