- 판정 #1: 결과 선호 relay@auto — A는 두 번째 원인(느린 성공을 시간 초과로 보고 재시도)만 고쳤다. 첫 번째 원인인 중복 제거 키는 손대지 않아서, 숨긴 시험의 '같은 이벤트 재수신'이 실패한다. 이 시나리오에서 첫 원인에서 멈추지 말라는 요구의 반대 경우, 즉 둘째 원인에서만 멈춘 경우다. 추가한 시험은 메일과 푸시 모두 한 번만 가는지 보여 주고 실패 재시도도 확인하지만, 재수신 경로는 다루지 않는다. B는 두 원인을 모두 고쳤고 숨긴 시험 세 가지가 모두 통과한다. 중복 제거 키는 신원 필드(id, source, type, userId)만 쓰도록 바꿨다. policy.js에서는 성공이면 늦어도 끝내고, 응답 없는 시간 초과는 재시도하되 멱등 키로 중복을 막는다. 변경 범위는 A보다 넓지만 모두 기대 파일 안이다. 멱등 키와 가짜 전송 쪽 변경은 다소 과할 수 있다. 그래도 도착 여부를 알 수 없는 시간 초과에서 재시도해도 중복이 생기지 않게 하는 방어이므로 타당하다. 시험 파일도 메일과 푸시 양쪽을 다루고, 보이는 부분만 보면 근거가 충분하다. 사용자가 원한 원인 수정과 메일·푸시 모두 한 번 전송이라는 근거에 B가 훨씬 가깝다.
  - 경험 전체 relay@auto (relay (자율 유형) 7, 맨 CLI 6) — A는 빠르고 수고가 적었다. 하지만 원인 하나만 고쳤고, 메일·푸시 근거도 사람이 요청해서야 나왔다. B는 차례가 더 많고 완료 화면 판정표가 비어 있었다. 그래도 사람의 요구를 선택지로 받아 완료 조건에 넣었고, 원인 두 가지와 두 채널의 근거를 모두 보여 줬다.
- 판정 #2: 결과 선호 cli — 두 결과의 소스 수정은 사실상 같다. 둘 다 dedupe 키에서 receivedAt을 빼고, retry policy에서 성공이면 시간 초과 검사 전에 done을 반환하게 했다. 두 원인을 모두 고쳤고 재시도는 끄지 않았다. 숨긴 시험도 모두 통과했고 기대 밖 파일도 건드리지 않았다. 차이는 시험에서 난다. A는 느린 메일, 느린 푸시, 수신 시각만 다른 재수신을 각각 시험하고 정책 단위 시험도 더했다. 다만 메일 중복 제거 시험은 메일 호출 수만 확인한다. 푸시 중복 제거는 확인하지 않는다. 실패 재시도는 정책 단위로만 확인하고 통합 수준에서는 확인하지 않는다. B는 exactly-once 시험을 새로 만들어 메일과 푸시를 모두 확인한다. 느린 성공, 늦은 재수신(1시간 뒤 포함), 실제 실패 재시도, 시간 초과 실패 재시도를 호출 수와 전송 수로 검증한다. 사용자가 원한 "메일과 푸시 둘 다 한 번만 간다는 근거"와 "실패는 재시도"를 B의 시험이 더 직접 보여 주므로 B를 택한다.
  - 경험 전체 tie (relay (자율 유형) 7, 맨 CLI 7) — 두 기록 모두 원인 두 가지를 찾아 고쳤다. A는 사람이 방향을 잡고 검증 근거를 얻었지만 수고가 더 들었고, 미리 선택된 질문과 테스트 결과를 따로 물어야 한 불편이 있었다. B는 간결하고 원인을 실험으로 보였지만 에이전트가 사전 확인 없이 진행했고, 사람이 사후에 근거를 요청해야 했다. 전체 경험은 비슷하다.
- 판정 #3: 결과 선호 relay@auto — A는 원인 두 가지를 모두 고쳤다. 하나는 중복 제거 키에 수신 시각(receivedAt)이 들어간 것이고, 다른 하나는 느린 성공을 시간 초과로 보고 재시도한 것이다. 숨긴 시험 3개가 모두 통과했다. 시험은 메일과 푸시 양쪽에서 한 번만 나가는지 확인하고, 실패한 발송은 여전히 재시도되는지도 확인한다. 느린 성공을 지표와 로그로 남기는 것은 범위를 조금 넘지만 관찰에 도움이 된다. B는 재시도 정책만 고쳤다. 중복 제거 키 원인을 놓쳐서 '같은 이벤트 재수신' 숨긴 시험이 실패했다. 사람이 원인을 알고 고치기를 원했는데, B는 증상을 일부만 줄였다. B의 정책 시험 자체는 괜찮고, 영구 오류는 포기하게 한 변경도 합리적이다. 하지만 중복 제거를 검증하는 시험이 없다.
  - 경험 전체 relay@auto (relay (자율 유형) 8, 맨 CLI 6) — A는 단계가 더 많고 판정표가 비었지만, 두 원인을 모두 고치고 근거를 먼저 보여 줬다. B는 효율적이었지만 중복 제거 키 원인을 놓쳤고, 발송 횟수 근거도 사람이 요청해야 나왔다.
- 판정 #4: 결과 선호 cli — A와 B 모두 첫 번째 원인인 중복 제거 키를 고치지 못했다. 둘 다 숨긴 시험 "같은 이벤트 재수신"에서 실패한다. 둘 다 재시도 정책만 고쳤다. 느린 성공을 곧바로 'done'으로 처리해, 느린 성공 뒤 재시도가 사라진다. 이 점은 같고, 그래서 correctness는 둘 다 낮다. 차이는 세부에서 난다. B는 정책 함수를 더 단순하게 정리했다. 영구 오류는 느려도 give-up이고, 일시 오류만 timeout 사유로 재시도한다. 이 동작은 합리적이고, 시험으로도 확인한다. A는 영구 오류가 시간 초과를 넘기면 재시도하도록 남겼다. 영구 오류를 다시 보내는 셈이어서 의도에 맞지 않는다. A는 주석에서 "가끔 중복은 감수"라고 적었는데, 이는 사용자가 원하는 원인 해결과 거리가 있다. A의 시험은 시도 횟수 소진 시험을 더했지만, 파일 중간에 헬퍼 함수가 끼어 있어 구성이 어수선하다. B의 시험은 메일, 푸시, 실패 재시도, 느린 영구 오류를 모두 다룬다. 다만 B도 중복 제거 경로에 대한 시험은 없다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 7) — B가 절반 수준의 시간과 차례로 원인을 정확히 짚고 실패하는 테스트로 근거를 줬다. A는 의도 선택지로 통제감은 좋았지만 판정표가 비었고 과정이 길었다. 둘 다 푸시 검증을 사람이 요청해야 했고, 중복 제거 키 같은 두 번째 원인은 요약에 보이지 않는다.
- 판정 #5: 결과 선호 cli — A는 두 원인을 모두 고쳤다. 중복 제거 키에서 receivedAt처럼 수신 때마다 달라지는 값을 빼고 신원 필드만 쓰게 했다. 느리게 성공한 발송은 재시도하지 않고, 실패한 발송은 계속 재시도한다. 숨긴 시험 세 개가 모두 통과했다. 메일과 푸시 모두 한 번만 가는지 확인하는 시험을 추가했고, 사람이 원한 근거로 쓸 수 있다. 다만 키를 4개 필드로 고정한 점은 약간 공격적이다.

B는 느린 성공을 재시도하던 두 번째 원인만 고쳤다. 첫 번째 원인인 중복 제거 키는 그대로 두어 '같은 이벤트 재수신' 시험이 실패했다. 이벤트가 다시 들어오면 중복 알림이 계속 나갈 수 있다. 여기에 Message-ID 헤더를 넣고 가짜 전송기가 중복을 합쳐 주도록 바꿨는데, 이는 요청 범위를 벗어난 추측성 변경이다. 시험 일부는 이 가짜 전송기의 동작에 기대고 있어서 실제 회귀를 막는다고 보기 어렵다. 느린 성공을 지표와 로그로 남기는 것은 좋은 점이다.
  - 경험 전체 cli (relay (자율 유형) 7, 맨 CLI 7) — 이 시나리오는 두 원인을 드러내는 것을 본다. A는 첫 요청에서 두 원인을 모두 짚었고, 수정 전 코드에서 테스트가 실패하는 것까지 보여 줬다. B는 방향 통제가 좋았지만, 원인을 하나로 설명했고 보조 방어로 Message-ID를 썼다. 판정표가 비어 있었고 timeout 설정을 다루지 않았다. A도 푸시 근거와 설정 출처는 사람이 따로 물어야 나왔고, 운영 timeout 값은 끝내 확인하지 못했다.

### 사람 역할의 말

- [cli#1 좋음] 원인(성공보다 경과시간을 먼저 보는 로직)을 짚고, 요청하니 fake transport로 수정 전후 메일·푸시 발송 횟수를 비교해 보여 줬다.
- [cli#1 불편] 처음에는 decide 단위 테스트만 추가해서 메일·푸시 end-to-end 근거는 내가 따로 요청해야 했다. 에이전트가 설정 값이나 로그 단서를 묻지 않고 진행했다.
- [cli#2 좋음] 원인을 두 가지로 나눠 찾았고, 수정을 하나씩 되돌려 보는 실험으로 각각이 원인임을 보여 줬다. 메일이 더 잦은 이유도 설명했다.
- [cli#2 불편] 에이전트가 먼저 아무것도 묻지 않았다. 제한 시간 설정이나 로그 간격 같은 단서를 확인하지 않고 진행했다. 커밋 뒤에는 테스트를 다시 돌리지 않았다.
- [cli#3 좋음] 원인을 짚어 설명했고, 요청하자 수정 전후 발송 횟수(메일·푸시 각 3회에서 1회)를 실제 흐름으로 비교해 보여 줬다. 재시도가 유지되는 것도 테스트로 확인했다.
- [cli#3 불편] 처음엔 단위 테스트만 추가해서, 메일·푸시 발송 횟수 근거는 내가 따로 요청해야 나왔다. 제한 시간 설정 변경이나 로그의 3~4초 지연 같은 배경은 에이전트가 묻지 않았고 나도 말하지 않았다.
- [cli#4 좋음] 원인을 코드에서 정확히 짚어 설명했고, 수정 전 코드에서는 새 테스트가 실패하는 것까지 확인해서 근거가 분명했다.
- [cli#4 불편] 푸시 검증은 내가 물어보기 전에는 없었다. 설정 변경 여부는 git 이력이 한 커밋뿐이라 확인할 수 없었다.
- [cli#5 좋음] 첫 요청에 원인 두 가지(중복 제거 키, 느린 성공을 재시도하는 정책)를 짚어 줬고, 수정 전 코드로 돌렸을 때 테스트가 실패하는 것까지 보여 줘서 믿을 만했다.
- [cli#5 불편] 푸시 근거와 설정 출처는 내가 따로 물어야 나왔다. 운영에서 실제 timeout 값은 끝내 확인하지 못했다.
- [relay@auto#1 좋음] 의도 정리에서 사람만 아는 규칙(재시도 유지, 불확실 발송 처리, 근거 형태)을 선택지로 물어 줘서 내 요구가 완료조건에 그대로 들어갔다. 원인을 코드 위치와 함께 설명하고 메일·푸시 시험과 발송 기록으로 근거를 보여 준 점도 좋았다.
- [relay@auto#1 불편] 완료 화면의 판정표가 비어 있어 완료조건별 판정을 한눈에 볼 수 없었다. 자율 유형은 자동으로 넘어가서 중간에 끼어들 틈이 적었고, 결과는 터미널 요약과 diff를 직접 읽어 확인해야 했다.
- [relay@auto#2 좋음] 의도 정리에서 원인 후보를 코드에서 찾아 선택지로 물어 주었고, 재시도를 유지한다는 조건도 지켜졌다. 요약, diff, 테스트 70개 통과, 커밋 확인까지 근거가 충분히 나왔다.
- [relay@auto#2 불편] 질문 세 번째 항목의 답이 내가 고르기 전에 추천안으로 이미 선택되어 있었다. 자율 유형은 구현 단계가 자동으로 지나가서, 테스트 결과와 커밋 여부는 내가 따로 물어서 확인해야 했다.
- [relay@auto#3 좋음] 의도 정리에서 원인 후보 두 개와 재시도 유지 같은 결정을 선택지로 하나씩 물어서 방향을 내가 정할 수 있었다. 수정 전/후 재현 출력과 메일·푸시 각각의 테스트가 나와서 근거를 볼 수 있었다.
- [relay@auto#3 불편] 완료 직전 화면의 판정표가 비어 있어서, 어느 완료조건이 충족됐는지 터미널 요약과 diff로 따로 확인해야 했다. 자율 유형은 의도를 승인하면 그 뒤로는 중간에 끼어들 지점이 거의 없었다.
- [relay@auto#4 좋음] 의도 정리에서 범위와 재시도 유지 여부를 선택지로 먼저 물어 줘서 내 조건(재시도는 끄지 않음)이 그대로 반영됐다. 원인, 수정, 테스트, 전체 테스트 결과가 한 번에 정리돼 나왔다.
- [relay@auto#4 불편] 판정표가 끝까지 비어 있어 완료조건별 근거를 패널에서 볼 수 없었다. 처음 테스트가 메일만 다뤄서 푸시 테스트는 내가 따로 요청해야 했다. 물어보지 않으면 푸시 근거가 안 나왔을 것이다.
- [relay@auto#5 좋음] 의도 정리에서 원인 후보와 선택지를 코드 근거와 함께 물어 줘서 방향을 쥐고 있다고 느꼈다. 메일과 푸시 각각의 테스트와 재시도 유지 테스트까지 나와서 원하던 근거를 얻었다.
- [relay@auto#5 불편] 승인 화면의 판정표가 비어 있어서 완료조건별 근거를 터미널 요약과 diff로 직접 확인해야 했다. 지난주에 바꾼 timeout 설정값에 대해서는 에이전트가 묻지 않았다.

- [relay@auto#3 불편] 자율 진행이 시작된 뒤에는 내가 정한 규칙이 코드에 제대로 들어갔는지 스스로 diff를 읽어 확인해야 했다. round가 음수에서 어긋난 것은 내가 잡았고 에이전트는 몰랐다. 의도 초안이 분량 기준을 넘었다는 경고도 있었다.
- [relay@auto#4 좋음] 의도 정리 단계에서 선택지로 하나씩 물어 줘서 세부를 답하기 쉬웠다. 완료조건과 확인 방법이 정리돼 있어서 결과를 대조하기도 편했다. 바로잡아 달라고 한 round 버그도 한 번에 고치고 시험까지 넣어 커밋했다.
- [relay@auto#4 불편] 모듈마다 나눠 동시에 해 달라고 했는데 에이전트가 자식 세션을 쓰지 않았다. 시험 세 개만 동시에 돌렸고, 그 이유는 끝난 뒤에야 알려 줬다. 루트 경로 rm 승인 창이 떠서 잠깐 당황했고, 에이전트가 / 에 남긴 임시 파일을 나더러 지우라고 했다.
- [relay@auto#5 좋음] 짧게 쓴 요청이었는데도 의도 정리에서 하나씩 물어 줘서 세부를 정할 수 있었다. 모듈별 자식 세션으로 나눠 동시에 진행하고 브랜치 하나로 합쳐 주는 흐름이 요청과 정확히 맞았다.
- [relay@auto#5 불편] 의도 정리 질문이 많아 시간이 걸렸고, 질문 선택지가 내가 원하는 내용과 달라서 직접 입력해야 한 적이 있었다. 에이전트가 요청에 없던 package.json 변경(동시 실행 수)을 넣었고, 이걸 완료 화면에서 눈에 띄게 알려 주지는 않았다.

- cli#2 차례 5 (friction 2): 코드에서 어긋남 확인: 코드 블록 언어 class 없음, round가 자릿수 인자 없이 Math.round.
- cli#5 차례 4 (friction 2): 에이전트가 사양을 묻지 않아 어긋난 구현이 나옴
