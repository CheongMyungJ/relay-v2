- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 정지 규칙은 모두 구현했다. 정지 중 결제·배송·안내 제외, 재개 시 결제일을 정지한 일수만큼 밀기, 최대 28일, 자동 재개, 연간 플랜 거절이 해당한다.

A는 기존 조건을 `cancelledOn || status === 'paused'`로 좁게 고쳐 변경 범위가 작다. 기존 해지 판정 방식은 그대로 둔다. 연간 플랜 판정은 `period === 'annual'`로 직접 적었다. 시험은 결제·배송·안내 각각을 따로 검증한다. 자동 재개 경계(28일째는 정지 유지, 29일째 재개)와 재개 직후 결제·배송·안내가 이어지는지도 확인한다.

B는 `status !== 'active'`로 바꿨다. 이 조건은 결제·안내에서 cancelledOn 대신 status를 쓰게 만들어, 기존 시험 데이터나 상태값에 따라 동작이 달라질 수 있는 위험이 있다. 또 `runDaily`의 반환 형태에 `resumed`를 추가해 요청 밖의 공개 동작을 바꿨다. 연간 거절은 `period !== 'monthly'`로 적어, 나중에 플랜 주기가 늘면 의도와 다르게 막힐 수 있다. 시험은 정지 중 결제·배송·안내를 합산해서 확인하므로 어느 쪽이 깨졌는지 알기 어렵다. 지연 실행 시 28일 상한 시험은 있어 좋다.

종합하면 A가 범위, 코드 품질, 시험 면에서 조금 낫다.
  - 경험 전체 cli (relay 5, 맨 CLI 8) — B는 설계를 먼저 보여 주고 열린 질문을 정리해 물어 짧은 시간에 끝났다. A는 단계는 투명했으나 추천 선택지가 요구와 어긋났고 연간 규칙을 리뷰에서 직접 추가해야 해 수고가 컸다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 숨긴 시험을 전부 통과했고 핵심 규칙도 맞게 구현했다. 재개 때 결제일을 정지한 날 수만큼 밀고, 정지 기간은 최대 28일로 제한하며, 28일이 지나면 자동 재개하고, 연간 플랜은 정지를 거절한다. 결제·안내는 cancelledOn으로, 배송은 status로 해지를 거르는 함정도 둘 다 처리했다. 세 곳(결제·배송·안내)에서 모두 paused를 걸렀다.

차이는 다음과 같다.
- A는 pausedOn 필드를 helpers.js의 기본 구독과 subscribe()에 추가했다. 이는 합리적이지만 변경 범위가 조금 넓다. B는 pausedOn을 helpers에 넣지 않았고 테스트에서 직접 지정한다.
- A는 runDaily의 반환값에 resumed를 추가했다. 이는 API 변경이다.
- B는 내부 resume 함수를 공유해 자동 재개와 수동 재개가 중복 없이 같은 규칙을 쓰게 했다. A는 resumeSubscription을 재사용하며 비슷한 효과를 낸다.
- B는 'active인 구독만 정지 가능'과 '월간만 정지 가능'으로 검사했다. A는 연간만 거절한다. 월간·연간 외의 플랜 주기가 생기면 동작이 달라질 수 있다.
- 시험은 B가 더 촘촘하다. 재개 후 배송·안내·결제 재개, 정지 28일째 자동 재개, 작업이 빠져 늦게 재개돼도 28일만 미는 경우, 정지 중 해지를 다뤘다. A도 핵심 경로는 다뤘지만 B보다 얇다.

전체적으로 B가 회귀 방지 면에서 더 낫다.
  - 경험 전체 cli (relay 6, 맨 CLI 7) — A는 수고가 적고 빠르게 끝났다. B는 의도 정리와 검증 근거가 더 좋았지만 단계가 많았고 잘못 입력한 일이 있었다. 둘 다 연간 플랜 규칙을 먼저 묻지 않았다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 핵심 규칙은 같은 구조로 구현했다. 정지 중 결제·배송·안내 제외, 재개 시 결제일 연장, 28일 상한, 하루 작업에서 결제 전에 자동 재개, 연간 플랜 거절이 같다. 차이는 주변 부분에서 난다. B는 요구에 없는 예외를 넣었다. 결제일이 정지일 이전이면 재개해도 결제일을 밀지 않는다. 사람이 말한 "정지한 날 수만큼 민다"와 어긋나고, 이 판단은 사람에게 확인받지 않았다. 반면 A는 결제일이 정지 중에 지난 구독도 쉰 날 수만큼 민다는 시험을 두어 규칙대로 일관되게 동작한다. B는 README와 config에도 손을 댔다. README는 기대 범위 밖이지만 설명을 갱신하는 정도라 해가 작다. config.maxPauseDays 분리와 resumeOn 필드는 쓸 만한 설계이나 필수는 아니다. A는 index.js에 export를 추가했다. 호출 경로가 service.js라 꼭 필요하진 않으나 공개 진입점과 맞추는 합리적인 변경이다. 시험은 A가 별도 파일에 상태 전이, 연간 거절, N일 재개, 28일 초과, 같은 날 재개 같은 경계 사례를 더 넓게 다룬다. B는 daily와 subscriptions 시험에 나눠 넣었고 자동 재개는 잘 다루지만 경계 사례는 상대적으로 적다.
  - 경험 전체 cli (relay 6, 맨 CLI 7) — 두 쪽 모두 연간 플랜 규칙은 묻지 않아 사람이 정정했다. A는 선택지 질문과 판정표가 강점이지만 차례와 시간이 두 배 넘게 들었다. B는 짧고 빠르게 설계 확인과 diff 검토를 마쳤다.

### 사람 역할의 말

- [relay#1 좋음] 단계마다 요약과 판정표, 변경 내용이 나와서 무엇이 왜 바뀌었는지 확인하기 쉬웠다. 완료조건마다 테스트가 있고 통과했다는 근거도 같이 보였다.
- [relay#1 불편] 에이전트가 연간 플랜을 정지할 수 있는지 끝까지 묻지 않았다. 리뷰 단계에서야 내가 직접 짚어서 추가해야 했다. 또 "추천"으로 표시된 선택지가 실제 요구와 달라서(기간 제한 없음) 직접 입력해야 했다.
- [relay#2 좋음] 의도 정리 단계에서 에이전트가 결제일과 정지 기간 상한을 선택지로 물어 줬다. 완료조건마다 판정표와 근거가 나오고 전체 diff도 볼 수 있어서 결과를 믿고 승인할 수 있었다.
- [relay#2 불편] [Work 설정]을 누른다는 게 프로젝트 설정(받을 봇 칸)이 열렸는데, 거기에 수정 요청을 잘못 입력했다. 에이전트는 연간 플랜 정지 불가를 먼저 묻지 않았고, 내가 알아채고 말해서 바로잡았다.
- [relay#3 좋음] 의도 정리에서 에이전트가 결제일, 정지 기간, 리포트와 문자를 선택지로 물었고, 완료조건별 판정표로 결과를 확인할 수 있었다.
- [relay#3 불편] 연간 플랜 규칙은 에이전트가 묻지 않아 내가 초안을 보고 직접 정정해야 했다. 터미널 선택지 조작 방식도 처음엔 약간 낯설었다.
- [cli#1 좋음] 코드를 짜기 전에 설계안을 먼저 보여 줬다. 결제, 배송, 알림이 cancelledOn만 보고 있다는 함정도 스스로 찾아냈다. 열린 질문을 정리해 물어서 내가 방향을 정하기 쉬웠다.
- [cli#1 불편] 설계안이 길어서 스크롤로 읽어야 했다. 28일 상한이나 연간 플랜 제외 같은 규칙은 내가 먼저 말해 줘야 반영됐다. 에이전트가 먼저 이런 규칙을 물어봤다면 더 좋았을 것이다.
- [cli#2 좋음] 코드를 고치기 전에 설계를 짧게 보여 줬다. 결제·알림·배송처럼 건드려야 할 다른 모듈도 스스로 찾아냈다.
- [cli#2 불편] 연간 플랜 거절은 에이전트가 묻지 않았다. 오히려 설계에 연간도 같은 방식이라고 적혀 있어서 내가 직접 짚어야 했다. 이런 정책 예외는 먼저 물어봐 주면 좋겠다.
- [cli#3 좋음] 코드를 고치기 전에 설계안을 먼저 보여 줬다. 결제·배송·알림 모듈까지 짚었고, 확인할 질문(자동 재개, 최대 기간)을 던져서 내가 28일 규칙을 바로 바로잡을 수 있었다.
- [cli#3 불편] 연간 플랜을 정지할 수 있다고 가정한 설계안이 나왔고, 이를 묻는 질문은 없었다. 내가 먼저 바로잡아야 했다. 설계안도 꽤 길었다.
