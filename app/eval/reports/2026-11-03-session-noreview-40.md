- 판정 #1: 결과 선호 cli — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 파일 범위도 기대한 대로다. 차이는 엣지 케이스 처리와 시험의 폭이다. A는 잘못된 날짜를 넣으면 조용히 0이나 이상한 값을 돌려준다. 닫히지 않은 따옴표도 조용히 받아들인다. addWorkdays는 n<0이면 오류를 낸다. 시험은 적당하지만 월·연 경계, 잘못된 입력, 근무일 왕복은 다루지 않는다. B는 날짜 형식을 검사해 RangeError를 내고, 닫히지 않은 따옴표에 SyntaxError를 낸다. parseKrw는 `₩-1` 같은 변형도 처리하고, 음수 n도 지원한다. 시험은 경계, 오류, 왕복까지 더 넓게 다룬다. 요청에 없던 음수 n 지원과 검증을 더한 점은 범위가 약간 넓지만 해롭지 않다. 전체적으로 B가 견고하고 회귀 방지력이 더 낫다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 8) — 결과와 브랜치 분리는 비슷했다. B는 수고와 시간이 훨씬 적었다. A는 질문, 승인, diff 확인으로 명확성과 확신을 조금 더 얻었지만, 질문하지 않고 TypeError로 정한 문제는 그대로 남았다.
- 판정 #2: 결과 선호 relay@auto — 숨긴 시험은 둘 다 모두 통과했고 구조도 비슷하다. 차이는 "toCsv로 쓴 것을 읽으면 그대로" 요구를 어떻게 다뤘느냐다. B는 칸이 하나뿐이고 빈 글인 행을 toCsv에서 '""'로 쓰게 고쳤다. 그래서 [['a'],['']] 같은 입력도 왕복이 되고, 이 경우를 시험에도 넣었다. A는 toCsv를 건드리지 않아서, 마지막 행이 [''] 이면 끝 줄바꿈 규칙 때문에 그 행이 사라진다. 요구한 왕복이 이 경우에는 깨진다. B가 toCsv를 고친 것은 범위를 조금 넓힌 셈이지만 요구에 필요한 수정이라 정당하다. A는 날짜와 n에 대한 입력 검증이 더 꼼꼼하고 시험도 더 많다. 하지만 이 검증은 요구에 없던 것이다. 그래서 명시된 요구를 더 완전하게 지킨 B를 근소하게 앞선 것으로 본다. 모듈별 브랜치 나눔은 주어진 기록에서 확인할 수 없어 평가에 반영하지 않았다.
  - 경험 전체 relay@auto (relay (자율 유형) 7, 맨 CLI 5) — A는 더 빠르고 단계가 적었다. 하지만 에이전트가 규칙을 임의로 정해 사람이 결과를 보고 고쳐야 했고, diff도 보지 않아 확신이 낮았다. B는 시간이 더 걸리고 단계가 많았으며 선택지에 원하는 안이 없었다. 그래도 규칙을 사전에 확인했고 의도 승인과 diff 검토로 신뢰 근거를 얻었다. 그래서 B가 더 낫다.
