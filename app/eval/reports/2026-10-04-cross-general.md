### 사람 역할의 말

- [relay#1 좋음] 완료조건 판정표에 항목마다 근거가 있었다. 수정 전 코드에서 새 테스트가 실패한다는 확인까지 있어서 결과를 믿기 쉬웠다.
- [relay#1 불편] 한 줄짜리 버그인데 단계가 많고 승인할 곳이 여러 번 나온다. 완료 화면은 오른쪽 패널이 좁아서 표가 잘려 보였다.
- [relay#2 좋음] 판정표에 완료조건별 통과 여부와 근거가 나오고 전체 변경 diff도 바로 볼 수 있어서, 파일을 직접 열지 않고도 결과를 믿을 수 있었다.
- [relay#2 불편] 한 줄짜리 간단한 버그인데도 의도 승인과 리뷰 승인 단계를 거쳐야 해서 조금 무거웠다. 새 Work 창에서 유형을 골라야 시작이 켜진다는 점도 처음엔 바로 알기 어려웠다.
- [relay#3 좋음] 완료조건별 판정표와 근거가 나와서 결과를 믿기 쉬웠다. 의도 승인 화면에서 테스트 추가도 완료조건에 들어가 있었다.
- [relay#3 불편] 한 줄짜리 버그인데 단계가 많고 승인도 여러 번 해야 해서 조금 무거웠다.
- [relay@general#1 좋음] 완료조건별 판정표와 근거, 전체 변경 diff를 바로 볼 수 있어서 승인 전에 확인하기 쉬웠다. 회귀 테스트도 자동으로 추가됐다.
- [relay@general#1 불편] 간단한 버그인데 단계가 많았고, '일반' 유형을 골랐더니 bugfix로 바꾸라는 질문이 한 번 더 나왔다.
- [relay@general#2 좋음] 완료조건별 판정표와 근거, 전체 변경 diff를 한 화면에서 볼 수 있어서 코드를 따로 열지 않고도 결과를 믿을 수 있었다.

A는 요청에 없는 규칙을 더했다. 음수 가격을 RangeError로 막는다. 이 규칙은 사람이 말한 적이 없어 범위를 조금 넘는다. B는 정렬 비교 함수를 SORTS 객체에 모아 읽기 쉽다. Object.hasOwn으로 'toString' 같은 값도 막는다. B의 시험은 listProducts()와 page:1이 기존과 같은 결과인지 확인한다. 모든 쪽을 모아 중복과 누락이 없는지도 확인한다. 필터와 정렬 조합, 한쪽 끝만 지정한 범위도 다룬다. 이 덕에 회귀 방지력이 A보다 약간 낫다. A의 시험도 원본 불변과 경계를 잘 확인하지만, 위의 차이 때문에 B를 약간 더 높게 본다.

A는 SORTS 비교 함수 맵과 Object.hasOwn으로 'toString' 같은 값을 막아 구조가 깔끔하다. 시험으로 기존 호출을 page 1~4까지 명시적으로 고정해 "기존 화면이 안 깨졌다"는 확인을 더 직접 제공한다.   - 경험 전체 relay@general (relay 6, relay (일반 유형) 8) — A는 설계 단계에서 한 번의 수정 지시로 규칙이 반영되어 바로 승인했다. B는 같은 수정이 의도 문서와 어긋나 되감기와 재입력이 필요했다. 둘 다 결과를 믿을 근거는 충분했지만, 수고와 헷갈림은 B가 더 컸다.

전체적으로 A가 동작 보존 근거와 문서화에서 조금 더 낫다.
  - 경험 전체 relay (relay 8, relay (일반 유형) 7) — 두 기록 모두 동작 그대로라는 근거를 제시했고 설문 점수도 같다. 차이는 B에서 유형 재질문 마찰이 한 번 있었고 차례가 하나 더 많았다는 점이다. 그래서 A를 근소하게 우위로 본다.
