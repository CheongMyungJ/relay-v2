  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — 두 기록은 시간과 설문 점수가 거의 같다. A는 단계가 한 번 적고 유형 권유로 인한 마찰이 없다. 또 수정 전 테스트 실패 확인이 있어 근거가 조금 더 있다. 둘 다 한 줄 버그에 비해 승인 절차가 많다는 불만이 있다.

### 사람 역할의 말

- [relay#1 좋음] 완료조건 판정표에 항목마다 근거가 있었다. 수정 전 코드에서 새 테스트가 실패한다는 확인까지 있어서 결과를 믿기 쉬웠다.
- [relay#1 불편] 한 줄짜리 버그인데 단계가 많고 승인할 곳이 여러 번 나온다. 완료 화면은 오른쪽 패널이 좁아서 표가 잘려 보였다.
- [relay#2 좋음] 판정표에 완료조건별 통과 여부와 근거가 나오고 전체 변경 diff도 바로 볼 수 있어서, 파일을 직접 열지 않고도 결과를 믿을 수 있었다.
- [relay#2 불편] 한 줄짜리 간단한 버그인데도 의도 승인과 리뷰 승인 단계를 거쳐야 해서 조금 무거웠다. 새 Work 창에서 유형을 골라야 시작이 켜진다는 점도 처음엔 바로 알기 어려웠다.
- [relay#3 좋음] 완료조건별 판정표와 근거가 나와서 결과를 믿기 쉬웠다. 의도 승인 화면에서 테스트 추가도 완료조건에 들어가 있었다.
- [relay#3 불편] 한 줄짜리 버그인데 단계가 많고 승인도 여러 번 해야 해서 조금 무거웠다.

- [relay@general#1 불편] 간단한 버그인데 단계가 많았고, '일반' 유형을 골랐더니 bugfix로 바꾸라는 질문이 한 번 더 나왔다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과하고, 바뀐 파일도 기대한 범위 안이다. 구현은 거의 같다. 다른 점은 아래와 같다.

A는 exportOrders가 options를 그대로 toCsv에 넘긴다. options가 undefined여도 toCsv의 기본값 처리 덕분에 동작하고, 코드가 단순하다. 테스트에는 기본 쉼표, 세미콜론, 탭, 구분자가 든 값의 따옴표 처리가 있다. 세미콜론일 때 쉼표만 든 값은 감싸지 않는다는 것, 따옴표와 줄바꿈이 쉼표·세미콜론·탭에서 모두 감싸진다는 것, exportOrders의 옵션 전달도 확인한다.

B는 exportOrders가 `{ delimiter } = {}`로 구조 분해한 뒤 `{ delimiter }`를 다시 만들어 넘긴다. undefined를 넘기면 toCsv의 기본값이 적용되므로 동작은 맞지만 약간 중복이다. B는 toCsv 위에 옵션 설명 주석을 달았는데, "한 글자"라고만 적고 검증은 하지 않는다. 테스트는 세미콜론, 탭, 따옴표·줄바꿈, 기본값, exportOrders 전달을 다룬다. 다만 따옴표·줄바꿈은 세미콜론에서만 확인하고, 기본 쉼표 테스트는 `{}`를 넘겨서 옵션 자체를 생략하는 경우를 직접 확인하지 않는다. 이 경우는 기존 테스트가 일부 덮는다.

두 결과 모두 구분자 검증이 없다. 그래서 A의 테스트가 조금 더 촘촘하고 코드가 조금 더 단순한 A를 약간 더 높게 본다.
  - 경험 전체 relay@general (relay 6, relay (일반 유형) 7) — 두 기록의 차례 수, 행동 수, 입력량, 설문 점수가 거의 같다. B는 설계 승인 단계가 없어 시간이 0.7분 짧고 승인이 한 번 적었다. A는 승인을 여러 번 눌러야 해서 무겁다고 했다. B에는 유형 재확인 질문이라는 작은 헷갈림이 있었다.
- 판정 #2: 결과 선호 tie — 두 결과 모두 같은 세 파일만 바꿨고 숨긴 시험과 레포 시험을 통과한다. toCsv의 구현은 사실상 같다. 구분자 기본값은 쉼표이고, 구분자가 든 값은 따옴표로 감싸며, 탭도 지원한다. A는 exportOrders에서 options를 그대로 넘겨 더 간결하다. B는 구조 분해 후 다시 묶어 넘기는데, 동작은 같다. 시험은 둘 다 충분하다. A는 구분자 종류와 쉼표 비감쌈을 폭넓게 다루고, B는 따옴표와 줄바꿈이 구분자와 무관하게 감싸지는 경우를 다룬다. 우열을 가를 만한 차이가 없다.
  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — A는 차례와 행동이 적고 마찰이 없었다. B는 약간 더 빨리 끝났지만 유형 변경 권유와 리뷰 지적 질문이 끼어 절차가 더 번거로웠다. 둘 다 설문 점수는 같고, 승인 단계가 무겁다는 불만도 같았다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 같은 세 파일만 바꿨다. 구현도 거의 같다. 둘 다 구분자가 든 값이나 따옴표, 줄바꿈이 든 값을 감싸고, 기본값은 쉼표다. 코드 품질은 비슷하다. A는 구분자가 한 글자라고 가정한다는 점을 주석으로 밝혔고, `exportOrders`는 옵션을 그대로 넘긴다. B는 `needsQuote` 변수로 읽기 쉽게 나눴지만, `exportOrders`에서 옵션을 풀었다가 다시 묶는다. 시험은 A가 더 촘촘하다. A는 세미콜론일 때 쉼표가 든 값을 감싸지 않는 경우와 구분자와 상관없이 줄바꿈 값을 감싸는 경우까지 시험한다. B는 세미콜론, 탭, 따옴표 감싸기, 주문 내보내기를 시험하지만 이 두 경우는 빠졌다.   - 경험 전체 relay (relay 7, relay (일반 유형) 6) — A가 더 적은 차례와 행동으로 끝났다. 작은 일을 빨리 끝내려는 선호에 더 맞았다. B는 diff를 볼 수 있었지만 의도 질문이 세 번 나오고 대기도 길었다. 확신과 통제는 비슷하다.

- 판정 #1: 결과 선호 relay@general — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 동작상 핵심 규칙(경계 포함, id 오름차순 동률 처리, RangeError, 기존 호출 유지)을 맞게 구현했다. 어느 쪽도 설계를 먼저 사람에게 보여 주거나 선택지를 묻지는 않았다. 이 기록에서는 그 점이 차이를 만들지 않는다.

A는 src/products.js와 test/products.test.js만 바꿨다. 범위가 필요한 만큼이다. 가격 검증에서 Infinity를 거르고, `Object.hasOwn`으로 sort를 검사해 'toString' 같은 값도 막는다. 이 부분이 B보다 꼼꼼하다. 테스트는 기존 호출을 `deepStrictEqual`로 전체 비교해 기존 화면이 깨지지 않았다는 확인에 가장 직접적이다. 필터와 정렬, 쪽 넘김, 오류 경우도 폭넓게 다룬다.

B는 `docs/knowledge/products/list-input-errors.md`를 새로 만들었다. 요청하지 않은 파일이라 scope가 어긋난다. 또 `isNumber`가 Infinity를 허용한다. 테스트는 충실하고 정렬이 원본을 바꾸지 않는다는 확인까지 있다. 다만 sort 검증은 `SORTS.includes`라서 문제가 없다.

종합하면 A가 범위와 검증 면에서 더 낫다.
  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — 두 기록의 수고와 통제는 거의 같다. 둘 다 설계가 경계 규칙을 묻지 않아 사람이 직접 고쳤다. B는 기존 호출 호환을 명시한 테스트와 요약된 가정으로 확신을 더 줬다. A는 약간 빠르고 입력이 적었지만 유형 권유 질문과 불명확한 경고가 있었다.
- 판정 #2: 결과 선호 relay@general — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 핵심 규칙인 같은 가격의 id 오름차순, min>max와 모르는 sort의 RangeError, 양 끝 포함, 기존 호출 유지를 지켰다. 차이는 범위와 시험에서 난다. A는 기대 범위 밖인 docs/knowledge 문서 2개를 추가했다. 또 요청에 없는 음수 가격 거부 규칙을 넣었다. B는 src/products.js와 test/products.test.js만 바꿨고, 정렬 비교 함수를 SORTS 객체에 모아 읽기 쉽다. Object.hasOwn으로 'toString' 같은 sort 값도 막았고, 이 경우를 시험으로도 확인했다. B의 시험은 모든 쪽을 모아 중복과 누락이 없는지 보는 회귀 시험과, 기존 호출 결과를 고정하는 시험을 포함해 쪽 넘김 문제를 더 직접 막는다. 두 결과 모두 설계를 먼저 보여 주거나 사람에게 묻는 과정은 기록에 나타나지 않는다. 그래서 그 점은 비교 요소로 쓰지 않았다.
  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — 두 기록 모두 설계를 먼저 보여 줬지만, 에이전트가 경계 규칙을 먼저 묻지 않아 사람이 직접 지적해야 했다. A는 차례가 하나 적고 설계에 기존 호출 불변 확인이 들어 있어 조금 낫다. B는 유형 선택 질문이 헷갈렸고 대기도 더 길었다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험을 통과하고 로직이 사실상 같으며, 기대 밖 문서 파일을 추가한 점도 같다. A는 코드가 약간 더 깔끔하고(`SORTS` 맵, `Object.hasOwn`) 기존 호출 회귀 시험이 촘촘하다. 반면 불필요한 배열 복사가 있다. B는 시험이 더 넓다(minPrice만·maxPrice만, 빈 결과, null·Infinity, 검증 순서, 원본 불변, 동률 그룹). 시험 폭의 차이로 B를 근소하게 선호한다.
  - 경험 전체 relay@general (relay 6, relay (일반 유형) 8) — A는 설계 단계에서 한 번 고치고 바로 승인해 흐름이 매끄러웠다. B는 설계 단계에서 고친 내용이 의도 문서와 어긋나 되감기와 재지시가 필요했고, 의도 단계가 두 번 생겨 수고와 혼란이 컸다. 최종 결과와 확인 수단은 비슷했다.

### 사람 역할의 말

- [relay#1 좋음] 의도 정리 단계에서 에이전트가 묻지 않고 가정으로 초안을 썼는데, 어긋난 부분을 바로 지적해 고칠 수 있었다. 요약과 가정이 한눈에 보여 검토하기 쉬웠다. 마지막 판정표는 완료조건마다 근거가 있어 믿을 만했다.
- [relay#1 불편] 에이전트가 동점 정렬 기준과 min>max 처리를 묻지 않고 임의로 가정해서, 내가 직접 읽고 고쳐 달라고 해야 했다. 리뷰 단계에서 stop hook 형식 오류가 터미널에 노출돼 잠깐 혼란스러웠다.
- [relay#2 좋음] 의도 정리와 설계 단계에서 요구와 가정을 먼저 보여 줘서, 내가 아는 규칙(RangeError, id 순 동률)이 빠진 것을 코드 전에 바로잡을 수 있었다. 마지막 판정표와 전체 변경으로 완료조건별 근거와 diff를 한 화면에서 확인할 수 있었다.
- [relay#2 불편] 에이전트가 minPrice>maxPrice 같은 규칙을 먼저 묻지 않고 가정으로 정해서, 내가 직접 잡아내야 했다. 완료 뒤 터미널이 "새 세션을 띄우는 중"이라는 문구와 resume 안내만 보여 줘서 조금 어리둥절했다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 세 모듈로 나누었고, 숨은 버그(0원 행만 있는 분류가 빠짐)를 고치지 않고 그대로 두었다. 숨긴 시험도 둘 다 통과했다. 코드 구조도 거의 같다.

A는 buildReport를 통한 특성화 시험 13개를 추가했다. 0원·비숫자·빈 금액 행 제외, 음수, 같은 금액일 때 이름순, CRLF, 열 순서, 열 너비, 소수 금액, 빈 입력 같은 경계를 폭넓게 고정한다. 동작이 그대로라는 근거를 보고 싶다는 요청에 잘 맞는다. 바뀐 파일도 src와 test 안에 머물렀다.

B의 시험은 4개뿐이다. 0과 NaN 제외는 summarize 단위 시험 한 곳에서만 확인한다. 0원만 있는 분류가 빠지는 동작을 buildReport 출력으로 고정하지는 않았다. 또 마지막 시험은 buildReport가 세 단계를 이은 것과 같다는 동어반복에 가까워서 회귀를 막는 힘이 약하다. 게다가 요청하지 않은 docs/knowledge 문서를 새로 만들어, 관계없는 변경이 섞이지 않았으면 좋겠다는 선호와 맞지 않는다.
  - 경험 전체 relay (relay 8, relay (일반 유형) 7) — 두 기록은 시간과 설문 점수가 거의 같다. A는 단계가 적고, 기준 코드와 최종 코드에서 통과하는 안전망 테스트를 남겼으며, 관계없는 수정이 없었다. B는 유형 권유로 한 번 더 답했고 요청하지 않은 docs가 커밋에 들어왔는데, 이는 사람의 선호에 어긋난다.
- 판정 #2: 결과 선호 relay — 두 결과 모두 세 모듈로 나눴고 숨은 버그(0원 행만 있는 분류가 빠짐)를 고치지 않고 그대로 뒀다. 숨긴 시험도 둘 다 통과했다.

A는 summarize가 정렬과 합계까지 맡고, formatReport는 출력 글만 만든다. 모듈 책임이 깔끔하게 나뉜다. 안전망 시험이 buildReport 출력을 고정한다. 0원과 NaN 행, 동점 정렬, 폭 맞춤, 헤더 순서, CRLF, 빈 입력을 다룬다. 사람이 원한 "동작이 그대로라는 근거"에 잘 맞는다. 단점은 docs/knowledge/…/known-quirks.md를 새로 만든 점이다. 기대 밖 파일이라 scope는 감점했다. 다만 숨은 버그를 "적어 두는" 쪽에는 부합한다. 문서에 "따옴표 안의 쉼표" 같은 이번 일과 관계없는 항목까지 넣은 점은 약간 과하다.

B는 변경 범위가 가장 좁다. 하지만 정렬이 formatReport 안에 들어가서, 주석의 "집계/정렬/출력" 분담이 덜 자연스럽다. summarize가 Map만 돌려주는 설계도 약하다. 시험은 모듈별 단위 시험 위주다. 0원만 있는 분류가 빠지는 경계를 buildReport 수준에서 고정하지 않는다. 단위 시험에서 0원 행이 빠지는 것은 확인한다. 하지만 "0원 행과 다른 행이 섞인 분류"나 CRLF, 헤더 순서 같은 회귀 경계는 덜 다룬다.

종합하면 A가 동작 보존의 근거를 더 잘 제시한다. 문서 파일 추가는 작은 감점이다.
  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — 두 기록은 결과가 비슷하다. A는 질문 없이 진행돼 수고가 적었고, 숨은 버그를 문서로 적어 둔 점과 기준 코드에서의 테스트 통과가 근거가 됐다. 다만 범위 밖 문서 커밋이 섞인 것은 사람의 선호와 어긋난다. B는 범위가 깔끔하고 출력 비교 근거도 좋았지만, 이미 고른 유형을 다시 묻는 질문이 끼어들었다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 세 모듈로 나누고 buildReport가 셋을 차례로 부른다. 숨은 버그(0원 행만 있는 분류가 빠짐)는 고치지 않았고, 숨긴 시험과 레포 시험도 모두 통과한다. 기대 밖 파일도 없다. 소스 동작은 사실상 같고 차이는 요약 결과의 모양과 시험에 있다.

A는 요약 결과를 `[분류, 합계]` 튜플로 넘긴다. 시험은 모듈별 단위 시험 위주다. 0원만 있는 분류가 빠지는 경계는 `x,0` 한 줄짜리 buildReport 시험이 간접적으로만 잡는다. 같은 금액일 때 이름순 정렬은 summarize 단위 시험에 있다. 하지만 trim, 열 너비 확장, 음수 금액은 buildReport 출력으로 확인하지 않는다. 또 summary.js 주석에는 0원 행을 뺀다는 말이 없어서, 지금 동작이 알려진 한계라는 기록이 없다.

B는 요약 결과를 `{category, total}` 객체로 넘겨 읽기 더 쉽다. summary.js 주석에 "금액이 0이거나 숫자가 아닌 행은 뺀다"고 적어 현재 동작을 문서로 남겼다. 다만 이것을 버그라고 표시하거나 다음 주에 고칠 예정이라고 적지는 않았다. 시험은 buildReport 출력 기준으로 쓴 회귀 시험 6개다. 0원·숫자 아님·빈 금액 줄 제외, 빈 줄과 공백 trim, 같은 금액일 때 이름순, 긴 분류 이름의 열 너비, 빈 입력, 음수 금액을 다룬다. 내부 구조가 바뀌어도 출력이 같은지 확인하므로 "동작이 그대로"라는 근거로 더 낫다.

두 결과 모두 시험이 `0원만 있는 분류가 빠지는 현재 동작`을 명시적인 시험 이름으로 고정하지는 않는다. B는 시험 범위가 더 넓고 주석으로 현재 동작을 남겼다. 그래서 B를 선호한다.
  - 경험 전체 relay (relay 7, relay (일반 유형) 6) — 두 기록 모두 동작을 그대로 두고 근거를 보여 주었다. 차이는 A에서 유형을 다시 묻는 마찰이 한 번 있었고, 그래서 차례와 행동이 조금 더 많았다는 점이다. B는 마찰 없이 더 빨리 끝났다.
