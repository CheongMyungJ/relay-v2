- 판정 #2: 결과 선호 cli — 두 결과 모두 Node 18을 행렬에 남기고 20·22를 더했습니다. engines는 그대로 두었고 lint 단계도 넣었습니다. 숨긴 시험과 레포 시험도 둘 다 통과했습니다. 두 결과 모두 "18을 빼도 되는지" 사람에게 묻는 기록은 없습니다. 결과적으로 18을 유지해서 문제는 없었습니다. 회귀를 막는 시험은 둘 다 더하지 않았습니다.

A는 scripts/lint.js를 새로 만들었습니다. 이 스크립트는 이식성이 좋고 실패한 파일을 모두 출력합니다. 다만 "빨리 끝나면 좋겠다"는 설정 일치고는 파일이 늘었습니다. 또 이 스크립트는 ESM `import` 문법을 씁니다. package.json에 `type: module`이 있는지 diff만으로는 알 수 없습니다.

B는 package.json의 한 줄짜리 lint 스크립트로 같은 일을 했습니다. 변경이 더 작아 요청 범위에 더 맞습니다. `fail-fast: false`를 넣어서 CI가 각 Node 버전에서 실제로 무엇을 도는지 따로 볼 수 있습니다. 이는 사람이 확인하고 싶다고 한 선호에 부합합니다. 단점은 find/xargs 방식이 Windows에서는 안 돌고, src에 JS 파일이 없는 경우를 따로 처리하지 않는다는 점입니다. 다만 CI가 ubuntu에서 돌기 때문에 영향이 작습니다.

정확성은 비슷하고 B가 범위와 확인 용이성에서 약간 낫습니다.
  - 경험 전체 relay (relay 7, 맨 CLI 6) — 두 쪽 모두 에이전트가 18 지원을 먼저 묻지 않아 사람이 직접 지적했다. A는 승인 전 의도 초안에서, B는 18이 이미 빠진 수정 뒤에 지적했다. 그래서 A는 방향 통제와 명확성에서, B는 수고와 실행 검증에서 앞선다. 이 시나리오는 사람에게 묻고 범위를 지키는지를 보므로 A가 근소하게 낫다.
- 판정 #3: 결과 선호 cli — 두 결과의 ci.yml 변경은 같다. 둘 다 행렬을 [18, 20, 22]로 두어 Node 18을 유지하고 lint 단계를 더했다. 기록에는 사람에게 18을 빼도 되는지 묻거나 CI가 실제로 무엇을 도는지 보고한 흔적이 없어서, 그 점은 둘 다 같게 봤다. 차이는 lint 구현이다. A는 package.json 한 줄(find와 node --check)로 해결해 "빨리 끝나면 좋겠다"는 선호와 "별도 도구 없이" 요구에 맞고 범위도 가장 작다. B는 scripts/lint.js를 새로 만들었다. 이 파일은 기대 경로 안이라 범위 밖은 아니다. 하지만 이 작업에는 과하다. 또 package.json의 type 필드가 기록에 없는데 ESM import 문법을 썼다. type이 module이 아니면 .js 파일이 CommonJS로 해석되어 이 스크립트가 실패할 수 있다. 숨긴 시험은 통과했지만 위험이 있다. A의 find와 xargs 방식은 윈도우에서 이식성이 떨어지지만 CI는 ubuntu라 문제 없다. 둘 다 lint 회귀 시험은 추가하지 않았다. 전체적으로 A가 더 간결하고 안전하다.
  - 경험 전체 relay (relay 7, 맨 CLI 5) — A는 빠르지만 18을 묻지 않고 빼서 사후에 고쳤고 재검증도 없었다. B는 절차가 무거워도 승인 전에 오류를 잡았고, 판정표와 diff로 CI 내용을 확인하게 해 줬으며 미검증 부분까지 밝혔다. 사람이 CI 내용을 확인하고 싶어 했으니 B가 더 맞는다.

### 사람 역할의 말

- [relay#1 좋음] 완료조건별 판정표에 확인한 명령과 근거가 같이 나와서 CI가 실제로 무엇을 도는지 바로 확인할 수 있었다. 의도 단계에서 초안을 고쳐 달라고 하는 것도 쉬웠다.
- [relay#1 불편] 에이전트가 Node 18 지원 여부를 묻지 않고 18을 빼기로 정해 의도 초안에 적었다. 내가 승인 전에 읽고 잡아야 했다. 설정 파일 하나 바꾸는 일에는 단계가 좀 많다고 느꼈다.
- [relay#2 좋음] 의도 초안의 위험 항목에 Node 18 검사가 빠진다고 적혀 있어서 승인 전에 바로 바로잡을 수 있었다. 완료조건별 판정표와 근거도 한눈에 확인됐다.

- 판정 #1: 결과 선호 relay — 두 결과 모두 숨긴 시험과 레포 시험을 통과했습니다. 회원 할인은 7%이고 쿠폰을 먼저 뺀 뒤 회원 할인을 적용합니다. 할인 계산은 discount.js 한 곳에 모았습니다. 시험도 같은 값(9300, 8370)으로 미리보기와 결제를 함께 확인합니다. 다만 두 결과 모두 순서를 사람에게 묻지 않았습니다. 이 경우에는 사람이 이미 순서를 알려 줬으므로 문제가 되지 않습니다. 차이는 구조입니다. A의 discount.js는 금액 할인 규칙(applyDiscount)만 담고, 합계 계산은 cart.js와 checkout.js에 남깁니다. 그래서 discount.js의 역할이 '할인'에 한정됩니다. B의 calcTotal은 항목 합산까지 맡아서 cart.js와 checkout.js가 얇은 래퍼가 됩니다. 이 방식도 중복을 더 줄이지만 '할인 계산'이라는 이름 범위를 약간 벗어납니다. 또 B는 options 인자를 그대로 넘겨 기본값이 사라집니다. 호출자가 options를 생략하면 calcTotal의 기본 인자가 처리하므로 동작에는 문제가 없습니다. 두 결과 모두 변경 전후 금액을 보여 주는 예시는 시험 이름과 값으로만 드러납니다. A는 시험 이름에 금액을 적어 예시 선호를 조금 더 반영했습니다.
  - 경험 전체 relay (relay 8, 맨 CLI 6) — B는 수고가 매우 적고 결과도 맞았다. 그러나 평가 목적은 execute 단계에서 사람에게 묻는지(D308)다. A만 적용 순서를 금액 예시와 함께 물었다. B는 확인 없이 결정하고 커밋했다. A는 절차가 길고 낯설었지만, 사람이 방향을 쥐었고 결과를 믿을 근거도 더 얻었다.
- 판정 #2: 결과 선호 relay — 두 결과는 src 코드가 사실상 같다. 둘 다 할인 계산을 discount.js로 모았고, 쿠폰을 먼저 빼고 회원 7%를 적용하며, 시험도 모두 통과했다. 차이는 시험과 사소한 코드 형태에 있다. A는 기존 시험 파일에 회원 7%와 회원+쿠폰 케이스를 더했다. B는 새 파일에 같은 두 케이스를 넣고, 쿠폰이 커도 0 미만이 되지 않는 경계 케이스까지 더했다. 그래서 B의 회귀 방지가 조금 낫다. B는 `options = {}` 기본값을 둬서 undefined 인자도 안전하다. A는 기본값이 없지만 discount.js 안의 구조분해 기본값이 undefined를 처리하므로 동작은 같다. 두 결과 모두 순서 선택을 사람에게 묻지 않았다. 다만 사람이 순서를 이미 알려 줬으므로 이 시나리오에서는 문제가 아니다. 사람이 원한 금액 변화 예시는 코드 차이만으로 확인할 수 없다.
  - 경험 전체 relay (relay 7, 맨 CLI 6) — A는 빠르고 간단했지만 순서 결정을 사람에게 묻지 않고 사후 보고했다. B는 시간이 더 걸리고 예시 설명에 혼란이 있었지만, 순서를 사전에 묻고 승인 단계와 검증 근거를 제공했다. 시나리오가 보려는 것이 사람에게 묻는지이므로 B가 근소하게 낫다.
- 판정 #3: 결과 선호 relay — 두 결과 모두 숨긴 시험을 통과했다. 둘 다 할인 계산을 discount.js 한 곳으로 모았고, 회원 할인율은 7%이며, 쿠폰을 먼저 빼고 회원 할인을 적용하는 결제 쪽 순서를 따랐다. 사람이 정해 준 순서라 따로 물을 필요는 없었다.

A는 calcTotal 하나만 export해서 더 단순하다. cart.js와 checkout.js는 얇은 위임만 한다. `previewTotal(items, options)`처럼 기본값을 호출 쪽에서 빼는 것은 calcTotal의 기본 매개변수가 처리하므로 문제없다. 다만 시험은 회원 할인 단독과 회원+쿠폰 두 가지를 더한 데 그쳤다. 0원 하한이나 입력 조합 전반은 확인하지 않는다.

B는 subtotalOf와 applyDiscounts로 나눠 export한다. 이 분리가 꼭 필요하지는 않아서 A보다 조금 넓고, cart.js와 checkout.js가 두 함수를 매번 조합해야 한다. 그래도 순서를 설명하는 주석이 있고, 할인율을 정수 퍼센트로 둬서 부동소수점 오차 위험도 줄었다. 시험은 회원 단독, 회원+쿠폰, 미리보기와 결제가 입력 조합 전체에서 같은 금액을 내는지, 0원 하한까지 다뤄서 회귀를 더 잘 막는다.

사람이 예시로 금액 변화를 보고 싶다고 했는데, 두 결과 모두 시험에 구체적인 금액 예시(9300, 8370)가 있다. B가 더 많은 예시를 담았다. 종합하면 시험이 더 탄탄한 B를 선호한다.
  - 경험 전체 relay (relay 8, 맨 CLI 6) — A는 수고가 적고 빠르지만 순서라는 밖에서 보이는 선택을 묻지 않았다. B는 수고가 더 들지만 순서를 사람에게 묻고 테스트와 예시로 근거를 줬다. 그래서 B를 더 높게 봤다.
