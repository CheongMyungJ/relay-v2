- 판정 #1: 결과 선호 tie — A와 B 모두 숨긴 시험과 레포 시험을 통과했고, 바뀐 파일도 기대한 범위 안이다. 시험 파일 내용은 잘려서 보지 못했다. 줄 수는 A가 많지만 이것만으로 더 낫다고 보기는 어렵다.

A의 장점은 입력 검증이다. parseCron과 nextRun에서 인자 타입을 확인하고, 필드 값이 범위를 벗어나거나 형식이 틀리면 필드 이름이 든 오류를 던진다. 일과 요일 필드가 `*`로 시작하는지로 제한 여부를 가려서, `*/2` 같은 값도 표준 cron처럼 `*`로 본다. 단점은 수식을 파싱하면서 바로 계산한다는 것이다. 그래서 `1/0 +`처럼 문법이 틀린 식에서 'syntax' 대신 'division by zero'가 나올 수 있다.

B의 장점은 수식을 AST로 만든 뒤 계산해서 문법 오류가 계산 오류보다 먼저 나온다는 것이다. Markdown 링크에서는 javascript: 같은 위험한 스킴을 걸러 낸다. 이것은 요청에 없던 동작이라 범위를 조금 넘지만 안전에는 도움이 된다. 단점은 두 가지다. 일 필드를 `=== '*'`로만 비교해서 `*/2`를 제한된 값으로 취급한다. 또 `5-`처럼 끝이 빠진 값이 들어오면 필드 이름이 든 오류 대신 TypeError가 날 수 있다.

두 구현의 장단점이 비슷하게 상쇄되어 동률로 본다.
  - 경험 전체 relay (relay 7, relay (자율 유형) 6) — 수고와 마찰은 거의 같았다. A는 설계 결정을 확인·승인했고 리뷰 지적을 고르는 개입 자리가 있었으며 시험도 더 많아 통제와 확신에서 앞섰다. B는 조금 빨랐지만 승인 뒤 개입할 곳이 적었고 분량 경고도 있었다.
- 판정 #1: 결과 선호 relay@auto — 숨긴 시험에서 A는 cron 계산이 실패했고 B는 네 항목을 모두 통과했다. A의 parseCron은 필드 이름 없이 배열의 배열을 돌려준다. B는 FIELDS 이름을 키로 쓰는 객체를 돌려준다. 요구는 "필드마다 정렬된 값 목록"이라서 B 쪽이 이름으로 필드를 가리키는 형태에 더 가깝다. 이 모양 차이가 A의 실패 원인일 가능성이 크지만, 코드 차이가 중간에서 잘려 있어 확정하지는 못했다. 두 쪽 모두 바뀐 파일이 기대 범위 안이어서 scope는 같다. 시험 파일은 B가 487줄로 A의 전체 382줄보다 많지만, 시험 내용은 보이지 않아 B의 tests는 한 단계만 높게 줬다. A는 cron 시험이 이 실패를 잡지 못했다는 점에서 tests 점수를 낮췄다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 7) — A는 한 번의 입력으로 1.9분 만에 끝나 수고가 가장 적었다. B는 질문과 승인으로 통제와 확신을 더 얻었다. 그 대가로 6.3분이 걸렸고, 승인 뒤에는 개입할 자리가 없어 기다리기만 했다. 이 상황에서는 A의 속도와 단순함이 조금 더 낫다고 봤다.
- 판정 #2: 결과 선호 tie — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 바뀐 파일도 기대한 여섯 개뿐이다. 시험 파일 본문은 diff에서 잘려 보이지 않았다. A는 링크 주소를 걸러 위험한 주소를 막고, round가 부동소수 오차에 더 강하다. 다만 cron에서 '*/2' 같은 값을 제한된 필드로 취급해 표준 cron과 다르다. B는 '*'로 시작하면 별표로 보아 표준에 더 가깝고 시험 코드도 더 많다. 하지만 링크 주소를 걸러내지 않고, round는 경계값에서 오차가 날 수 있다. 장단이 비슷해 동률로 본다.
  - 경험 전체 relay@auto (relay 6, relay (자율 유형) 7) — A가 차례, 행동, 시간이 더 적었고 규칙 확인 질문이 있어 확신도 더 높았다. B는 round 규칙을 묻지 않아 사람이 오류를 직접 짚고 고치게 했다. 고치는 과정은 매끄러웠으나 부담이 늘었다.
- 판정 #2: 결과 선호 cli — 두 결과 모두 숨긴 시험과 레포 시험을 통과했고, 바뀐 파일도 기대한 여섯 개뿐이라 범위는 같다. 차이는 잔가지에서 난다. B는 cron에서 일·요일 필드가 '*'로 시작하면(예: */2) 제한 없음으로 본다. 이는 표준 cron 동작에 더 가깝다. A는 정확히 '*'일 때만 그렇게 본다. B의 round는 -0을 0으로 돌려주고, 변수 값은 숫자로 바꿔 쓴다. 그래서 round(-0.4) 같은 경계에서 B가 약간 더 안전하다. A는 함수 인자 개수를 표로 정리했고 오류 메시지도 더 자세하다. A의 markdown은 코드와 링크를 먼저 쪼개 처리해 구조가 깔끔하다. B는 자리표시자를 쓰는 방식이다. 시험은 diff가 잘려 내용을 확인하지 못했고, 줄 수(A 430줄, B 385줄)만 비슷했다. 그래서 시험 점수는 같게 매겼다. 전체적으로 거의 비슷하지만 B가 경계 동작에서 조금 낫다.
  - 경험 전체 cli (relay (자율 유형) 6, 맨 CLI 7) — B는 3분의 1 이하 시간에 한 번의 요청으로 끝나 수고가 매우 적었다. A는 통제와 확신 근거가 더 좋았지만 기다림이 길고 진행이 안 보였다. B의 묻지 않고 정한 선택은 감점 요인이다.

### 사람 역할의 말

- [relay#1 좋음] 요청 하나로 세 모듈을 맡겼는데 단계가 알아서 진행됐다. 판정표에 완료조건마다 통과 여부와 근거가 붙어 있어서 결과를 믿기 쉬웠다.
- [relay#1 불편] 독립 리뷰 중에는 터미널이 비어 있고 기다리는 시간이 길었다. 그동안 무슨 일이 일어나는지 알기 어려웠다.
- [relay#2 좋음] 단계별 산출물, 판정표, 독립 리뷰가 보여서 결과를 검토하기 쉬웠다. 요청 하나로 세 모듈을 맡겼는데 모듈별 시험 파일까지 나왔다.
- [relay#2 불편] round 반올림 규칙처럼 요청에 정의가 없는 부분을 에이전트가 묻지 않고 정해서, 내가 결과를 보고 직접 짚어야 했다. 의도 초안이 길다는 경고도 떴다.
- [cli#1 좋음] 요청 하나로 세 모듈과 시험, 커밋까지 질문 없이 빨리 끝났고 요약도 읽기 쉬웠다.
- [cli#1 불편] 에이전트가 아무것도 묻지 않아서 애매한 부분은 에이전트가 알아서 정했다. 그 결정을 내가 직접 확인해야 했다.
- [cli#2 좋음] 요청 하나로 세 모듈과 시험, 커밋까지 끝났다. 명세에 없는 선택도 요약에 정리해 줬다.
- [cli#2 불편] 에이전트가 아무것도 묻지 않고 혼자 정해서 진행했다. 요약에 적힌 선택들(링크 주소 차단, 9년 탐색 한도 등)은 내가 시킨 적이 없는 것들이다.
- [relay@auto#1 좋음] 핵심 규칙 두 가지만 선택지로 묻고 나머지는 알아서 TDD로 진행해서 수고가 적었다. 판정표와 테스트 결과, 변경 코드로 확인하기 쉬웠다.
- [relay@auto#1 불편] 의도 승인 뒤에는 개입할 자리가 거의 없었다. 독립 리뷰 중에는 터미널이 읽기 전용이라 기다리기만 했고, 의도 초안이 분량 기준을 넘었다는 경고도 있었다.
- [relay@auto#2 좋음] 의도 정리 단계에서 cron의 일/요일 OR 규칙을 정확히 짚어 물었고, 완료조건마다 확인 방법과 판정표가 나와 결과를 믿기 쉬웠다.
- [relay@auto#2 불편] 자율 진행에 들어간 뒤에는 독립 리뷰가 도는 동안 화면이 읽기 전용이고 진행이 잘 안 보여 그냥 기다려야 했다. 2^3^2나 round(-2.5) 같은 세부 규칙은 에이전트가 묻지 않아 코드를 직접 보지 않으면 맞는지 알 수 없었다.
