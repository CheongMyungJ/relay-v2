# 요약 메일 중복 발송 수정: 성공 후 시간 초과를 오류로 보지 않고, 중복 방지 키에서 실행 id를 뺀다

## 요약
아침 요약 메일이 같은 날 고객에게 2~3통 나가던 문제를 원인 두 가지를 고쳐 해결한다. 재시도 횟수·지연은 그대로이고 실제 실패는 계속 재시도로 다시 발송된다.

## 원인
1. `withDeadline`이 발송은 성공했는데 3초를 넘겼다는 이유로 시간 초과 오류를 던져, 접수된 메일이 재시도로 최대 3통 나갔다.
2. 중복 방지 키에 `runId`가 있어 재실행·재시작한 스케줄러·수동 실행마다 키가 달랐고, 동시 실행은 확인과 기록 사이 틈으로 둘 다 보냈다.

## 변경
- `src/digest/deadline.js`: 성공 후 초과는 오류 대신 `overrun`으로 알리고 지표·경고 로그를 남긴다.
- `src/digest/key.js`: 키를 `digest:기간:사용자`로 한다(실행별 집계는 기록의 `runId`).
- `src/digest/ledger.js`, `runner.js`: `claim`/`release`로 동시 실행을 막고, 실패(메시지 생성 실패 포함) 시 권리를 놓아 재시도를 가능하게 한다.
- `docs/knowledge/digest/digest-key-and-claim.md`: 위 사실 기록.

## 테스트
- `npm test`: 84건 통과(기준 74건).
- 경로별(최초 발송, 재시도, 수동 재실행, 스케줄러 재실행, 동시 실행) 한 번만 받는 테스트와 실패 시 재발송 테스트 추가. 기준 코드에서는 새 테스트 7건이 실패한다.
- 한계: `claim`은 프로세스 메모리 기준이다. 서버 간 동시 실행은 운영 DB ledger의 원자적 claim이 필요하다.
