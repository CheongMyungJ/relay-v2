## 원인
- 원인: (A) `withDeadline()`이 성공한 발송도 제한 시간을 넘기면 `SendTimeoutError`(transient)를 던져, 이미 간 요약을 runner가 실패로 보고 재시도함(원장에 sent도 안 남음). (B) `digestKey()`에 `runId`가 들어 있어, 재시도 아닌 다른 실행(스케줄러 재시작·수동 재실행, runId는 실행 시각으로 만들어짐)은 같은 고객·기간이어도 다른 키가 되어 중복 방지가 작동하지 않음.
- 근거: `src/digest/deadline.js`(수정 전 17~19줄)의 성공 후 throw, `src/digest/key.js`의 `digest:${period}:${runId}:${userId}`. 수정 전 테스트 실패, 수정 후 통과(코드를 고쳐 버그가 사라지는 것을 확인). 같은 실행 안의 `ledger.has` 검사는 같은 runId라 정상 동작 → "2통"은 A, "가끔 3통"은 A 반복(maxAttempts 3) 또는 A+B 조합으로 설명됨. 메일은 지연이 길어 A가 더 자주 걸림.
- 사람 추정 판정: 없음 (intent에 추정 없음)
- 기각한 가설: 스케줄러 `lastPeriod` 중복 실행 — 한 프로세스 안에서는 `lastPeriod`로 막혀 통과(기존 테스트 '하루 한 번만 돈다'). 프로세스 재시작 시의 재실행은 B로 막음. 인박스 중복 담기 — `inbox.add`가 키로 막고 기존 테스트로 확인.

## 변경 요약
- src/digest/deadline.js — 성공 시 예외 대신 `slow` 표시만 반환. 제한 시간은 실패한 발송에만 적용(실패 오류는 그대로 전달, 시간 초과로 실패한 발송은 기존처럼 재시도).

## 경로별 "고객이 한 번만 받는다" 근거
| 경로 | 근거 |
|---|---|
| 첫 발송이 제한 시간 초과 후 성공 | 테스트 '제한 시간을 넘겼지만 성공한…': 호출 1회, 원장 ['sent'] |
| 실행 안 재시도(일시 오류) 후 성공 | 기존 '일시적 오류는…' + '재시도 끝에 성공한 뒤 다시 실행해도…' |
| 스케줄러 재시작/수동 재실행(다른 runId) | 테스트 '요약 실행을 다시 해도…': `already: 1`, 발송 1통 |
| 일부만 성공한 실행의 재실행 | 테스트 '일부만 보낸 실행을…': 못 보낸 고객에게만 발송 |
| 같은 프로세스의 tick 반복 | 기존 '하루 한 번만 돈다' |
| 실제 실패는 재발송 | 테스트 '시간 초과로 실패한…', 기존 '일시적 오류는…' |
