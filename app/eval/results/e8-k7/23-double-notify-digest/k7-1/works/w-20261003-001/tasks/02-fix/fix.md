## 재현
- 재현 절차: 가상 시계 테스트에서 메일 transport 지연을 제한 시간(발송 2000ms, 요약 3000ms)보다 길게 두고 성공시킨다. `setup({ mail: { latencyMs: 3000 } })` 후 `notifier.handle(shippedEvent())`, 재시도 워커를 돌린다. 요약은 `digestSetup({ mail: { latencyMs: 4000 } })` 후 `notifier.digest.tick()`. 수정 전 코드에 추가한 테스트를 `npm test`로 돌려 확인했다.
- 결과: 재현됨
- 기대: 메일이 1통만 나가고 재시도 대기열은 비어 있다. 요약도 1통만 나간다.
- 실제: 발송은 성공했는데 `retry-scheduled`로 처리되어 재시도 때 한 번 더 나갔다(시도 3회면 최대 3통). 요약도 같은 방식으로 여러 통이 나갔다.

## 원인
- 원인: 어댑터 호출이 성공해도 걸린 시간이 제한 시간을 넘으면 "시간 초과"로 간주해 재시도했다. 실제로는 이미 도착한 발송이라 같은 알림이 2~3번 전달된다. 응답이 느린 메일 중계 서버에서 더 자주 생기므로 메일이 더 잦다(푸시 기본 지연 80ms는 제한 시간 안).
- 근거: `src/retry/policy.js` `decide()`가 `elapsedMs > timeoutMs`를 `outcome.ok`보다 먼저 검사했다. 요약 경로 `src/digest/deadline.js` `withDeadline()`은 `fn()` 성공 뒤 시간이 넘으면 `SendTimeoutError`를 던졌고, `runner.js`가 이를 일시적 오류로 재시도했다. 수정 전 테스트 3건 실패(번호 33, 59, 72), 수정 후 전부 통과했다. 빠른 발송(400ms)에서는 재현되지 않는 점도 설명된다.
- 사람 추정 판정: 없음
- 기각한 가설: 수신 중복 제거(`src/dedupe`) 결함 — 같은 이벤트가 두 번 들어오는 경우가 아니라 한 이벤트의 발송이 반복되므로 이 경로와 무관하다. 요약 `digestKey`에 runId가 들어가 다른 실행끼리는 중복 방지가 안 되는 점 — 설계 주석에 의도로 적혀 있고 같은 실행 안에서는 막히며, 수동 재실행이라는 별개 경로라 이번 원인이 아니다.

## 변경 요약
- src/retry/policy.js — 성공(`outcome.ok`)이면 걸린 시간과 무관하게 `done`. 실패한 발송의 시간 초과 재시도는 그대로다.
- src/digest/deadline.js — 성공한 호출은 시간이 넘어도 던지지 않고 `slow` 표시만 돌려준다.
- src/digest/runner.js — `slow`면 경고 로그만 남기고 성공으로 기록한다.
