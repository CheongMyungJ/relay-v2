# fix: 요약 메일 중복 발송 수정 (느린 성공 재시도 방지, 발송 키에서 실행 ID 제거)

## 요약
아침 요약 메일이 같은 날 고객에게 2~3통 가던 문제를 고쳤다. 실패한 발송의 재시도는 그대로 유지한다.

## 원인
- `withDeadline()`이 성공한 발송도 걸린 시간이 제한을 넘기면 시간 초과 오류로 바꿔, 이미 전달된 요약을 재시도했다(최대 3회).
- `digestKey`에 `runId`가 들어 있어 다른 실행(재시작, 수동 재실행, 서버 여러 대) 사이에서는 이미 보낸 키 검사가 작동하지 않았다.

## 변경
- `src/digest/deadline.js`: 성공을 오류로 바꾸지 않고 `slow` 표시만 돌려준다.
- `src/digest/key.js`: 키를 `digest:{기간}:{사용자}`로 바꿨다(runId 제거).
- `src/digest/runner.js`: 느린 성공은 `digest.slow` 지표와 경고 로그만 남긴다.
- `docs/knowledge/`: 재시도·요약 관련 지식 정리.
- `src/digest/ledger.js`, `runner.js`: 발송 전에 키를 선점(`claim`)해 동시에 도는 실행(서버 두 대)이 같이 보내지 않게 하고, 실패하면 풀어(`release`) 재시도·다음 실행이 다시 보낼 수 있게 했다. 선점은 `claimTtlMs`(기본 10분) 뒤 저절로 풀린다.
- 배포 직후에는 기존 키와 형식이 달라 당일 1회 중복이 있을 수 있다.

## 테스트
- `npm test`: 81개 통과. 새 테스트 7개(느린 성공 1통, 다른 실행 재실행 1통, 실패 후 재시도로 1통, 영구 오류 뒤 재실행 가능, 동시 실행 두 개 1통, 동시 실행 중 실패 재시도 1통, 영구 오류 뒤 선점 해제).
- 수정 전 코드에서는 새 테스트 2개가, 선점 전 runner에서는 동시 실행 테스트가 실패한다.
- 요약 경로는 메일뿐이며 위 테스트로 고객 수신 1회를 확인했다.
- 남은 위험: ETIMEDOUT 뒤 실제 전달된 메일, 운영 공유 DB의 `claim`은 원자적 연산이어야 함.
