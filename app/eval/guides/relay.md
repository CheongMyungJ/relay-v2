# relay 사용법 (요약)

relay는 Claude Code CLI를 앱 안의 터미널에 띄우고, 버그 수정, 기능 추가·변경, 리팩터링, 설계, 일반 일을 단계(task)로 나눠 진행하는 데스크톱 앱이다.

- 화면: 왼쪽은 프로젝트와 Work 목록, 가운데 위는 단계 탭, 그 아래는 고른 단계의 터미널(에이전트 세션), 오른쪽은 고른 단계의 패널(진행 상황, 승인할 때는 [요약], [산출물], [변경] 탭)이다. 프로젝트는 이미 등록되어 있다.
- [새 Work]에서 유형(버그 수정 / 기능 추가·변경 / 리팩터링 / 설계 / 일반)을 고르고 요청(버그 설명, 만들 기능이나 바꾸거나 없앨 동작, 바꿀 구조, 정할 설계, 할 일)을 쓴 뒤 [시작]하면 단계가 차례로 진행된다. 유형은 기본 선택이 없어 고르기 전에는 [시작]이 꺼져 있다. 잘못 골랐으면 의도 정리에 말한다. 의도 정리가 맞는 유형으로 Work 초안을 쓰면 오른쪽 패널의 초안 카드에서 [새 Work로 만들기]로 다시 만든다. Work마다 git worktree와 브랜치(기본 `relay/<work-id>-<임의의 4자>`)가 따로 생기고, 에이전트가 단계마다 커밋한다. 다른 설정은 기본값 그대로 두어도 된다.
- 단계: 버그 수정은 의도 정리 → 원인 분석과 수정. 기능 추가·변경(새 동작을 더하거나 지금 동작을 바꾸거나 없애는 일)은 의도 정리 → 설계와 계획 → 구현이다. 설계와 계획은 유저 시나리오, 요구사항, 구현 계획을 쓰고 코드는 바꾸지 않는다. 구현은 테스트를 먼저 쓰고 구현한다. 리팩터링은 의도 정리 → 계획과 리팩터링이다. 계획과 리팩터링은 지금 동작을 잡는 안전망 테스트를 먼저 커밋한 뒤 구조를 단계마다 바꿔 커밋하고, 동작은 바꾸지 않는다(찾은 버그는 고치지 않고 적는다). 일반(다른 유형에 맞지 않는 일)은 의도 정리 → 실행이다. 의도 정리에서 완료조건마다 확인 방법(실행할 명령, 읽을 곳, 또는 사람)을 적고, 실행은 정해진 절차 없이 일하고 커밋하며 완료조건마다 확인 방법을 돌려 본다. 확인 방법이 '사람'인 항목은 마무리 때 사람에게 묻는다. 설계(구현 전에 설계만 정하는 큰 일)는 의도 정리 → 설계 문답이다. 의도 정리에서 설계를 적을 문서(새 문서나 기존 문서)와 정할 것을 맞추고, 설계 문답은 주제 목록을 먼저 보여 확인받은 뒤 주제마다 선택지로 결정을 묻고 답을 그 문서에 적어 커밋한다. 코드는 바꾸지 않는다. 다시 볼 만한 결정은 Work 완료 화면의 '다시 볼 결정'에 보인다. 바꾸려면 승인 전에 그 터미널에 말한다. 설계와 계획은 사람이 승인한다. 마지막이 아닌 단계 가운데 자동 승인으로 정해 둔 것(커스텀 유형에 있을 수 있다)은 15초 카운트다운 뒤 넘어가고([취소]로 멈출 수 있다), 화면은 다음 단계로 넘어간다.
- 커스텀 유형: 레포의 팀이 정해 둔 유형이 있으면 [새 Work]의 유형 줄에서 기본 다섯 뒤 구분선 다음에 '<이름> (레포)'로 보인다. 고르면 설명과 단계 목록(의도 정리 → 팀이 정한 단계들)이 보인다. 단계는 팀이 쓴 절차대로 진행하고, 단계마다 탭 이름은 그 단계 이름이다. 마지막 단계는 다른 유형처럼 Work를 마무리한다. 완료조건은 일반처럼 줄마다 확인 방법을 붙인다. 자동 승인 여부는 유형이 단계마다 정해 두었다. [설정]의 [업무 유형…]에서 기본 유형과 레포 유형 목록을 볼 수 있다.
- 지난 단계 다시 보기: 가운데 위의 단계 탭(예: `02 원인 분석과 수정`, `03 구현`)을 누르면 오른쪽 패널에 그 단계의 [요약](원인이나 설계, 결정, 위험), [산출물], [변경](그 단계의 diff)이 읽기 전용으로 뜬다. 자동 승인으로 지나간 단계도 여기서 본다. 지금 단계 탭을 누르면 다시 지금 단계를 따라간다.
- 단계마다 새 에이전트 세션이 뜬다. 에이전트가 산출물을 쓰고 "승인 대기"가 되면 오른쪽 패널에서 확인하고 [승인]한다(의도 정리는 [의도 승인]). 고칠 점이 있으면 승인하지 말고 터미널에서 에이전트에게 말한다. 에이전트가 고쳐 다시 승인 대기가 된다.
- 에이전트가 선택지로 질문하면 터미널에서 방향키와 Enter로 고르거나 글로 답한다.
- 마무리: 따로 리뷰 단계는 없고, 마지막 작업 단계(원인 분석과 수정, 구현, 계획과 리팩터링, 실행, 설계 문답, 커스텀 유형의 마지막 단계)가 제 일을 마친 뒤 Work를 마무리한다. 완료조건별 판정표를 쓰고 독립 리뷰를 요청하면 relay가 그 세션을 닫고 "독립 리뷰 중"이 된다(몇 분 걸린다. 패널에 찾기·확인 진행이 보인다. 기다리면 된다). 리뷰가 끝나면 같은 대화가 다시 열리고, 지적이 있으면 에이전트가 어느 지적을 반영할지 선택지로 묻는다. 고른 지적을 고치고 판정을 고친 뒤, 실패하거나 판정할 수 없는 완료조건이 있으면 어떻게 할지 묻는다. 그다음 PR 초안을 쓰고 승인 대기가 된다.
- 마지막 작업 단계의 승인 화면이 Work 완료 화면이다(이 단계는 자동 승인되지 않는다): [완료만] / [push] / [PR 생성]. 이 평가에서는 [완료만]이면 된다.
- 고치기와 다시 하기: 앞 단계로 돌아가는 버튼은 없다. 고칠 것은 지금 단계의 터미널에 말하면 그 단계가 고친다(마지막 단계도 독립 리뷰의 지적이나 실패한 완료조건을 그 자리에서 고친다). 요구 자체를 바꾸거나 근본부터 다시 하려면 지금 단계나 [곁 세션 열기]로 연 곁 세션에 그렇게 말한다. 에이전트가 새 Work의 초안을 쓰면 오른쪽 패널의 초안 카드에서 [새 Work로 만들기]를 누르고, 대화상자의 "원래 Work 포기"로 이 Work를 끝낸다.
- [즉시 중단]은 지금 세션을 끝내고, [재개]로 같은 세션을 다시 연다. 앱이 꺼졌다 켜지면 끊긴 task를 [재개]로 이어 간다.
- 그 밖에 [이 단계 끝나면 멈춤], [Work 설정](단계별 자동 승인 등), [Work 포기], [Work 정리](완료 뒤 worktree 제거)가 있다.
- 여러 Work를 동시에 진행할 수 있다. 각 Work는 따로 브랜치에서 진행된다.
- push와 PR은 에이전트가 아니라 앱이 한다.
- [새 Work] 창에 "지식 정리 후보 n건"이 보이면, 앱이 `docs/knowledge/`의 팀 지식에서 중복(같은 anchor)이나 코드에 없는 이름을 가리키는 항목 같은 정리 후보를 찾았다는 뜻이다. [지식 정리 Work로 채우기]를 누르면 유형이 일반으로, 요청이 후보 목록으로 채워진다.
