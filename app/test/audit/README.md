## 재현된 문제

### B1. 오류 보고에서 버림/대체를 골라도 공유 대기의 옛 규칙이 PR에 실림 — P1

**재현:** 공유 대기에 `빈 배열의 평균은 NaN이다`를 둔다. 다음 Work의 verify가 해당 id에 knowledge_feedback을 남긴다. 완료 화면의 오류 보고에서 `버림` 또는 `대체: 빈 배열의 평균은 0이다`를 고르고 PR을 생성한다. 공유 대기 쪽의 기본값은 `함께 싣기`로 둔다.

**기대:** 버림이면 옛 항목을 싣지 않고 사본을 제거한다. 대체이면 새 규칙만 활성 상태로 남긴다.

**실제:** 전달은 `{ok: true}`다. 버림에서도 옛 규칙이 active로 실리고, 대체에서는 NaN/0 규칙이 둘 다 active로 실린다. 실제 Work 진행과 로컬 원격 전달까지 재현했다.

**원인:** `planKnowledge`가 공유 대기의 쓰기 목록을 먼저 만들고, 뒤의 feedback 처리는 삭제 목록만 추가한다. `dedupe`가 이미 쓰기 목록에 있는 id를 삭제 목록에서 제거하므로 옛 규칙이 다시 살아남는다. 화면에서 같은 항목에 두 개의 결정을 내릴 수 있는 것도 혼란을 키운다.

**개선:** id별 단일 최종 행동을 계산하고 명시적 버림/대체가 기본 함께 싣기보다 우선하도록 한다. 같은 항목의 선택을 화면에서도 동기화한다. 삭제 대상이 repo/pending/carry에 남지 않는 불변조건을 검사한다.

**근거:** A17, A18, F-drop, F-replace. [실제 전달 결과: 버림](../../audit-artifacts/F-drop.json), [대체](../../audit-artifacts/F-replace.json). 코드: [공유 대기 처리](../../src/core/knowledge.ts), 831행 및 852~916행.

### B2. 대체 항목의 이동/삭제가 원본의 대체됨 사본과 분리됨 — P1

**재현:** 팀 규칙을 고쳐 새 대체 항목과 원본의 `superseded` 사본을 만든다. 새 항목만 `나만으로` 옮기거나 버린다.

**기대:** 개인화라면 팀 쪽 원본의 사용 가능성을 보존하고 개인 범위에서 대체한다. 대체 취소/삭제라면 원본을 복원하거나 두 항목을 어떻게 처리할지 명시한다. 공유되는 대체 관계가 비공유/없는 id를 가리키면 안 된다.

**실제:** 이동 시 공유 대기에 원본의 대체됨 사본만 남고 대상은 개인 저장소로 빠진다. 삭제 시 참조 대상이 사라지며 다음 Work의 유효 지식 수가 0이 된다. 원본 사본에는 `superseded_by`가 그대로 남는다. Electron에서도 이동을 재현했다.

**개선:** 대체 관계를 하나의 변경 묶음으로 관리하고 이동·삭제·이번 PR에서 빼기를 관계 단위로 검증한다. 팀→개인 변경은 원본 팀 항목을 손상시키지 않는 개인 대체로 변환한다. 선택 결과를 “팀의 원본 유지 / 개인에게만 대체”처럼 보여준다.

**근거:** A12, A13, G03. [화면](../../audit-artifacts/G03-private-target-public-tombstone.png), [화면 API 결과](../../audit-artifacts/G03-screen.json). 코드: [editKnowledge](../../src/main/knowledge.ts), 647~656, 667~692행.

### B3. 다음 Work의 공유 대기 정리와 사용자 편집이 겹치면 수정본 소실 — P1

**재현:** 이미 기본 브랜치에 같은 내용이 머지된 공유 대기 사본을 만든다. 다음 Work의 `pool()`이 사본을 읽은 직후 대기시킨다. 그 사이 지식 화면의 편집 API로 새 규칙을 저장하고, `pool()`을 계속 진행시킨다.

**기대:** 정리 대상인지 잠금 안에서 현재 내용을 다시 확인하여 새 수정은 보존한다.

**실제:** 편집은 성공했지만 이후 공유 대기 파일이 삭제된다. 기대 배열 `['동시 편집한 새 규칙']` 대신 `[]`가 나온다.

**원인:** 머지 여부를 잠금 밖에서 읽은 내용으로 판단하고, `dropPending()`은 잠금 안에서 id만 보고 삭제한다. 쓰기 잠금은 있지만 판단에 사용한 버전의 유효성을 확인하지 않는다.

**개선:** 판단 때의 내용 해시/리비전을 삭제 요청에 넣고, 잠금 안에서 일치하는 경우에만 삭제한다. 인덱스도 그 삭제와 함께 갱신한다.

**근거:** A31, [테스트](knowledge-audit.test.ts). 재현은 저장소 읽기를 잠시 멈추는 방식으로 실행 순서만 통제했다. 파일·Git·편집·잠금·삭제는 실제 구현이며, 무작위 스트레스 테스트에서 측정한 발생률은 아니다. 코드: [pool / dropPending](../../src/main/knowledge.ts), 168~199행.

### B4. knowledge.json 손상 시 열린 PR 편집 잠금이 경고 없이 풀림 — P2

**재현:** 공유 대기 항목에 PR #42 기록을 저장하고 `knowledge.json`을 파싱 불가능한 내용으로 만든 뒤 화면을 열고 항목을 고친다.

**실제:** 경고 `[]`, `carriedPr: null`, 편집 결과 `null`(성공), 파일 내용도 변경된다. 정상 인덱스에서는 동일 항목의 편집·이동·버림이 모두 막힌다(A09).

**개선:** 파일 없음과 손상을 구분한다. 손상 상태에서는 진단과 백업 복원을 제공하고 PR 연결을 확인하기 전까지 잠금이 필요한 변경을 제한한다. 인덱스 구조와 schema_version도 검증한다.

**근거:** A10, [관측값](../../audit-artifacts/A10-corrupt-index.json). 코드: [KnowledgeStore.index](../../src/adapters/knowledge.ts), 163행부터. 손상 주입 실험이며 정상 종료에서 자연 발생했다는 뜻은 아니다.

### B5. 첫 번째 긴 규칙은 문맥 분량 상한을 무시 — P2

**재현:** 길이 약 20,000자의 한 줄 규칙을 저장하고 해당 용어로 `renderKnowledge`를 호출한다. limit은 기본값 1,500이다.

**실제:** 참고 지식 본문이 20,220자다. 첫 항목은 `lines.length > 0` 조건 때문에 항상 포함된다. 저장/편집에 별도 제목 길이 상한도 없다.

**개선:** 긴 규칙은 저장할 때 요약을 요구하거나, 주입에서는 요약+id+파일 경로만 넣는다. 첫 항목에도 상한을 적용하고 경고·폴더 안내에 쓸 여유를 포함해 예산을 계산한다. 긴 항목 하나 때문에 뒤의 짧은 관련 항목을 모두 잃지 않도록 선택 정책도 검토한다.

**근거:** A26. 코드: [renderKnowledge](../../src/core/knowledge.ts), 471~490행. 실제 모델 비용 증가나 답변 성능 저하는 측정하지 않았다.

### B6. 한국어/공백 경로가 요청에서 정확하게 추출되지 않음 — P2

**재현/실제:** `src/결제/정산.ts를 수정해 주세요` → 경로 `[]`. ``Fix `src/billing rules.ts` please`` → `['src/billing', 'rules.ts']`.

**영향:** 파일명을 적어도 경로 기반 지식 선택이 누락되거나 넓은 경로로 잘못 매칭될 수 있다. 용어가 별도로 맞으면 지식이 들어갈 수 있으므로 모든 관련 지식이 항상 누락되는 것은 아니다.

**개선:** 백틱/따옴표 경로를 먼저 추출하고 Unicode 경로를 지원한다. 가능하면 실제 Git 파일 목록과 대조하여 조사·문장부호를 분리한다. Windows 구분자와 공백 경로도 회귀 사례로 둔다.

**근거:** A24, A25. 코드: [pathsInText](../../src/core/knowledge.ts), 296~309행.

### B7. 대체됨 팀 항목의 고침이 다시 대체됨 항목을 만듦 — P2

**재현:** 이미 `superseded`인 팀 항목을 지식 화면 API로 고친다.

**실제:** 성공 응답과 새 id가 생기지만 새 항목도 superseded다. 다음 Work의 active 지식에는 새 규칙이 들어가지 않는다. 화면은 대체됨 항목에도 고침을 제공한다.

**개선:** 보관된 원본의 고침을 막고 현재 대체 항목으로 안내하거나, 별도의 복원 동작에서 `active`, `superseded_by: null`을 명시한다.

**근거:** A28. 코드: [editKnowledge](../../src/main/knowledge.ts), 647~656행, [ScreenEntry](../../src/renderer/src/Knowledge.tsx).

### B8. 빈 규칙 저장이 성공으로 처리됨 — P2

**재현:** 개인 지식의 규칙을 공백만 남기고 저장한다.

**실제:** 편집기가 닫히고 오류 없이 기존 규칙이 남는다. API는 성공이다. 후보 편집의 `candidateProblem`은 빈 규칙을 거부하지만 지식 화면 편집은 기존 규칙으로 치환한 뒤 검사한다.

**개선:** 사용자가 명시적으로 빈 문자열을 보낸 경우와 필드를 보내지 않은 경우를 구분한다. 저장 성공 후에만 편집기를 닫고 오류를 해당 입력란에 표시한다.

**근거:** A06, G02. [화면](../../audit-artifacts/G02-blank-rule-silent-success.png). 코드: [applyEdit](../../src/main/knowledge.ts), 590행, [저장 버튼](../../src/renderer/src/Knowledge.tsx), 544~550행.

### B9. 지식 파일 검사 경고가 화면까지 전달되지 않음 — P2

**재현:** 유효한 머리글·규칙·이유만 있고 코드불가/유인 절이 없는 Markdown을 개인 저장소에 둔다.

**실제:** 파서는 절 누락 경고를 만들지만 저장소 로더는 성공 결과의 warnings를 버려 지식 화면에 경고가 없다. 완전히 깨진 파일은 별도 경고하며 정상 항목을 계속 읽는다(A22).

**개선:** 오류와 경고를 함께 전달하고 파일명·필드·복구 방법을 표시한다. 현재 설계가 허용하는 경고를 곧바로 저장 실패로 격상할 필요는 없다.

**근거:** A23. 코드: [parsed](../../src/adapters/knowledge.ts), 44~47행 및 [checkKnowledgeFile](../../src/core/validate.ts), 627행부터.

300개 화면 열기는 이 환경의 단일 실행에서 앱 시작 포함 약 0.9초였다. 이 수치를 대규모 성능 보장이나 병목으로 해석하지 않았다. 관측된 문제는 수백 항목의 탐색 수단 부족이다.

후보 유사도는 같은 종류·파일·겹치는 용어로 판단하도록 최근 D326에서 정한 정책이다. 이를 이번 감사에서 버그로 단정하지 않았다. 향후 서로 다른 규칙을 채택 해제하는 경우를 실제 사용 자료로 평가하고, 유사 후보를 나란히 비교하는 UI를 고려할 수 있다.

## 정상 확인한 주요 동작

기본 등록/저장, 한국어·이모지 왕복, 정상 편집·재열기, 용어 개수 검증, 개인↔공유 대기 이동, 공유 끔, 정상 PR 잠금, 팀 수정 시 원본 레포 미변경, 코드 해시 기반 재확인, 무관한 파일 변경 제외, 공유 보류, 지식 커밋 재시도 중복 방지, 머지된 사본 정리, 손상 파일 격리, 개인 삭제 지속, origin 실패 시 캐시와 경고를 확인했다.

기존 70개 테스트에서는 Work 간 주입, 되감기 후보 제외, PR 대응의 변경/삭제, 머지/머지 없이 끝내기, 전달 실패·재시작 후 재시도, 기능 끔도 통과했다. 신규 발견은 주로 여러 상태가 조합되는 구간에 있다.

## 실행과 근거

레포 루트가 아닌 `app/`에서 실행한다. 테스트는 임시 레포만 변경하며 내부적으로 임시 bare 원격의 main에 fixture를 넣기도 한다. 이것은 **relay-v2의 main에 push하는 동작이 아니다**.

```sh
npm ci
npm run contracts

# 이번에 확인한 기존 지식관리 테스트: 70 통과
npx vitest run --project unit --project adapters --project flow knowledge

# 신규 재현: 33개, 현재 기준 14개 실패가 재현되는 것이 정상
npx vitest run --config test/audit/vitest.config.ts

# 실제 Electron 화면: 6개, 현재 기준 2개 실패
npm run build
npx playwright test --config test/audit/playwright.config.ts

npm run typecheck
npx eslint test/audit
npx prettier --check test/audit
```

Linux GUI 실행에는 DISPLAY와 Electron 시스템 라이브러리가 필요하다. 이번 환경은 권한상 시스템 apt 설치가 불가능하여 Debian 패키지를 `/workspace/scratch/gui`에 풀고 Xvfb를 사용했다. 이 세션의 재실행에서는 `DISPLAY=:99 LD_LIBRARY_PATH=/workspace/scratch/gui/usr/lib/x86_64-linux-gnu`를 GUI 명령 앞에 붙인다. Electron 바이너리는 Node의 프록시 지원을 켜 내려받았고 앱 실행 시 `--no-sandbox`는 격리된 GUI 테스트 환경에 한정했다. 제품 설정을 바꾸지 않았다.

## 이번 결과의 한계

- **미실행:** 실제 Claude/Codex 모델을 사용한 지식 추출 품질·재사용 정답률 평가. 기존 flow의 모델 응답은 제어 가능한 fixture이며 이를 실제 모델 성공으로 집계하지 않았다. Claude CLI는 이 환경에 없고 Codex CLI의 로그인 상태는 확인했으나 실제 모델 기반 파이프라인은 실행하지 않았다.
- **미실행:** 실제 GitHub PR 생성/리뷰/머지, Windows 설치본, OS 강제 종료·전원 차단. 실제 외부 계정/팀 레포를 변경하지 않고 로컬 테스트 원격을 사용했다.
- **범위 밖:** 서버형 다중 사용자 권한은 현재 데스크톱·Git 기반 구조에 없는 기능이다. 개인/팀/공유 대기 및 열린 PR 편집 제한을 검사했다.
- **측정하지 않음:** 동시 편집 문제의 자연 발생률, 대량 데이터의 장시간 성능, 수천~수만 항목 규모.
- 실패 16건은 고유 버그 16개가 아니다. 원인 9개 중 일부를 API·Work 흐름·GUI에서 중복 확인했다. 추가한 테스트와 보고서 외 제품 소스 변경은 없으며, 게시 대상은 위 감사 브랜치뿐이다.
